01

한 줄로 이해하기

Spark는 인메모리 분산 계산 엔진이다. 데이터를 디스크가 아닌 RAM에 올려두고 반복 연산하기 때문에 Hadoop MapReduce보다 최대 100배 빠르다. 핵심은 두 가지 — 무엇을 계산할지만 선언하고 실제 실행은 Action이 트리거할 때까지 미루는 Lazy Evaluation, 그리고 데이터 이동 비용을 결정하는 Narrow vs Wide Transformation 구분이다.

i

인메모리 계산이 전부다

MapReduce는 Map → Disk → Reduce 사이에 디스크 I/O가 필수다. Spark는 중간 결과를 메모리에 유지한다. ML처럼 같은 데이터를 수십 번 반복하는 작업에서 이 차이가 10~100배 성능 차이로 나타난다.

ii

추상화 3단계: RDD → DataFrame → Dataset

RDD(2014)는 저수준 분산 컬렉션 — 타입 안전, 최적화 없음. DataFrame(2015)은 스키마 + Catalyst 옵티마이저 적용 — 대부분의 용도에 충분. Dataset은 DataFrame + 컴파일 타임 타입 검사 (Scala/Java 전용).

iii

Lazy Evaluation — DAG를 먼저 짓는다

Transformation(filter, map, groupBy)은 즉시 실행되지 않는다. Action(collect, count, write)이 호출될 때 DAG(방향 비순환 그래프)를 최적화한 후 실행한다. 불필요한 단계를 Catalyst가 제거하거나 재배열한다.

iv

셔플이 성능의 핵심 변수다

Narrow Transformation(filter, map)은 파티션 내부에서 처리 — 네트워크 이동 없음. Wide Transformation(groupByKey, join)은 파티션 간 데이터 이동(셔플) 발생. 셔플은 디스크 I/O + 네트워크 직렬화를 수반하므로 최소화해야 한다.

v

Driver + Executor 역할 분리

Driver는 DAG를 생성하고 Task를 스케줄링하는 컨트롤 플레인. Executor는 실제 데이터를 처리하는 워커. Cluster Manager(YARN/K8s/Standalone)가 리소스를 Executor에 할당한다. Driver는 절대 실제 데이터를 처리하지 않는다.

vi

언제 Spark가 필요한가

단일 서버 RAM에 데이터가 들어가면 pandas가 빠르다. 데이터가 수십 GB를 넘거나, ML 피처 파이프라인을 클러스터에서 돌리거나, 실시간 스트리밍 + 배치를 같은 코드로 처리해야 할 때 Spark가 의미 있다. 오버엔지니어링 주의.

01클러스터 아키텍처

Spark 애플리케이션은 항상 Driver 하나와 N개의 Executor로 구성된다. Driver는 SparkContext를 생성하고 DAG를 Stage → Task 단위로 분해해 스케줄링한다. Executor는 Task를 실행하고 결과를 Driver에 돌려준다.

Cluster Manager는 Executor 컨테이너의 CPU·메모리를 할당하는 역할만 한다. YARN은 Hadoop 환경, K8s는 컨테이너 환경, Standalone은 Spark 전용 클러스터에서 쓴다.

언제 쓰나

Driver OOM은 대부분 collect()로 모든 데이터를 드라이버로 당겨올 때 발생한다. Executor 수·메모리는 데이터 크기와 셔플 비용을 보고 조정한다.

02추상화 계층

RDD는 타입 안전하고 세밀한 제어가 가능하지만 Catalyst 옵티마이저가 적용되지 않아 성능 최적화를 개발자가 직접 해야 한다. DataFrame은 스키마 정보를 가지므로 Catalyst가 실행 계획을 자동 최적화한다. 실제로 같은 연산이 RDD보다 DataFrame이 2~5배 빠른 경우가 많다.

Dataset은 DataFrame의 타입 안전 버전이지만 Python에서는 지원하지 않는다. PySpark에서는 DataFrame이 사실상 Dataset[Row]에 해당한다.

언제 쓰나

PySpark에서는 DataFrame API를 기본으로 쓴다. 커스텀 직렬화·저수준 파티셔닝 제어가 필요할 때만 RDD로 내려간다.

HIGH Spark SQL / DataFrame Catalyst 옵티마이저 · 스키마
MID Dataset[T] 타입 안전 · Scala/Java 전용
LOW RDD 저수준 제어 · 수동 최적화
BASE 분산 JVM / Python Worker 실제 실행 환경

03Lazy Evaluation — DAG

Transformation을 호출할 때마다 Spark는 실행 계획 그래프(DAG)에 노드를 추가할 뿐 실제 데이터를 건드리지 않는다. Action이 호출되는 순간 Catalyst가 DAG 전체를 분석해 불필요한 단계를 제거하고, Stage로 묶어 Executor에 Task로 배분한다.

이 덕분에 중간에 아무리 많은 Transformation을 쌓아도 실행 시에는 최적화된 계획 하나만 돈다. 반면 collect()나 show()를 loop 안에서 반복 호출하면 매번 전체 DAG를 재실행한다는 함정이 있다.

언제 쓰나

중간 결과를 여러 번 재사용한다면 .cache() 또는 .persist()로 메모리에 고정한다. 재사용 횟수가 1회라면 캐시 비용이 더 클 수 있다.

transformation

transformation

↓ ACTION 호출 시 실행

04Narrow vs Wide Transformation

Narrow: 출력 파티션이 하나의 입력 파티션에만 의존한다. filter, map, flatMap이 여기에 속한다. 파티션 내부에서만 처리되므로 네트워크 I/O가 없다.

Wide: 출력 파티션이 여러 입력 파티션을 필요로 한다. groupByKey, reduceByKey, join, distinct가 해당한다. 셔플(네트워크를 통한 데이터 재분배)이 발생하며, 이 지점에서 Stage 경계가 생긴다.

언제 쓰나

groupByKey보다 reduceByKey를 쓴다 — 셔플 전에 로컬에서 미리 집계하기 때문에 네트워크 전송 데이터가 줄어든다. 조인은 broadcast join으로 작은 테이블을 메모리에 올려 셔플을 없앤다.

05Spark 에코시스템

Spark Core 위에 4개의 고수준 모듈이 올라간다. Spark SQL은 DataFrame API와 SQL 쿼리를 제공하며 Hive · Parquet · Delta Lake 연동이 가능하다. Structured Streaming은 배치와 동일한 DataFrame API로 스트리밍을 처리한다.

MLlib은 분산 ML 알고리즘과 Pipeline API를 제공한다. scikit-learn Pipeline과 비슷한 구조지만 데이터가 클러스터 전체에 분산된다. GraphX는 그래프 계산용이며 실무에서는 활용 빈도가 낮다.

언제 쓰나

피처 엔지니어링(대용량 조인·집계)은 Spark SQL, 모델 학습은 MLlib 또는 외부 프레임워크(XGBoost-on-Spark, PyTorch), 실시간 파이프라인은 Structured Streaming + Kafka.

06Catalyst Optimizer

Spark SQL의 쿼리 최적화 엔진이다. SQL 문자열 또는 DataFrame 코드가 동일한 파이프라인을 통과한다. Analysis: 카탈로그에서 테이블·컬럼 스키마 검증, 미해결 참조 해결. Logical Optimization: predicate pushdown(필터를 스캔 직전으로), column pruning(불필요한 컬럼 제거), constant folding.

Physical Planning: 조인 알고리즘 선택(Broadcast Hash Join vs Sort-Merge Join), 파티셔닝 전략 결정. Tungsten Code Generation: JVM 바이트코드를 직접 생성해 인터프리터 오버헤드를 제거하고 CPU 캐시 지역성을 높인다. AQE(Adaptive Query Execution)는 런타임 통계를 기반으로 Physical Plan을 재최적화한다.

explain() 활용

df.explain(mode="extended")로 Parsed → Analyzed → Optimized → Physical Plan을 모두 출력한다. == Physical Plan ==에서 BroadcastHashJoin이 보이면 broadcast join이 선택된 것이다. Exchange 노드가 보이면 셔플이 발생한다는 뜻이다.

07Unified Memory Model

Spark 1.6+의 통합 메모리 모델이다. JVM 힙에서 spark.memory.fraction(기본 0.6)만큼을 Spark Memory로 예약하고, 나머지는 User Memory(UDF 객체, 직접 생성 자료구조)가 사용한다.

Spark Memory는 Storage Memory(broadcast 변수, persist() 캐시)와 Execution Memory(셔플 버퍼, 조인 해시 테이블, 정렬 버퍼)로 나뉜다. 두 영역은 동적으로 서로 빌려 쓸 수 있다. Execution이 부족하면 Storage를 축출하지만, 반대는 불가능하다. Execution이 빌린 공간이 부족해지면 Spill to Disk가 발생한다.

OOM vs Spill 구분

Spill은 느리지만 작업이 완료된다. OOM은 executor가 죽는다. OOM의 주요 원인은 User Memory 초과(큰 UDF 객체, Python UDF) 또는 spark.executor.memoryOverhead(off-heap) 부족이다. spark.memory.fraction을 높이면 Spark Memory가 늘지만 User Memory가 줄어 OOM이 오히려 늘 수 있다.

대용량 처리 — 빅테크 패턴

TB~PB 규모에서 Spark 성능 차이의 90%는 알고리즘이 아니라 설정·파티션 전략·메모리 모델 이해에서 온다. Spark 3.0의 AQE, 스큐 처리 패턴, 메모리 아키텍처, 오픈 테이블 포맷, 핵심 설정 — Meta·Netflix·Uber·Databricks의 실운영 결정들을 정리한다.

Spark 3.0+
AQE — Adaptive Query Execution
사용 Databricks Meta Netflix LinkedIn

Spark 2.x까지는 DAG를 컴파일 시점에 고정했다. AQE는 각 Stage 완료 후 수집한 런타임 통계를 바탕으로 다음 Stage 실행 계획을 동적으로 재최적화한다. Spark 3.2+에서 기본 활성화.

① 셔플 파티션 동적 병합 — Stage 완료 후 실제 파티션 크기를 측정해 너무 작은 파티션들을 합친다. shuffle.partitions=200 기본값의 "200개 중 190개가 빈 파티션" 문제를 자동 해결.

② 조인 전략 동적 전환 — 컴파일 시에 크다고 판단해 sort-merge join으로 계획했더라도, 실제 데이터가 브로드캐스트 임계치 이하면 런타임에 broadcast join으로 전환.

③ 스큐 조인 자동 분할 — 스큐 파티션을 여러 개로 쪼개 병렬 처리. skewJoin.skewedPartitionFactor=5·skewedPartitionThresholdInBytes=256MB가 판단 기준.

Meta 사례

전사 Spark 설정에 AQE 기본 활성화. 10PB+ 일일 처리 파이프라인에서 셔플 파티션 수를 AQE가 자동 결정하도록 위임 — 잡 튜닝 공수 70% 감소.

Memory Architecture
Spark 메모리 모델 — Unified Memory Manager

Spark 1.6부터 도입된 Unified Memory Manager는 JVM Heap을 4개 영역으로 분리한다. 가장 중요한 변화는 실행 메모리와 저장 메모리가 동적으로 경계를 공유한다는 점이다 — 한쪽이 부족하면 다른 쪽을 빌려 쓴다.

Reserved Memory(300MB 고정) — Spark 내부 객체용. 나머지가 usable heap.
Spark Memory(memory.fraction = 0.6 기본) — Execution + Storage 공유 풀.
User Memory(나머지 40%) — RDD 파티션 메타데이터, UDF 내부 자료구조.
Execution Memory — 셔플·집계·정렬 중간 버퍼. 부족하면 디스크로 Spill.
Storage Memory — .cache()·.persist()·broadcast 변수.

Off-Heap Memory(Tungsten) — JVM GC 밖에서 직접 관리. GC 압박이 심한 장시간 잡에 유효. spark.memory.offHeap.enabled=true·offHeap.size 설정 필요.

OOM / Spill 진단 순서

Spark UI → Stages → "Spill (memory)" 컬럼 확인 → 크면 executor memory 증가 또는 파티션 수 늘리기. GC Time이 20% 이상이면 executor.cores 줄이거나 off-heap 검토.

데이터 스큐 & Salting
사례 Uber Meta

스큐는 가장 빈번한 대용량 처리 병목이다. 특정 키에 데이터가 집중되면 해당 파티션의 Executor 하나가 나머지를 기다리게 만들어 전체 Stage가 블록된다. Uber는 뉴욕 맨해튼 셀의 배달 이벤트가 전체의 30%를 차지하는 스큐를 Salting으로 해결했다.

Salting 2-phase 패턴: 키에 랜덤 정수 접미사를 붙여 파티션을 강제 분산(Phase 1) → 접미사 제거 후 재집계(Phase 2). 아래 코드 카드 참고.

AQE의 skewJoin.enabled=true는 조인 시 스큐를 자동 감지해 파티션을 분할한다. 단, groupBy·agg의 스큐는 AQE가 처리 못하므로 Salting이 필요하다.

언제 쓰나

Spark UI에서 Tasks 중 일부가 나머지보다 10배+ 오래 걸리면 스큐다. 조인 스큐 → AQE skewJoin. groupBy 스큐 → Salting. 전체적으로 느리면 파티션 수 조정.

오픈 테이블 포맷 — Delta Lake · Iceberg · Hudi

Raw Parquet는 ACID 트랜잭션·스키마 진화·타임 트래블이 없다. 오픈 테이블 포맷 3종은 메타데이터 레이어를 추가해 이를 해결한다. 빅테크마다 선택이 갈린다.

Tuning
핵심 설정 튜닝 — GC · Shuffle · OOM

Netflix는 과거 실행 이력 기반 Auto-tuner로 shuffle.partitions·executor memory를 자동 추천한다. Meta도 잡 특성별 최적 설정 DB를 구축해 수동 튜닝 공수를 줄였다. 기본값은 소규모 워크로드 기준이므로 대용량에서는 반드시 조정해야 한다.

설정 키 권장값 설명
spark.sql.shuffle.partitions 데이터 크기 / 200MB 기본 200은 소규모용. 1TB 데이터면 5000 이상. AQE 활성화 시 자동 병합됨
spark.executor.memory 4g ~ 16g 너무 크면 GC 시간 증가. 단일 JVM에 64g 이상은 G1GC·ZGC 검토 필요
spark.executor.cores 2 ~ 4 코어 수 많을수록 GC 경쟁 심화. 5코어 이상은 일반적으로 역효과
spark.memory.fraction 0.6 (기본) Spark 관리 메모리 비율. Spill 빈번하면 0.7~0.75로 올리되 User Memory 여유 확인
spark.memory.offHeap.enabled true (GC 심할 때) JVM GC 밖 Tungsten 메모리. GC Time이 Stage 시간의 20% 이상이면 검토
spark.sql.files.maxPartitionBytes 128MB ~ 256MB 파일 읽기 시 파티션 최대 크기. 256MB로 늘리면 태스크 수 감소 → 스케줄링 오버헤드 절감
spark.sql.autoBroadcastJoinThreshold 10MB → 100MB 기본 10MB는 작다. 메모리 여유 시 100MB~1GB로 확대해 셔플 없는 조인 범위 넓히기
spark.executor.extraJavaOptions -XX:+UseG1GC Heap 4g 이상 시 G1GC 권장. 32g+ 이상이면 ZGC. GC log 출력으로 튜닝 근거 확보

PySpark

실전 코드

PySpark DataFrame API 기준. SparkSession이 진입점이고 모든 작업은 여기서 시작한다. 코드 카드 헤더를 클릭하면 펼쳐진다.

대용량 처리 SparkSession — AQE + 메모리 + GC 설정

production config 
from pyspark.sql import SparkSession

spark = (SparkSession.builder
    .appName("large-scale-job")

    # AQE — 런타임 재최적화 (Spark 3.2+부터 기본값이나 명시 권장)
    .config("spark.sql.adaptive.enabled", "true")
    .config("spark.sql.adaptive.coalescePartitions.enabled", "true")
    .config("spark.sql.adaptive.skewJoin.enabled", "true")
    .config("spark.sql.adaptive.skewJoin.skewedPartitionFactor", "5")

    # 셔플 파티션 — 200은 소규모용. 데이터 크기(바이트) / 200MB 로 계산
    .config("spark.sql.shuffle.partitions", "2000")

    # Executor 메모리 — cores 2~4, memory 4~16g 조합이 GC 안정적
    .config("spark.executor.memory", "8g")
    .config("spark.executor.cores", "4")
    .config("spark.executor.memoryOverhead", "2g")  # off-heap + Python용 버퍼

    # 메모리 모델 튜닝
    .config("spark.memory.fraction", "0.7")     # 기본 0.6 → Spill 빈번하면 올리기
    .config("spark.memory.storageFraction", "0.3") # Storage에 덜 예약 → Execution 우선

    # GC 튜닝 — G1GC는 4g+ heap에서 STW pause 최소화
    .config("spark.executor.extraJavaOptions",
           "-XX:+UseG1GC -XX:G1HeapRegionSize=16m "
           "-XX:InitiatingHeapOccupancyPercent=35 "
           "-XX:+PrintGCDetails -XX:+PrintGCDateStamps")

    # 파일 읽기 파티션 크기 — 256MB로 늘려 태스크 수 감소
    .config("spark.sql.files.maxPartitionBytes", "268435456")  # 256MB

    # Broadcast join 임계치 확대 — 셔플 없는 조인 범위 늘리기
    .config("spark.sql.autoBroadcastJoinThreshold", "104857600")  # 100MB

    .getOrCreate())
포인트. memoryOverhead는 JVM 밖 메모리(Python 프로세스·off-heap 버퍼)다. PySpark는 Python 워커가 별도 프로세스로 뜨므로 executor.memory의 10~20%를 추가 확보해야 YARN/K8s에서 컨테이너가 OOM-kill되지 않는다.

데이터 스큐 — Salting 2-phase 집계

skew handling 
from pyspark.sql import functions as F
import math

# 스큐 키의 파티션 분산 목표 수 (핫 키의 데이터 크기 / 목표 파티션 크기)
SALT_BUCKETS = 50

# Phase 1: 키에 랜덤 접미사 추가 → 파티션 강제 분산
df_salted = df.withColumn(
    "salt", (F.rand() * SALT_BUCKETS).cast("int")
).withColumn(
    "salted_key", F.concat(F.col("user_id"), F.lit("_"), F.col("salt"))
)

agg1 = (df_salted
    .groupBy("salted_key", "event_type")
    .agg(
        F.sum("amount").alias("sum_amount"),
        F.count("*").alias("cnt"),
    ))

# Phase 2: 접미사 제거 후 원래 키로 최종 집계
result = (agg1
    .withColumn("user_id",
        F.regexp_extract(F.col("salted_key"), r"^(.+)_\d+$", 1))
    .groupBy("user_id", "event_type")
    .agg(
        F.sum("sum_amount").alias("total_amount"),
        F.sum("cnt").alias("total_cnt"),
    ))

# AQE skewJoin은 조인에만 적용 — groupBy 스큐는 Salting이 유일한 해법
result.write.parquet("s3://bucket/output/user-agg/")
포인트. SALT_BUCKETS는 핫 키가 차지하는 데이터 비율에 비례해서 정한다. 핫 키가 전체의 30%를 차지하고 목표 파티션 크기를 200MB로 잡으면, 30% × 전체 데이터 / 200MB = 버킷 수. 너무 많으면 Phase 2 집계의 셔플이 커지므로 균형을 맞춰야 한다.

SparkSession 초기화 + 기본 DataFrame 연산

entry point 
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StructField, StringType, IntegerType

# SparkSession — 모든 Spark 작업의 진입점
spark = (SparkSession.builder
    .appName("example")
    .config("spark.sql.shuffle.partitions", "200")  # 기본 200, 데이터 크기 맞게 조정
    .getOrCreate())

# Parquet 읽기 — 컬럼 프루닝·predicate pushdown 자동 적용
df = spark.read.parquet("s3://bucket/events/")

# Transformation 체이닝 — 이 시점에는 아무것도 실행되지 않음
result = (df
    .filter(F.col("event_type") == "purchase")
    .withColumn("revenue_krw", F.col("amount") * 1300)
    .groupBy("user_id", F.date_trunc("month", F.col("ts")).alias("month"))
    .agg(
        F.sum("revenue_krw").alias("total_revenue"),
        F.count("*").alias("purchase_count"),
    )
    .filter(F.col("total_revenue") > 100000)
    .orderBy(F.col("total_revenue").desc()))

# Action — 여기서 비로소 DAG가 실행됨
result.write.mode("overwrite").parquet("s3://bucket/output/monthly_revenue/")

spark.stop()
포인트. filter를 최대한 앞에 배치하면 Catalyst가 predicate pushdown을 통해 Parquet 파일 레벨에서 불필요한 row group을 건너뛴다. groupBy 뒤의 두 번째 filter는 HAVING 절에 해당한다.

Window Function — 누적합 · 랭킹 · 이전값 참조

analytics 
from pyspark.sql import Window
from pyspark.sql import functions as F

# 윈도우 스펙 — 파티션·정렬 기준 정의
w_user = (Window
    .partitionBy("user_id")
    .orderBy("ts")
    .rowsBetween(Window.unboundedPreceding, Window.currentRow))

w_rank = (Window
    .partitionBy("month")
    .orderBy(F.col("total_revenue").desc()))

result = (df
    # 사용자별 누적 매출
    .withColumn("cumulative_revenue", F.sum("amount").over(w_user))
    # 이전 구매 시점 (lag)
    .withColumn("prev_purchase_ts", F.lag("ts", 1).over(w_user))
    # 월별 매출 랭킹
    .withColumn("rank_in_month", F.dense_rank().over(w_rank))
    .filter(F.col("rank_in_month") <= 100))  # 월별 top 100

result.show(10, truncate=False)
포인트. Window Function은 Wide Transformation이므로 셔플이 발생한다. partitionBy 컬럼의 카디널리티가 낮으면(예: 성별) 데이터 스큐가 심각해진다. 이 경우 partitionBy에 카디널리티가 높은 컬럼을 추가해 파티션을 분산시킨다.

Broadcast Join — 셔플 없는 조인

optimization 
from pyspark.sql import functions as F

# 큰 테이블 (수억 row)
events = spark.read.parquet("s3://bucket/events/")

# 작은 룩업 테이블 (수만 row 이하)
products = spark.read.parquet("s3://bucket/products/")

# broadcast hint — products를 각 Executor 메모리에 복사
# 셔플 없이 map-side join으로 처리됨
result = events.join(
    F.broadcast(products),
    on="product_id",
    how="left"
)

# spark.sql.autoBroadcastJoinThreshold (기본 10MB)보다
# 작은 테이블은 자동으로 broadcast됨
# 명시적 hint가 더 안전함
result.write.parquet("s3://bucket/output/enriched_events/")
포인트. Broadcast join은 작은 테이블(보통 100MB 이하)을 각 Executor에 복사해 셔플 없이 조인한다. Shuffle sort-merge join 대비 수십 배 빠를 수 있다. 단, 브로드캐스트 테이블이 Executor 메모리에 맞아야 하므로 크기 확인이 필수다.

Structured Streaming — Kafka → 집계 → Delta Lake

streaming 
from pyspark.sql import functions as F
from pyspark.sql.types import StructType, StringType, LongType, TimestampType

# 이벤트 스키마 정의
schema = (StructType()
    .add("user_id", StringType())
    .add("event_type", StringType())
    .add("amount", LongType())
    .add("ts", TimestampType()))

# Kafka 스트림 읽기
raw_stream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "purchase-events")
    .option("startingOffsets", "latest")
    .load())

# JSON 파싱 → 집계
# watermark: 늦게 도착하는 데이터를 10분까지 허용
agg_stream = (raw_stream
    .select(F.from_json(F.col("value").cast("string"), schema).alias("e"))
    .select("e.*")
    .withWatermark("ts", "10 minutes")
    .groupBy(
        F.window(F.col("ts"), "5 minutes"),  # 5분 텀블링 윈도우
        "event_type"
    )
    .agg(
        F.sum("amount").alias("total"),
        F.count("*").alias("cnt"),
    ))

# Delta Lake에 Append 모드로 기록
query = (agg_stream.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://bucket/checkpoints/purchase-agg/")
    .trigger(processingTime="1 minute")
    .start("s3://bucket/delta/purchase-agg/"))

query.awaitTermination()
포인트. withWatermark는 늦게 도착하는 이벤트를 처리할 최대 지연 시간을 정의한다. watermark 시간을 넘긴 late data는 버려진다. checkpoint 위치는 장애 복구 시 정확히 한 번 처리(exactly-once)를 보장하는 핵심이다.

MLlib Pipeline — 피처 엔지니어링 + 모델 학습

machine learning 
from pyspark.ml import Pipeline
from pyspark.ml.feature import (
    StringIndexer, OneHotEncoder, VectorAssembler, StandardScaler
)
from pyspark.ml.classification import GBTClassifier
from pyspark.ml.evaluation import BinaryClassificationEvaluator
from pyspark.ml.tuning import ParamGridBuilder, CrossValidator

# 학습/검증 데이터 분할
train_df, test_df = df.randomSplit([0.8, 0.2], seed=42)

# 카테고리컬 인코딩
indexer = StringIndexer(inputCol="category", outputCol="cat_idx")
encoder = OneHotEncoder(inputCol="cat_idx", outputCol="cat_vec")

# 피처 벡터 조합
assembler = VectorAssembler(
    inputCols=["cat_vec", "amount", "purchase_count", "days_since_last"],
    outputCol="features_raw"
)
scaler = StandardScaler(inputCol="features_raw", outputCol="features")

# Gradient Boosted Trees 분류기
gbt = GBTClassifier(featuresCol="features", labelCol="label", maxIter=50)

# Pipeline — 단계별 fit/transform 자동화
pipeline = Pipeline(stages=[indexer, encoder, assembler, scaler, gbt])

# 하이퍼파라미터 그리드 + 교차 검증
param_grid = (ParamGridBuilder()
    .addGrid(gbt.maxDepth, [3, 5])
    .addGrid(gbt.stepSize, [0.05, 0.1])
    .build())

cv = CrossValidator(
    estimator=pipeline,
    estimatorParamMaps=param_grid,
    evaluator=BinaryClassificationEvaluator(),
    numFolds=3,
)

# 학습 — 분산 환경에서 각 fold를 병렬 실행
model = cv.fit(train_df)

# 예측 + 평가
predictions = model.transform(test_df)
auc = BinaryClassificationEvaluator().evaluate(predictions)
print(f"AUC: {auc:.4f}")

# 모델 저장
model.bestModel.save("s3://bucket/models/churn-gbt/")
포인트. MLlib Pipeline은 scikit-learn과 동일한 fit/transform 인터페이스를 제공하지만 실행이 Spark 클러스터에 분산된다. CrossValidator는 각 파라미터 조합·fold를 병렬로 실행하므로 단일 머신 그리드 서치보다 훨씬 빠르다. 단, 모델 자체가 100GB 이상 되지 않는 한 XGBoost-on-Spark나 PyTorch DDP가 더 적합한 경우가 많다.
