01
TL;DR

한 줄로 이해하기

카프카는 분산 커밋 로그(Distributed Commit Log)다. 메시지를 전달하고 지우는 큐가 아니라, 디스크에 순서대로 영속 저장하고 컨슈머가 원하는 오프셋부터 언제든 다시 읽을 수 있다. 이 단순한 원칙 하나가 수평 확장, 재처리, 이벤트 소싱을 모두 가능하게 한다.

01

토픽 · 파티션 · 오프셋

토픽은 논리적 채널이고, 파티션은 물리적 단위다. 각 파티션은 append-only 로그이며, 메시지마다 단조 증가하는 오프셋이 부여된다. 컨슈머는 오프셋을 직접 관리하므로 임의 지점부터 재처리가 가능하다. 파티션 수가 병렬처리 상한선이다.

02

프로듀서 배치 · 압축

linger.ms와 batch.size로 메시지를 묶어 보내고, Snappy/LZ4/ZSTD로 압축한다. 브로커는 압축된 배치를 그대로 디스크에 기록하고 컨슈머에 전달한다 — 한 번도 압축 해제하지 않는다. Zero-Copy sendfile(2)로 커널 버퍼에서 NIC로 직접 전달한다.

03

컨슈머 그룹 · 파티션 할당

동일 group.id를 가진 컨슈머들이 파티션을 나눠 담당한다. 컨슈머 1개당 파티션 1개 이상이 할당되고, 파티션보다 컨슈머가 많으면 유휴 상태가 된다. 그룹 코디네이터가 heartbeat를 감지해 멤버 변화 시 리밸런싱을 트리거한다.

04

ISR · 복제 · 내구성

각 파티션에는 Leader 1개와 Follower N개가 있다. ISR(In-Sync Replicas)는 Leader를 따라잡은 Follower 목록이다. acks=all이면 모든 ISR이 기록을 확인해야 프로듀서에 응답한다. Leader 장애 시 ISR 중 새 Leader를 선출한다.

05

Exactly-Once Semantics (EOS)

프로듀서 enable.idempotence=true + transactional.id로 브로커 측 중복 제거를 활성화한다. 트랜잭션 코디네이터가 두 토픽 쓰기를 원자적으로 묶는다. 컨슈머는 isolation.level=read_committed로 커밋된 메시지만 읽는다.

06

Kafka vs RabbitMQ vs Pulsar

RabbitMQ는 메시지 소비 후 삭제 — 복잡한 라우팅과 낮은 지연이 필요할 때. Kafka는 로그 보존 · 재처리 · 높은 처리량이 필요할 때. Pulsar는 멀티 테넌시 · 계층적 저장(BookKeeper + S3 오프로딩)이 필요할 때. CDC, 이벤트 소싱, 로그 집계는 Kafka가 정답이다.

Architecture

핵심 개념 도감

01브로커 클러스터

브로커는 파티션 리더/팔로워 역할을 동시에 맡는다. ZooKeeper(KRaft 이전)가 컨트롤러 선출과 메타데이터를 관리하고, 브로커는 KRaft 모드에서는 내부 메타데이터 토픽(@metadata)으로 이를 대체한다.

Kafka 3.3+ KRaft GA: ZooKeeper 없이 브로커가 Raft 합의로 컨트롤러를 선출한다. 클러스터 규모 확장 시 ZooKeeper 병목이 사라졌다.

브로커 수 선택

일반적으로 파티션 수 / 복제 인수 비율로 결정한다. LinkedIn: 1,400+ 브로커, 900TB+ 일일 처리량.

02파티션과 오프셋

파티션은 물리적으로 세그먼트 파일(.log) 묶음이다. 기본 세그먼트 크기는 1GB(log.segment.bytes). 읽기는 페이지 캐시를 통해 이뤄지며, 순차 I/O이므로 SSD와 HDD 모두 고처리량을 달성한다.

오프셋은 64비트 정수. 컨슈머 그룹의 커밋 오프셋은 __consumer_offsets 내부 토픽에 저장된다.

03컨슈머 그룹

하나의 파티션은 동일 그룹 내 하나의 컨슈머에만 할당된다. 파티션 수보다 컨슈머가 많으면 초과 컨슈머는 대기 상태가 된다. 그룹이 다르면 동일 파티션을 독립적으로 소비할 수 있다 — 파이프라인 팬아웃에 유용하다.

Static Group Membership(group.instance.id): 재시작 시 불필요한 리밸런싱을 방지한다. 쿠버네티스 롤링 업데이트에서 중요하다.

리밸런싱 최소화

session.timeout.ms를 충분히 크게, max.poll.interval.ms를 처리 시간에 맞게 설정한다. Incremental Cooperative Rebalancing(Kafka 2.4+)으로 Stop-The-World 리밸런싱을 제거한다.

04ISR 복제

Leader가 메시지를 받으면 Follower들이 Fetch로 복제한다. replica.lag.time.max.ms(기본 30s) 이내에 따라오지 못한 Follower는 ISR에서 제거된다. min.insync.replicas: ISR 최소 수. 이 수보다 ISR이 적으면 쓰기를 거부한다.

권장 내구성 설정

복제 인수 3 + min.insync.replicas=2 + acks=all. 브로커 1개 장애에서도 데이터 손실 없음.

05전달 보장 스펙트럼

At-Most-Once: acks=0, 빠르지만 손실 가능. At-Least-Once: acks=all + 재시도, 중복 가능. Exactly-Once: enable.idempotence=true + 트랜잭션 API, 브로커가 PID+Sequence로 중복을 차단한다.

EOS는 같은 Kafka 클러스터 내 read-process-write 파이프라인에만 보장된다. 외부 시스템(DB, S3)에 쓸 때는 멱등 설계가 별도로 필요하다.

EOS 비용

처리량 약 20% 감소, 지연 증가. 결제·재고 등 정확성이 중요한 파이프라인에만 적용한다.

03
Large Scale

대용량 처리

LinkedIn은 Kafka로 하루 7조 건 이상의 메시지를 처리한다. Uber는 초당 1백만 건의 이벤트를 4,000+ 토픽으로 분산한다. 이 수치의 배경에는 파티셔닝 전략, I/O 튜닝, 컨슈머 랙 관리가 있다.

01 · Partitioning
파티셔닝 전략 — 핫스팟 없이 균등 분산
사례 LinkedIn Uber Confluent

기본 파티셔너는 키 해시(murmur2). 키가 없으면 라운드로빈. 핫 키 문제: 특정 user_id나 merchant_id에 트래픽이 집중되면 단일 파티션이 병목이 된다.

해결책: 컴포지트 키(user_id + random_suffix), 또는 커스텀 파티셔너로 고트래픽 키를 여러 파티션에 분산한다. 컨슈머 쪽에서는 합산 처리한다.

파티션 수 확장: 기존 파티션 키 할당이 바뀌어 순서 보장이 깨진다. 파티션 수는 처음부터 여유 있게 설정하는 것이 권장된다(LinkedIn: 일부 토픽 3,000+ 파티션).

파티션 수 공식

파티션 수 = max(목표 프로듀서 처리량 / 단일 파티션 쓰기 처리량, 목표 컨슈머 처리량 / 단일 파티션 읽기 처리량). 단일 파티션은 일반적으로 10~50 MB/s.

02 · Throughput
처리량 튜닝 — 배치 · 압축 · Zero-Copy
적용 Netflix Airbnb

프로듀서 배치: linger.ms=5~20, batch.size=65536~262144. 배치가 클수록 압축률과 처리량이 올라가지만 지연은 증가한다.

압축: ZSTD가 압축률(Snappy 대비 30~40% 더 작음)과 CPU 효율 모두 우수하다. 브로커는 압축된 배치를 그대로 저장하고 전달한다(zero decompression). 컨슈머가 직접 해제한다.

Zero-Copy: sendfile(2) 시스템 콜로 페이지 캐시 → NIC 버퍼로 데이터를 직접 전달한다. user space 복사 없음. 단일 브로커 기준 2M+ msg/sec 처리량의 핵심이다.

페이지 캐시 활용

Kafka가 사용하는 힙(JVM) 크기를 작게(6~8GB) 유지하고 나머지 메모리를 OS 페이지 캐시로 남긴다. 읽기 작업의 대부분이 캐시 히트로 처리된다.

03 · Consumer Lag
컨슈머 랙 관리 — 지연 감지와 백프레셔
모니터링 Burrow Cruise Control

컨슈머 랙: 최신 오프셋 - 커밋 오프셋. 랙이 증가하면 컨슈머 처리 속도가 프로듀서 속도를 따라가지 못하는 것이다. kafka.consumer.records-lag-max 메트릭으로 추적한다.

랙 대응: (1) 컨슈머 인스턴스 추가(파티션 수 이내), (2) max.poll.records 줄여 처리 배치 크기 감소, (3) 처리 로직 최적화. 파티션 수 자체가 상한선이므로 미리 충분히 설정해야 한다.

Cruise Control(LinkedIn): 클러스터 부하를 자동으로 재분산한다. 브로커 간 리더 파티션 수, 디스크 사용량, 네트워크 처리량을 균등하게 유지한다.

리텐션 vs 랙

랙이 리텐션 기간을 넘으면 오래된 메시지가 삭제되어 데이터 손실이 발생한다. 크리티컬 토픽은 리텐션을 길게, 또는 무한(log.retention.bytes=-1)으로 설정한다.

04
Hands-On

실전 코드

kafka-python과 confluent-kafka 기준. 프로덕션에서는 confluent-kafka(librdkafka 기반)가 성능과 EOS 지원 면에서 권장된다.

01. 고처리량 Producer

producer 
from confluent_kafka import Producer
import json

# 배치 + 압축 + 멱등성 설정
producer = Producer({
    'bootstrap.servers': 'kafka-1:9092,kafka-2:9092,kafka-3:9092',
    'acks': 'all',                    # ISR 전체 확인
    'enable.idempotence': 'true',       # 중복 제거
    'compression.type': 'zstd',          # ZSTD 압축
    'linger.ms': '10',                  # 10ms 배치 대기
    'batch.size': '131072',             # 128KB 배치
    'buffer.memory': '33554432',        # 32MB 버퍼
    'retries': '2147483647',            # 무한 재시도
    'max.in.flight.requests.per.connection': '5',
})

def delivery_report(err, msg):
    if err:
        print(f'전달 실패: {err}')

def produce_events(events: list[dict]):
    for event in events:
        producer.produce(
            topic='orders',
            key=event['user_id'].encode(),     # 키 기반 파티셔닝
            value=json.dumps(event).encode(),
            on_delivery=delivery_report,
        )
        producer.poll(0)   # 논블로킹 이벤트 처리

    producer.flush()       # 버퍼 전부 전송 후 반환
포인트. enable.idempotence=true는 자동으로 acks=all, max.in.flight=5 이하를 강제한다. 멱등성과 고처리량을 동시에 달성한다.

02. Consumer 그룹 — 수동 오프셋 커밋

consumer 
from confluent_kafka import Consumer, KafkaError

consumer = Consumer({
    'bootstrap.servers': 'kafka-1:9092',
    'group.id': 'order-processor-v2',
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': 'false',     # 수동 커밋
    'max.poll.interval.ms': '300000',  # 처리 최대 5분
    'session.timeout.ms': '45000',
    'isolation.level': 'read_committed', # EOS: 커밋된 것만 읽기
})

consumer.subscribe(['orders'])

try:
    while True:
        msg = consumer.poll(timeout=1.0)
        if msg is None:
            continue
        if msg.error():
            if msg.error().code() == KafkaError._PARTITION_EOF:
                continue
            raise Exception(msg.error())

        # 비즈니스 처리
        process_order(msg.value())

        # 처리 성공 후에만 커밋
        consumer.commit(asynchronous=False)

finally:
    consumer.close()
포인트. enable.auto.commit=false + 수동 커밋으로 at-least-once를 보장한다. 처리 실패 시 재처리되므로 비즈니스 로직을 멱등하게 설계해야 한다.

03. Exactly-Once — 트랜잭션 프로듀서

exactly-once 
from confluent_kafka import Producer

producer = Producer({
    'bootstrap.servers': 'kafka-1:9092',
    'transactional.id': 'order-txn-producer-1',  # 트랜잭션 ID
    'enable.idempotence': 'true',
})

producer.init_transactions()

def process_with_eos(input_msg, consumer):
    try:
        producer.begin_transaction()

        # 처리 결과 쓰기 (두 토픽에 원자적으로)
        producer.produce('processed-orders', value=transform(input_msg))
        producer.produce('audit-log', value=audit_record(input_msg))

        # 컨슈머 오프셋도 같은 트랜잭션에 포함
        producer.send_offsets_to_transaction(
            consumer.position(consumer.assignment()),
            consumer.consumer_group_metadata(),
        )

        producer.commit_transaction()

    except Exception as e:
        producer.abort_transaction()
        raise
포인트. send_offsets_to_transaction으로 소비 오프셋을 트랜잭션에 묶는다. 커밋 실패 시 오프셋도 롤백되어 정확히-한-번 read-process-write가 보장된다.

06. 컨슈머 랙 모니터링

monitoring 
from confluent_kafka import Consumer, TopicPartition

def get_consumer_lag(group_id: str, topic: str) -> dict[int, int]:
    consumer = Consumer({
        'bootstrap.servers': 'kafka-1:9092',
        'group.id': group_id,
    })

    # 토픽 메타데이터로 파티션 목록 조회
    metadata = consumer.list_topics(topic)
    partitions = [
        TopicPartition(topic, p)
        for p in metadata.topics[topic].partitions
    ]

    # 커밋 오프셋 vs 최신 오프셋 비교
    committed = consumer.committed(partitions)
    lags = {}

    for tp in committed:
        lo, hi = consumer.get_watermark_offsets(tp)
        committed_offset = tp.offset if tp.offset >= 0 else lo
        lags[tp.partition] = hi - committed_offset

    consumer.close()
    return lags

# 사용 예시
lags = get_consumer_lag('order-processor-v2', 'orders')
for partition, lag in lags.items():
    print(f'Partition {partition}: lag={lag}')
포인트. 프로덕션에서는 Burrow나 kminion 같은 전용 모니터링 도구를 사용한다. 랙이 임계치를 넘으면 PagerDuty/Slack 알럿을 보내고, Kubernetes HPA로 컨슈머를 자동 스케일한다.
