01
TL;DR

한 줄로 이해하기

동시성 문제의 본질은 여러 실행 흐름이 공유 상태를 비원자적으로 읽고 쓰는 것이다. 읽기-수정-쓰기(RMW) 시퀀스 사이에 다른 스레드가 끼어들면 결과가 의도와 달라진다. 해결책은 계층마다 다르며, 잘못된 계층에서 잘못된 도구를 선택하면 성능 저하나 데드락을 유발한다.

01

Race Condition — 비원자적 RMW

스레드 A가 잔액 100을 읽고, 스레드 B도 100을 읽은 뒤, A가 50을 더해 150을 쓰고, B도 30을 더해 130을 쓴다. 최종값은 130이지만 올바른 값은 180이다. Lost Update가 발생했다. 원인: Read → Compute → Write 세 단계가 원자적이지 않아서 두 스레드의 작업이 겹쳤다. DB의 UPDATE accounts SET balance = balance + 50은 서버 사이드에서 원자적으로 처리되므로 안전하다.

02

Deadlock — 순환 대기

A가 Lock1을 잡고 Lock2를 요청, B가 Lock2를 잡고 Lock1을 요청하면 서로 영원히 기다린다. 4가지 조건: 상호 배제(Mutual Exclusion), 점유와 대기(Hold and Wait), 비선점(No Preemption), 순환 대기(Circular Wait). 이 중 하나만 깨면 데드락이 발생하지 않는다. PostgreSQL은 자동으로 데드락을 감지해 한 트랜잭션을 롤백한다.

03

DB 이상현상 — Dirty / Non-repeatable / Phantom Read

Dirty Read: 다른 트랜잭션의 커밋되지 않은 데이터를 읽는다. Non-repeatable Read: 같은 쿼리를 두 번 실행했더니 다른 결과가 반환된다(다른 트랜잭션이 그 사이에 커밋). Phantom Read: 범위 쿼리를 두 번 실행했더니 처음에 없던 레코드가 생겼다. 격리 수준을 높일수록 이 이상현상들을 차례로 제거하지만 성능 비용도 증가한다.

04

Optimistic Locking — 낙관적 잠금

충돌이 드물다는 가정 하에 잠금 없이 읽고, 쓰기 직전에 버전(또는 타임스탬프)을 확인한다. 버전이 달라졌으면(다른 사람이 먼저 수정) 재시도한다. DB에서는 UPDATE ... WHERE id=? AND version=?로 구현한다. 영향 행이 0이면 충돌이 발생한 것. 경합이 낮은 환경에서 높은 처리량을 달성한다.

05

MVCC — 읽기가 쓰기를 막지 않는다

Multi-Version Concurrency Control: 데이터를 수정할 때 기존 버전을 지우지 않고 새 버전을 추가한다. 읽기 트랜잭션은 자신이 시작한 시점의 스냅샷을 본다. 결과적으로 읽기와 쓰기가 서로를 블로킹하지 않는다. PostgreSQL과 InnoDB(MySQL) 모두 MVCC를 사용한다. 오래된 버전은 VACUUM(PG) 또는 Purge Thread(InnoDB)가 정리한다.

06

CAS & 원자적 연산 — 하드웨어 수준 보장

Compare-and-Swap(CAS)은 CPU 명령어 수준에서 "현재 값이 expected면 new로 교체"를 원자적으로 실행한다. Java의 AtomicInteger.compareAndSet(), C의 __sync_bool_compare_and_swap()이 이를 사용한다. 락 없이 스레드 안전한 카운터, 큐, 스택을 구현할 수 있다. ABA 문제: 값이 A → B → A로 바뀌었지만 CAS는 변경을 감지 못한다. 버전 태그를 함께 사용해 해결한다.

01Race Condition & Lost Update

두 스레드가 동시에 잔액을 읽고 각자 수정해 쓰면 한 쪽의 쓰기가 사라진다. 이것이 Lost Update다. 조건: (1) 공유 상태에 대한 (2) 비원자적 RMW 시퀀스.

해결책은 3가지다. ① DB 원자 연산: UPDATE SET balance = balance + :delta(서버 사이드 계산). ② 비관적 잠금: SELECT FOR UPDATE로 읽을 때 락 획득. ③ 낙관적 잠금: version 컬럼 확인 후 쓰기.

check-then-act 패턴 주의

"재고 > 0인지 확인 → 차감" 사이에 다른 스레드가 재고를 가져가면 음수 재고가 된다. DB 레벨의 원자적 연산이나 SELECT FOR UPDATE를 사용해야 한다.

시간Thread AThread B
T1
READ balance=100
T2
READ balance=100
T3
WRITE 100+50=150
T4
WRITE 100+30=130 (덮어씀!)
결과: 130 (올바른 값: 180) — A의 +50이 사라짐
수정: UPDATE SET balance = balance + 50 (원자적)

02Deadlock — 순환 대기

데드락 발생 4조건 중 순환 대기(Circular Wait)를 깨는 것이 가장 실용적이다. 항상 같은 순서로 락을 획득한다(예: 항상 user_id 오름차순으로 잠금). 또는 락 타임아웃을 설정해 일정 시간 후 포기하고 재시도한다.

DB 데드락: PostgreSQL은 1초 간격으로 데드락을 감지해 ERROR: deadlock detected를 반환하고 한 트랜잭션을 롤백한다. 애플리케이션은 이 에러를 잡아 재시도해야 한다. 데드락 위험을 줄이는 법: 트랜잭션을 짧게 유지하고, 락 획득 순서를 일관되게 하고, 불필요한 SELECT FOR UPDATE를 제거한다.

Livelock vs Starvation

Livelock: 두 스레드가 서로를 피하려 계속 상태를 바꾸지만 진전이 없다(마주오는 두 사람이 서로 비켜서다 충돌 반복). Starvation: 특정 스레드가 계속 락을 얻지 못해 실행되지 않는 상태(공정성 부재). ReentrantLock의 fair=true로 대기 순서를 보장한다.

Thread A
보유: Lock1
Thread B
보유: Lock2
Lock2 요청 → ← Lock1 요청
DEADLOCK: 서로 상대방의 락을 기다리며 진행 불가
해결: PostgreSQL이 자동 감지 → 한 TX 롤백 → 에러 잡아 재시도
예방: 락 획득 순서 통일 (항상 id 오름차순)

03DB 이상현상 3가지

Dirty Read: TX A가 쓴 미커밋 데이터를 TX B가 읽는다. TX A가 롤백하면 B는 없는 데이터를 본 것. Read Uncommitted 격리 수준에서만 발생한다. 실무에서 이 격리 수준은 거의 사용하지 않는다.

Non-repeatable Read: TX B가 같은 행을 두 번 읽었을 때 TX A의 커밋으로 값이 달라진다. Read Committed에서 발생, Repeatable Read 이상에서 방지된다. Phantom Read: TX B가 범위 조건(WHERE age > 30)으로 두 번 조회하면 TX A가 삽입한 레코드가 두 번째에 나타난다. Repeatable Read에서도 발생 가능, Serializable에서 방지된다.

PostgreSQL의 특이점

PostgreSQL의 Repeatable Read는 MVCC 기반 스냅샷 격리로 Phantom Read를 사실상 방지한다(표준 SQL과 다름). Serializable 격리는 SSI(Serializable Snapshot Isolation)를 사용해 쓰기 충돌도 감지한다.

Dirty Read
TX A: UPDATE balance=200
(미커밋)
→
TX B: 200 읽음
(TX A 롤백 → 없는 값)
Non-repeatable Read
TX B: 1차 READ 100 → (TX A: UPDATE→커밋) → 2차 READ 200 (달라짐)
Phantom Read
TX B: 1차 COUNT(*)=5 → (TX A: INSERT→커밋) → 2차 COUNT(*)=6 (유령 행)

04격리 수준 매트릭스

SQL 표준은 4가지 격리 수준을 정의한다. 격리 수준이 높을수록 이상현상을 방지하지만 동시성이 줄고 레이턴시가 증가한다. 대부분의 애플리케이션에서 Read Committed가 충분하다.

PostgreSQL 기본: Read Committed. MySQL InnoDB 기본: Repeatable Read. Serializable은 직렬 실행과 동일한 결과를 보장하지만 충돌 시 트랜잭션을 자동 롤백하므로 재시도 로직이 필요하다.

실무 선택 기준

보고서·배치 쿼리처럼 일관된 스냅샷이 필요하면 Repeatable Read. 재무 데이터의 정확한 합산이 필요하면 Serializable. 일반 OLTP는 Read Committed. Dirty Read가 허용되는 경우는 없다.

05Optimistic vs Pessimistic Locking

비관적 잠금(Pessimistic): 읽을 때부터 락을 잡는다. SELECT ... FOR UPDATE. 충돌 가능성이 높고, 락 보유 시간이 짧고, 실패 비용이 높을 때 사용한다(좌석 예약, 재고 차감). 데드락 위험이 있다.

낙관적 잠금(Optimistic): 락 없이 읽고, 쓰기 시 version을 확인한다. UPDATE ... WHERE id=? AND version=?. 충돌이 드물고, 읽기가 많고, 충돌 시 재시도 비용이 낮을 때 사용한다(소셜 미디어 좋아요, 프로필 수정). 충돌이 잦으면 재시도 폭풍이 발생한다.

선택 기준

동시 경합이 높고 충돌 비용이 크면 Pessimistic. 읽기 위주이고 충돌이 드물면 Optimistic. Optimistic 재시도는 지수 백오프(exponential backoff)와 최대 재시도 횟수(3~5회)를 설정한다.

Pessimistic — SELECT FOR UPDATE
TX A: 락 획득 → 읽기 → 수정 → 커밋(락 해제)
TX B: 락 대기...
→ 획득 후 읽기
Optimistic — version 컬럼
TX A: 읽기(v=1) → 수정
UPDATE WHERE v=1 → 성공(v=2)
TX B: 읽기(v=1) → 수정
UPDATE WHERE v=1 → 0행 → 재시도

06MVCC — 스냅샷 기반 동시성

PostgreSQL MVCC: 모든 행에 xmin(생성한 TX ID)과 xmax(삭제/갱신한 TX ID)가 있다. 읽기 TX는 자신의 스냅샷에서 xmin <= snapshot_xid < xmax인 행 버전을 본다. 쓰기는 새 행 버전을 삽입하고 기존 행의 xmax를 설정한다.

결과: 읽기가 쓰기를 막지 않는다. 읽기 TX는 현재 진행 중인 쓰기의 영향 없이 일관된 스냅샷을 본다. VACUUM 필요성: 오래된 행 버전(dead tuple)이 쌓여 테이블이 비대해진다. VACUUM이 이를 정리한다. autovacuum이 자동으로 실행되지만, 대량 갱신 후 VACUUM ANALYZE를 수동으로 실행하기도 한다.

Transaction ID Wraparound

PostgreSQL의 TX ID는 32비트(약 21억). 21억 개 트랜잭션 후 ID가 순환하면 과거 행이 미래로 보여 데이터 손실 위험이 있다. VACUUM FREEZE가 오래된 행의 xmin을 FrozenTransactionId로 바꿔 이를 방지한다.

Solutions

해결 패턴

동시성 문제는 어느 계층에서 발생하느냐에 따라 해결책이 다르다. DB 레벨, 애플리케이션 레벨, 분산 환경 레벨로 구분해 적절한 도구를 선택한다.

01 · Database
DB 레벨 잠금 전략
도구PostgreSQLMySQL InnoDB

SELECT FOR UPDATE: 조회한 행에 배타적 잠금. 같은 행을 다른 TX가 SELECT FOR UPDATE 또는 UPDATE하려 하면 대기한다. NOWAIT: 즉시 실패 반환. SKIP LOCKED: 잠긴 행을 건너뛰고 다음 행 처리 — 작업 큐 패턴에 유용하다.

Advisory Lock: 애플리케이션이 정의한 64비트 정수로 잠금. 테이블 행과 무관한 논리적 잠금. pg_try_advisory_lock(key)는 즉시 반환, pg_advisory_lock(key)는 대기한다. 세션 종료 시 자동 해제된다. 분산 락 대신 단일 DB 환경에서 사용한다.

낙관적 잠금 with version: UPDATE ... SET value=?, version=version+1 WHERE id=? AND version=?로 영향 행 수를 확인한다. 0이면 충돌 발생. 재시도 시 최신 데이터를 다시 읽어 계산을 반복한다.

SKIP LOCKED 작업 큐 패턴

다수의 Worker가 동일 테이블에서 미처리 작업을 가져갈 때: SELECT * FROM jobs WHERE status='pending' LIMIT 1 FOR UPDATE SKIP LOCKED. 여러 Worker가 동시에 실행해도 같은 작업을 중복 처리하지 않는다.

SELECT ... FOR UPDATE — 비관적 (행 락)
SELECT ... FOR UPDATE SKIP LOCKED — 작업 큐
UPDATE SET v=v+1 WHERE id=? AND ver=? — 낙관적
pg_advisory_lock(42) — 논리적 잠금
락 선택: 경합 높음→FOR UPDATE / 경합 낮음→Optimistic / 큐→SKIP LOCKED
02 · Application
애플리케이션 레벨 동시성 제어
언어PythonJava

Python: GIL(Global Interpreter Lock)로 인해 한 번에 하나의 Python 스레드만 실행된다. CPU 바운드 작업은 GIL 때문에 멀티스레드로 병렬화 불가 — multiprocessing을 사용한다. I/O 바운드는 threading이나 asyncio가 효과적이다. threading.Lock()으로 공유 상태를 보호한다. asyncio에서는 asyncio.Lock()을 사용한다(blocking I/O 없이 코루틴 간 동기화).

Java: synchronized는 메서드·블록 단위 상호 배제. ReentrantLock은 tryLock(timeout), lockInterruptibly() 등 세밀한 제어. ReadWriteLock은 다수 읽기·단일 쓰기를 허용해 읽기 처리량을 높인다. AtomicInteger·AtomicReference는 CAS 기반으로 락 없이 스레드 안전한 연산을 제공한다.

채널 기반(Go): 공유 메모리 대신 채널로 통신한다. "Don't communicate by sharing memory; share memory by communicating." 뮤텍스보다 데드락이 덜 발생하고, 고루틴 간 협력이 자연스럽다.

03 · Distributed
분산 환경 동시성 — Redis 분산 락
도구Redis RedlockZooKeeper

Redis SET NX EX: SET lock_key random_value NX EX 30. NX(Not eXists): 키가 없을 때만 설정. EX 30: 30초 만료(잠금 누수 방지). 해제 시 Lua 스크립트로 값 확인 후 삭제(다른 클라이언트의 락을 실수로 해제 방지).

Redlock 알고리즘: Redis 5개 인스턴스(또는 홀수)에 동시에 락 획득 시도. 과반(3개+) 획득 성공 + 총 소요 시간이 만료 시간 미만이면 락 획득 성공. 단일 Redis 장애에도 내구성이 있다. 비판: Antirez(Redis 창시자)와 Martin Kleppmann이 안전성 논쟁 — 분산 환경에서 TTL 기반 락은 GC 일시정지나 네트워크 지연으로 안전하지 않을 수 있다. Fencing Token(단조 증가 번호)을 함께 사용하면 안전성이 높아진다.

ZooKeeper/etcd 기반 락: Paxos/Raft 기반으로 더 강한 일관성 보장. 퍼포먼스는 Redis보다 낮지만 데이터 정합성이 더 중요한 경우 사용한다.

SET order:lock:123 {uuid} NX EX 30
OK → 락 획득
→ 비즈니스 로직
→ DEL (Lua 검증)
nil → 이미 잠김
→ backoff(100ms)
→ 재시도 또는 실패
해제 Lua: if redis.call("get",k)==v then redis.call("del",k) end
Fencing Token: 락 획득 시 단조 증가 번호 수령 → DB 쓰기 시 번호 검증

진단 & 프로파일링

PostgreSQL 락 조회: pg_locks 뷰와 pg_stat_activity를 조인해 대기 중인 쿼리와 블로킹 쿼리를 확인한다. lock_timeout = '5s'와 deadlock_timeout = '1s'를 서버 설정에 추가해 대기 상한을 설정한다.

MySQL InnoDB 락 진단: SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK 섹션에서 데드락 히스토리를 확인한다. information_schema.INNODB_LOCKS로 현재 대기 중인 락을 조회한다.

Python threading 디버깅: threading.settrace()나 faulthandler.dump_traceback_later()로 스레드 덤프를 수집한다. py-spy: 실행 중인 Python 프로세스의 스택 트레이스를 무중단 수집한다. 데드락 발생 시 모든 스레드가 blocked 상태임을 확인할 수 있다.

연결 풀 고갈 진단

DB 연결이 부족해 애플리케이션이 대기 상태가 되는 경우도 동시성 문제로 오인된다. pg_stat_activity에서 wait_event_type='Client'인 연결 수가 많으면 연결 풀 크기나 쿼리 실행 시간을 점검한다.

-- 블로킹 쿼리 확인 (PostgreSQL)
SELECT pid, wait_event_type, wait_event,
  query FROM pg_stat_activity
WHERE state = 'active' AND wait_event IS NOT NULL;
-- 락 대기 체인 확인
SELECT blocking.pid AS blocking_pid,
  blocked.query AS blocked_query
FROM pg_locks blocked
JOIN pg_locks blocking ON blocked.transactionid = blocking.transactionid
WHERE NOT blocked.granted;
동시성 버그의 특징: 재현하기 어렵고, 테스트에서 발견하기 어렵고, 프로덕션에서 가끔씩 발생한다. 설계 단계에서 공유 상태를 최소화하고, 불변 객체(immutable)를 선호하고, 상태를 단일 스레드가 소유하는 Actor 패턴을 사용하는 것이 사후 수정보다 훨씬 효과적이다. Go의 채널, Erlang의 프로세스, Akka의 Actor가 이 철학의 구현체다.

낙관적 잠금 — version 컬럼

optimistic
from sqlalchemy import Column, Integer, String
from sqlalchemy.orm import Session

class Account(Base):
    __tablename__ = "accounts"
    id = Column(Integer, primary_key=True)
    balance = Column(Integer)
    version = Column(Integer, default=0)  # 낙관적 잠금 버전

def transfer_optimistic(session: Session, account_id: int, delta: int,
                         max_retries: int = 5):
    for attempt in range(max_retries):
        account = session.get(Account, account_id)
        if not account:
            raise ValueError("계좌 없음")

        new_balance = account.balance + delta
        if new_balance < 0:
            raise ValueError("잔액 부족")

        # WHERE version=현재값 — 다른 TX가 수정했으면 0 행 갱신
        affected = session.execute(
            """UPDATE accounts
               SET balance=:bal, version=version+1
               WHERE id=:id AND version=:ver""",
            {"bal": new_balance, "id": account_id, "ver": account.version},
        ).rowcount

        if affected == 1:
            session.commit()
            return  # 성공

        # 충돌 — 지수 백오프 후 재시도
        session.rollback()
        time.sleep(0.01 * (2 ** attempt))

    raise RuntimeError(f"낙관적 잠금 실패: {max_retries}회 재시도 초과")
재시도 설계. 재시도 횟수와 백오프를 제한한다. 무한 재시도는 CPU 폭풍(retry storm)을 유발한다. max_retries=5, 지수 백오프가 실무 표준이다.

Redis 분산 락 — Lua 스크립트로 안전한 해제

distributed lock
import uuid, time
from contextlib import contextmanager
import redis

r = redis.Redis(host="redis", port=6379)

# 해제용 Lua: 내 값인지 확인 후 삭제 (원자적)
UNLOCK_SCRIPT = """
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
"""

@contextmanager
def redis_lock(key: str, ttl: int = 30, retry: int = 10, interval: float = 0.1):
    token = str(uuid.uuid4())
    lock_key = f"lock:{key}"
    acquired = False

    for _ in range(retry):
        # NX=없을 때만, EX=TTL(초) — 원자적으로 세트
        if r.set(lock_key, token, nx=True, ex=ttl):
            acquired = True
            break
        time.sleep(interval)

    if not acquired:
        raise TimeoutError(f"락 획득 실패: {key}")

    try:
        yield token
    finally:
        # 내 토큰인지 확인 후 삭제 (다른 클라이언트 락 해제 방지)
        r.eval(UNLOCK_SCRIPT, 1, lock_key, token)

# 사용
with redis_lock("order:123", ttl=10):
    # 임계 영역 — 한 번에 하나의 프로세스만 실행
    process_order("123")
Lua 원자성. get + del을 두 번의 커맨드로 실행하면 사이에 다른 클라이언트가 락을 갱신할 수 있다. Lua 스크립트는 Redis에서 원자적으로 실행되므로 이 문제가 없다.

SKIP LOCKED — 작업 큐 패턴

job queue
-- jobs 테이블: id, status, payload, created_at -- Worker가 미처리 작업을 가져가는 쿼리 -- 여러 Worker가 동시 실행해도 중복 처리 없음 BEGIN; SELECT id, payload FROM jobs WHERE status = 'pending' AND scheduled_at <= NOW() ORDER BY scheduled_at LIMIT 1 FOR UPDATE SKIP LOCKED; -- 이미 잠긴 행 건너뜀 -- 취득 성공 시 상태 갱신 UPDATE jobs SET status = 'processing', started_at = NOW() WHERE id = :job_id; COMMIT; -- 처리 완료 UPDATE jobs SET status = 'done', finished_at = NOW() WHERE id = :job_id; -- 처리 실패 (retry 증가) UPDATE jobs SET status = CASE WHEN retry_count < 3 THEN 'pending' ELSE 'failed' END, retry_count = retry_count + 1, scheduled_at = NOW() + INTERVAL '5 minutes' WHERE id = :job_id;
DB 기반 큐의 장점. Redis Queue와 달리 작업 상태, 재시도 횟수, 실행 히스토리를 DB에서 트랜잭셔널하게 관리한다. 작업 수가 수십만 이하이면 별도 큐 시스템 없이 PostgreSQL로 충분하다.

asyncio.Lock vs threading.Lock. asyncio.Lock은 코루틴 간 동기화에만 사용한다. blocking I/O(requests 라이브러리 등)와 함께 쓰면 이벤트 루프가 멈춘다. blocking 작업은 run_in_executor로 스레드 풀에서 실행한다.
