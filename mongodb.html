01
TL;DR

한 줄로 이해하기

MongoDB는 BSON 도큐먼트를 기본 단위로 하는 NoSQL 데이터베이스다. 중첩 배열과 서브 도큐먼트를 하나의 도큐먼트에 담아 JOIN 없이 관련 데이터를 함께 읽는 패턴이 핵심이다. WiredTiger 스토리지 엔진, 레플리카셋 기반 HA, 샤딩 클러스터로 수평 확장을 지원한다.

01

도큐먼트 모델 — 데이터 지역성

관련 데이터를 하나의 도큐먼트에 임베드(embed)하면 단일 읽기 작업으로 완결된다. RDBMS의 JOIN은 네트워크 왕복과 인덱스 조인 비용을 유발한다. 임베드 vs 참조: 함께 읽히는 데이터는 임베드, 독립적으로 갱신되거나 크기가 큰 데이터는 별도 컬렉션으로 참조한다.

02

WiredTiger — MVCC + 압축

WiredTiger는 MVCC(Multi-Version Concurrency Control)를 사용한다. 읽기와 쓰기가 서로를 차단하지 않는다. 체크포인트는 60초마다 수행되며, 그 사이의 변경은 WAL(Journal)에 기록된다. 기본 압축: snappy(50~70% 저장 절약).

03

레플리카셋 · 오퍼튜니스틱 읽기

레플리카셋은 Primary 1개 + Secondary N개(최소 3개 권장)로 구성된다. Primary 장애 시 Secondary가 선거(Election)로 새 Primary를 선출한다. ReadPreference: secondaryPreferred로 읽기를 Secondary에 분산하면 Primary 부하를 줄인다(단, 복제 지연만큼 읽기가 오래될 수 있음).

04

샤딩 — 수평 확장

mongos 라우터가 샤드 키 기반으로 요청을 적절한 샤드로 라우팅한다. Config Server가 청크 메타데이터를 관리하고, 밸런서가 청크를 자동으로 재분배한다. 각 샤드는 레플리카셋으로 구성된다. 샤드 키 선택이 가장 중요한 설계 결정이다 — 변경이 매우 어렵다.

05

집계 파이프라인

SQL의 GROUP BY / JOIN / HAVING을 스테이지 파이프라인으로 표현한다. $match → $group → $sort → $project 순서로 스트리밍 처리한다. $lookup: 다른 컬렉션을 LEFT OUTER JOIN. $unwind: 배열을 풀어 각 요소를 별도 도큐먼트로 변환.

06

Change Stream · 트랜잭션

Change Stream: Oplog를 구독해 실시간으로 변경 이벤트를 받는다. CDC 파이프라인과 실시간 알림에 사용된다. 트랜잭션(4.0+): 레플리카셋 내 ACID, 4.2+에서 샤드 클러스터 간 분산 트랜잭션 지원. 단, 트랜잭션은 오버헤드가 크므로 꼭 필요한 경우에만 사용한다.

02
Architecture

핵심 개념 도감

01도큐먼트 모델

BSON은 JSON의 바이너리 인코딩이다. 추가 타입을 지원한다: ObjectId, Date, Decimal128, Binary. 도큐먼트 최대 크기는 16MB.

임베디드 도큐먼트는 쿼리 시 점 표기법으로 접근한다: "address.city". 배열 필드는 $elemMatch로 복합 조건을 적용한다.

임베드 한계

무제한 성장하는 배열(예: 이벤트 로그, 댓글)은 임베드하지 않는다. 도큐먼트가 16MB를 초과하거나 자주 갱신되는 서브 필드가 있으면 참조 패턴을 사용한다.

02레플리카셋

모든 쓰기는 Primary로 가고 Oplog를 통해 Secondary에 비동기 복제된다. writeConcern: majority: 과반 멤버가 기록을 확인해야 응답. Election: Primary 장애 시 10~30초 내에 새 Primary 선출.

Arbiter는 데이터 없이 선거 투표권만 가진다. 짝수 노드일 때 타이 브레이킹 역할로 추가하지만, Atlas 등 관리형 서비스에서는 권장하지 않는다.

PSS vs PSA

PSS(Primary-Secondary-Secondary): 모든 노드가 데이터를 보유, 고가용성 최대. PSA(Primary-Secondary-Arbiter): 스토리지 비용 절약, 하지만 가용성 낮음. 프로덕션은 PSS + 최소 3노드가 권장된다.

03샤딩 클러스터

데이터를 여러 샤드(레플리카셋)에 분산한다. mongos 라우터가 샤드 키 기반으로 요청을 라우팅한다. Config Server(레플리카셋)가 청크 맵을 유지한다.

청크(Chunk): 기본 64MB 범위의 데이터 단위. 밸런서가 청크 수가 불균형할 때 자동으로 마이그레이션한다. 마이그레이션 중에도 쿼리는 계속 처리된다.

대상 쿼리 vs 산탄총 쿼리

샤드 키를 포함한 쿼리는 특정 샤드만 쿼리(Targeted). 샤드 키 없는 쿼리는 모든 샤드에 브로드캐스트(Scatter-Gather). 비용이 선형으로 증가하므로 샤드 키를 쿼리에 항상 포함해야 한다.

04인덱스 유형

모든 인덱스는 B-Tree 기반(Text, Hashed, 2dsphere 제외). _id는 자동으로 유니크 인덱스가 생성된다. 인덱스는 WiredTiger 캐시에 상주하므로 인덱스 크기가 캐시를 초과하면 성능이 급락한다.

ESR 규칙

복합 인덱스 필드 순서: Equality(동등) → Sort(정렬) → Range(범위). 이 순서로 필드를 배치하면 인덱스 효율이 최대화된다.

05집계 파이프라인

도큐먼트가 스테이지를 순서대로 통과하며 변환된다. 각 스테이지의 출력이 다음 스테이지의 입력이 된다. 파이프라인 최적화: $match를 최대한 앞에 배치해 처리 도큐먼트 수를 줄인다.

$facet: 단일 파이프라인에서 여러 집계를 병렬로 실행. 검색 결과 페이지의 필터 개수를 한 번에 계산할 때 유용하다.

allowDiskUse

집계 파이프라인 중간 결과가 100MB를 초과하면 에러 발생. allowDiskUse: true로 디스크 임시 파일을 허용한다. 단, 성능이 크게 저하되므로 쿼리 최적화를 먼저 시도한다.

07Write/Read Concern 트라이앵글

Write Concern(w): 쓰기를 몇 개 노드가 확인해야 응답할지. w:1은 Primary만, w:majority는 과반 Secondary 복제 확인 후 응답. 후자는 Primary 장애 시 데이터 손실이 없지만 레이턴시가 약 수 ms 증가한다.

Read Preference: 어느 노드에서 읽을지. primary는 항상 최신, secondaryPreferred는 Secondary에서 읽어 Primary 부하를 분산하지만 복제 지연만큼 stale할 수 있다.

Read Concern(majority): 과반 노드에 기록된 데이터만 읽는다. w:1로 쓴 뒤 readConcern:majority로 읽으면 방금 쓴 데이터가 보이지 않을 수 있다. 이 조합이 가장 흔한 stale read 원인이다.

카운터 패턴 주의

w:1 + readPreference:secondary 조합으로 재고 카운터를 읽으면 아직 복제되지 않은 값을 읽어 overselling이 발생할 수 있다. 재고·결제 등 정합성이 중요한 읽기는 반드시 primary + readConcern:majority를 사용한다.

08Oplog 구조

Oplog(Operations Log)는 capped collection(local.oplog.rs)이다. 최대 크기에 도달하면 가장 오래된 항목부터 덮어쓴다. Secondary는 Oplog의 마지막 항목부터 tail하며 변경을 재적용한다.

Oplog의 모든 연산은 멱등성(idempotent)을 갖도록 변환된다. $inc: 1은 $set: {n: 42}로 변환된다. Secondary가 같은 Oplog 항목을 두 번 적용해도 결과가 동일해야 하기 때문이다.

Replication Lag: Secondary가 Primary Oplog를 따라가지 못하면 Lag이 발생한다. Oplog 크기가 너무 작으면 Secondary가 따라잡기 전에 항목이 덮어쓰여져 Oplog 윈도우 이탈 상태가 된다 — 이 경우 Secondary의 초기 동기화가 필요하다.

Oplog 크기 계산

최소 24~72시간의 쓰기를 수용해야 한다. rs.printReplicationInfo()로 현재 Oplog 보존 시간을 확인한다. Change Stream의 재개(resume_after) 가능 시간도 Oplog 크기에 의존한다.

06WiredTiger 페이지 구조

각 B-Tree 리프 페이지는 Disk Image(불변)와 In-Memory Update List로 구성된다. 쓰기는 Disk Image를 수정하지 않고 Update List에 새 버전을 추가한다. 읽기는 트랜잭션 시작 시점의 timestamp를 기준으로 visible한 버전만 반환한다.

체크포인트(Reconciliation) 시 Update List를 Disk Image에 통합해 새 .wt 파일 블록을 기록한다. 이후 오래된 버전은 해제된다. 장기 트랜잭션이 오래된 스냅샷을 보유하면 Update List를 비울 수 없어 캐시가 팽창한다.

Eviction 임계치

eviction_target(기본 80%): 이 아래로 유지하기 위해 background workers 시작. eviction_trigger(기본 95%): 초과 시 application threads도 eviction 참여 → p99 레이턴시 급등. wiredTigerConcurrentReadTransactions(기본 128)로 동시 읽기 트랜잭션 수 제한.

03
Large Scale

대용량 처리

Forbes Global 2000 기업의 60%+가 MongoDB를 사용한다. 미국 최대 의료 기록 플랫폼 Epic은 수억 개의 환자 도큐먼트를 처리하고, Booking.com은 수억 개의 숙박 예약을 MongoDB로 관리한다.

01 · Shard Key
샤드 키 설계 — 가장 중요한 결정
중요도Critical

샤드 키는 컬렉션 생성 후 변경이 매우 어렵다(5.0+에서 리샤딩 지원하지만 비용이 큼). 잘못 선택하면 전체 클러스터가 단일 샤드에 집중되는 핫스팟이 발생한다.

나쁜 샤드 키 패턴: (1) 단조 증가값(_id, 타임스탬프) — 항상 마지막 청크에 데이터가 집중. (2) 카디널리티 낮은 필드(예: status 3개 값) — 최대 3개 청크만 생성 가능. (3) 쿼리에 포함되지 않는 필드 — 모든 쿼리가 Scatter-Gather.

좋은 패턴: 해시 샤드 키(hashed)로 균등 분산. 또는 컴포지트 샤드 키(tenant_id + _id)로 tenant 격리와 균등 분산을 동시에 달성한다.

Zone Sharding

특정 샤드 키 범위를 특정 샤드(또는 지역)에 고정하는 기능. 지역 데이터 주권(GDPR) 요구나 멀티 테넌시에서 테넌트를 특정 샤드에 격리할 때 사용한다.

02 · Index Strategy
인덱스 전략 — 캐시 & ESR
핵심ESR RulePartial Index

인덱스 수 최소화: 각 인덱스는 쓰기 시 추가 비용을 발생시키고 WiredTiger 캐시를 소비한다. 사용되지 않는 인덱스는 즉시 삭제한다($indexStats로 확인).

Covered Query: 쿼리에 필요한 필드가 모두 인덱스에 있으면 도큐먼트 자체를 읽지 않는다. explain()에서 IXSCAN만 보이면 Covered이다.

Partial Index: 특정 조건을 만족하는 도큐먼트만 인덱싱한다. 예: 활성 상품만 인덱싱 → {"status": "active"}. 전체 인덱스 대비 크기가 작아 캐시 효율적이다.

인덱스 빌드 전략

롤링 인덱스 빌드: Secondary에 순차적으로 빌드 후 Primary를 Secondary로 강등해 빌드. 프로덕션에서 downtime 없이 인덱스를 추가한다.

03 · WiredTiger Internals
WiredTiger — MVCC · Eviction · 체크포인트
핵심MVCCEvictionCheckpoint

MVCC (Multi-Version Concurrency Control): 각 쓰기는 페이지의 Disk Image를 수정하지 않고 in-memory Update List에 새 버전을 추가한다. 읽기 트랜잭션은 시작 시점의 global timestamp를 기록하고, 그 이전에 커밋된 버전만 본다. 읽기와 쓰기가 서로를 블로킹하지 않는 이유다.

Eviction 3단계: (1) 정상 구간(캐시 <80%): background eviction workers(기본 4개) 미작동. (2) eviction_target(80%) 도달: workers가 clean/dirty 페이지를 디스크로 내보내기 시작. (3) eviction_trigger(95%) 초과: application threads 자신이 eviction 수행 → p99 레이턴시 수십 배 급등. mongostat에서 dirty%가 지속 상승하면 캐시 크기를 늘리거나 워킹셋을 줄여야 한다.

Dirty Eviction vs Clean Eviction: dirty 페이지(변경된 페이지)는 디스크에 기록 후 제거하므로 I/O가 발생한다. clean 페이지는 단순히 캐시에서 제거만 한다. wiredTiger.engineConfig.eviction.dirtyTargetPercent(기본 5%)를 낮게 유지하면 dirty burst를 방지한다.

체크포인트 & Journal: 60초마다(또는 2GB dirty 데이터 누적 시) Reconciliation을 수행해 Update List를 새 Disk Image로 통합한다. 체크포인트 사이의 모든 변경은 Journal(WAL)에 기록된다(commitIntervalMs 기본 100ms마다 fsync). 장애 복구 순서: 마지막 체크포인트 로드 → Journal replay → 데이터 일관성 복원.

압축: 기본 snappy(CPU 최소, 압축률 50~60%). zstd로 변경하면 65~75% 압축(CPU 2~3배). 콜드 스토리지 컬렉션은 zstd 권장. 인덱스는 별도 압축 설정 가능(indexConfig.prefixCompression: 기본 활성화).

장기 트랜잭션 주의

트랜잭션이 오래 열려 있으면 해당 트랜잭션의 스냅샷 timestamp 이전 버전을 모두 보존해야 한다. Update List가 누적되어 캐시 압박이 증가하고 eviction이 실패한다. MongoDB 드라이버의 기본 트랜잭션 타임아웃은 60초이며, transactionLifetimeLimitSeconds(기본 60)로 서버 측에서도 강제 종료된다.

01. 연결 설정 — 레플리카셋 + 연결 풀

connection
from pymongo import MongoClient, ReadPreference, WriteConcern
from pymongo.read_concern import ReadConcern

# 레플리카셋 연결
client = MongoClient(
    "mongodb://user:pass@host1:27017,host2:27017,host3:27017/",
    replicaSet="rs0",
    maxPoolSize=100,
    minPoolSize=10,
    serverSelectionTimeoutMS=5000,
    connectTimeoutMS=3000,
    socketTimeoutMS=10000,
    compressors="zstd",      # 네트워크 압축
)

# 내구성 있는 쓰기 + 읽기 분산
db = client.get_database(
    "mydb",
    write_concern=WriteConcern(w="majority", j=True),
    read_preference=ReadPreference.SECONDARY_PREFERRED,
    read_concern=ReadConcern("majority"),
)

orders = db["orders"]
포인트. w="majority"는 과반 레플리카 확인 후 응답한다. j=True는 Journal flush까지 기다린다. 성능이 중요하면 w=1, j=False로 낮추되 장애 시 최대 100ms 데이터를 잃을 수 있다.

02. 집계 파이프라인 — 카테고리별 매출 분석

aggregation
from datetime import datetime, timedelta

def sales_by_category(days: int = 30) -> list[dict]:
    since = datetime.utcnow() - timedelta(days=days)

    pipeline = [
        # 1단계: 날짜 필터 (인덱스 활용)
        {"$match": {
            "status": "confirmed",
            "created_at": {"$gte": since},
        }},
        # 2단계: 상품 배열 펼치기
        {"$unwind": "$items"},
        # 3단계: 카테고리로 조인
        {"$lookup": {
            "from": "products",
            "localField": "items.product_id",
            "foreignField": "_id",
            "as": "product",
            "pipeline": [{"$project": {"category": 1}}],
        }},
        {"$unwind": "$product"},
        # 4단계: 카테고리별 집계
        {"$group": {
            "_id": "$product.category",
            "revenue": {"$sum": {"$multiply": ["$items.qty", "$items.price"]}},
            "count": {"$sum": 1},
        }},
        {"$sort": {"revenue": -1}},
    ]

    return list(orders.aggregate(pipeline, allowDiskUse=True))
포인트. $lookup pipeline은 조인 시 불필요한 필드를 미리 제거해 메모리 효율을 높인다. $match는 항상 파이프라인 최상단에 배치해 처리 도큐먼트 수를 최소화한다.

03. 트랜잭션 — 재고 차감 + 주문 생성

transaction
from pymongo import MongoClient
from pymongo.errors import PyMongoError

def create_order_with_inventory(
    user_id: int,
    product_id: int,
    qty: int,
    price: float,
) -> str:
    with client.start_session() as session:
        with session.start_transaction():
            try:
                # 재고 차감 (낙관적 동시성 제어)
                result = db.inventory.find_one_and_update(
                    {"product_id": product_id, "stock": {"$gte": qty}},
                    {"$inc": {"stock": -qty}},
                    session=session,
                    return_document=True,
                )
                if not result:
                    raise ValueError("재고 부족")

                # 주문 생성
                order = {
                    "user_id": user_id,
                    "items": [{"product_id": product_id, "qty": qty, "price": price}],
                    "status": "confirmed",
                    "created_at": datetime.utcnow(),
                }
                insert_result = db.orders.insert_one(order, session=session)

                # 세션이 with 블록 끝에 자동 커밋
                return str(insert_result.inserted_id)

            except Exception as e:
                # 예외 시 자동 롤백
                raise
포인트. $inc: {stock: -qty}는 원자적 연산이다. 트랜잭션 없이 사용해도 단일 도큐먼트 수준에서는 안전하다. 트랜잭션은 여러 도큐먼트/컬렉션에 걸친 원자성이 필요할 때만 사용한다(오버헤드 3~10배).

04. Change Stream — 실시간 이벤트 구독

change-stream
import threading
from pymongo import MongoClient

def watch_orders(callback):
    # 관심 이벤트 필터
    pipeline = [
        {"$match": {
            "operationType": {"$in": ["insert", "update"]},
            "fullDocument.status": "confirmed",
        }}
    ]

    resume_token = None

    while True:
        try:
            # resume_after로 중단 지점부터 재개
            with orders.watch(
                pipeline,
                full_document="updateLookup",  # update 시 전체 도큐먼트 포함
                resume_after=resume_token,
            ) as stream:
                for change in stream:
                    callback(change["fullDocument"])
                    resume_token = change["_id"]  # 재개 토큰 저장

        except Exception as e:
            # 재연결 후 resume_token으로 이어받음
            print(f"재연결 중: {e}")
            continue
포인트. resume_after는 Change Stream이 중단된 지점부터 이벤트를 다시 받는다. Oplog 보존 기간 안에서만 재개가 가능하다. 프로덕션에서는 resume_token을 외부 저장소(Redis, DB)에 주기적으로 저장해야 한다.

05. 대량 쓰기 — bulk_write 최적화

bulk
from pymongo import UpdateOne, InsertOne, DeleteOne

def batch_upsert_products(products: list[dict], batch_size: int = 1000) -> dict:
    total_matched = 0
    total_modified = 0
    total_upserted = 0

    for i in range(0, len(products), batch_size):
        batch = products[i : i + batch_size]
        operations = [
            UpdateOne(
                {"product_id": p["product_id"]},
                {"$set": p, "$currentDate": {"updated_at": True}},
                upsert=True,
            )
            for p in batch
        ]

        result = db.products.bulk_write(
            operations,
            ordered=False,  # 병렬 실행, 오류 계속 처리
        )
        total_matched += result.matched_count
        total_modified += result.modified_count
        total_upserted += result.upserted_count

    return {
        "matched": total_matched,
        "modified": total_modified,
        "upserted": total_upserted,
    }
포인트. ordered=False는 오류가 발생해도 나머지 작업을 계속 처리한다. 대량 업서트 시 처리량이 2~3배 향상된다. $currentDate는 서버 시간 기준으로 타임스탬프를 설정한다 — 클라이언트 시계 차이를 피할 수 있다.
