01
TL;DR

한 줄로 이해하기

Feature Store는 ML 피처를 중앙 저장·서빙하는 인프라다. 학습용 배치 피처와 추론용 온라인 피처가 동일한 정의에서 나오도록 보장해 학습-서빙 스큐(Training-Serving Skew)를 제거한다. 한 번 계산한 피처를 여러 모델이 재사용하고, Point-in-Time Correct Join으로 데이터 누수 없이 학습 데이터를 생성한다.

01

이중 저장소

오프라인 스토어(Hive/S3, 학습용)와 온라인 스토어(Redis/DynamoDB, 추론 <10ms)를 동일한 피처 정의에서 채운다. 학습과 서빙이 같은 로직을 공유하므로 스큐가 구조적으로 불가능하다.

02

Point-in-Time Correct Join

학습 데이터 생성 시 레이블 시점 이전 피처만 조회한다. 미래 정보를 학습에 포함하는 데이터 누수(Label Leakage)를 방지한다. 오프라인 집계는 레이블 타임스탬프 기준으로 경계를 잘라낸다.

03

피처 공유

한 팀이 계산한 user_purchase_count_7d를 추천·광고·사기탐지 모델 모두가 재사용한다. 중복 파이프라인 제거, 일관된 피처 정의, 계산 비용 절감이 동시에 달성된다.

04

실시간 피처

Kafka 스트림 → Flink 집계 → 온라인 스토어 경로로 수초 이내 지연의 실시간 피처를 서빙한다. 배치 피처(일별)와 스트리밍 피처(초 단위)를 혼합해 추론 시 결합한다.

05

빅테크 현황

Uber가 Feast를 오픈소스로 공개. Meta FBLearner, Google Feast, LinkedIn Frame, Airbnb Zipline이 각자 독자 구현을 운영한다. 공통 패턴은 오프라인/온라인 이중 저장소 + Feature Registry다.

06

핵심 Trade-off

온라인 스토어 P99 <5ms 달성을 위한 Redis 운영 복잡도 vs 오프라인 PIT 정확성을 위한 타임스탬프 관리 정밀도 vs 스트리밍 파이프라인 유지 비용의 세 축이 항상 충돌한다.

02
Architecture

이중 저장소 아키텍처

01이중 저장소

피처 파이프라인은 오프라인 스토어와 온라인 스토어에 동시에 쓴다. 학습 시에는 오프라인에서 대량 배치로 읽고, 추론 시에는 온라인에서 단건 저지연으로 읽는다. Feature Registry가 피처 정의와 메타데이터를 중앙 관리한다.

오프라인은 컬럼형 포맷(Parquet/Hive)으로 쿼리 효율을 높이고, 온라인은 키-값(Redis/DynamoDB)으로 ms 이내 응답을 보장한다.

언제 쓰나

같은 피처를 학습과 서빙 양쪽에서 써야 할 때. 여러 모델이 공통 피처를 재사용할 때. 스큐로 인한 모델 성능 저하가 반복될 때.

02Point-in-Time Correct Join

레이블 이벤트(t3)가 발생했을 때, 그 시점 이전의 가장 최신 피처(t2)만 학습에 사용한다. t3 이후 시점의 피처(t4)를 포함하면 미래 정보가 학습에 유출된다.

잘못된 조인: LEFT JOIN ON entity_id — 레이블 시점을 무시하고 최신 피처를 그대로 붙인다. 올바른 PIT 조인: 레이블 타임스탬프보다 작거나 같은 피처만 선택한다.

누수가 위험한 이유

오프라인 백테스트에서 성능이 높게 나오다가 실제 배포 후 성능이 급락한다면 PIT 조인 누락이 1순위 의심 대상이다. 사기 탐지, 신용 평가, 이탈 예측에서 특히 치명적이다.

03스트리밍 vs 배치 파이프라인

배치 파이프라인은 Spark로 대용량 집계를 처리해 오프라인 스토어에 저장한다. 지연은 시간~일 단위지만 처리량과 정확도가 높다.

스트리밍 파이프라인은 Kafka → Flink → Redis 경로로 초 단위 지연의 실시간 피처를 온라인 스토어에 지속 갱신한다. 둘을 혼합하면 추론 시 배치 피처(7일 집계)와 스트리밍 피처(최근 1시간)를 결합할 수 있다.

파이프라인 선택 기준

신선도 SLA <60초이면 스트리밍 필수. 신선도 SLA 1시간 이상이고 대용량 집계가 필요하면 배치로 충분. 대부분의 프로덕션은 두 경로를 병행 운영한다.

Large Scale

대용량 처리

빅테크 Feature Store 운영의 핵심은 온라인 스토어 레이턴시와 오프라인 PIT 정확성을 동시에 달성하는 것이다. Uber Feast는 5억 개 이상의 피처를 p99 <3ms로 서빙하고, Meta FBLearner는 1조 이상의 피처를 관리한다.

01 · Serialization
직렬화 전략 — Redis 피처 페이로드 최소화
측정 Uber LinkedIn

Protobuf > MessagePack > JSON. Uber 내부 측정에서 Protobuf는 JSON 대비 40% 작은 페이로드를 만든다. Redis에 저장되는 피처 벡터 크기가 작을수록 네트워크 대역폭과 메모리 사용량이 줄어든다.

피처 벡터 하나에 수십~수백 개의 숫자형 피처가 들어간다. 1억 엔티티 × 100 피처 × 4바이트(float32) = 40GB가 JSON이면 100GB+로 부풀어오른다. 직렬화 포맷 선택이 인프라 비용을 직접 결정한다.

직렬화 선택 기준

피처 스키마가 고정적이면 Protobuf. 스키마가 자주 바뀌거나 임시 탐색용이면 MessagePack. JSON은 디버깅 용도로만 사용한다.

02 · Multi-Layer Cache
다층 캐시 — L1 인메모리 · L2 Redis · L3 DynamoDB
패턴 Uber Airbnb Meta

L1 — 프로세스 내 인메모리 캐시(100μs). 요청 배치 내에서 동일 엔티티를 중복 조회하는 경우를 잡는다. LRU 정책, 최대 수천~수만 엔티티, 짧은 TTL(수십초)로 운영한다. Caffeine(Java), cachetools(Python) 등이 일반적이다.

L2 — Redis 클러스터(1~3ms). 서비스 전체의 공유 캐시. 피처 TTL을 엔티티 유형별로 다르게 설정한다(활성 사용자 5분, 비활성 사용자 1시간). Hash 자료구조로 엔티티 단위로 모든 피처를 묶어 저장한다.

L3 — DynamoDB/Cassandra(5~10ms). Cold 엔티티나 Redis에서 만료된 피처의 fallback. 비용이 높으므로 자주 접근되는 엔티티는 Redis로 워밍업한다.

캐시 워밍업 전략

추론 서버 배포 시 또는 Redis 장애 복구 후, 핵심 엔티티(DAU Top 10%)를 미리 Redis에 적재한다. Cold start latency spike를 방지한다.

03 · Hot Entity
파티셔닝과 핫 엔티티 처리 — 인기 아이템 핫스팟
패턴 Meta Airbnb

엔티티 ID 기반 샤딩. Redis 클러스터는 CRC16(key) mod 16384로 슬롯을 배정한다. user_id나 item_id로 키를 구성하면 자동으로 분산된다. 그러나 인기 아이템 몇 개에 트래픽이 집중되면 특정 슬롯이 핫스팟이 된다.

핫 엔티티 처리. 인기 아이템(Top 0.1%)의 피처는 여러 Redis 키에 복제한다. 요청 시 복제본 중 하나를 랜덤 선택해 읽기 부하를 분산한다. 쓰기는 fan-out으로 모든 복제본에 동시 갱신한다.

핫스팟 감지 방법

redis-cli --hotkeys 또는 OBJECT FREQ 명령으로 접근 빈도가 높은 키를 식별한다. 특정 슬롯의 ops/sec가 평균의 3배 이상이면 복제 적용을 검토한다.

Gotchas

Gotchas

가정
학습-서빙 스큐 — 같은 피처 이름이면 같은 값이다
"두 갈래 코드 경로가 만드는 조용한 불일치"

핵심 가정. 학습 코드와 서빙 코드가 별도로 작성되면 같은 이름의 피처라도 계산 방식이 달라질 수 있다. 정규화 통계값(평균·분산)을 학습 시 데이터로 계산했지만 서빙 시에는 하드코딩하거나, 결측값 처리 방식이 다르거나, 집계 윈도우 경계를 다르게 자르는 경우가 대표적이다.

가정이 깨지는 순간. 모델 재학습 후 오프라인 평가(AUC 0.91)는 그대로인데 온라인 A/B 테스트 지표가 하락하는 경우. 코드베이스를 뒤지면 학습 때 쓴 fillna(0)이 서빙 코드에는 fillna(-1)로 되어 있거나, 학습 시 1000으로 클리핑하던 피처를 서빙에서 클리핑하지 않는 식의 불일치가 발견된다.

처방 — Feature Store가 근본 해결책. 피처 계산 로직을 Feature View 하나에 정의하고, 학습 시에는 오프라인 스토어에서, 서빙 시에는 온라인 스토어에서 읽는다. 두 스토어 모두 같은 파이프라인이 채우므로 코드 경로가 하나로 수렴된다. Feature Store 도입 전 임시 처방은 학습-서빙 피처 분포 모니터링(KL divergence, PSI)이다.

함정
Point-in-Time 누수 — label leakage
"레이블 이후 시점의 피처를 학습에 쓰면 미래를 아는 모델"

함정의 구조. 레이블이 발생한 시점(t_label) 이후의 피처 값이 학습 데이터에 포함되면 모델이 미래 정보를 이용해 과거를 예측하는 셈이 된다. 오프라인 AUC는 매우 높게 나오지만 실제 배포 후 성능이 크게 떨어진다.

구체적 시나리오 — 거래 사기 탐지. 사기 거래 발생(t0) 후 사기 판정(t0+7일)이 이루어진다. 사기 판정 시점에 학습 데이터를 생성하면서 t0~t0+7일 사이의 계정 행동 피처(거래 횟수 감소, 계정 잠금 여부 등)가 포함된다. 이 피처들은 이미 사기 발생 이후 행동이므로 실시간 예측에는 존재하지 않는 정보다.

또 다른 패턴 — 오프라인 집계 윈도우 초과. "7일 평균 구매액"을 집계할 때 레이블 시점 기준으로 7일을 자르지 않고 최신 데이터 기준 7일을 쓰면 누수가 발생한다. 특히 배치 파이프라인이 매일 실행되어 날짜 경계를 매번 다르게 계산하면 재현이 어렵다.

처방 1 — get_historical_features 사용. Feast의 get_historical_features(entity_df=labels)는 entity_df의 event_timestamp를 기준으로 PIT 조인을 수행한다. 레이블 데이터프레임에 정확한 레이블 발생 시점을 넣으면 그 이전 최신 피처만 반환한다.

처방 2 — 누수 탐지 테스트. 학습 데이터를 시간 순서로 분리(temporal split)해 검증한다. 만약 시간 역순으로 학습해도 성능이 유지된다면 누수를 의심한다. 피처 중요도가 갑자기 높은 피처가 있다면 해당 피처의 생성 시점을 확인한다.

함정
온라인-오프라인 일관성 깨짐 — 서로 다른 집계 윈도우
"오프라인 7일 이동평균 vs 온라인 캐시 만료 후 null"

함정의 구조. 오프라인 스토어에서는 7일 이동평균으로 정의된 피처가, 온라인 스토어에서는 Redis TTL 만료로 인해 null을 반환하거나 다른 집계 윈도우(예: 1시간)로 계산된다. 모델은 학습 때 본 분포(7일 집계)와 다른 분포(null 또는 1시간 집계)를 추론 입력으로 받는다.

Redis TTL 만료 시나리오. 피처 TTL을 1시간으로 설정했는데 스트리밍 파이프라인이 지연되거나 장애가 발생하면, 1시간 이상 접근 없는 엔티티의 피처가 만료된다. 추론 요청이 들어왔을 때 null 또는 stale 피처를 반환하면 모델 입력이 학습 때와 완전히 다른 분포가 된다.

처방 — Fallback 레이어 설계. 온라인 스토어 조회 실패 시 (1) 기본값(피처 평균), (2) 오프라인 스토어 fallback, (3) null 허용 모델 입력 순으로 처리 레이어를 정의한다. Fallback이 발생한 비율을 메트릭으로 추적하고, 임계치(예: 1% 이상)를 넘으면 알럿을 발송한다.

함정
피처 TTL과 신선도 — 오래된 피처가 조용히 성능을 낮춘다
"TTL 모니터링 없이 운영하면 모델이 과거를 보고 있다"

함정의 구조. 실시간 피처가 신선하지 않은 값을 반환할 때 모델 성능이 서서히 저하된다. 예를 들어 "사용자 최근 1시간 클릭 수" 피처가 1시간 이상 오래된 값을 반환하면 CTR 예측 모델의 클릭률 추정이 부정확해진다. 배포 직후에는 정상이다가 시간이 지나면서 성능이 감소하는 패턴으로 나타난다.

실제 시나리오. 스트리밍 파이프라인(Flink)이 Kafka consumer lag 누적으로 처리가 지연된다. 온라인 스토어의 피처는 1시간 전 값이 그대로 남아있지만 TTL이 24시간이어서 만료되지 않는다. 모델은 신선하지 않은 피처를 마치 최신인 것처럼 사용한다. Flink lag 모니터링이 없으면 며칠이 지나도 탐지가 안 된다.

처방 — Freshness SLA 정의와 모니터링.

피처 유형 Freshness SLA 모니터링
실시간 클릭·노출 <60초 Flink lag + 피처 생성 시각
사용자 행동 집계 <1시간 배치 완료 시간 추적
장기 통계 (7일 평균) <24시간 일별 배치 완료 여부

Fallback 전략. 피처가 Freshness SLA를 초과하면 (1) 더 오래된 배치 피처로 교체, (2) 이 피처를 사용하는 모델에 degraded mode 신호 전달, (3) 기본값 사용 순으로 fallback 처리한다.

Hands-On

실전 코드

Feast 기반 구현 예제. Feast는 Uber가 오픈소스로 공개한 Feature Store로 오프라인/온라인 이중 저장소, PIT Correct Join, 실시간 materialization을 지원한다.

01. Feast Feature Definition

definition 
from feast import FeatureStore, Entity, FeatureView, Field, FileSource
from feast.types import Float64, Int64
from datetime import timedelta

# 엔티티 정의 — 피처 조인 키
user = Entity(
    name="user_id",
    join_keys=["user_id"],
    description="사용자 ID",
)

# 오프라인 소스 (Parquet / S3)
user_source = FileSource(
    path="s3://my-bucket/features/user_features.parquet",
    timestamp_field="event_timestamp",  # PIT 조인에 사용되는 타임스탬프
    created_timestamp_column="created",
)

# 피처 뷰 정의 — 학습과 서빙이 공유하는 단일 정의
user_features = FeatureView(
    name="user_features",
    entities=[user],
    ttl=timedelta(days=1),          # 온라인 스토어 TTL
    schema=[
        Field(name="purchase_count_7d", dtype=Int64),
        Field(name="avg_order_value",   dtype=Float64),
        Field(name="days_since_last_purchase", dtype=Int64),
        Field(name="total_spend_30d",   dtype=Float64),
    ],
    source=user_source,
    tags={"team": "growth", "model": "churn,recommendation"},
)

# Feature Store 초기화 및 적용
store = FeatureStore(repo_path=".")
store.apply([user, user_features])   # Feature Registry에 등록
포인트. ttl은 온라인 스토어에서 피처가 유효한 기간이다. TTL 만료 후 조회 시 null이 반환되므로 Freshness SLA보다 넉넉하게 설정하고, 파이프라인 지연을 별도로 모니터링해야 한다.

02. Point-in-Time Correct Training Data

pit-join 
import pandas as pd
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# 레이블 데이터프레임 — event_timestamp가 PIT 기준점
# 이 시점 이전의 가장 최신 피처만 조회된다
labels = pd.DataFrame({
    "user_id": [1001, 1002, 1003, 1004],
    "event_timestamp": pd.to_datetime([
        "2026-01-10",   # 이 날짜 이전 피처만 조회
        "2026-01-11",
        "2026-01-12",
        "2026-01-15",
    ]),
    "churned": [1, 0, 1, 0],  # 예측 대상 레이블
})

# PIT Correct Join — timestamp 이전 최신 피처만 조회
training_df = store.get_historical_features(
    entity_df=labels,
    features=[
        "user_features:purchase_count_7d",
        "user_features:avg_order_value",
        "user_features:days_since_last_purchase",
        "user_features:total_spend_30d",
    ],
).to_df()

# 결과: labels + 피처 컬럼들이 PIT 기준으로 join된 데이터프레임
print(training_df.columns.tolist())
# ['user_id', 'event_timestamp', 'churned',
#  'purchase_count_7d', 'avg_order_value', ...]

# 데이터 누수 검증 — 피처 생성 시각이 레이블 시각 이후이면 경고
assert (training_df["event_timestamp"] >=
        training_df["__user_features__event_timestamp"]).all(), \
    "PIT 조인 실패 — 미래 피처 포함"
포인트. get_historical_features는 내부적으로 each entity의 event_timestamp를 기준으로 feature store를 time-travel 조회한다. 레이블 데이터프레임에 정확한 레이블 발생 시각을 반드시 포함해야 PIT가 올바르게 동작한다.

03. Online Feature Serving — 추론 시 저지연 조회

online-serving 
import redis
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Feast 온라인 스토어 조회 (Redis 내부 사용, <10ms)
feature_vector = store.get_online_features(
    features=[
        "user_features:purchase_count_7d",
        "user_features:avg_order_value",
        "user_features:days_since_last_purchase",
    ],
    entity_rows=[{"user_id": 1001}],
).to_dict()

# null 피처 처리 (TTL 만료 or 신규 엔티티)
def safe_get(d: dict, key: str, default):
    val = d.get(key, [None])[0]
    return val if val is not None else default

purchase_cnt = safe_get(feature_vector, "purchase_count_7d", 0)

# Redis 직접 배치 조회 — 대량 엔티티 추론 시 (p99 <3ms)
r = redis.Redis(
    host="feature-store-redis.internal",
    port=6379,
    decode_responses=False,
    socket_connect_timeout=0.1,
)

def batch_get_features(user_ids: list[int]) -> list[dict]:
    pipeline = r.pipeline(transaction=False)  # 파이프라인으로 RTT 최소화
    for user_id in user_ids:
        pipeline.hgetall(f"user:{user_id}:features")
    raw_results = pipeline.execute()

    # 역직렬화 + null 처리
    results = []
    for uid, raw in zip(user_ids, raw_results):
        if raw:
            results.append({k.decode(): float(v) for k, v in raw.items()})
        else:
            results.append({"purchase_count_7d": 0.0, "avg_order_value": 0.0})
    return results

# 배치 추론 — 1000개 사용자 피처를 한 번에 조회
user_ids = list(range(1001, 2001))
features = batch_get_features(user_ids)
포인트. Redis Pipeline은 다수의 명령을 단일 TCP 왕복으로 처리한다. 1000개 엔티티를 개별 조회하면 RTT 1000번이지만, pipeline으로 묶으면 RTT 1번으로 처리된다. Uber Feast 내부 측정에서 batch 100~500 크기에서 p99 <3ms를 달성한다.
