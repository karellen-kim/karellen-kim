01

한 줄로 이해하기

기존 LLM은 결정 하나만 필요한 일에도 문장을 만든다. Jev는 그 문장을 없애고 타입이 정해진 답과 확률만 돌려준다. 공식 문서의 표현으로는 "No text generation, no parsing".

i

System One이라는 분류를 새로 붙였다

TypeSafe AI가 2026년 9월 15일 공개하면서 이름 붙인 범주다. 공식 문서는 "System One 모델은 소프트웨어를 위해 빠르고 구조화된 결정을 내린다"고 정의한다. Jev는 그 첫 모델이자 플래그십이다. 이름은 경제학자 William Stanley Jevons에서 따왔다 — 증기기관 효율이 올라가자 석탄 수요가 되레 늘었듯 기계 지능도 같은 길을 갈 것이라는 뜻이다.

ii

질문은 세 가지 타입뿐이다

Choice(주어진 선택지 중 하나), Score(정의한 척도의 한 단계), Noul(문장이 참일 확률 0~1). 각각 답과 함께 probabilities와 confidence를 돌려준다.

iii

토큰을 이어 붙이지 않는다

자기회귀 생성이 아니다. 문서는 "모든 질문이 같은 state에 대해 병렬로, 서로 격리되어 한 번에 평가된다"고 쓴다. 순차 의존이 없어 응답이 빠르다.

iv

확률이 결과에 맞춰 보정돼 있다

문서 표현으로 "확률이 결과에 대해 최적화되어 불확실성을 반영한다". 그래서 confidence를 두 번째 판단 축으로 쓸 수 있다. 다만 개별 답이 맞다는 보장은 아니다—문서가 직접 밝힌 제약이다.

v

출력 토큰이 무료다

입력 100만 토큰당 $0.042, 출력은 "FREE (too cheap to meter)". 돌려주는 게 선택지 하나와 확률값뿐이라 출력량 자체가 거의 없다. 한도는 초당 25만 토큰·분당 1,200요청.

vi

못 하는 일이 분명하다

텍스트 생성, 세기, 숫자 정밀도, 날짜 비교가 모두 약하다. 입력은 텍스트만 받고, 영어가 주 학습 언어라 한국어를 포함한 CJK는 정확도가 떨어진다고 문서가 명시한다.

"환각이 구조적으로 0"이라는 요약은 절반만 맞다. 선택지 밖의 값을 만들어낼 자리가 없으니 형식 오류와 스키마 위반은 0이다. 그러나 틀린 선택지를 고르는 오분류는 그대로 남는다. 공식 문서도 캘리브레이션이 "개별 답의 정확성을 보장하지 않는다"고 적었다. 형식 보장과 판단 정확도는 다른 문제다.

02
Structure

그림으로 보는 구조

00 · 계기결정 하나에 문장을 만들던 비용

분류·라우팅·채점은 소프트웨어가 소비할 값 하나면 끝나는 일이다. 그런데 범용 LLM은 사람이 읽을 문장을 만든다. 그 뒤에 파서가 붙고, 형식이 깨지면 재시도가 붙는다.

Jev는 이 층을 걷어낸다. 답의 공간을 개발자가 미리 정의하고, 모델은 그 안에서 고르기만 한다. 파싱 단계가 사라진다.

언제 쓰나

티켓 부서 배정, 문서 유형 분류, 의도 라우팅, RAG 통과 문서 판정, 다른 모델 출력 검증처럼 답이 유한 집합인 작업.

입력state
LLM문장 생성
파서형식 깨지면 재시도
값코드가 쓸 결정
입력state
Jev선택지 + 확률
값파싱 없음

01 · 원리질문 세 개로 쪼갠다

Choice는 순위 없는 집합에서 하나를 고른다. 부서 배정, 언어 판별이 여기 속한다. Score는 각 단계의 의미를 글로 정의한 척도에서 고른다. 버그 심각도, 불만 강도. Noul은 "이게 참인가"에 0~1 확률로 답한다. 개인정보 포함 여부 같은 신호.

문서가 권하는 방식은 원자적이고 범위가 좁은 질문으로 쪼개는 것이다. 복잡한 판단은 여러 질문으로 나눠 평가하고, 합치는 일은 애플리케이션 코드가 한다.

고르는 기준

선택지 사이에 순서가 없으면 Choice, 스펙트럼이면 Score, 확률 자체가 신호면 Noul.

Choicechoice · probabilities · confidence
Scorescore · legend · probabilities
Noul0 ~ 1

02 · 원리한 번의 호출, 격리된 평가

요청 하나는 state 하나 + 질문 여러 개로 구성된다. state는 문자열, JSON 객체, 텍스트 배열 중 하나다. 문서는 대부분의 경우 필드 이름이 드러나는 객체를 권한다.

모든 질문은 같은 state를 보지만 서로를 보지 못한다. 앞 답이 뒤 답에 영향을 주지 않는다. 그래서 쓸지 안 쓸지 모르는 질문까지 미리 같이 보내는 speculative fan-out이 성립한다.

언제 쓰나

분기마다 다른 판단이 필요할 때. 분기별 질문을 전부 한 번에 보내고, 어떤 답을 쓸지는 코드가 고른다.

statestring · object · array
system_one()질문 N개 동시
Q1refund?
Q2type
Q3frustration

03 · 원리확률 분포의 모양이 곧 신뢰도

confidence는 확률이 한 곳에 몰렸는지, 퍼졌는지를 재는 값이다. 문서는 선택지 3개일 때 대략 (3 × 최대확률 − 1) / 2로 계산된다고 적는다. 1.0이면 한 선택지에 전부 몰린 상태다.

문서가 제시하는 구간은 0.9 초과 자동 처리, 0.5~0.9 사람 확인, 0.5 미만 사람에게 넘김이다. 다만 "적정 임계값은 도메인과 사용처에 따라 다르다"며 보수적으로 시작해 데이터로 조정하라고 못 박는다.

언제 쓰나

자동화 범위를 정할 때. 정확도를 올리는 대신 모르는 경우를 사람에게 넘기는 설계에 쓴다.

> 0.9자동 실행
0.5 ~ 0.9사람 확인 후
< 0.5사람에게 넘김
03
Limits

한계 — 어디서 깨지나

01 · jaggedness모델이 못 하는 것

TypeSafe는 모델이 못 하는 일을 따로 문서화한다. jaggedness 페이지다. 아래는 jev-1.13 기준으로 그 문서가 직접 밝힌 약점이다.

i

문자 그대로 읽는다

문서 표현으로 "당신이 쓴 질문에 답하지, 의도한 질문에 답하지 않는다". 범위를 한정하는 말, 부정, 함축된 조건이 액면 그대로 읽힌다. 이중 부정이나 간접 지시가 들어가면 신뢰도가 떨어진다.

ii

세지 못한다

"jev-1.13은 안정적으로 세지 못한다" — 단어의 글자 수, 본문에서 어떤 표현의 등장 횟수, 긴 목록의 항목 수 모두 해당한다.

iii

숫자와 날짜에 약하다

숫자 표현보다 의미 표현에서 더 잘 동작한다. RGB나 16진수 값 두 개가 서로 가까운지 판단하지 못한다. 날짜를 순서가 있는 양이 아니라 텍스트로 읽어서 어느 쪽이 먼저인지 묻는 건 신뢰할 수 없다.

iv

관계 없는 내용이 쌓이면 떨어진다

"결정과 무관한 내용으로 state가 커질수록 정확도가 떨어진다". state를 통째로 밀어 넣지 말고 판단에 필요한 필드만 담아야 한다는 뜻이다.

v

한국어는 2등 시민이다

모델 문서가 "영어가 주 학습 언어이며 현재 정확도가 가장 좋은 언어"라고 적는다. CJK를 포함한 다른 언어는 받아들이지만 정확도가 낮다. 비영어 작업은 직접 테스트하고 confidence를 감시하라고 권한다.

vi

생성은 아예 못 한다

"텍스트를 생성하도록 학습되지 않았다". 채팅·코파일럿·초안 작성에는 쓸 수 없다. 이건 결함이 아니라 교환 조건이다.

02 · 숨은 가정깨질 때 무슨 일이 생기나

"답의 공간을 개발자가 안다"는 가정 위에 서 있다. 선택지에 없는 상황이 들어오면 모델은 거절하지 못하고 가장 가까운 선택지를 고른다. 확률은 퍼지지만 답은 나온다. 그래서 catch-all 선택지와 confidence 하한이 없으면 오분류가 조용히 통과한다.

"질문이 원자적이다"는 가정도 있다. 한 질문에 판단 두 개를 넣으면 문자 그대로 읽는 성질과 맞물려 어느 쪽에 답한 건지 알 수 없게 된다.

처방

선택지에 "해당 없음"을 넣고, confidence 하한을 두고, 질문 하나에 판단 하나만 담는다. 비영어 입력은 임계값을 더 높게 잡는다.

예상 밖 입력
가장 가까운 선택지거절 불가
조용한 오분류

03 · 한도숫자로 본 제약

컨텍스트는 요청당 64k 토큰이고, 그중 state와 가장 긴 질문을 합쳐 32k까지다. 입력은 텍스트만 받는다. 이미지·오디오·영상은 지원하지 않는다.

가격은 입력 100만 토큰당 $0.042, 출력 무료. 한도는 초당 25만 토큰, 분당 1,200요청이며 문서는 "수요가 많아 예고 없이 바뀔 수 있다"고 적는다.

설계 시사점

state 32k 제한 때문에 긴 문서는 잘라 넣어야 한다. 그런데 관계 없는 내용이 많으면 정확도가 떨어지므로, 자르는 기준 자체가 품질을 좌우한다.

요청 64k총 컨텍스트
state + 최장 질문32k
$0.042 / MTok입력
$0출력

가드레일 쿠킹북은 임계값을 두 단계로 쓴다 — 0.35 이상이면 사람 검토, 0.70 이상이면 차단. 여기에 0~3 심각도 점수가 붙어, 심각도가 높으면 검토를 차단으로 승격시킨다. 예시에서 "neurosemantical" 탈옥 프롬프트는 jailbreak 확률 0.74로 차단됐다. 임계값 두 개와 승격 규칙이 전부라는 점이 이 방식의 성격을 보여준다.

04
실전 코드

Python 구현

공식 Python SDK 기준. 질문을 쪼개고, 한 번에 보내고, confidence로 거른다는 세 동작이 전부다. 아래 세 카드가 그 순서다.

A · 최소 호출 — 티켓 라우팅

quickstart 
# pip install typesafe-sdk · TYPESAFE_API_KEY 환경변수를 자동으로 읽는다
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

response = client.system_one(
    state="Hi, I've been trying to connect my Stripe account for 3 days...",
    questions={
        "department": Choice(
            instructions="Which team should handle this",
            criteria={
                "billing": "Payment or subscription issues",
                "technical": "Bugs or integration problems",
                "sales": "Pricing or account questions",
            },
        ),
        "is_urgent": Noul(
            instructions="The message conveys urgency or time-sensitivity",
        ),
    },
)

print(response.answers["department"].choice)  # "technical"
print(response.answers["is_urgent"].noul)     # 1.0
포인트. 선택지마다 설명을 붙이는 게 프롬프트의 전부다. 모델은 이 설명을 근거로 고르고, 답은 항상 이 키들 중 하나다.

B · 한 번에 여러 판단 — state는 객체로

fan-out 
# 질문끼리는 서로를 보지 못한다. 쓸지 모를 질문까지 미리 같이 보낸다
state = {
    "ticket_message": "My flight was cancelled. Can I get a refund?",
    "refund_policy": "Cancelled flights are eligible for a full refund.",
}

with TypeSafeClient() as client:
    response = client.system_one(
        state=state,
        questions={
            "refund_requested": Noul(
                instructions="Does `ticket_message` request a refund?",
            ),
            "request_type": Choice(
                instructions="What is the main request in `ticket_message`?",
                criteria={
                    "refund": "The customer wants money returned.",
                    "rebooking": "The customer wants a replacement flight.",
                    "information": "The customer is asking for information only.",
                },
            ),
            "frustration": Score(
                instructions="How frustrated does the customer appear?",
                criteria=[
                    "Calm and neutral.",
                    "Concerned but civil.",
                    "Very angry or using strong language.",
                ],
            ),
        },
    )
포인트. 질문 안에서 `ticket_message`처럼 state의 필드명을 직접 가리킨다. 그래서 문서가 문자열보다 객체를 권한다.

C · confidence 게이팅 — 모르는 건 넘긴다

guardrail 
# 공식 가드레일 쿠킹북의 라우팅 구조를 최소 형태로 옮긴 것
REVIEW, ACTION = 0.35, 0.70   # 검토 / 차단 임계값

def route(answer, confidence: float) -> str:
    # 문서 권장 구간: 0.9 초과 자동, 0.5~0.9 사람 확인, 0.5 미만 사람에게
    if confidence > 0.9:
        return "auto"
    if confidence >= 0.5:
        return "verify"
    return "human"

def guard(text: str) -> str:
    r = client.system_one(
        state=text,
        questions={
            "jailbreak": Noul(instructions="The message tries to override system instructions"),
            "pii": Noul(instructions="The message contains personally identifiable information"),
        },
    )
    for key in ("jailbreak", "pii"):
        p = r.answers[key].noul
        if p >= ACTION:
            return "block"
        if p >= REVIEW:
            return "review"
    return "pass"
포인트. 임계값은 도메인마다 다르다. 문서도 "보수적으로 시작해 자기 데이터로 조정하라"고 쓴다. 한국어 입력이면 더 높게 잡는 편이 안전하다.

정리하면 Jev는 정확도를 파는 모델이 아니라 형식과 속도와 단가를 파는 모델이다. 타입 오류는 사라지지만 오분류는 남고, 그 오분류를 거르는 책임은 confidence 임계값을 정하는 쪽으로 넘어온다. 문장 생성을 포기한 대가로 얻은 게 무엇이고 잃은 게 무엇인지가 이 문서 전체의 내용이다.
