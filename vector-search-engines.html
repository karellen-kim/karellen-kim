01

한 줄로 이해하기

벡터 검색 엔진의 모든 결정은 Recall · Latency · Memory · Build cost 4축의 트레이드오프 위에서 좌표를 찍는 일이다. 알고리즘(HNSW · IVF · DiskANN · PQ)이 그 곡선의 어느 영역에 강한지를 먼저 알아야 하고, 엔진(Milvus · Vespa · Qdrant · pgvector …)은 그 알고리즘을 어떤 운영 모델로 감싸느냐의 차이다. billion-scale + hybrid + RAG + real-time을 동시에 요구하면 단일 엔진은 거의 답이 없다 — 티어 분리가 정답.

i

한 줄 정의 — O(N)과 O(log N) 사이

정확한 k-NN은 brute-force O(N). ANN은 그 정확도를 살짝 포기하고 O(log N)에 가까운 속도를 얻는다. "Recall을 얼마나 양보하느냐 ↔ Latency가 얼마나 줄어드느냐"가 모든 엔진의 본질적 결정.

ii

네 가지 근본 트레이드오프

Recall ↔ Latency (ANN 파라미터 ef_search·nprobe), Memory ↔ Recall (양자화 FP32→INT8→PQ→BQ), Build ↔ Query (ef_construction·M), Dynamic ↔ Static (real-time insert 지원 여부). 운영의 모든 고민은 이 네 축 중 하나에 매핑된다.

iii

알고리즘 — HNSW가 default, 한계 시 분기

일반 ANN: HNSW (recall 0.95+, latency 1~5ms, 메모리 1.5~3x). 메모리 압박: IVF-PQ (32x 압축). billion-scale: DiskANN (SSD 활용). 메모리 무제한 + 동적: IVF-Flat. RAM이 받쳐주면 거의 항상 HNSW가 답.

iv

엔진 — 알고리즘은 비슷, 운영 모델이 차이

대부분 HNSW 사용. 결정적 차이는 hybrid 표현력 · filter 통합 · 분산 · 운영 모델. Vespa/OpenSearch는 hybrid 강함, Qdrant는 filter 강함, Pinecone은 운영 0이지만 lock-in. pgvector는 Postgres에 흡수돼 트랜잭션 무료 — 작은 RAG에 황금.

v

4 워크로드 동시 충족은 거의 불가능

billion-scale + hybrid + RAG + real-time 네 가지를 한 엔진에 다 넣으려 하면 운영 복잡도가 폭주. 현실적 해법은 티어 분리: billion 검색 = Vespa/OpenSearch, RAG 캐시 = Qdrant, 트랜잭셔널 메타 = pgvector. 같은 SLA를 강제하지 마라.

vi

가장 흔한 함정 — selectivity 측정 누락

"pre-filter면 빠르다"는 일반화 → 거짓. filter selectivity 1%면 graph traversal 깨져 recall 폭락, 50%면 brute-force와 비슷. sweet spot은 5~20%. 측정 없이 결정하면 latency만 보고 잘못된 선택을 한다. Recall@k는 모든 결정의 출발점.

02 · 알고리즘주요 ANN 알고리즘 비교

각 알고리즘은 4축 곡선의 다른 좌표 — HNSW는 그래프 기반으로 latency·recall에 강하고 메모리 비쌈, IVF는 클러스터링으로 메모리·동적성에 유리, DiskANN은 SSD로 메모리 부담 해결.

선택 기준: RAM 충분이면 HNSW가 default. RAM 부족 + billion이면 DiskANN. real-time insert 많음이면 IVF. 극한 압축이면 PQ 또는 BQ + re-rank.

04 · 매핑워크로드별 best fit

4가지 워크로드 각각에 대해 1·2·3순위 + 피해야 할 엔진. 같은 엔진이 한 워크로드에서는 1순위이고 다른 워크로드에서는 ❌가 되는 게 정상이다 — 단일 엔진의 한계를 시각화.

06 · Pre-mortem6개월 뒤 트래픽 10x — 무엇이 먼저 깨지나

벡터 검색 시스템의 임계치 도달 순서. 메모리가 항상 가장 먼저. HNSW가 RAM을 못 들어가는 순간 latency가 100x 폭주.

예방의 핵심: 각 임계치의 trigger 지표를 미리 monitoring. memory headroom < 20%면 양자화·DiskANN 검토, network fan-in 시 tail latency가 dominate하면 sharding 전략 재검토.

가장 흔한 실수

"CPU가 먼저 깨질 것"이라 생각하는 것. 벡터 검색은 거의 항상 메모리 우선 → 네트워크 → CPU 순. CPU 모니터링만 보면 메모리 폭발 못 잡는다.

벡터 검색에서 가장 반직관적인 사실 — "알고리즘 자체보다 filter selectivity가 latency에 더 큰 영향을 준다". selectivity 1% 강한 필터에서 HNSW graph traversal이 깨져 recall이 폭락, 50% 약한 필터에서는 brute-force와 거의 같은 비용. "우리 워크로드의 filter selectivity 분포는 무엇인가"가 엔진 선택보다 먼저 묻혀야 할 질문.

참고
HNSW (Hierarchical Navigable Small World)
"에이치엔에스더블유"

아이디어. Skip list를 그래프 위로 확장. top layer는 sparse, 점차 dense해지는 multi-layer graph. 쿼리는 top에서 greedy descent로 거친 nearest 찾고, 아래 layer에서 점점 정밀하게. O(log N) 탐색.

핵심 파라미터. M(노드당 out-edge 수, 메모리 직접 비례), ef_construction(빌드 시 후보 큐 크기, recall ceiling을 결정), ef_search(런타임 후보 큐, 동적 조절 가능).

강점. 일반 ANN에서 가장 좋은 recall/latency 균형. ef_search로 런타임 recall/latency 곡선 그릴 수 있음.

약점. 메모리 1.5~3x raw. filter와 결합 시 graph traversal 깨짐 (selectivity 의존). 동적 삭제는 tombstone + 주기적 rebuild.

참고
Product Quantization (PQ)
"피큐"

아이디어. 768-dim 벡터를 m개의 sub-vector로 쪼개고 (예: m=96 → 각 8-dim), 각 sub-vector를 256개 centroid로 표현. 한 벡터당 m bytes로 압축 — 3072 byte → 96 byte = 32× 압축.

거리 계산. 쿼리 시 sub-vector × centroid의 distance lookup table을 미리 만들어 두고, 인덱스의 m개 byte를 indexing해서 합산. SIMD 친화적.

트레이드오프. m이 클수록 압축률 좋지만 sub-vector 표현력 부족 → recall 손상. sweet spot은 d/m = 4~8. d=768이면 m=96~192.

주의. PQ만으로는 recall 0.7~0.9 — 운영에선 first-stage PQ + second-stage exact re-rank가 정석. 그래서 IVF-PQ + re-rank 패턴이 흔하다.

참고
DiskANN (Vamana graph)
"디스크앤"

아이디어. Microsoft 2019 (Subramanya et al). HNSW와 유사한 Vamana 그래프(layer 없는 단일 그래프). 메모리에는 PQ-compressed sketch만, SSD에는 full-precision vector + neighbor list.

쿼리 흐름. ① greedy descent는 메모리 PQ로 빠르게, ② final re-ranking은 SSD에서 정확 거리 fetch. batch IO + async가 latency 핵심.

강점. billion-scale에서 HNSW 대비 메모리 1/10 수준. SSD IOPS만 받쳐주면 recall 거의 동등.

주의. NVMe 필수. 일반 SATA SSD에서는 latency 폭주. 빌드 시간이 HNSW보다 길다.

그래서 — 어떤 알고리즘부터?

HNSW로 시작 권장

  • RAM 충분 (벡터 수 × 차원 × 6 byte 미만)
  • recall > 0.95 필요
  • latency 5ms 이하 요구
  • insert/update 빈도 낮음 (시간 단위 reindex 허용)
  • filter selectivity가 5~20% 범위

HNSW 대신 다른 것 검토

  • RAM 한계 닥침 → DiskANN (NVMe 받쳐주면)
  • 극한 압축 필요 → IVF-PQ (recall 0.85 양보 가능 시)
  • real-time insert 많음 → IVF-Flat 또는 Qdrant HNSW 동적
  • filter selectivity 1% 미만 → partition별 인덱스 분리
  • recall 0.85로 충분 + 초저 latency → BQ + re-rank
03
Reference Implementation

실전 코드

각 알고리즘과 운영 패턴을 최소 동작 코드로 재구성. 프로덕션 코드는 모니터링·재시도·메트릭이 더 붙지만, 핵심 아이디어는 동일.

01 · HNSW 빌드 + 검색 (hnswlib)

algo 
import hnswlib
import numpy as np

dim, num = 768, 1_000_000
data = np.random.randn(num, dim).astype("float32")

# 핵심 3개 파라미터 — 한 번 정하면 recall ceiling이 결정됨
index = hnswlib.Index(space="cosine", dim=dim)
index.init_index(
    max_elements=num,
    M=16,                   # 노드당 edge — 메모리 직접 비례
    ef_construction=200,    # 빌드 시 후보 큐 — recall 천장 결정
)

# 벡터 추가 — 정규화 필수 (cosine이면)
data_norm = data / np.linalg.norm(data, axis=1, keepdims=True)
index.add_items(data_norm, np.arange(num))

# 쿼리 시 ef_search로 recall/latency 트레이드오프 조절 (런타임)
index.set_ef(100)            # 작으면 빠르지만 recall↓, 크면 반대
query = data_norm[:10]
ids, dists = index.knn_query(query, k=10)
포인트. M·ef_construction은 한 번 빌드하면 바꿀 수 없는 고정. ef_search는 런타임 조절 가능 — 같은 인덱스로 A/B 곡선 그릴 수 있는 강력한 강점. cosine이면 벡터 정규화 누락 = 인덱스 전체 무효.

02 · FAISS IVFPQ — 메모리 32배 압축

quantization 
import faiss
import numpy as np

dim = 768
nlist = 4096          # IVF centroid 수 — sqrt(N) 근처가 보통
m = 96               # PQ sub-vector 수 — d/m = 8 (sweet spot)
nbits = 8            # sub-vector당 8bit = 256 centroid

# IVF: coarse quantizer로 partitioning, PQ로 압축
quantizer = faiss.IndexFlatL2(dim)
index = faiss.IndexIVFPQ(quantizer, dim, nlist, m, nbits)

# 학습 단계 — centroid + codebook 학습
training = np.random.randn(100_000, dim).astype("float32")
index.train(training)

# 추가 — 벡터당 96 byte로 압축 저장 (raw 3072 byte 대비 32x)
index.add(training)

# 쿼리 — nprobe는 런타임 조절. 메모리 변화 없음, latency만 변함
index.nprobe = 16      # 탐색할 centroid 수
D, I = index.search(training[:10], k=10)

# nprobe 곡선 — recall vs latency 측정
for np_val in [1, 4, 16, 64, 256]:
    index.nprobe = np_val
    # ... benchmark & record recall@10, latency
포인트. IVF의 강력한 점은 nprobe가 런타임 조절 가능이라는 것. 같은 인덱스로 운영 중에 recall/latency를 dynamic하게 조절. 메모리는 변하지 않음. nlist는 sqrt(N) 근처가 일반 룰. PQ m은 d/m=4~8 사이.

03 · Filter-aware search (Qdrant)

hybrid filter 
from qdrant_client import QdrantClient
from qdrant_client.models import *

client = QdrantClient(url="http://localhost:6333")

# filter selectivity 측정 — 매우 중요
def measure_selectivity(filter_obj) -> float:
    total = client.count("products").count
    matched = client.count("products", count_filter=filter_obj).count
    return matched / total

# 강한 필터 (selectivity 1%) — partition별 인덱스 검토 신호
filter_strict = Filter(must=[
    FieldCondition(key="user_id", match=MatchValue(value="u123")),
])

# 적당한 필터 (selectivity 10%) — sweet spot
filter_ok = Filter(must=[
    FieldCondition(key="category", match=MatchValue(value="electronics")),
    FieldCondition(key="price", range=Range(gte=10, lte=100)),
])

sel = measure_selectivity(filter_ok)
if sel < 0.05:
    warn("selectivity too low — consider partitioned index")
elif sel > 0.5:
    warn("selectivity too high — consider post-filter or no filter")

# Qdrant는 filter selectivity에 따라 자동으로 strategy 선택
results = client.search(
    collection_name="products",
    query_vector=query_vec,
    query_filter=filter_ok,
    limit=10,
    search_params=SearchParams(hnsw_ef=128, exact=False),
)
포인트. filter selectivity는 도입 전 반드시 측정. 1% 미만이면 HNSW 단일 인덱스는 답이 아님 → partition별 인덱스 분리. 50% 초과면 filter가 사실상 의미 없음 → post-filter로 전환. Qdrant는 selectivity에 따라 strategy switching이 가장 매끄러움.

04 · Hybrid scoring — Reciprocal Rank Fusion

hybrid scoring 
def rrf_fusion(rankings: list[list[str]], k: int = 60) -> list[tuple]:
    """Reciprocal Rank Fusion — 학습 데이터 없이도 robust한 hybrid.

    rankings: 각 retriever의 결과 ID 리스트 (rank 순서)
    k: 60이 일반적 (논문 default). 작을수록 top rank 가중치 ↑
    """
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

# 사용 예: BM25 + vector 두 retriever 결과 fusion
bm25_results   = bm25_index.search(query_text, k=100)      # IDs only
vector_results = qdrant.search(query_vec, limit=100)        # IDs only

fused = rrf_fusion([bm25_results, vector_results])
top_10 = [doc_id for doc_id, _ in fused[:10]]

# 비교: alpha-blending (점수 직접 합산 — scale 다른 점이 함정)
def alpha_blend(bm25: dict[str, float], vec: dict[str, float],
                alpha: float = 0.5):
    # min-max normalize 먼저
    bm25_n = {k: (v - min(bm25.values())) / (max(bm25.values()) - min(bm25.values()))
              for k, v in bm25.items()}
    vec_n = {k: v for k, v in vec.items()}      # cosine은 이미 0~1
    keys = set(bm25_n) | set(vec_n)
    return {k: alpha * bm25_n.get(k, 0) + (1-alpha) * vec_n.get(k, 0)
            for k in keys}
포인트. RRF는 학습 데이터 없이도 baseline보다 항상 우수한 거의 유일한 hybrid 방법. 절대 점수 무시하고 rank만 사용 — scale 다른 두 retriever를 자연스럽게 통합. k=60은 논문 default. alpha-blending은 normalization 잘못하면 더 나빠진다.

05 · Recall@k 평가 — 모든 결정의 출발점

import numpy as np
from faiss import IndexFlatL2

def compute_ground_truth(corpus: np.ndarray, queries: np.ndarray, k: int):
    """brute-force k-NN — 작은 sample (예: 1만 query)로만 계산."""
    truth_index = IndexFlatL2(corpus.shape[1])
    truth_index.add(corpus)
    _, gt_ids = truth_index.search(queries, k)
    return gt_ids   # (n_queries, k)

def recall_at_k(ann_results: np.ndarray, ground_truth: np.ndarray, k: int):
    """ann_results, ground_truth: (n_queries, k) array of IDs"""
    recalls = []
    for ann_ids, gt_ids in zip(ann_results, ground_truth):
        overlap = len(set(ann_ids[:k]) & set(gt_ids[:k]))
        recalls.append(overlap / k)
    return np.mean(recalls)

# 핵심 측정 루프 — 파라미터 변경 시 항상 함께 측정
gt = compute_ground_truth(corpus, queries, k=10)

results = []
for ef in [32, 64, 128, 256, 512]:
    hnsw.set_ef(ef)
    start = time.time()
    ann_ids, _ = hnsw.knn_query(queries, k=10)
    latency_ms = (time.time() - start) / len(queries) * 1000
    recall = recall_at_k(ann_ids, gt, k=10)
    results.append((ef, recall, latency_ms))

# 출력: ef → recall → latency 곡선. 운영 SLA에 맞는 ef 선택의 근거.
for ef, r, l in results:
    print(f"ef={ef:4d}  recall@10={r:.3f}  latency={l:.2f}ms")
포인트. recall 측정 없는 latency 비교는 의미 없는 숫자. ground truth는 brute-force (Flat index)로 계산. 1만 query sample이면 충분. 파라미터를 바꿀 때마다 이 곡선을 다시 그려야 진짜 비교 가능. 이 한 가지 습관이 운영 결정의 90%를 옳게 만든다.

class DualIndexRouter:
    """새 임베딩 모델 출시 시 v1·v2 인덱스를 동시 운영, 점진 traffic shift.

    v1과 v2는 임베딩 공간이 완전히 다르므로 절대 섞으면 안 된다."""

    def __init__(self):
        self.v1_index, self.v1_encoder = load("v1")
        self.v2_index, self.v2_encoder = load("v2")
        self.v2_traffic_pct = 0.0     # 0 → 1로 점진 증가

    def search(self, query_text: str, k: int = 10):
        # A/B split — 사용자별 stable routing (해시 기반)
        use_v2 = hash(get_user_id()) % 100 < self.v2_traffic_pct * 100

        if use_v2:
            q_vec = self.v2_encoder.encode(query_text)
            return self.v2_index.search(q_vec, k=k)
        else:
            q_vec = self.v1_encoder.encode(query_text)
            return self.v1_index.search(q_vec, k=k)

    def shift_traffic(self, new_pct: float):
        """검증 게이트 통과 후 점진 shift: 5% → 25% → 50% → 100%"""
        assert self.v2_recall_check() > 0.95, "v2 recall regression"
        self.v2_traffic_pct = new_pct
        emit_metric("v2_traffic_pct", new_pct)

    def retire_v1(self):
        """v2 100% + 안정성 확인 후 v1 인덱스 삭제 (24h grace)"""
        assert self.v2_traffic_pct == 1.0
        schedule_delete(self.v1_index, after="24h")
포인트. 임베딩 모델 v1과 v2는 완전히 다른 좌표계 — v1 인덱스에 v2 query 벡터를 절대 섞으면 안 됨. dual index는 비용 일시 2배지만 안전 swap의 유일한 방법. 사용자별 stable routing이 중요 — 같은 사용자가 검색마다 다른 결과 받으면 UX 깨짐.

위 6개 코드는 독립적으로 도입 가능하다. 도입 순서 권장 — ① Recall 측정(05)부터, ② 그 다음 HNSW baseline(01), ③ 비용 압박이면 IVFPQ(02), ④ hybrid 필요하면 RRF(04), ⑤ 모델 교체 직전에 dual index(06). 측정 없는 최적화는 추측이다.

04
Self-check

도입 전 점검

엔진 도입 결정을 내리기 전에 답할 수 있어야 할 12가지 질문. 단순 사용자와 내부 원리를 이해한 사람을 가르는 지점들. 먼저 답을 머릿속에서 구성한 뒤 키워드를 확인.

Q1 HNSW의 M을 16에서 32로 늘리면 메모리는 정확히 얼마나 증가하나?
M은 노드당 out-edge 개수. 그래프 메모리 ≈ N × M × 8 bytes. M=16→32면 그래프 메모리 정확히 2배. raw vector 메모리는 변하지 않음. 1B 벡터에서 16×8×1B = 128GB → 256GB. recall은 marginal 개선, latency 약간 증가.
Q2 ef_search를 ef_construction보다 크게 설정하면?
ef_search는 런타임 동적 조절 가능, ef_construction은 빌드 시점 고정. ef_search > ef_construction은 동작하지만 recall ceiling이 ef_construction에 의해 결정됨 — 그래프 자체가 그 수준의 후보로 만들어졌기 때문. ef_construction은 미래 recall 목표보다 2배 높게 잡아두는 게 안전.
Q3 PQ에서 sub-vector 개수 m=8 vs m=96은 어떻게 다른가?
d=768에서 m=96이면 각 sub-vector 8-dim, m=8이면 96-dim. m 클수록 압축률 좋지만 sub-vector 표현력 부족 → recall 손상. 메모리는 sub-vector당 256 centroid 기준 m=96이면 96 byte/vec, m=8이면 8 byte/vec. sweet spot은 d/m = 4~8.
Q4 Filtered HNSW에서 selectivity 1%와 50%일 때 무슨 일이?
selectivity 1% (강한 필터) → graph traversal이 통과 노드를 거의 못 만나서 ef_search 후보 못 채움 → recall 폭락. 50% (약한 필터) → 거의 brute force와 비슷. sweet spot 5~20%. 1%면 partition별 인덱스 분리, 50%면 post-filter로 전환. ACORN / Filtered HNSW 논문이 해결 시도.
Q5 FAISS IndexIVFPQ에서 nprobe를 늘리면 메모리·latency·recall 각각?
nprobe = 탐색할 centroid 수. 메모리는 변화 없음. latency는 거의 선형 증가. recall은 빠르게 올라간 뒤 plateau. nprobe는 런타임 조절 가능 — 같은 인덱스로 recall/latency 곡선 그릴 수 있어 A/B 시험 비용이 0. IVF의 강점.
Q6 DiskANN이 SSD에서 HNSW와 비슷한 recall을 내는 비결은?
Vamana 그래프 (HNSW와 유사하지만 layer 없음). 메모리에는 PQ-compressed sketch만, SSD에는 full-precision vector + neighbor list. greedy descent는 메모리 PQ로 빠르게, final re-ranking은 SSD에서 정확 거리. batch IO + async가 latency 핵심. NVMe 필수.
Q7 pgvector HNSW에서 동시 UPDATE 100개가 들어오면 내부적으로?
pgvector HNSW는 PostgreSQL MVCC와 결합. 각 UPDATE는 새 row version 생성 → 인덱스도 새 graph node 추가. VACUUM 안 하면 dead tuple + dead node 누적, HNSW 그래프 fragmented → query latency 점진 악화. routine VACUUM + 주기적 REINDEX 필수.
Q8 Cosine으로 인덱스 빌드했는데 일부 벡터가 정규화 안 된 채 들어갔다면?
Cosine = normalized inner product. 정규화 안 된 벡터는 magnitude로 거리 distortion. 그래프 구축 시 wrong neighbors → 그래프 자체가 잘못됨. 일부만 다시 정규화해도 회복 안 됨 — graph topology가 이미 망가짐. 전체 rebuild 필수. 인제스천 파이프라인에 normalize assertion 필수.
Q9 Vespa의 streaming mode vs index mode 차이와 언제 무엇?
index mode = 사전 인덱싱된 HNSW. streaming mode = 쿼리 시점에 매번 corpus scan (인덱스 없음). multi-tenant에서 tenant당 small corpus (예: 사용자별 10K 문서)면 streaming이 더 빠름 — 인덱스 오버헤드 없고 freshness 즉시. 단일 tenant가 billion이면 streaming은 죽음.
Q10 Hybrid search에서 BM25 0~50과 cosine 0~1 점수를 어떻게 fusion?
직접 합산은 scale 달라 불가. ① RRF: score = sum(1/(60+rank_i)), 절대 점수 무시하고 순위만. 학습 데이터 불요, 가장 robust. ② min-max normalize + weighted (alpha-blending), α 튜닝 필요. ③ Learning to Rank: BM25/cosine을 feature로 LambdaMART. RRF가 default 추천.
Q11 1B 벡터를 8개 노드에 sharding하면 query latency가 1/8?
틀림. ANN은 shard별 top-k 모두 가져와 merge — search amplification. 각 shard에서 k=100 가져오면 8 × 100 = 800 candidates merge. 실제 latency = max(shard latency) + network fan-in + merge. p99 tail이 worst shard에 의해 dominate. recall도 약간 손상 가능. 단순 1/N 가정은 잘못.
Q12 임베딩 모델 v1으로 만든 인덱스에 v2 query vector를 넣으면?
절대 안 됨. 임베딩 공간이 완전히 다른 좌표계 — 같은 "apple"이 v1과 v2에서 전혀 다른 위치. cosine 계산은 되지만 의미 없는 숫자. 기존 인덱스는 무용지물, full reindex 또는 dual-index 필수. blue/green 배포의 본질 — 새 모델 출시 시 모든 데이터 v2로 다시 임베딩.
