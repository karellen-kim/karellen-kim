01

한 줄로 이해하기

ML 플랫폼은 모두 같은 목표를 갖는다 — 데이터 사이언티스트가 production-grade 모델을 빠르게 만들 수 있게. 하지만 각 회사가 처한 컨텍스트(기존 인프라 · 조직 규모 · 도메인 · 오픈소스 전략)에 따라 답이 완전히 다르다. 6개 빅테크의 ML platform을 5가지 축으로 교차 비교 — 어떤 결정이 어떤 trade-off를 만들었는지.

i

공통 문제 — 같은 6-step lifecycle

모든 ML 플랫폼이 data → train → eval → deploy → predict → monitor 같은 lifecycle을 다룬다. Uber Michelangelo가 2017년에 표준화한 이 6단계가 사실상 업계 표준. 회사별 차이는 "stage가 무엇인가"가 아니라 "각 stage를 어떻게 표현·실행하는가"에 있다.

ii

5가지 비교 축

① Developer interface (notebook · CLI · monorepo) ② Workflow 표현 (YAML · Python class · `@step` 데코레이터 · operator · 타입 DAG) ③ Build system (Docker · Bazel · custom) ④ Artifact 관리 (registry · monorepo · S3) ⑤ Deployment lifecycle (shadow · canary · A/B). 같은 stage라도 어떤 축을 어떻게 풀었는지가 platform의 정체성.

iii

Uber Canvas — SWE 워크플로우 차용

2020 launch. ML Monorepo + Bazel + Docker + CI/CD가 핵심. ML 자산도 일반 코드처럼 PR/리뷰/test gate. ML Application Framework (MAF)가 DL 등 복잡한 패턴 템플릿 제공. "Jupyter 시대 졸업" 선언. MA Studio가 통합 UI.

iv

Netflix Metaflow — Python 데코레이터 + DAG

2019 오픈소스. @step 데코레이터로 Python 함수를 워크플로우 노드화. self.next()로 edge. @resources(gpu=4)로 컴퓨트 명세. "DSL을 만들지 마라, 그냥 Python"이라는 인간 중심 디자인. 3K+ 프로젝트 · 수억 job.

v

Meta FBLearner / Lyft Flyte / Airbnb Bighead

FBLearner: Python 데코레이터 + operator → 자동 UI 생성. 사내 사용 25%+. Flyte: Kubernetes-native, 타입 워크플로우, 오픈소스, 월 1M pipelines (Lyft). Bighead: Redspot (multi-tenant Jupyter) + Zipline (feature store) — notebook 중심.

vi

GenAI 시대 — 모든 플랫폼이 같은 곳으로 수렴

2024+ 모든 ML 플랫폼에 LLM Gateway · Prompt Management · LLM Eval Framework가 추가됨. Uber Gen AI Gateway, Netflix Metaflow의 LLM module, Meta의 GenAI infra — 거의 동일한 추상화. predictive와 generative를 같은 platform 위에서 운영한다는 공통 결론.

01 · 공통모든 ML 플랫폼이 다루는 6-step lifecycle

Uber Michelangelo가 2017년에 정착시킨 6단계가 사실상 업계 표준이 됨. Kubeflow · MLflow · Vertex AI Pipelines · SageMaker Pipelines · Metaflow 등 모두 같은 단계를 다룬다.

회사별 차이는 stage 자체가 아니라 "각 stage를 어떤 인터페이스·DSL로 표현하는가". 같은 train 스텝이 Canvas에서는 Python class, Metaflow에서는 @step, Flyte에서는 typed task가 된다.

핵심 관찰

새 ML 플랫폼이 이 6단계를 다 다루지 않으면 — 다른 도구로 보완해야 한다. ML lifecycle "전 영역"을 다루는 게 platform이 되느냐 단순 라이브러리가 되느냐의 분기점.

02 · 비교6 플랫폼 capability matrix

같은 6 stage를 처리하지만 각 stage에서 어떤 도구·DSL을 선택했는지가 platform의 정체성을 만든다. Uber는 SWE 워크플로우 흡수, Netflix는 인간 중심, Meta는 사내 통합, Lyft는 K8s-native, Airbnb는 notebook-first.

라이센스도 결정적 차이 — Metaflow와 Flyte는 오픈소스라 다른 회사도 채택 가능, Canvas/FBLearner/Bighead는 사내 전용. 오픈소스 전략이 곧 platform의 long-term 영향력.

패턴

오픈소스 플랫폼(Metaflow · Flyte)은 외부 생태계가 강함. 사내 플랫폼(Canvas · FBLearner)은 사내 인프라와 깊게 통합 — 외부 채택 불가하지만 사내 성능 최적화는 압도적.

03 · 워크플로우5가지 워크플로우 표현 방식

ML 워크플로우를 어떻게 코드로 표현할 것인가가 platform 디자인의 가장 큰 분기점. Python class · 데코레이터 · operator · 타입 워크플로우 · YAML config 등 5가지 주요 스타일이 있다.

선택 기준은 "누가 쓰는가" — 데이터 사이언티스트(Python 친화) vs 플랫폼 엔지니어(타입 안전) vs PM/매니저(UI 친화). Metaflow와 Canvas가 양극단 — Metaflow는 데이터 사이언티스트 친화 데코레이터, Canvas는 SWE 친화 monorepo.

고르는 기준

팀이 Python 데이터 사이언티스트 중심이면 → 데코레이터 (Metaflow/FBLearner). 플랫폼 엔지니어 중심이면 → typed workflow (Flyte). SWE와 통합되어야 하면 → monorepo + class (Canvas).

Python class
Uber Canvas (MAF) — 모델·feature·pipeline을 Python class로 정의. SWE 워크플로우 (monorepo + PR + CI)와 통합. ML이 일반 코드와 같은 워크플로우.
canvas
데코레이터 + DAG
Netflix Metaflow · Meta FBLearner — 함수에 @step 또는 operator 데코레이터. self.next()로 edge. 가장 Python 친화적, 데이터 사이언티스트가 그대로 쓸 수 있음.
metaflow
Typed workflow
Lyft Flyte — input/output에 Python 타입 명시. compile-time 검증, lineage 추적, K8s native. 플랫폼 엔지니어가 좋아하는 robustness.
flyte
Notebook-first
Airbnb Bighead (Redspot) — multi-tenant Jupyter 호스팅. 데이터 사이언티스트가 실험하기 가장 빠름. 단, production-grade 보장은 별도 노력 필요.
bighead
UI-driven (auto-gen)
Meta FBLearner 자동 UI — 파이프라인 정의에서 UI 자동 생성. 비엔지니어(PM·analyst)도 모델 학습 가능. Meta의 25%+ engineering 채택의 비결.
fblearner

04 · 진화개발자 인터페이스 — 10년 변화

2014년경 Jupyter notebook 위주로 시작 → 2017~2019년 플랫폼 SDK + Web UI → 2020년 이후 monorepo + CI/CD + 통합 UI로 수렴. 매 단계 trigger는 "이전 방식으로는 production-grade 보장이 안 됨"이었다.

2024+는 GenAI 통합이 결정적 변화 — Prompt Toolkit 같은 신규 자산이 등장. 다음은 AutoML + agent가 SDK의 일부가 될 것 (이미 Uber MA Assistant 등 시도).

다음 단계 예측

2026~: 자연어로 ML 작업 의뢰 → 플랫폼이 자동으로 코드 생성 + 학습 + 평가. 사람은 결과 검증만. Cursor for ML 같은 형태.

~2016
Jupyter Notebook 단독각 ML 엔지니어가 자기 노트북에서 실험. production 가는 길 없음. 코드는 ad-hoc.
2016~2019
Platform SDK + Central Web UIUber Michelangelo v1 · Meta FBLearner · Airbnb Bighead Redspot. notebook은 유지하되 SDK가 plumbing 제공.
2019~2023
오픈소스 워크플로우 SDKNetflix Metaflow OSS · Lyft Flyte OSS · 데이터 사이언티스트가 Python으로 작성, 회사가 채택. Python 데코레이터가 lingua franca.
2024~

05 · 수렴GenAI 시대 — 모든 플랫폼이 같은 구조로

2024년 이후 모든 ML 플랫폼이 거의 동일한 GenAI 추상화로 수렴 — Prompt Toolkit + LLM Gateway + Eval Framework. Uber Gen AI Gateway, Netflix Metaflow LLM module, Meta GenAI infra 모두 같은 모양.

이 수렴의 의미: predictive ML과 generative AI가 한 platform 위에서 운영되는 게 표준이 됨. prompt도 일급 자산 (model·feature와 동급), LLM 호출도 거버넌스 대상.

가장 큰 변화

"prompt를 code로 관리한다"는 인식. 2023까지는 prompt가 ad-hoc 텍스트였지만, 2024+에는 version control · code review · A/B test 대상.

앱 · 에이전트 · 사내 도구모든 LLM 호출은 게이트웨이 경유 (직접 SDK 호출 금지)
LLM Gatewayvendor abstraction + 4 guardrails (log · cost · safety · PII)
Prompt Toolkitversioned · CI/CD
Model Catalogin-house + 3P
LLM Evalrubric · A/B

가장 흥미로운 사실 — "같은 문제를 다른 회사가 다르게 풀었지만 결국 비슷한 곳으로 수렴 중". Uber Canvas와 Netflix Metaflow는 출발 철학이 완전 달랐다(SWE 워크플로우 vs 인간 중심 Python). 그러나 2024+에는 모두 monorepo · CI/CD · GenAI gateway · Prompt toolkit 같은 공통 추상화로 모임. 진화는 발산 후 수렴.

참고
Metaflow @step 데코레이터 패턴
"step 데코레이터"

정의. Python 함수를 워크플로우 노드(step)로 등록하는 Metaflow 핵심 데코레이터. self.next(self.train)으로 다음 step 지정 → 함수 호출이 DAG의 edge.

강점. 새 DSL 학습 비용 0 — Python을 아는 누구나 즉시 작성. @resources(gpu=4, memory=200000)로 컴퓨트 요구 명시. 같은 코드가 로컬 머신 + AWS Batch + K8s 모두에서 실행.

2024 신규. Config 객체 추가 — 배포 시점에 resolve되는 설정 분리. 같은 flow를 환경별로 다르게 구성 가능. 같은 flow의 prod/staging 다른 GPU 할당 등.

스케일. Netflix에서 3K+ 프로젝트 · 수억 job · 수십 PB 데이터 + 모델 운영. ML 엔지니어 SDK의 사실상 표준.

참고
Canvas Monorepo + Bazel
"바젤 모노레포"

왜 Bazel인가. Uber 사내 SWE 인프라가 Bazel monorepo 기반. ML 자산을 같은 monorepo에 두면 SWE와 ML 사이 경계가 사라짐 — feature 정의가 backend service 코드와 같은 PR에 들어갈 수 있음.

구조. projects/eta_prediction/ 디렉토리에 model.py · features.py · BUILD (Bazel target) · app.yaml (배포 config). git PR마다 CI가 sample 학습 + eval gate 자동 통과 검증.

운영 효과. ML 의존성(특정 Python lib 버전 등)을 Bazel이 hermetic하게 격리 — "내 PC에서는 됐는데" 문제 원천 차단. Docker 이미지도 같은 Bazel target에서 빌드.

비용. Bazel 자체 학습 곡선이 가파름. Bazel 운영 인력 없는 회사는 차용 어려움. Uber 같은 monorepo 회사가 아니면 MLflow + git이 더 현실적.

그래서 — 우리 조직은 어떤 platform을?

Open-source 차용

  • ML 모델 50~500개 + 팀 다양 → Metaflow (Python 친화, 적용 쉬움)
  • K8s 인프라 갖춤 + 타입 안전성 중요 → Flyte (production-grade)
  • Python 표준 워크플로우 원함 + 외부 인력 onboarding → Metaflow가 가장 보편적

자체 구축 시 차용할 패턴

  • SWE 워크플로우 통합 → Canvas의 monorepo + CI/CD
  • 비엔지니어 사용 → FBLearner의 auto-generated UI
  • Python 친화 + 분산 학습 → Metaflow의 데코레이터 + @resources
  • GenAI 도입 시 → Michelangelo의 Gen AI Gateway + 4 guardrails
  • Feature store 필수 → Uber Palette 또는 OSS Feast

01 · Uber Canvas — Python class + MAF (ML as Code)

# projects/churn_predictor/model.py
from michelangelo.maf import Model
from palette.features import UserActivity30d, DaysSinceLast

class ChurnPredictor(Model):
    """모델 = 일반 Python class. PR 리뷰 대상, CI/CD 통과해야 머지."""

    name = "churn_v2"
    framework = "xgboost"
    tier = 1                       # MES 거버넌스 high-impact

    features = [UserActivity30d(), DaysSinceLast()]

    def train(self, X, y):
        import xgboost as xgb
        self.booster = xgb.XGBRegressor(max_depth=6).fit(X, y)

    def predict(self, X):
        return self.booster.predict(X)

02 · Netflix Metaflow — @step 데코레이터 DAG

metaflow 
from metaflow import FlowSpec, step, Parameter, resources, Config

class ChurnFlow(FlowSpec):
    """@step 함수가 노드, self.next()가 edge. 그게 전부."""

    config = Config("hyperparams", default="prod.yaml")
    n_trees = Parameter("n_trees", default=500)

    @step
    def start(self):
        import pandas as pd
        self.df = pd.read_parquet("s3://data/users.parquet")
        self.next(self.train)

    @resources(gpu=4, memory=200_000)        # 컴퓨트 명세
    @step
    def train(self):
        import xgboost as xgb
        X, y = self.df[self.features], self.df["churn"]
        self.model = xgb.XGBRegressor(
            n_estimators=self.n_trees,
            max_depth=self.config.max_depth,
        ).fit(X, y)
        self.next(self.evaluate)

    @step
    def evaluate(self):
        # self.model · self.df 같은 인스턴스 변수가 자동으로 artifact 저장
        self.auc = compute_auc(self.model, self.df)
        self.next(self.end)

    @step
    def end(self):
        print(f"trained model auc={self.auc:.3f}")

if __name__ == "__main__":
    ChurnFlow()

# 실행: python churn_flow.py run --n-trees 1000
#       python churn_flow.py run --with batch  # AWS Batch에서 실행
#       python churn_flow.py run --with kubernetes  # K8s에서 실행
포인트. Metaflow의 매력 = "같은 코드가 로컬·AWS Batch·K8s 모두에서 실행". --with batch만 추가하면 클라우드. 데이터 사이언티스트가 인프라 변경 없이 scale. self.* 인스턴스 변수는 자동 artifact화 (S3 저장 + 검색 가능).

03 · Meta FBLearner — Operator + Auto UI

fblearner 
from fblearner.flow import operator, workflow, types

@operator
def load_data(table_name: types.String) -> types.DataFrame:
    """각 operator가 input/output 타입을 명시 — auto UI가 form 생성."""
    return hive.query(f"SELECT * FROM {table_name}")

@operator
def train_model(df: types.DataFrame,
                n_estimators: types.Int = 500) -> types.Model:
    return xgb.XGBRegressor(n_estimators=n_estimators).fit(...)

@operator
def evaluate_model(model: types.Model,
                   eval_df: types.DataFrame) -> types.Float:
    return compute_auc(model, eval_df)

@workflow
def churn_pipeline(table: types.String):
    """workflow는 operator들의 조합. Python futures로 자동 병렬화."""
    train_df = load_data(table)
    eval_df  = load_data("churn_eval")
    model    = train_model(train_df, n_estimators=1000)
    auc      = evaluate_model(model, eval_df)
    return auc

# --- 실행 ---
# FBLearner UI에서:
#   - workflow 자동으로 form 생성 (table 입력, 하이퍼파라미터 슬라이더)
#   - 비엔지니어(PM)도 실행 가능
#   - 결과는 자동 시각화 (operator 타입 기반)
포인트. FBLearner의 차별점 = auto-generated UI. operator의 input/output 타입을 기반으로 form/visualization 자동 생성 — Meta 사내 25%+ engineer가 사용할 수 있는 이유. Python futures로 데이터 의존성 분석해 자동 병렬화. 사내 전용이라 외부 채택 불가.

04 · Lyft Flyte — Typed Workflow + K8s native

flyte 
from flytekit import task, workflow, Resources
from typing import NamedTuple
import pandas as pd

# 타입을 NamedTuple로 명시 — compile-time 검증
TrainOutput = NamedTuple("TrainOutput", model=bytes, auc=float)

@task(requests=Resources(cpu="4", mem="8Gi", gpu="1"))
def train_task(df: pd.DataFrame, n_trees: int) -> TrainOutput:
    """task는 Docker 컨테이너로 실행. Flyte가 K8s pod 자동 생성."""
    model = xgb.XGBRegressor(n_estimators=n_trees).fit(...)
    return TrainOutput(model=pickle(model), auc=eval(model))

@task(requests=Resources(cpu="2", mem="4Gi"))
def register_task(model_bytes: bytes, auc: float) -> str:
    if auc < 0.85:
        raise ValueError(f"recall regression: auc={auc:.3f}")
    return model_registry.register(model_bytes, auc=auc)

@workflow
def churn_workflow(table: str, n_trees: int = 500) -> str:
    """workflow도 typed — compile-time 의존성 검증."""
    df = load_data(table=table)
    out = train_task(df=df, n_trees=n_trees)
    model_id = register_task(model_bytes=out.model, auc=out.auc)
    return model_id

# 실행: pyflyte run churn_workflow.py churn_workflow --table users
# Flyte가 자동으로 K8s pod 스케줄링, 의존성 따라 병렬 실행
# lineage UI에서 task 간 흐름 시각화
포인트. Flyte는 "production grade가 default". NamedTuple 타입으로 input/output 명시 → compile-time 의존성 검증. @task마다 Docker container + K8s pod. 월 1M pipelines (Lyft)에서 검증된 robust한 아키텍처. Metaflow보다 진입 장벽 높지만 typed safety는 압도적.

05 · Airbnb Bighead — Notebook + Redspot + Wrappers

bighead 
# Redspot의 multi-tenant Jupyter notebook에서 작성
# 동료들과 공유 가능, 같은 환경에서 실행

from bighead import ml_pipeline, deepthought
from zipline import Feature

# Zipline feature store에서 feature 정의·조회
user_activity = Feature.load("user.activity_30d_v2")
days_since_last = Feature.load("user.days_since_last_session")

# Bighead library가 sklearn/xgboost wrapper 제공
from bighead.models import XGBoostWrapper

model = XGBoostWrapper(
    features=[user_activity, days_since_last],
    target="churn",
    hyperparams={"max_depth": 6, "n_estimators": 500},
)

# 학습 — notebook에서 즉시 결과 볼 수 있음
model.fit(train_set="2024-01-01", eval_set="2024-02-01")
model.plot_feature_importance()

# Deepthought (deployment UI)로 staging 배포
deepthought.deploy(model, name="churn_v2", env="staging")

# notebook 자체를 production pipeline화 가능 (ml_pipeline decorator)
@ml_pipeline(schedule="daily", owner="growth-team")
def churn_daily():
    return XGBoostWrapper(...).fit_and_deploy("churn_v2")
포인트. Bighead의 철학 = "notebook이 빠른 실험의 최선". Redspot의 multi-tenant Jupyter로 협업 + 환경 일관성. wrapper 라이브러리로 production화. 실험은 빠르지만 SWE 규율(PR review, CI)이 약함 — 그 절충안.

위 5개 코드는 같은 작업(churn 모델 학습+평가+등록)을 5가지 다른 platform DSL로 작성한 것. 코드 줄 수는 비슷하지만 "누가 어떻게 쓰는가"는 완전히 다르다. Canvas는 SWE 협업, Metaflow는 개인 실험 + 자동 클라우드, FBLearner는 비엔지니어 UI, Flyte는 typed production, Bighead는 notebook 협업. "좋은 DSL은 사용자가 자연스럽게 쓰는 코드 모양과 같다"는 디자인 원리.
