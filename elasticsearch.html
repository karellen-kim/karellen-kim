01
TL;DR

한 줄로 이해하기

Elasticsearch는 Lucene 세그먼트 위에 분산 레이어를 얹은 검색 엔진이다. 도큐먼트를 색인하면 역인덱스(Inverted Index)가 만들어지고, 쿼리 시 BM25 스코어링으로 관련성 순위를 매긴다. 8.x부터는 kNN 벡터 검색을 내장해 시맨틱 검색과 전문 검색을 하나의 엔진에서 처리한다.

01

역인덱스 · 세그먼트 · 불변성

Lucene은 문서를 토큰화해 역인덱스를 만든다. 색인은 여러 세그먼트로 나뉘며, 각 세그먼트는 불변(immutable)이다. 삭제는 세그먼트에 삭제 마크를 남기고 병합(merge) 시 실제 제거된다. .refresh() 후 새 세그먼트가 오픈되어 검색 가능해진다.

02

샤드 · 복제본 · 라우팅

인덱스는 여러 프라이머리 샤드로 분산된다. 기본 라우팅: shard = hash(routing) % num_shards. 레플리카 샤드는 읽기 처리와 내구성을 담당한다. 프라이머리 샤드 수는 인덱스 생성 후 변경 불가 — 처음 설계가 중요하다.

03

BM25 스코어링

BM25는 TF-IDF의 개선 버전이다. TF에 포화(saturation)를 적용해 극단적 빈도를 완화하고, 문서 길이 정규화(b 파라미터)를 포함한다. k1(기본 1.2): TF 포화 속도, b(기본 0.75): 문서 길이 영향도. 도메인에 맞게 튜닝한다.

04

Query · Fetch 2단계

검색은 두 단계로 이뤄진다. Query Phase: 코디네이터가 각 샤드에 요청 전달 → 각 샤드가 상위 N개 doc_id + 점수 반환. Fetch Phase: 코디네이터가 최종 상위 N개의 실제 도큐먼트를 가져온다. Deep Pagination의 비용은 Fetch가 아닌 Query Phase에서 발생한다.

05

인덱스 생명주기 관리(ILM)

Hot → Warm → Cold → Frozen → Delete 단계. Hot은 SSD, Warm은 HDD, Cold/Frozen은 S3로 오프로딩된다. Searchable Snapshot(Frozen): S3에 저장된 스냅샷을 직접 쿼리한다. 페타바이트 규모의 로그 분석에서 스토리지 비용을 90%+ 절감한다.

06

kNN 벡터 검색 (8.x)

HNSW 그래프 기반 근사 최근접 이웃(ANN). dense_vector 필드에 index: true로 설정하면 HNSW 인덱스가 생성된다. knn 쿼리와 query(BM25)를 bool로 결합한 하이브리드 검색은 시맨틱 + 키워드를 동시에 처리한다. RRF(Reciprocal Rank Fusion)로 점수를 정규화한다.

01역인덱스

역인덱스는 단어(term) → 문서 목록(posting list)의 매핑이다. Lucene은 FST(Finite State Transducer)로 term dictionary를 압축 저장하고, posting list는 Frame of Reference 인코딩으로 Delta 압축한다.

Analyzer 파이프라인: Character Filter → Tokenizer → Token Filter. 한국어는 nori analyzer를 사용한다. 분석 결과가 역인덱스의 질을 결정하므로 도메인 맞춤 설정이 중요하다.

02샤드 구조

각 샤드는 독립된 Lucene 인스턴스다. 프라이머리 샤드에서 색인이 이뤄지고, 레플리카로 복제된다. 레플리카 샤드는 읽기 트래픽 분산과 장애 복구에 사용된다.

샤드 크기 가이드라인: Elastic 권장 샤드 크기는 10~65GB. 너무 작으면 메타데이터 오버헤드가 크고, 너무 크면 복구 시간이 길어진다.

03쿼리 실행 경로

코디네이터 노드가 모든 관련 샤드(프라이머리 또는 레플리카 중 하나)에 쿼리를 분산한다. 각 샤드는 로컬 BM25 통계로 점수를 계산해 doc_id와 점수를 반환한다.

DFS Query Phase(search_type=dfs_query_then_fetch): 글로벌 IDF로 정확한 점수 계산. 샤드가 많을 때 결과 품질 향상, 네트워크 왕복 1회 추가.

Deep Pagination 회피

from/size는 코디네이터가 모든 샤드의 상위 (from+size)개를 수집해 정렬한다. 1만 건 이상은 search_after 또는 Scroll API를 사용한다.

04인덱스 생명주기

ILM은 시간·크기 기준으로 인덱스를 자동으로 다음 단계로 전환한다. Hot 단계에서는 빠른 SSD로 색인과 검색을 수행하고, Warm/Cold로 넘어가면서 HDD나 S3로 이동한다.

Frozen: Searchable Snapshot으로 S3에서 직접 쿼리. 로컬 캐시에서 블록 단위로 읽는다. 쿼리 지연은 크지만 스토리지 비용을 90%+ 절감한다.

05하이브리드 검색

BM25(키워드)와 kNN(시맨틱)의 점수를 결합한다. 두 방식은 점수 범위가 다르므로 직접 합산이 어렵다. RRF(Reciprocal Rank Fusion): 랭킹 기반 결합으로 점수 정규화 없이 두 결과를 합친다.

num_candidates: HNSW 탐색 후보 수. 클수록 recall은 올라가지만 지연도 증가한다. 일반적으로 num_candidates = k * 10으로 시작한다.

언제 하이브리드 검색을 쓰나

단독 BM25: 정확한 키워드 매칭이 필요할 때. 단독 kNN: 의미 유사도 기반 검색. 하이브리드: 쿼리 표현이 다양하고 키워드 매칭도 중요할 때.

07Segment Merge

Elasticsearch는 Lucene의 불변 Segment를 기반으로 한다. 쓰기는 in-memory buffer에 쌓이다가 refresh(기본 1초)마다 새 Segment로 변환되어 검색 가능해진다. Segment는 불변이라 삭제는 논리 삭제(.del 파일)이고 merge 시 실제 제거된다.

작은 Segment가 누적되면 검색 시 모든 Segment를 순회해야 하므로 성능이 저하된다. Background Merge가 자동으로 작은 Segment들을 하나로 합친다. Force Merge(POST /index/_forcemerge)로 수동 병합해 최적화하지만, 쓰기가 없는 cold index에만 적용한다 — 활성 인덱스에서는 I/O를 폭발시킨다.

refresh_interval 조정

대량 색인 중에는 refresh_interval: -1로 자동 refresh를 끄면 처리량이 2~3배 향상된다. 색인 완료 후 1s로 복원하고 _refresh API를 한 번 호출한다.

03
Large Scale

대용량 처리

Elastic의 대형 고객들은 단일 클러스터에서 수 PB의 데이터를 운영한다. Uber는 Elasticsearch로 초당 수백만 건의 로그를 실시간 집계하고, Airbnb는 수천만 개의 숙소 검색을 처리한다.

01 · Shard Design
샤드 설계 — 처음이 전부다
사례ElasticUber

샤드 수 선택이 가장 중요한 결정이다. 프라이머리 샤드는 인덱스 생성 후 변경 불가다(Reindex만 가능). 잘못 설계하면 전체 재색인이 필요하다.

Oversharding 문제: 샤드가 너무 많으면 클러스터 상태 크기가 커지고, 마스터 노드에 부하가 집중된다. 샤드당 힙 사용량도 증가한다(Lucene 세그먼트당 ~1.5KB, 샤드당 수십 MB).

권장: 인덱스 크기 목표 / 50GB = 샤드 수. 시간 기반 인덱스(로그)는 롤오버로 샤드 크기를 50GB 이내로 유지한다.

Shrink / Split API

shrink: 샤드 수 축소. split: 샤드 수 확장. 단, 두 작업 모두 전체 재색인 없이 새 인덱스를 생성하며 다운타임 없이 진행 가능하다.

02 · Ingest Tuning
인제스천 튜닝 — 색인 속도 최대화
패턴Bulk APIIngest Pipeline

Bulk API: 단건 색인 대신 1,000~5,000개를 묶어 한 번에 전송한다. 요청당 오버헤드를 분산한다. 응답에 오류 항목이 포함되므로 파싱 필수다.

refresh_interval: 기본 1초. 대량 색인 시 -1(비활성화)로 설정하면 색인 속도가 3~5배 향상된다. 작업 완료 후 1s로 복원한다.

색인 중 레플리카를 0으로 줄이고 완료 후 복원하는 패턴도 유효하다(단, 장애 시 데이터 손실 위험 있음).

Ingest Pipeline

노드에서 색인 전 전처리(GeoIP 변환, 필드 파싱, 정규화)를 수행한다. Logstash 없이 ES 내부에서 처리 가능하다.

03 · Memory & JVM
힙 & 서킷 브레이커 — OOM 방지
중요도Critical

힙 크기: 물리 메모리의 50%로 설정, 최대 30.5GB(Compressed OOPs 한계). 나머지 50%는 Lucene의 페이지 캐시(파일 캐시)로 활용된다.

서킷 브레이커: 메모리 임계치 초과 시 요청을 거부해 OOM을 방지한다. Parent: 전체 힙의 95%. Field Data: 40%. Request: 60%. 대용량 집계 쿼리가 Field Data 한도를 초과하면 CircuitBreakingException이 발생한다.

G1GC: ES 기본 GC. -XX:+UseG1GC -XX:G1HeapRegionSize=8m. GC 시간 목표: -XX:MaxGCPauseMillis=50.

Field Data 캐시

집계·정렬 시 역인덱스를 메모리에 올린다(Fielddata). 힙 압박의 주요 원인. doc_values를 사용하면 디스크 기반으로 처리되어 힙을 절약한다. 분석 대상 필드는 항상 doc_values: true(기본값)를 유지한다.

                }
            }
        }
    },
    "mappings": {
        "properties": {
            "title": {
                "type": "text",
                "analyzer": "korean",
                "fields": {"keyword": {"type": "keyword"}}
            },
            "embedding": {
                "type": "dense_vector",
                "dims": 768,
                "index": True,         # HNSW 인덱스 활성화
                "similarity": "cosine"
            },
            "price": {"type": "double"},
            "created_at": {"type": "date"},
        }
    }
}

es.indices.create(index="products", body=mapping)
포인트. keyword와 text를 multi-field로 설정하면 전문 검색과 정확 매칭/집계를 동시에 지원한다. dense_vector에 index:true를 설정하면 HNSW kNN 인덱스가 생성된다.

02. Bulk 색인 — 대량 데이터 처리

bulk
from elasticsearch.helpers import bulk, streaming_bulk
from elasticsearch import Elasticsearch

es = Elasticsearch(
    ['http://localhost:9200'],
    http_compress=True,          # HTTP 압축
    request_timeout=30,
    retry_on_timeout=True,
    max_retries=3,
)

def generate_docs(products: list[dict]):
    for product in products:
        yield {
            "_index": "products",
            "_id": product["id"],
            "_source": product,
        }

# 대량 색인 전 refresh 비활성화
es.indices.put_settings(
    index="products",
    body={"refresh_interval": "-1"}
)

try:
    success, errors = bulk(
        es,
        generate_docs(products),
        chunk_size=1000,         # 1,000개씩 배치
        request_timeout=60,
        raise_on_error=False,    # 오류 항목 수집
    )
    print(f"성공: {success}, 실패: {len(errors)}")
finally:
    # 색인 완료 후 refresh 복원
    es.indices.put_settings(
        index="products",
        body={"refresh_interval": "1s"}
    )
    es.indices.refresh(index="products")
포인트. refresh_interval=-1은 대량 색인 시 처리량을 3~5배 향상시킨다. Generator로 메모리 효율적으로 처리하고, 완료 후 반드시 설정을 복원한다.

03. 하이브리드 검색 — BM25 + kNN + RRF

hybrid
def hybrid_search(
    query_text: str,
    query_vector: list[float],
    k: int = 10,
    num_candidates: int = 100,
) -> list[dict]:
    response = es.search(
        index="products",
        body={
            "size": k,
            "query": {
                "bool": {
                    "should": [
                        # BM25 전문 검색
                        {"match": {"title": {"query": query_text, "boost": 1.0}}},
                    ],
                    "minimum_should_match": 0,
                }
            },
            # kNN 시맨틱 검색
            "knn": {
                "field": "embedding",
                "query_vector": query_vector,
                "k": k,
                "num_candidates": num_candidates,
                "boost": 1.0,
            },
            # RRF로 점수 결합 (ES 8.8+)
            "rank": {
                "rrf": {"window_size": 100, "rank_constant": 60}
            },
        }
    )
    return [hit["_source"] for hit in response["hits"]["hits"]]
포인트. RRF는 두 결과 목록의 랭킹을 합산한다 — 1/(rank+k). 점수 정규화 없이 동작하므로 두 검색 방식의 스코어 범위가 달라도 결합이 가능하다.

04. 집계 쿼리 — 실시간 분석

aggregation
def product_analytics(category: str) -> dict:
    response = es.search(
        index="products",
        body={
            "size": 0,  # 히트 없이 집계만
            "query": {
                "term": {"category.keyword": category}
            },
            "aggs": {
                "price_stats": {
                    "stats": {"field": "price"}
                },
                "price_histogram": {
                    "histogram": {
                        "field": "price",
                        "interval": 10000
                    }
                },
                "brand_counts": {
                    "terms": {
                        "field": "brand.keyword",
                        "size": 10
                    }
                },
            }
        }
    )
    return response["aggregations"]
포인트. size:0으로 히트를 제외하면 집계만 수행한다. Terms 집계는 내부적으로 doc_values를 사용하므로 힙 효율적이다. 고카디널리티 필드 집계는 execution_hint: map을 피하고 기본값(ordinals)을 유지한다.

05. ILM 정책 설정

ilm
# ILM 정책: 로그 인덱스 생명주기
ilm_policy = {
    "policy": {
        "phases": {
            "hot": {
                "actions": {
                    "rollover": {
                        "max_size": "50GB",
                        "max_age": "7d",
                    },
                    "set_priority": {"priority": 100}
                }
            },
            "warm": {
                "min_age": "7d",
                "actions": {
                    "shrink": {"number_of_shards": 1},
                    "forcemerge": {"max_num_segments": 1},
                }
            },
            "cold": {
                "min_age": "30d",
                "actions": {
                    "searchable_snapshot": {
                        "snapshot_repository": "s3_repo"
                    }
                }
            },
            "delete": {
                "min_age": "365d",
                "actions": {"delete": {}}
            }
        }
    }
}

es.ilm.put_lifecycle(name="logs-policy", body=ilm_policy)
포인트. Warm 단계의 forcemerge(max_num_segments=1)는 읽기 전용 인덱스의 세그먼트를 1개로 병합한다. 검색 성능이 향상되고 저장 공간이 줄어든다. Cold 단계의 Searchable Snapshot은 S3 비용으로 로컬 스토리지를 대체한다.
