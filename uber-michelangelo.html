01

한 줄로 이해하기

Michelangelo는 ML 플랫폼이 8년에 걸쳐 거치는 전형적인 진화 궤적의 살아있는 사례다 — Spark 기반 모놀리식 (2016) → Python 친화적 모듈화 (2018, PyML) → Kubernetes federation (2024 MAJC) → Generative AI Gateway 통합 (2024 Michelangelo 2.0). 각 단계의 trigger는 분명했고, 결정이 만든 운영 부담도 함께 따라왔다.

i

2016 — Spark 기반 모놀리식 시작

당시 Uber는 "팀마다 ML 시스템을 처음부터 다시 만드는" 상태. Michelangelo가 6-step 워크플로우(data → train → eval → deploy → predict → monitor)를 표준화. 핵심은 Palette Feature Store — 10K+ 피처를 중앙에서 공유, 팀 간 중복 제거. 인프라는 HDFS + Spark + Cassandra + XGBoost.

ii

2018 — PyML과 모듈화 전환

Scala/config 워크플로우가 빠른 iteration을 막음. PyML SDK로 어떤 Python 모델이든 서빙 — DataFrameModel/TensorModel 추상 클래스 + 3-file 패턴(model.py · requirements.txt · setup.sh). Docker 자동 빌드 → online(gRPC + Unix socket) + offline(PySpark) 같은 코드로 양쪽 환경 지원. 이후 2019에 모델 표현 자체도 Spark ML 표준으로 전환.

iii

Michelangelo 2.0 — 4 user-facing themes

2024 출시. ① Model Excellence Score (MES) + 4-tier project — 우선순위 + 거버넌스. ② Canvas — version-controlled ML monorepo + Docker + CI/CD. ③ DL first-class — Ray + Horovod + Triton native. ④ MA Studio — 모든 ML 자산이 한 UI에서 version control 가능.

iv

MAJC + Ray on Kubernetes

K8s 클러스터들이 region/AZ별로 흩어져 GPU 활용이 깨짐 → MAJC가 federation layer로 abstract (load-aware · bin-pack · compute affinity · data affinity 4 policy). 2025에 DL 학습 인프라를 MADLJ on Peloton(Mesos) → KubeRay로 재구축, 학습 속도 1.5~4× 향상. ML 엔지니어는 K8s 복잡도를 모르고 작업만 제출.

v

GenAI Gateway — predictive + generative 통합

2024 추가. 사내·외부 LLM(OCI·GCP·OpenAI 등) 모두 단일 게이트웨이로. 4 guardrails: logging/auditing · cost attribution · safety policy · PII redaction. 부수적으로 Prompt Toolkit(prompt as code) + LLM Eval Framework(in-house vs 3P 비교).

vi

운영 규모 — ML 플랫폼의 현실

400+ active 프로젝트 · 5K+ 모델 in production · 월 20K+ training job · peak 10M predictions/sec · 20K+ features in Palette · 5K+ GPU. 1.37억 MAU에게 10K+ 도시에서 서빙. 이 규모가 곧 platform 운영의 모든 결정에 작용한다.

01 · 진화8년 타임라인 — 모놀리식에서 GenAI까지

각 단계 전환에는 분명한 trigger가 있었다. Scala 모놀리식 → Python 모듈화는 developer velocity가 trigger. 단일 K8s → MAJC federation은 region별 GPU 활용 불균형이 trigger. predictive → generative는 LLM 도입 시 거버넌스 부재가 trigger.

한 가지 일관된 원칙 — "플랫폼이 한 가지 워크로드만 잘하면 결국 다른 워크로드가 사이드 시스템을 만든다". Michelangelo는 매번 새 워크로드(DL · LLM)를 첫 시민으로 흡수해왔다.

일반 교훈

"플랫폼 1.0이 완성된 것 같다"는 순간이 가장 위험. ML/AI 영역은 6개월마다 패러다임이 바뀐다. 모듈화 + 확장 포인트가 곧 생존.

02 · 워크플로우6-step ML 워크플로우 (원조 패턴)

2017년 Michelangelo가 업계 표준으로 정착시킨 6-step. 이전엔 팀마다 다른 단계 정의를 썼지만, 이후 거의 모든 ML 플랫폼(Kubeflow, MLflow, Vertex AI, SageMaker Pipelines)이 이 6단계를 따른다.

핵심은 monitor 단계의 first-class 취급 — 배포 후 모델 성능을 지속 추적하는 게 workflow의 일부. "deploy 끝"이 아니라 "deploy + monitor가 한 단위".

왜 6-step인가

이 단계 외에 추가가 필요한 작업은 보통 "feature engineering"인데, 그건 Palette Feature Store에 흡수됨. 그래서 6단계가 minimum complete set.

[01]
Manage Data Palette Feature Store · HDFS · Cassandra. 10K+ 피처 공유
[02]
Train Models Spark MLLib · XGBoost · TensorFlow/PyTorch (DL). 분산 학습
[03]
Evaluate Models holdout 평가 · 시각화 · 모델 간 비교 · regression detection
[04]
Deploy Models online (수백 대 cluster · 로드밸런서) · offline (Spark batch)
[05]
Make Predictions RPC online (P95 <10ms) + scheduled batch · 10M/s peak
[06]
Monitor Predictions data drift · model regression · alerts. first-class step으로 처음 정착

03 · 2.0Michelangelo 2.0 — 4 user-facing themes

Michelangelo 2.0의 reorganization은 사용자 시점에서 본 평가가 핵심. 백엔드 아키텍처가 아니라 "ML 엔지니어가 매일 만지는 4가지"를 정렬했다.

MES(Model Excellence Score)는 ML 거버넌스의 묘안 — 각 모델을 lifecycle stage별로 정량 평가, 4-tier로 분류해서 운영 리소스 우선순위 결정. Canvas는 ML도 일반 코드처럼 monorepo + version control + CI/CD가 되어야 한다는 선언.

가장 큰 영향

Canvas의 "ML as code" 전환 — Jupyter notebook 기반 개발이 끝나고 Python module + Docker + git workflow로. ML 엔지니어와 일반 SWE의 toolchain이 합쳐졌다.

01Model Quality + Project Tiering
Model Excellence Score (MES) — 각 lifecycle stage 정량 평가. 4-tier project 분류로 high-impact에 리소스 우선 배분. ML 거버넌스.
02Canvas — ML as Code
ML Application Framework (MAF) + ML Monorepo + Docker packaging + CI/CD. Jupyter 시대 졸업. 모든 ML 자산이 PR 리뷰 대상.

TensorFlow · PyTorch native. Horovod distributed training on Ray. Triton inference server 통합. elastic GPU resource management.
04MA Studio — Unified Web UI
전 ML 자산(model · feature · pipeline · prompt)을 한 UI에서 version control + code review. 흩어진 도구들 통합.

04 · 인프라Michelangelo Job Controller (MAJC)

K8s 클러스터들이 region/AZ별로 흩어져 있어 GPU 활용이 cluster boundary에 갇힘. 한 클러스터는 GPU 놀고 다른 클러스터는 queue 폭주 — 그래도 cross-cluster 스케줄링 불가능했다.

MAJC는 그 boundary를 federation layer로 abstract. ML 엔지니어는 K8s 클러스터 자체를 모르고 "job 제출"만 함. 스케줄러가 4가지 policy로 자동 라우팅 — load-aware · bin-pack · compute affinity · data affinity.

왜 자체 federation?

K8s 자체 federation v2는 ML 워크로드 특수성(긴 학습 · GPU 친밀도 · data locality)을 표현하기 어려웠다. 그래서 자체 layer를 ML-specific하게 만든 게 MAJC의 결정.

05 · GenAIGen AI Gateway — vendor abstraction + guardrails

LLM 도입 시 가장 큰 문제는 "누가 어떤 모델을 얼마나 쓰는지 추적 안 됨" + "PII가 외부로 새는지 모름". Michelangelo는 단일 게이트웨이를 두고 모든 LLM 호출(in-house · OCI · GCP · OpenAI 등)을 통과시킨다.

4 guardrails이 한 자리에서 강제 — logging/auditing · cost attribution · safety policy · PII redaction. 이건 단순 proxy가 아니라 policy enforcement layer. 팀이 어떤 LLM을 쓰든 거버넌스는 일관.

왜 자체 게이트웨이?

각 LLM 벤더 SDK를 직접 쓰면 거버넌스가 팀마다 분산 → 일관성 0. 게이트웨이가 있어야 PII redaction을 외부 API 호출 전에 보장할 수 있다.

앱 · 에이전트 · 사내 도구(직접 LLM SDK 호출 금지 — 모든 트래픽이 게이트웨이를 통과)

06 · 종합전체 종합 아키텍처

앞서 본 5개 부분도가 어떻게 한 시스템으로 연결되는지 정리. 최상단은 MA Studio UI(ML 엔지니어 진입점), 중앙은 MAJC federation(작업 분배 경계), 하단은 두 실행 경로 — Predictive(전통 ML) + Generative(LLM Gateway).

핵심 디자인 원칙: ① 진입점 단일화 (MA Studio · Gateway), ② 인프라 추상화 (MAJC), ③ 거버넌스 일관 (guardrails · MES). 각 layer가 다음 layer의 복잡도를 감춤.

핵심 원리

"플랫폼은 좋은 인터페이스를 제공하기 위해 좋은 인터페이스 위에 만들어진다." MA Studio → MAJC → K8s → GPU. 각 층은 위 층에 깔끔한 API만 노출.

Michelangelo 진화에서 가장 반직관적 결정은 "Scala 모놀리식이 잘 돌아갈 때 Python으로 옮긴 것". 성능·안정성은 Scala가 우위였지만 developer velocity가 결국 플랫폼의 가치를 결정한다는 인식. 이후 Canvas("ML as code")까지의 모든 결정이 이 통찰의 연장선이다 — ML 도구는 SWE 도구와 같은 워크플로우로 수렴해야 한다.

참고
Palette Feature Store
"팔레트"

정의. Michelangelo의 중앙 feature store — 모든 팀이 만든 ML feature를 한 곳에 모아 공유·재사용 가능하게 한 인프라. 현재 20K+ features.

왜 필요했나. 2016 이전, 각 팀이 자체 ETL로 feature 만들어 중복·일관성 깨짐 — 같은 "운전자 평점"을 5개 팀이 각자 다르게 계산. Palette가 이름 + schema + 계산 로직 + offline/online 일관성 보장.

구조. ① Offline 자동 계산(Spark daily) → HDFS 저장 → 학습용. ② Online은 같은 로직을 Cassandra real-time lookup으로 → 서빙용. 같은 feature가 두 환경에서 동일 값을 보장(training-serving skew 방지).

Meta Store 재구축 (2024). 메타데이터 레이어를 재설계 — 객체 모델 FeatureGroup · Feature · Dataset · Storage · FeatureServingGroup로 정형화. K8s 컨트롤러가 ObjectConfig 캐시 동기화. 온보딩 시간 95%↓, Cassandra 마이그레이션 90%↓, offline metadata update 1시간 → 15분.

업계 영향. 이 패턴이 Feast · Tecton · Vertex Feature Store 등 후속 feature store들의 원형이 됨.

참고
MAJC (Michelangelo Job Controller)
"매직 / 엠에이제이씨"

정의. 여러 K8s 클러스터를 abstract하는 federation layer. 단일 작업 제출 인터페이스를 제공하고 클러스터들 사이를 자동으로 라우팅·스케줄.

4가지 policy. ① Load aware: 클러스터 부하 균등 분산. ② Bin-pack: 자원 밀도 최대화 (fragment 최소). ③ Compute affinity: 연관 작업을 인접 노드에. ④ Data affinity: 데이터 이동 비용 최소화 (대규모 dataset은 그 데이터가 있는 클러스터로).

왜 자체 구현? K8s native federation(KubeFed 등)은 ML 워크로드 특수성(긴 학습 · GPU 친화도 · data locality)을 표현하기 어려웠다. ML-specific하게 만들어야 했다.

운영 효과. ML 엔지니어가 K8s 클러스터를 몰라도 됨. 클러스터 추가/삭제도 사용자 영향 0. 17개 GPU/CPU SKU를 통합 관리.

2025 Ray on K8s 전환. DL 학습 인프라를 MADLJ(Michelangelo Deep Learning Jobs) on Peloton/Mesos → KubeRay로 재구축. federated control plane(API server · job controller · scheduler) + 로컬 K8s 클러스터. uOwn asset management 통합. 결과: 학습 속도 1.5~4× 향상 · GPU 활용도 개선.

참고
MES (Model Excellence Score)
"멤"

정의. 모델 lifecycle의 각 stage(training · eval · deploy · monitor)에서 핵심 지표를 정량 측정해 단일 점수로 합산한 거버넌스 framework.

왜 필요했나. 5K+ 모델이 동시 운영될 때 "어떤 모델이 건강한가"를 manual로 판단 불가능. MES가 signal-to-action 자동화 — 점수 낮은 모델은 우선순위 낮춤, 임계치 이하면 alert.

4-tier project 시스템. MES와 함께 도입 — 비즈니스 영향에 따라 모델을 Tier 1~4로 분류. Tier 1은 운영 리소스 우선 배정(GPU, monitoring, on-call), Tier 4는 best-effort. 한정된 운영 인력을 가장 가치 있는 곳에 집중.

적용 어려움. "어떤 지표가 excellence를 대표하는가" 정의가 도메인별로 다름. Uber도 처음엔 universal score를 시도했다 결국 domain-specific MES로 분기.

그래서 — 이 패턴을 우리 조직에 적용한다면?

도입 권장 시점

  • ML 모델 50개 이상 + 팀 5개 이상 — feature 중복이 통증
  • 같은 dataset에 대해 팀마다 다른 feature 정의가 있다 → Palette 우선 도입
  • K8s 클러스터 3개 이상 + GPU 활용 불균형 → MAJC-like federation
  • LLM 사용 시작 + 거버넌스 없음 → Gateway 우선 도입
  • ML 엔지니어들이 notebook에서 못 벗어나는 단계 → Canvas-like 모노레포

도입 자제 / 차용 부분

  • ML 모델 10개 미만 — 플랫폼 인프라가 과투자
  • K8s가 익숙치 않은 조직 — federation은 K8s 마스터한 후
  • MES 같은 전사 거버넌스 — 작은 팀엔 burden, 자유도 침해
  • Spark 의존 — Spark 운영 인력 없으면 다른 ETL 선택
  • "Michelangelo full stack" 복제 시도 — 1년 안에 못 끝남. 한 요소씩 차용이 정답
03
Scale Checkpoints

대용량 처리 체크포인트

ML 플랫폼 대용량 운영은 4가지 사전 체크에서 결정된다 — 학습 메모리 budget · 분산 학습 전략 · 추론 처리량 제어 · 배포 검증. 학습 작업이 며칠 걸리고 GPU 한 대당 $30/h인 상황에서 OOM 한 번은 비용과 시간 둘 다 잃는다.

01 · 학습 메모리GPU 메모리 사전 체크

DL 학습 GPU 메모리는 단순히 모델 크기가 아니다. 4 components의 합산: 모델 파라미터 + optimizer state + gradient + activation. Adam optimizer는 파라미터의 2배(m·v), gradient는 1배, activation은 batch·seq·layer 함수.

Llama 70B fine-tuning 예시 — 760GB 이상. Single H100 80GB로 불가. ZeRO-3 sharding + activation checkpointing + mixed precision 모두 동원해야 GPU 8~10대로 fit. 학습 시작 전에 4 components를 계산해야 어떤 분산 전략이 필요한지 결정된다.

핵심 트릭

Activation checkpointing — backward에 다시 forward 계산해서 activation 메모리 sqrt(N)으로 감소. compute 1.3x 늘지만 메모리 폭주 막음. 사실상 LLM 학습 default.

Component공식 (FP16)70B params
모델 파라미터N × 2 byte~140 GB
Optimizer state (Adam)N × 8 byte (m + v in FP32)~560 GB
GradientN × 2 byte~140 GB
Activation (batch=1, seq=2K)12 × L × H × seq × batch~200 GB
합계필요 GPU 메모리~1040 GB

02 · 분산 전략모델 크기별 사다리

모델이 single GPU에 fit하면 DDP가 가장 단순·빠름 (data parallel). Fit하지 않으면 FSDP / ZeRO-2 (optimizer shard) → ZeRO-3 (parameter shard) → CPU offload → Pipeline parallel 순으로 사다리.

규칙: 한 단계 위로 갈수록 MFU(Model FLOPs Utilization)가 떨어짐. 쓸 수 있는 최단순 전략부터 시도. ZeRO-3가 필요한데 ZeRO-2로 시작하면 OOM. ZeRO-3로 충분한데 CPU offload 추가하면 throughput만 손해.

잘못 흔히 한 선택

"DeepSpeed가 좋다더라" → 검증 없이 ZeRO-3 + CPU offload 모두 켜기. MFU 30% 미만. 먼저 ZeRO 없이 시도해 OOM 확인 후 사다리 올라가는 게 정석.

model fit
Single GPU — DataLoader + autograd. baseline. 모델이 GPU 메모리 70% 이하면 여기서 시작.
model fit
DDP (Data Parallel) — 모델 N×replication, gradient all-reduce. throughput N배. torch.nn.parallel.DistributedDataParallel.
model too big
FSDP / ZeRO-2 — optimizer state shard across GPUs. FullyShardedDataParallel 또는 deepspeed.zero_stage=2. 메모리 1/N로.
model massive
ZeRO-3 (Parameter shard) — params/grad/opt 모두 shard. communication 늘지만 가장 큰 모델 가능. deepspeed.zero_stage=3.
+ offload
+ CPU offload — optimizer state를 CPU RAM으로. 추가 메모리 확보, MFU 30~50% 손해. NVMe offload도 있음 (더 큰 손해).
+ pipeline
+ Pipeline parallel — layer 그룹별로 다른 GPU. bubble 발생 (MFU 추가 손해). 진짜 거대한 모델 (1T+)에서만.

03 · 추론 제어Triton dynamic batching + auto-scaling

Online inference에서 GPU 비용 최소화의 핵심은 dynamic batching. 짧은 시간(예: 500μs) 안에 들어오는 요청을 묶어 GPU 한 번에 처리. 단일 latency는 살짝 양보하되 throughput을 폭증시킴.

실패 패턴: queue depth 모니터링 없이 운영 → 트래픽 스파이크에 queue 폭주, p99 무한 증가. Auto-scaling은 GPU 인스턴스 수가 아니라 queue depth + GPU utilization 기준으로 트리거.

가장 흔한 실수

max_batch_size만 키우면 throughput 늘 거라고 생각. 실제로는 max_queue_delay_microseconds와 함께 튜닝해야 의미. 늦게 들어온 요청이 batch에 못 묶이면 latency 폭주.

[1]
max_queue_delay_microseconds batch가 충분히 차지 않아도 이 시간 후 강제 발사. 500μs가 default sweet spot
[2]
preferred_batch_size 가장 효율적인 batch size 후보 ([32, 64, 128] 등). 하드웨어별 sweet spot 측정 필수
[3]
instance_group count 같은 모델의 GPU 인스턴스 수. 메모리 ÷ 모델 크기. concurrency도 함께 결정
[4]
Queue depth 모니터링 실제 부하 지표. 임계치 초과 시 alarm + auto-scale 트리거
[5]
Auto-scaling (HPA) GPU utilization > 70% AND queue depth > threshold → replica 증가

04 · 배포 검증Staging → Shadow → Canary → 100%

ML 모델은 같은 input에도 학습 데이터에 따라 결과가 다름. 일반 SW와 달리 코드 정확성으로는 검증 불가. 4단계 게이트가 표준: staging offline eval → shadow traffic mirror → canary 점진 cutover → 100%.

Shadow는 응답 안 하고 측정만 — recall · latency diff · error rate. Canary 단계마다 임계치 위반 시 auto-rollback. Michelangelo는 이 흐름을 MA Studio에서 GUI로 제공.

Shadow의 함정

Green 인덱스에 read load만 들어가므로 cache 동작이 prod와 다를 수 있음. Cutover 후 latency가 더 나쁠 가능성 항상 염두. 그래서 canary 5%부터 시작.

[1]
Staging offline eval holdout test set · 정확도·F1·AUC 비교 · baseline 대비 regression 차단
eval set
[2]
Shadow traffic mirror prod query를 new model에도 복제 · 응답 버리고 측정만 · diff 비교
0% serve
[3]
Canary gradual cutover 사용자별 stable hash로 5% → 25% → 50% → 100% · 각 단계 검증
5→100%
[4]
Auto-rollback 임계치 위반 (recall/latency/error) 시 즉시 이전 model로 트래픽 복원 · oncall page
auto

가장 흔한 실수 — ① 학습 메모리 사전 체크 누락: 며칠 학습 중 OOM 발견 → 처음부터 다시. ② DeepSpeed/ZeRO를 검증 없이 max 설정: MFU 30% 미만으로 비용만 폭주. 사다리 한 단씩 올라가야 함. ③ Triton batching 단독 튜닝: max_batch_size만 늘리면 의미 없음. max_queue_delay와 함께. ④ Shadow 없는 모델 배포: offline eval만으로 prod regression 못 잡음. 거의 모든 model rollback의 trigger.

학습/배포 전 통과해야 할 4 게이트

통과 신호 (Go)

  • 학습 메모리 4 components 모두 계산, 가용 GPU 메모리 ≥ 1.3 × 추정치
  • 분산 전략 사다리에서 가장 단순한 옵션으로 시작
  • Triton config의 max_queue_delay_microseconds + preferred_batch_size 함께 측정 완료
  • Shadow traffic 24시간 이상 + recall/latency diff < threshold
  • Auto-rollback 트리거 + oncall page 자동화 검증

차단 신호 (Stop)

  • "DeepSpeed 좋다더라"로 ZeRO-3 + offload 모두 활성화
  • 학습 메모리 계산 안 함 / 추정만 함
  • Triton dynamic batching 비활성화 (GPU 자원 낭비)
  • Shadow 없이 staging만으로 prod 직배포
  • Auto-scaling이 CPU/메모리 기준 (queue depth 무시)
  • Canary 단계 건너뛰고 100% 즉시 cutover

def training_memory_gb(
    n_params: int,        # 모델 파라미터 수
    dtype: str = "fp16",
    optimizer: str = "adamw",
    seq_len: int = 2048,
    batch_size: int = 1,
    hidden_dim: int = 8192,
    n_layers: int = 80,
    activation_checkpoint: bool = True,
) -> dict:
    """학습 GPU 메모리의 4 components 추정 (GB)."""

    bytes_per = {"fp32": 4, "fp16": 2, "bf16": 2, "int8": 1}[dtype]

    # 1. 모델 파라미터
    model_gb = n_params * bytes_per / 1024**3

    # 2. Optimizer state (Adam = 2x params in FP32)
    opt_mult = {"sgd": 0, "adamw": 8, "adam": 8}[optimizer]   # FP32 기준
    opt_gb = n_params * opt_mult / 1024**3

    # 3. Gradient (= params size)
    grad_gb = model_gb

    # 4. Activation (transformer 근사식)
    act_factor = 12 if not activation_checkpoint else 2
    act_gb = (act_factor * n_layers * hidden_dim * seq_len * batch_size
              * bytes_per) / 1024**3

    total = model_gb + opt_gb + grad_gb + act_gb
    return {
        "model_gb": model_gb, "optimizer_gb": opt_gb,
        "gradient_gb": grad_gb, "activation_gb": act_gb,
        "total_gb": total, "safe_gb": total * 1.3,
    }

# Llama 70B fine-tuning 예시
m = training_memory_gb(n_params=70_000_000_000, dtype="fp16",
                       hidden_dim=8192, n_layers=80)
print(f"total {m['total_gb']:.0f}GB (safe {m['safe_gb']:.0f}GB)")
# → total 1040GB (safe 1352GB) — single H100 80GB로 절대 불가

def required_gpus(m: dict, gpu_mem_gb: int = 80) -> int:
    """ZeRO-3로 sharding 가정 시 필요 GPU 개수."""
    import math
    return math.ceil(m["safe_gb"] / (gpu_mem_gb * 0.7))   # 70% 사용 가정

print(f"H100 80GB × {required_gpus(m, 80)}대 필요")
# → H100 80GB × 25대 필요
포인트. 학습 메모리는 모델 크기 ≠ GPU 메모리 요구. Adam optimizer state가 보통 가장 큼 (params의 4배). activation checkpointing 켜면 act 메모리 1/6로 감소 — LLM 학습 사실상 default. 학습 시작 코드 가장 위에 training_memory_gb() assertion 박아두면 며칠 낭비 방지.

def recommend_strategy(model_gb: float, gpu_mem_gb: int = 80) -> str:
    """사다리 순서대로 시도 — 가능한 가장 단순한 전략."""
    safe_gpu = gpu_mem_gb * 0.7

    if model_gb < safe_gpu * 0.3:
        return "single-gpu"                  # 모델이 작음
    elif model_gb < safe_gpu * 0.5:
        return "ddp"                         # throughput만 키우기
    elif model_gb < safe_gpu:
        return "fsdp"                        # optimizer state shard
    elif model_gb < safe_gpu * 4:
        return "zero-3"                      # parameter shard
    elif model_gb < safe_gpu * 16:
        return "zero-3 + cpu-offload"        # MFU 손해 감수
    else:
        return "zero-3 + pipeline-parallel"  # 거대 모델

# 사용 예 — 모델 크기에 따른 추천
for n_params in [7e9, 13e9, 70e9, 175e9]:
    model_gb = n_params * 2 / 1024**3     # fp16
    strategy = recommend_strategy(model_gb, gpu_mem_gb=80)
    print(f"{n_params/1e9:>5.0f}B: model {model_gb:5.0f}GB → {strategy}")
#   7B: model    13GB → ddp
#  13B: model    24GB → ddp
#  70B: model   130GB → zero-3
# 175B: model   326GB → zero-3 + cpu-offload

import tritonclient.grpc as grpcclient
import time, numpy as np

client = grpcclient.InferenceServerClient("triton:8001")

def measure_throughput(batch_size: int, n_iters: int = 100) -> float:
    """특정 batch size에서의 throughput 측정 (req/sec)."""
    inputs = [grpcclient.InferInput("input_ids", [batch_size, 512], "INT64")]
    inputs[0].set_data_from_numpy(np.random.randint(0, 32000, (batch_size, 512)))

    start = time.time()
    for _ in range(n_iters):
        client.infer("llm_inference", inputs)
    elapsed = time.time() - start
    return (n_iters * batch_size) / elapsed

# 모든 batch size 후보 sweep — sweet spot 찾기
for bs in [1, 2, 4, 8, 16, 32, 64, 128]:
    tps = measure_throughput(bs)
    print(f"batch={bs:3d}: {tps:6.1f} req/sec")
# sweet spot이 plateau 시작점. preferred_batch_size로 설정.
포인트. max_batch_size는 절대 한계, preferred_batch_size는 효율 목표. dynamic batching의 진짜 가치는 max_queue_delay_microseconds + preferred_batch_size 조합. 측정 없이 default로 두면 GPU 자원 30% 이상 낭비.

04 · Canary deployment + auto-rollback

deploy 
import asyncio, hashlib
from dataclasses import dataclass, field

@dataclass
class DeployMetrics:
    requests: int = 0
    errors:   int = 0
    latency_ms: list[float] = field(default_factory=list)
    recall_overlap: list[float] = field(default_factory=list)

    def healthy(self, baseline: "DeployMetrics") -> bool:
        if self.requests < 100: return True           # 표본 부족
        err_rate = self.errors / self.requests
        avg_p99 = sorted(self.latency_ms)[int(len(self.latency_ms) * 0.99)]
        avg_recall = sum(self.recall_overlap) / len(self.recall_overlap)
        return (err_rate < baseline.errors/baseline.requests * 1.5
                and avg_p99 < sorted(baseline.latency_ms)[int(len(baseline.latency_ms) * 0.99)] * 1.10
                and avg_recall > 0.95)

class CanaryRouter:
    """사용자별 stable hash로 cutover · 임계치 위반 시 auto-rollback."""

    def __init__(self, baseline_model, candidate_model):
        self.baseline = baseline_model
        self.candidate = candidate_model
        self.baseline_metrics = DeployMetrics()
        self.candidate_metrics = DeployMetrics()
        self.cutover_pct = 0.0            # 0 → 0.05 → 0.25 → 0.5 → 1.0

    def route(self, user_id: str) -> str:
        # stable hash — 같은 사용자는 같은 model로 계속
        h = int(hashlib.md5(user_id.encode()).hexdigest(), 16)
        return "candidate" if (h % 10000) / 10000 < self.cutover_pct else "baseline"

    async def serve(self, user_id: str, query):
        target = self.route(user_id)
        model = self.candidate if target == "candidate" else self.baseline
        metrics = self.candidate_metrics if target == "candidate" else self.baseline_metrics

        start = time.monotonic()
        try:
            result = await model.predict(query)
            metrics.requests += 1
            metrics.latency_ms.append((time.monotonic() - start) * 1000)
        except Exception:
            metrics.errors += 1; raise

        # 헬스 체크 — 위반 시 즉시 rollback
        if target == "candidate" and not self.candidate_metrics.healthy(self.baseline_metrics):
            await self.rollback()

        return result

    async def advance(self):
        """정상 시 단계 진행 — 5 → 25 → 50 → 100"""
        assert self.candidate_metrics.healthy(self.baseline_metrics)
        stages = [0.05, 0.25, 0.5, 1.0]
        idx = stages.index(self.cutover_pct) if self.cutover_pct in stages else -1
        self.cutover_pct = stages[idx + 1]
        emit("canary_pct", self.cutover_pct)

    async def rollback(self):
        self.cutover_pct = 0.0
        page_oncall("canary unhealthy — rolled back")
포인트. Canary 핵심은 사용자별 stable hash — 같은 사용자가 검색마다 다른 결과 받으면 UX 깨짐. md5(user_id) % 10000 패턴. Auto-rollback 트리거 = error rate · p99 latency · recall regression 셋 모두. 하나만 보면 silent failure 놓침.

Architecture Evolution

아키텍처 진화 — 2017 vs 2024-2025

같은 시스템이 8년 동안 어떻게 변형되었는가 — 2017 모놀리식 단일 파이프라인에서, 2024-2025 5-layer hierarchical federation으로. 각 박스가 추가/대체된 이유는 §02 타임라인에 자세히.

2017

Linear Pipeline — 모놀리식 v1.0

single platform · all-in-one

특징. 5-layer 선형 파이프라인 (data → train → serve → monitor → UI). 모든 컴포넌트가 단일 platform 위 — separate ML 시스템이 없던 시대. Online serving은 gRPC · P95 < 10ms로 이미 production-grade. 병목: 단일 monolithic UI · Scala/JVM 단일 환경 · Spark 외 알고리즘 추가 어려움 · protobuf 모델 표현이 신규 transformer 막음. → 2018 PyML과 2019 Spark ML 표준화로 분기.

2024-2025

Hierarchical Federation — v2.0 + GenAI + Ray on K8s

5 layers · multi-region · multi-tenant

특징. 5-layer 계층 분리 — Developer / GenAI / Federation / Orchestration / Hardware + 별도 Data layer (Palette Meta Store). L4 GenAI Plane은 2024 신규 — predictive와 같은 platform 위. L3 MAJC가 multi-region K8s 클러스터들을 abstract (4 policies). L2 Orchestration은 2025에 Mesos/Peloton → KubeRay 전환 (학습 1.5-4× 빠름). 각 layer가 다음 layer의 복잡도를 감추는 "layered platform" 디자인 원리의 적용.

01 · Palette feature 정의 + 등록

feature store 
from palette import Feature, FeatureGroup, feature

@feature(
    name="driver_avg_rating_30d",
    description="기사 30일 평균 평점 · 운영팀 + ML 양쪽 사용",
    owners=["safety-team"],
    tier=2,                    # MES 거버넌스 — Tier 2
)
class DriverAvgRating30d(Feature):
    """offline/online 동일 로직 보장 — training-serving skew 방지."""

    entity = "driver_uuid"
    dtype = "float32"

    def offline_compute(self, batch_df):
        """daily Spark job — HDFS에 저장"""
        return (batch_df
            .filter("trip_completed_at > current_date() - INTERVAL 30 DAYS")
            .groupBy("driver_uuid")
            .agg({"rider_rating": "avg"})
            .withColumnRenamed("avg(rider_rating)", "value"))

    def online_compute(self, entity_id):
        """real-time Cassandra lookup — same logic"""
        return cassandra.get(
            keyspace="palette_driver_avg_rating_30d",
            key=entity_id,
            ttl=3600,
        )

# 등록: MA Studio에서 모든 팀이 검색·재사용 가능
DriverAvgRating30d().register()
포인트. Palette의 핵심은 offline/online 동일 로직 보장. 두 path를 한 class에 모아서 training-serving skew(학습 때 본 feature 값과 서빙 때 본 값이 달라 모델 무력화)를 원천 차단. tier가 MES 거버넌스의 entry point.

02 · PyML 3-file 패턴 (online + offline 같은 코드)

pyml 
# projects/churn_predictor/model.py
from michelangelo.pyml import DataFrameModel
import pandas as pd
import joblib

class ChurnPredictor(DataFrameModel):
    """DataFrameModel = pandas DataFrame 입출력 모델 (online + offline 공통)."""

    def load(self, artifact_path: str):
        """모델 weights 로드 — 한 번만 실행 (warm)."""
        self.clf = joblib.load(f"{artifact_path}/model.pkl")
        self.feature_cols = ["trip_count", "avg_rating", "days_since_last"]

    def predict(self, df: pd.DataFrame) -> pd.DataFrame:
        """input/output 모두 DataFrame — online RPC와 offline Spark 동일 호출."""
        X = df[self.feature_cols]
        df["churn_prob"] = self.clf.predict_proba(X)[:, 1]
        return df

03 · Canvas — ML as Code (monorepo + CI/CD)

canvas 
# projects/eta_prediction/model.py
from michelangelo.maf import MLApplication, Model
from palette.features import DriverAvgRating30d, TripDistance, WeatherZone

class EtaModel(Model):
    """모델 = 일반 Python module. PR 리뷰 대상."""

    name = "eta_v3"
    framework = "xgboost"
    tier = 1                       # Tier 1 = high-impact

    features = [
        DriverAvgRating30d(),
        TripDistance(),
        WeatherZone(),
    ]

    hyperparams = {
        "max_depth": 6,
        "learning_rate": 0.1,
        "n_estimators": 500,
    }

    def train(self, X, y):
        import xgboost as xgb
        self.booster = xgb.XGBRegressor(**self.hyperparams)
        self.booster.fit(X, y)

    def predict(self, X):
        return self.booster.predict(X)

# projects/eta_prediction/app.yaml — Docker + CI 설정
# trigger: PR → CI: train on sample → eval gate → deploy to staging
포인트. "Jupyter notebook으로 만든 모델을 어떻게 production으로 보내나"의 가장 깔끔한 답 — 처음부터 Python module로 작성. PR마다 CI가 sample 학습 + eval gate 통과해야 머지. Docker 패키징은 자동. "ML도 일반 코드와 같은 워크플로우"의 실체화.

06 · LLM Evaluation Framework

eval 
from michelangelo.eval import LLMEvaluator, Rubric

# 비교 대상: in-house vs OpenAI vs Gemini · prompt v2 vs v3 · 등등
candidates = [
    {"name": "v3 + llama-3-70b",    "prompt": "trip_summary_v3", "model": "in-house-llama-3-70b"},
    {"name": "v3 + gpt-4o",         "prompt": "trip_summary_v3", "model": "openai-gpt-4o"},
    {"name": "v2 + gpt-4o (baseline)", "prompt": "trip_summary_v2", "model": "openai-gpt-4o"},
]

# Rubric — LLM judge가 사용할 평가 기준
rubric = Rubric(
    criteria=[
        "factual_accuracy",       # 0~10
        "conciseness",             # 0~10
        "no_pii_leak",             # 0 or 1 (hard gate)
        "tone_neutrality",         # 0~10
    ],
    judge_model="openai-gpt-4o",    # 별도 강한 모델로 judge
)

# 평가 수행 (n=100 eval set)
evaluator = LLMEvaluator(eval_set=load_eval_set("trip_summary", n=100))
results = evaluator.compare(candidates, rubric)

# 결과 — 모든 candidate × 모든 criteria 점수 행렬
for cand in results:
    print(f"{cand.name:30s} acc={cand.scores['factual_accuracy']:.2f}  "
          f"pii={cand.scores['no_pii_leak']:.2f}  cost=${cand.cost_per_1k:.3f}")

# Promote 결정 — pass 게이트 통과한 candidate 중 비용 최소를 선택
winner = evaluator.recommend(
    results,
    require={"factual_accuracy": ">= 8.0", "no_pii_leak": "== 1.0"},
    optimize="cost",    # 비용 최소화
)
포인트. LLM Eval은 "여러 candidate를 동시에 객관적으로 비교"가 핵심. 사람이 비교하기 시작하면 일관성 0 + 비용 폭주. 강한 LLM을 judge로 두고 rubric으로 점수화. require + optimize 분리가 운영의 묘안 — "pass 기준은 강하게, 그 안에서 비용 최소"는 거의 모든 LLM 의사결정의 일반 패턴.

위 6개 코드는 오픈 소스로 거의 동일 구성 가능: ① Feature Store → Feast. ② PyML 3-file 패턴 → BentoML · MLflow Models. ③ Canvas-like 모노레포 → MLflow + git. ④ Triton은 이미 오픈 소스. ⑤ Gen AI Gateway → LiteLLM 또는 직접 구현. ⑥ LLM Eval → RAGAS, OpenAI evals, LangSmith. Michelangelo가 보여준 건 "이 컴포넌트들을 한 platform으로 묶어 거버넌스 일관성을 만든다"는 통합 사고방식.
