Agent Design
Patterns

"효과적인 에이전트 설계는 결국 컨텍스트 관리로 수렴한다." — 모델은 컨텍스트가 커질수록 나빠지고(context rot), 작업은 7개월마다 2배로 길어진다. 유한한 주의 예산을 다루는 8가지 패턴.

방향 Bitter Lesson
01

한 줄로 이해하기

좋은 에이전트는 좋은 프레임워크에서 나오지 않는다 — 좋은 컨텍스트 관리에서 나온다. 모델은 컨텍스트가 커질수록 성능이 떨어지고(context rot), 에이전트 작업 길이는 7개월마다 2배가 된다. Lance Martin이 정리한 8가지 패턴은 모두 유한한 주의 예산을 다음 스텝에 딱 맞게 채우는 방법이다.

i

컨텍스트는 유한 자원이다

Anthropic의 표현 — "컨텍스트는 한계효용이 체감하는 유한 자원으로 다뤄야 한다". Chroma는 이를 context rot(컨텍스트가 길어질수록 모델이 망가짐)으로, METR은 "작업 길이가 7개월마다 2배"로 측정했다. Karpathy: "딱 맞는 정보로 창을 채우는 섬세한 기술".

ii

에이전트에 컴퓨터를 줘라

파일시스템(영속 컨텍스트) + 셸(유틸·CLI·자기작성 코드 실행). Claude Code는 "네 컴퓨터에 산다", Manus는 e2b 가상 컴퓨터. Rauchg: "코딩 에이전트의 근본 추상은 CLI다".

iii

도구 정의를 컨텍스트에 쌓지 마라

도구를 100개 노출하지 말고 bash 하나를 노출해 코드로 엮어라. GitHub MCP 서버는 35개 도구가 정의만으로 ~26K 토큰. Claude Code는 ~12개, Manus는 20개 미만으로 유지한다.

iv

필요할 때만 보여주고, 밖으로 빼라

Progressive disclosure — 핵심만 먼저, 상세는 --help·인덱스·SKILL.md로 on-demand. Offload — 중간 결과·궤적을 파일시스템에 쓰고 선택적으로 읽되, 요약은 오프로딩의 효용이 떨어질 때만.

v

캐시하고, 격리하라

Manus는 "cache hit rate가 프로덕션 에이전트의 가장 중요한 지표"라 단언 — 캐시가 있으면 더 큰 모델이 더 싸질 수 있다. 컨텍스트가 한 창에 안 들어가면 sub-agent로 격리하고 git 히스토리로 진행을 공유한다.

vi

진화시키고, 결국 학습에 맡겨라

과거 궤적을 반성해 가중치가 아니라 컨텍스트(memory·skill)를 갱신(GEPA·Letta). 더 나아가 모델이 스스로 컨텍스트를 관리(RLM·sleep-time compute)하게 된다 — Bitter Lesson은 손으로 짠 scaffolding이 결국 모델 능력에 흡수된다고 예고한다.

02
Structure

그림으로 보는 구조

00 · 전제왜 컨텍스트를 관리하나

모든 패턴의 출발점은 하나의 사실이다 — 컨텍스트가 커지면 모델 성능이 떨어진다(context rot). 그런데 작업은 점점 길어진다(7개월마다 2배). 둘이 충돌한다.

그래서 컨텍스트는 무한 버퍼가 아니라 한계효용이 체감하는 유한 예산으로 다뤄야 한다. 8가지 패턴은 전부 이 예산을 아끼는 기법이다.

핵심 긴장

작업 길이↑ vs 유효 컨텍스트↓. 이 간극을 메우는 게 컨텍스트 엔지니어링이고, 패턴들은 그 도구함이다.

짧은 컨텍스트정확
누적50+ tool calls
context rot성능 저하
2026.01

8가지 패턴의 지도

substrate → manage → improve
읽는 법. 왼쪽 2개는 에이전트가 설 기반(컴퓨터·동작 공간), 가운데 4개는 유한한 컨텍스트를 관리하는 핵심, 오른쪽 2개는 시간이 지나며 스스로 나아지는 방향이다. 화살표는 "사람이 짜는 것 → 모델이 흡수"로 가는 Bitter Lesson 궤적.

02 · 핵심Multi-Layer Action Space

도구를 컨텍스트에 직접 정의하면 토큰을 잡아먹고, 기능이 겹쳐 모델을 혼란시킨다. 그래서 동작을 도구 호출 레이어에서 컴퓨터(OS)로 밀어내린다.

100개 도구 대신 bash 하나를 주면, 에이전트가 코드를 써서 수많은 동작을 엮는다. CodeAct 논문은 중간 결과를 거치지 않고 코드를 실행할 때 토큰이 절감됨을 보였다.

언제 쓰나

도구가 많아져 정의 토큰이 부담될 때(예: MCP 35 tools = 26K). 원자적 도구(bash·파일) 소수로 줄이고 나머지는 코드 실행으로.

LLM
atomic tools
bash / code
OS · CLI · scripts (무한 동작)

03 · 종합패턴이 합쳐진 루프

8패턴은 따로 노는 게 아니라 하나의 루프로 합쳐진다 — 초기화 → 반복(파일에 결과 기록) → 캐시 → 검증 → 추적(git) → 반성, 커지면 조율(sub-agent).

Martin의 결론 한 문장 — "컴퓨터를 주고 동작을 컴퓨터로 밀어내라. 파일시스템으로 offload·progressive disclosure 하라. sub-agent로 격리하라. 시간이 지나며 진화시키고, 캐시로 비용을 줄여라."

언제 쓰나

장기 실행(long-running) 에이전트. 단발성 작업엔 과하다 — 단순 워크플로우·프롬프트로 먼저 시도하고 안 될 때 이 루프로.

LLM
Plan / Init
Act → file
Verify
Reflect

Manus는 2024년 3월 이후 5번 재설계됐다(이후 Meta가 $2B+에 인수). 이게 Martin의 핵심 경고를 뒷받침한다 — 모델이 좋아질수록 harness를 단순하게 깎아내야 한다. 오늘의 정교한 scaffolding이 내일의 병목이 된다.

03
Patterns · 도입 전 평가

8가지 설계 패턴

01
Give Agents a Computer
"the fundamental abstraction is the CLI"

문제. LLM은 영속 저장·외부 연산·OS 수준 기본기를 직접 다룰 수단이 없으면 자율적으로 행동할 수 없다.

메커니즘. 파일시스템(영속 컨텍스트)과 셸(유틸·CLI·스크립트·자기작성 코드 실행)을 준다. Claude Code는 "네 컴퓨터에 산다", Manus는 e2b 가상 컴퓨터를 쓴다. Rauchg의 표현 — "코딩 에이전트의 근본 추상은 CLI다".

평가 관점. 샌드박스·권한·파일 영속성을 줄 수 있는 환경인가? 이게 안 되면 나머지 7개 패턴(특히 offload·evolve)이 대부분 작동하지 않는다 — 이 패턴이 토대다.

02
Multi-Layer Action Space
"expose bash, not 100 tools"

문제. 도구 정의를 컨텍스트에 직접 쌓으면 토큰을 잡아먹고, 기능이 겹쳐 모델이 잘못 고른다. GitHub MCP 서버는 35개 도구가 정의만으로 ~26K 토큰.

메커니즘. 동작을 도구 호출 레이어에서 컴퓨터로 밀어내린다. 원자적 도구(bash) 소수만 노출하고, 에이전트가 코드를 써서 동작을 엮는다. Claude Code는 ~12개, Manus는 20개 미만. CodeAct(arXiv 2402.01030)는 중간 결과를 안 거치고 코드 실행 시 토큰 절감을 입증.

평가 관점. 도구 수가 임계(수십 개)를 넘어 정의 토큰이 부담되기 시작하면 이 패턴으로 전환할 신호. LangGraph BigTool처럼 도구를 인덱싱해 retrieval 하는 보강도 있다.

03
Progressive Disclosure
"essential first, details on demand"

문제. 에이전트가 모든 도구 정보를 동시에 알 필요는 없다. 전부 미리 로딩하면 컨텍스트 예산을 낭비한다.

메커니즘. 핵심만 먼저 주고 상세는 on-demand로 — --help 플래그, 인덱스 retrieval, 파일에 저장된 설명. Manus는 instruction에 유틸 목록만 주고 필요 시 --help 호출. Cursor는 MCP 설명을 폴더에 동기화해 필요할 때만 전체 스펙을 읽는다. Anthropic skills 표준은 SKILL.md의 YAML frontmatter만 보고 전체 파일을 읽을지 결정한다.

평가 관점. 도구·스킬 설명이 길수록 효과가 크다. "전부 system에 박기"의 대안으로, 메타데이터 → 본문 2단계 로딩을 설계할 수 있는가.

04
Offload Context
"write to disk, summarize last"

문제. 장기 실행 에이전트는 컨텍스트 창을 초과한다. 그런데 무지성 요약은 정보를 잃는다.

메커니즘. 중간 결과·오래된 궤적·보조 데이터를 파일시스템에 쓰고 선택적으로 다시 읽는다. 요약은 오프로딩의 효용이 떨어질 때만 적용 — 정보 손실을 늦춘다. Manus는 오래된 도구 결과를 파일로 빼고 나서야 요약하고, Cursor는 결과·궤적을 파일로 offload해 선택 retrieval. 일부는 계획을 파일에 써두고 주기적으로 다시 읽어 목표를 강화·검증한다.

평가 관점. "요약부터" 가 아니라 "offload 먼저, 요약은 최후"가 핵심 순서. 결과 크기 임계(예: 2KB)에서 자동으로 파일로 빼는 정책을 둘 수 있는가.

05
Cache Context
"cache hit rate = 가장 중요한 지표"

문제. 매 동작마다 컨텍스트를 선형 히스토리에 덧붙이면 토큰 재처리 비용이 폭증한다 — 캐시 없는 코딩 에이전트는 "비용상 성립 불가"(@trq212).

메커니즘. prompt caching으로 prefix에서 재개한다. Manus는 "cache hit rate가 프로덕션 에이전트의 가장 중요한 지표"라 단언하며, 캐시가 있으면 더 고성능 모델이 저비용 모델보다 오히려 싸질 수 있다고 본다.

평가 관점. 프롬프트 prefix를 안정적으로 유지하는 설계인가(캐시는 prefix 일치에 민감). 도구 정의·system을 앞단에 고정 배치하면 hit rate가 오른다.

06
Isolate Context
"sub-agents, git으로 진행 공유"

문제. 장기 작업은 한 에이전트 컨텍스트에 안 들어간다. 그런데 병렬 에이전트는 서로의 작업을 못 보면 충돌하는 결정을 내린다.

메커니즘. 격리된 컨텍스트·도구·지시를 가진 sub-agent에 위임하고, 진행은 git 히스토리 등으로 공유한다. Claude Code는 sub-agent가 서로 다른 이슈를 병렬 리뷰. Ralph Wiggum 루프(@GeoffreyHuntley)는 plan 만족까지 반복 — 초기화 에이전트가 환경(plan·tracking 파일)을 세팅하고 sub-agent가 plan의 개별 작업을 처리. Gas Town(@Steve_Yegge)은 "Mayor" 에이전트 + merge queue + 역할 분담으로 수십 개 Claude Code를 git 기반으로 조율한다.

평가 관점. 병렬화 가능한 독립 작업인가. Cognition은 "공유 컨텍스트 가시성 부재 + compaction 손실"을 경고 — 단일 에이전트로 풀리면 멀티에이전트를 피하라.

07
Evolve Context
"가중치가 아니라 컨텍스트를 학습"

문제. 에이전트는 경험에서 배워 나아져야 하는데, 많은 배포가 적응 불능으로 실패한다(arXiv 2512.16301).

메커니즘. 모델 가중치 대신 컨텍스트(prompt·memory·skill)를 시간에 따라 갱신한다 — 과거 궤적을 반성해 학습을 컨텍스트에 반영. GEPA(arXiv 2507.19457)는 궤적을 모아 점수 매기고 실패를 반성해 작업별 프롬프트 변형을 제안. Letta는 "토큰 공간의 지속 학습"과 궤적 반성으로 재사용 스킬을 파일로 저장. Martin 본인은 Claude Code 세션을 일기로 정제·반성해 CLAUDE.md를 갱신하는 실험을 했다.

평가 관점. 궤적을 저장·반성·반영하는 피드백 고리가 있는가. memory가 무한 증식하지 않게 distill하는 정책이 함께 필요하다.

08
Learned Context Management
"scaffolding이 모델에 흡수된다"

문제. 압축·sub-agent 생성·offload 시점·학습 갱신을 손으로 프롬프팅하는 건 노동집약적이고 최적도 아니다.

메커니즘. 수작업 scaffolding 대신 모델이 스스로 컨텍스트를 관리하게 한다. Recursive Language Model(RLM, arXiv 2512.24601)은 LLM이 자기 컨텍스트 관리를 학습할 수 있음을 보인다. Sleep-Time Compute(arXiv 2504.13171, Letta)는 에이전트가 오프라인에서 과거 세션을 반성해 memory·skill을 자동 갱신.

평가 관점. 이것이 방향성이다 — The Bitter Lesson대로 컴퓨트·모델 스케일링이 손으로 짠 기법을 추월한다. 지금 쌓는 scaffolding 중 무엇이 곧 불필요해질지를 의식하고 설계하라.

04
Operations · 도입 후 운영

운영 — 가정·처방·미해결

패턴을 안다고 운영이 되는 게 아니다. 각 패턴이 암묵적으로 깔고 있는 전제가 깨지는 지점과, 실제로 어떤 순서로 도입할지의 처방, 그리고 아직 아무도 풀지 못한 과제를 정리한다.

가정
패턴이 깔고 있는 전제와 붕괴점
"이게 깨질 때 패턴이 역효과"

"파일시스템이 항상 있다"(P1·P4·P7). Give-computer 계열은 영속 샌드박스를 전제한다. 서버리스·짧은 수명 컨테이너처럼 파일이 휘발되는 환경에서는 offload·evolve가 무력화된다 — 상태가 다음 iteration에 남지 않는다.

"prefix가 안정적이다"(P5). 캐시는 프롬프트 prefix 일치에 의존한다. 도구 정의·system을 동적으로 바꾸면 cache hit rate가 무너져, 캐시를 켜고도 비용이 안 준다. 캐시 효과는 "측정"해야 하지 가정하면 안 된다.

"sub-agent가 협력한다"(P6). 격리는 가시성을 희생한다. Cognition의 경고대로, 서로의 컨텍스트를 못 보는 병렬 에이전트는 충돌하는 결정을 내린다. compaction으로 정보를 잃으면 통합 단계에서 모순이 드러난다.

"진화가 수렴한다"(P7·P8). 궤적 반성이 항상 더 나은 컨텍스트를 만들진 않는다 — 잘못된 교훈이 memory에 쌓이면 오히려 악화된다. distill·검증 없는 evolve는 노이즈를 축적한다.

권장 에이전트 루프

8패턴을 실제 실행 순서로 엮으면 이렇게 된다. "단순부터 시작, 안 되면 추가"가 대원칙.

  1. Initialize — 환경 세팅

    plan 파일·tracking 파일을 만든다(P1). 컨텍스트의 닻을 파일에 박아 둔다.

  2. Iterate — 실행하고 파일에 기록

    원자적 도구(bash)로 동작하고(P2), 결과는 파일시스템으로 offload(P4), 상세는 on-demand로(P3).

  3. Cache — prefix 캐시 유지

    도구·system을 앞단에 고정해 cache hit rate를 높인다(P5). 캐시 효과는 측정한다.

  4. Verify & Track — 검증하고 추적

    stop hook으로 매 iteration 작업을 검증하고, 진행은 git 히스토리로 추적·공유한다(P6).

  5. Reflect & Coordinate — 반성하고 조율

    궤적을 일기·skill로 distill(P7). 작업이 커지면 sub-agent를 띄우고 Mayor류 오케스트레이터로 정렬(P6).

아직 아무도 풀지 못한 것

Learned context management

  • 모델이 scaffolding을 흡수할 수 있는가
  • 어디까지 손으로 짜고 어디부터 맡길까
  • Bitter Lesson의 시점 판단

Multi-agent coordination

  • 병렬 에이전트의 공유 컨텍스트 가시성
  • 충돌 결정 방지를 위한 능동 소통
  • compaction 손실 없는 통합

Long-running 추상

  • 관측(observability) 표준 부재
  • 디버깅 인터페이스 · HITL 모니터링
  • 실패 시 graceful degradation

대원칙

  • 프롬프트·단순 워크플로우 먼저
  • 안 될 때만 에이전트로
  • 모델 개선에 맞춰 harness를 깎아라

안티패턴 — 패턴을 오용하는 곳caution

  • 단발 작업에 8패턴 풀세트 — long-running이 아니면 과설계. 프롬프트·워크플로우로 충분하다.
  • 측정 없는 캐시 신뢰 — prefix가 흔들리면 hit rate 0. 캐시를 켰다고 비용이 주는 게 아니다.
  • 성급한 sub-agent — 단일 에이전트로 풀리는 걸 격리하면 충돌·통합 비용만 는다(Cognition).
  • 검증 없는 evolve — 잘못된 교훈이 memory에 쌓여 악화. distill·검증 고리가 없으면 끄는 게 낫다.
  • harness 고착 — 모델이 좋아져도 구조를 안 깎으면 scaffolding이 병목이 된다.

import subprocess
def run_bash(cmd: str) -> str:
    # 에이전트가 ls·grep·python -c ... 무엇이든 코드로 엮는다 (CodeAct)

import pathlib, textwrap
WORK = pathlib.Path(".agent"); WORK.mkdir(exist_ok=True)

def handle_result(name: str, raw: str) -> str:
    # Offload: 큰 결과는 파일로, 컨텍스트엔 경로 + head만
    if len(raw) > 2000:
        p = WORK / f"{name}.txt"; p.write_text(raw)
        return f"[offloaded → {p}] 미리보기:\n{raw[:300]}\n… 전체는 grep/sed로 조회"
    return raw

# Progressive disclosure: 도구 목록은 한 줄, 상세는 --help로 그때그때
SYSTEM = textwrap.dedent("""
    사용 가능 유틸: build, test, lint, deploy.

D · Isolate Context — sub-agent (P6)

def sub_agent(task: str, tools: list) -> str:
    # 격리된 컨텍스트 — 부모 히스토리를 물려주지 않는다
    msgs = [{"role": "user", "content": task}]
    return run_loop(msgs, tools)            # 각자 깨끗한 창에서 실행

def orchestrate(plan_file: str):
    # Initializer가 plan 파일을 만들고, sub-agent가 항목별로 처리 (Ralph 패턴)
    tasks = pathlib.Path(plan_file).read_text().splitlines()
    for t in tasks:
        result = sub_agent(t, TOOLS)
        # 진행은 git으로 공유 — 충돌 가시성 확보 (Gas Town의 git-backed tracking)
        run_bash(f"git add -A && git commit -m 'subtask: {t[:40]}'")
포인트. sub-agent는 격리된 창에서 돈다 — 부모 컨텍스트 오염을 막는다. 단, 가시성을 잃으므로 git 히스토리로 진행을 공유해 충돌을 줄인다. 단일로 풀리면 쓰지 마라(Cognition).
