01
TL;DR

한 줄로 이해하기

Milvus는 클라우드 네이티브 벡터 데이터베이스다. 스토리지(S3), 계산(QueryNode), 코디네이션을 분리해 각 레이어를 독립 스케일한다. 수십억 벡터에서 밀리초 단위 ANN 검색을 제공하며, 전문 검색과 스칼라 필터를 결합한 하이브리드 검색을 지원한다.

01

HNSW — 계층 탐색 그래프

HNSW(Hierarchical Navigable Small World)는 계층적 그래프로 ANN 검색을 수행한다. 최상위 레이어는 소수의 허브 노드로 구성되어 진입점 역할을 하고, 최하위 레이어는 모든 벡터를 포함한다. ef_construction: 빌드 시 탐색 후보 수(높을수록 정확하지만 빌드 시간 증가). M: 노드당 최대 엣지 수(메모리-정확도 트레이드오프).

02

Growing · Sealed 세그먼트

새로 삽입된 벡터는 Growing 세그먼트에 들어간다. Growing은 메모리에 존재하며 HNSW 없이 선형 스캔으로 검색된다. 크기 임계치(기본 512MB)를 넘으면 Sealed 세그먼트로 변환되고 HNSW/IVF 인덱스가 빌드된다. Sealed 세그먼트는 S3에 영속 저장된다.

03

컴퓨트-스토리지 분리

Milvus 2.x는 스토리지(S3/MinIO), 계산(QueryNode, IndexNode), 코디네이션(Coordinator)을 분리한다. QueryNode는 세그먼트를 로드하고 벡터 검색을 수행한다. 스케일 아웃 시 QueryNode만 추가하면 된다. Etcd가 메타데이터 저장소로 사용된다.

04

IVF-PQ — 대규모 메모리 절약

IVF(Inverted File Index): 벡터 공간을 클러스터로 나눠 관련 클러스터만 탐색. PQ(Product Quantization): 벡터를 서브스페이스로 분해해 압축 저장. IVF-PQ로 HNSW 대비 메모리 사용량을 10~100배 줄일 수 있다. 단, recall이 떨어지므로 메모리 제약이 클 때 선택한다.

05

DiskANN — 디스크 기반 십억 규모

Microsoft에서 개발한 그래프 기반 인덱스로 SSD에 그래프를 저장한다. 메모리에는 압축(PQ) 버전만 올리고 상세 거리 계산은 디스크에서 수행한다. 메모리 사용량이 HNSW의 1/10 수준으로 10억+ 규모 단일 노드 배포가 가능하다.

06

하이브리드 검색 · 재정렬

Milvus 2.4+에서 BM25(희소 벡터)와 Dense 벡터 검색을 동시에 수행할 수 있다. 희소 벡터는 SPARSE_INVERTED_INDEX로 색인된다. RRF(Reciprocal Rank Fusion) 또는 가중 점수 결합으로 두 결과를 합친다. BGE-M3 같은 모델은 Dense/Sparse/ColBERT 세 가지를 동시에 출력한다.

02Growing / Sealed 세그먼트

데이터 삽입 흐름: Proxy → Message Queue(Kafka/Pulsar) → DataNode가 Growing 세그먼트에 기록. 크기 임계치 도달 시 Seal → IndexNode가 인덱스 빌드 → S3 업로드.

검색 시 QueryNode는 Growing 세그먼트(선형 스캔)와 Sealed 세그먼트(인덱스) 결과를 합산한다. 실시간 삽입과 검색이 동시에 가능한 이유다.

세그먼트 크기 튜닝

dataCoord.segment.maxSize=512(MB). 너무 작으면 빈번한 인덱스 빌드, 너무 크면 메모리 부하. Growing 세그먼트의 선형 스캔 비용을 줄이려면 삽입 빈도를 조절한다.

03클러스터 아키텍처

Milvus는 4개의 코디네이터 역할을 분리한다: RootCoord(컬렉션 관리), DataCoord(세그먼트 관리), QueryCoord(세그먼트 할당), IndexCoord(인덱스 빌드 스케줄링).

메시지 큐(Kafka/Pulsar)가 DataNode와 QueryNode 사이의 버퍼 역할을 한다. 스케일 아웃 시 QueryNode와 DataNode만 늘리면 된다.

Standalone vs Cluster

Standalone: 단일 프로세스로 모든 컴포넌트 실행. 개발·소규모 배포용. Cluster: 수십억 벡터, 고가용성 요구 시. Kubernetes Helm 차트 제공.

04인덱스 유형 비교

메모리, 처리량, 정확도 세 축에서 트레이드오프가 발생한다. HNSW가 최고 recall을 제공하지만 메모리 소비가 크다. 수십억 규모에서는 DiskANN이 현실적인 선택이다.

AUTOINDEX

Zilliz Cloud(매니지드 Milvus)의 AUTOINDEX는 데이터 특성에 맞게 인덱스 파라미터를 자동 최적화한다. 자가 호스팅 시 데이터 분포 분석 후 수동 선택한다.

05하이브리드 검색

Milvus 2.4+에서 같은 컬렉션에 Dense 벡터와 Sparse 벡터 필드를 동시에 가질 수 있다. hybrid_search API로 두 검색을 한 번에 수행하고 RRF로 결합한다.

희소 벡터 필드(SPARSE_FLOAT_VECTOR)는 SPARSE_INVERTED_INDEX 인덱스로 BM25 스타일 전문 검색을 지원한다.

BGE-M3 활용

하나의 임베딩 모델이 Dense(1024차원), Sparse(BM25 스타일), ColBERT(다중 벡터) 세 가지를 동시 출력한다. 세 채널의 결과를 RRF로 결합하면 단독 대비 recall이 크게 향상된다.

06데이터 플로우 — Insert에서 검색까지

삽입된 벡터가 검색 가능한 상태가 되기까지 여러 컴포넌트를 거친다. Message Queue(Kafka/Pulsar)가 WAL 역할을 한다. QueryNode는 Growing Segment를 메모리에 보유하며 실시간 삽입을 처리한다. Segment 크기가 threshold(기본 512MB)를 넘으면 DataNode가 flush하여 S3에 Sealed Segment로 저장한다.

IndexNode가 Sealed Segment를 읽어 HNSW/IVF 인덱스를 비동기로 빌드한다. 빌드 완료 후 QueryNode가 인덱스를 로드하면 Sealed Segment로 서빙된다. 검색은 Growing + Sealed 양쪽을 동시에 쿼리하고 결과를 merge한다.

Flush 시점 제어

collection.flush()는 현재 Growing Segment를 즉시 Sealed로 변환한다. 대량 삽입 후 검색 전에 호출하면 인덱스 빌드가 시작된다. 단, flush가 잦으면 작은 Segment가 누적되어 compact가 필요해진다.

07Consistency Level

Milvus는 클러스터 환경에서 4가지 일관성 수준을 제공한다. Strong: 항상 최신 데이터를 보장. 내부적으로 최신 타임스탬프를 기다린다. Bounded Staleness: 최대 T초 이전까지 stale 허용. 성능과 일관성의 균형.

Session: 같은 세션 내 인과적 일관성 — 내가 삽입한 데이터는 내가 즉시 볼 수 있다. Eventually: 가장 빠름. 일시적인 stale read 허용. 벡터 검색의 특성상 1~2개 누락이 결과에 거의 영향을 주지 않아 99%의 use case에서 Eventually로 충분하다.

일관성 수준 선택

금융 추천(최신 거래 반영 필요): Bounded Staleness(T=1s). 사용자 개인화 추천: Session. 대규모 ANN 검색(정밀도보다 처리량): Eventually. Strong은 대부분 불필요한 오버헤드다.

03
Large Scale

대용량 처리

Milvus는 10억+ 벡터를 단일 클러스터에서 처리하도록 설계됐다. Zilliz에 따르면 100억 벡터 클러스터를 운영 중인 고객이 있다. 이 규모에서는 메모리 전략과 인덱스 선택이 전체 비용을 결정한다.

01 · Memory Tier
메모리 계층 — 비용과 성능의 균형
전략Hot/WarmDiskANN

HNSW는 벡터 데이터를 전부 메모리에 올린다. 1억 개의 768차원 float32 벡터만 약 300GB 메모리를 필요로 한다(벡터 원본 + 그래프 엣지). 이는 클라우드 비용 관점에서 부담이 크다.

Hot/Warm 전략: 자주 검색되는 컬렉션은 메모리에 유지하고(HNSW), 덜 사용되는 컬렉션은 S3에서 필요 시 로드한다. queryNode.loadMmap=true로 메모리 매핑을 사용하면 중간 지점이다.

DiskANN: SSD에 그래프를 저장하고 메모리에는 압축 버전만 유지한다. 1억 벡터 기준 메모리를 30GB 수준으로 줄일 수 있다. QPS는 HNSW 대비 낮지만 비용 효율이 훨씬 높다.

비용 기준 선택

QPS > 1000 + 저지연 필요: HNSW. QPS 100~1000 + 대규모: DiskANN. QPS < 100: IVF-PQ로 메모리 최소화.

02 · Index Build
인덱스 빌드 최적화 — CPU · 시간 절약
팁IndexNodeGPU Index

HNSW 인덱스 빌드는 CPU 집약적이다. 1억 벡터 기준 단일 CPU로 수 시간이 걸릴 수 있다. IndexNode를 독립 노드로 분리하면 검색 성능에 영향 없이 병렬 빌드가 가능하다.

GPU 인덱스(RAFT/FAISS-GPU): NVIDIA GPU로 인덱스 빌드 속도를 10~100배 향상. Milvus는 CAGRA(GPU HNSW 변형)를 지원한다. 빌드 시 GPU를 사용하고 검색은 CPU에서 수행하는 혼합 전략도 가능하다.

배치 삽입 패턴: 실시간 스트림보다 대량 배치 후 Flush + Compact → Index Build 순서가 빌드 효율이 높다. 온라인 검색 중에는 최소 인덱스 빌드 작업을 스케줄한다.

Compaction 트리거

작은 세그먼트가 많으면 검색 성능이 낮아진다. common.retentionDuration과 dataCoord.compaction 설정으로 자동 컴팩션을 조정한다. 대량 삽입 후 수동 collection.compact() 호출도 효과적이다.

03 · Scalar Filtering
스칼라 필터링 — pre-filter vs post-filter
전략Pre-filterPost-filter

벡터 검색에 expr로 스칼라 조건을 추가할 때 실행 전략이 중요하다. Pre-filter: 먼저 스칼라 조건을 만족하는 벡터 ID를 구하고 ANN을 수행. 필터 선택도가 높으면(많은 것이 걸러짐) 검색 공간이 줄어 빠르다.

Post-filter: ANN으로 후보를 구하고 스칼라 조건으로 필터. 필터 선택도가 낮으면(대부분 통과) 후보가 너무 줄어 k개를 못 채울 수 있다.

Milvus 2.4+에서 자동으로 비용 기반으로 전략을 선택한다. 수동으로 제어하려면 consistency_level과 search_params를 조정한다.

파티셔닝으로 필터 성능 향상

자주 쓰이는 스칼라 조건(예: tenant_id, category)으로 파티션을 나누면 검색 대상 세그먼트를 크게 줄일 수 있다. 파티션당 최대 4,096개까지 지원한다.

IVF nprobe16~64검색 시 탐색 클러스터 수. 클수록 recall 높고 느림
dataCoord.segment.maxSize512세그먼트 최대 크기(MB). Seal 트리거 임계치

common.retentionDuration86400데이터 보존 기간(초). Time Travel 기능에 영향
Milvus vs Qdrant vs Weaviate: Milvus는 최대 규모와 다양한 인덱스 유형이 강점. Qdrant는 Rust 기반으로 단순하고 빠른 배포가 강점(소~중규모). Weaviate는 모듈 시스템으로 GraphQL API와 다중 모달 지원이 강점. 자가 호스팅 소규모 프로젝트라면 pgvector(PostgreSQL 확장)도 충분하다.

01. 컬렉션 생성 — HNSW 인덱스

from pymilvus import MilvusClient, DataType

client = MilvusClient(uri="http://localhost:19530")

# 스키마 정의
schema = MilvusClient.create_schema(

schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True)
schema.add_field(field_name="embedding", datatype=DataType.FLOAT_VECTOR, dim=768)
schema.add_field(field_name="category", datatype=DataType.VARCHAR, max_length=64)
schema.add_field(field_name="score", datatype=DataType.FLOAT)

index_params = MilvusClient.prepare_index_params()

    field_name="embedding",
    index_type="HNSW",
    metric_type="COSINE",
    params={"M": 16, "efConstruction": 200},

index_params.add_index(

포인트. 스칼라 필터 필드(category)에도 INVERTED 인덱스를 생성한다. 필터 조건 실행 속도가 크게 향상된다. enable_dynamic_field=True로 스키마에 없는 필드도 저장할 수 있다.

02. 대량 삽입 — 배치 처리

insert
import numpy as np
from pymilvus import MilvusClient

client = MilvusClient(uri="http://localhost:19530")

def batch_insert(
    collection_name: str,
    embeddings: np.ndarray,
    metadata: list[dict],
    batch_size: int = 1000,
):
    total = len(embeddings)
    inserted = 0

    for i in range(0, total, batch_size):
        batch_emb = embeddings[i : i + batch_size]
        batch_meta = metadata[i : i + batch_size]

        data = [
            {
                "id": i + j,
                "embedding": batch_emb[j].tolist(),
                **batch_meta[j],
            }
            for j in range(len(batch_emb))
        ]

        result = client.insert(
            collection_name=collection_name,
            data=data,
        )
        inserted += result["insert_count"]

    # 인덱스 빌드를 즉시 트리거
    client.flush(collection_name=collection_name)
    return inserted
포인트. 대량 삽입 후 flush()를 호출해야 Growing 세그먼트가 Seal되고 인덱스 빌드가 시작된다. 배치 크기 1,000~5,000이 일반적으로 최적 처리량을 제공한다.

03. 벡터 검색 — 스칼라 필터 결합

search
def vector_search(
    query_vector: list[float],
    category: str,
    top_k: int = 10,
    ef: int = 64,
) -> list[dict]:
    results = client.search(
        collection_name="products",
        data=[query_vector],
        anns_field="embedding",
        search_params={
            "metric_type": "COSINE",
            "params": {"ef": ef},  # 런타임 ef 조정
        },
        limit=top_k,
        filter=f'category == "{category}"',  # 스칼라 필터
        output_fields=["id", "category", "score"],
    )

    return [
        {"id": hit["id"], "distance": hit["distance"], **hit["entity"]}
        for hit in results[0]
    ]
포인트. ef는 런타임에 변경 가능한 유일한 HNSW 파라미터다. 지연 요구에 따라 동적으로 조정할 수 있다. ef=64는 균형점이며, recall을 높이려면 128~256으로 올린다.

04. 하이브리드 검색 — Dense + Sparse

hybrid
from pymilvus import AnnSearchRequest, RRFRanker, WeightedRanker

def hybrid_search(
    dense_vector: list[float],
    sparse_vector: dict[int, float],  # BM25 스타일
    top_k: int = 10,
) -> list[dict]:
    # Dense ANN 요청
    dense_req = AnnSearchRequest(
        data=[dense_vector],
        anns_field="dense_embedding",
        param={"metric_type": "COSINE", "params": {"ef": 64}},
        limit=top_k * 3,
    )

    # Sparse BM25 요청
    sparse_req = AnnSearchRequest(
        data=[sparse_vector],
        anns_field="sparse_embedding",
        param={"metric_type": "IP"},
        limit=top_k * 3,
    )

    # RRF로 두 결과 결합
    ranker = RRFRanker(k=60)

    results = client.hybrid_search(
        collection_name="hybrid_products",
        reqs=[dense_req, sparse_req],
        ranker=ranker,
        limit=top_k,
        output_fields=["id", "title"],
    )

    return [
        {"id": hit["id"], "score": hit["distance"], **hit["entity"]}
        for hit in results[0]
    ]
포인트. RRFRanker(k=60)는 두 랭킹을 1/(60+rank)로 합산한다. WeightedRanker([0.7, 0.3])로 가중 평균을 쓸 수도 있다. BGE-M3 모델로 Dense와 Sparse 벡터를 동시에 생성하면 단일 모델로 하이브리드 검색을 구현할 수 있다.
