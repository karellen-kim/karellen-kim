01

한 줄로 이해하기

Fable 5와 Mythos 5는 같은 모델이고, 차이는 오직 안전장치다. 그리고 이 강한 모델을 실제로 길게 굴리는 방법은 화려한 프레임워크가 아니라 — LLM이 도구를 반복 호출하는 단순한 루프와, 그 루프의 컨텍스트를 관리하는 몇 가지 전략이다.

i

같은 코어, 두 개의 래퍼

Anthropic 공식 발표 기준 — Fable 5 = Mythos 5는 동일한 기반 모델이다. Fable은 안전장치가 적용된 일반 출시판, Mythos는 일부 영역에서 안전장치가 해제된 제한 공개판(Project Glasswing).

ii

Mythos-class = Opus 위의 새 티어

"작업이 길고 복잡할수록 Fable 5의 우위가 커진다"가 핵심 주장. 1M 토큰 컨텍스트 · 최대 128k 출력. Stripe는 5천만 줄 코드베이스 마이그레이션을 하루에 끝냈다고 보고.

iii

안전은 "차단"이 아니라 "폴백"

Fable 5는 AI 분류기로 위험 요청을 탐지하면 응답을 막는 대신 Claude Opus 4.8로 폴백한다. 평균 5% 미만 세션에서만 발동 — 95% 이상은 폴백 없이 Fable이 그대로 응답한다.

iv

에이전트 = LLM이 도구를 루프로 호출

Lance Martin(LangChain)은 Anthropic 정의를 인용한다 — 에이전트는 "LLM이 도구를 루프(loop)로 호출하는 것". Manus 기준 전형적 작업이 ~50 tool calls. 문제는 그 결과가 컨텍스트에 쌓여 성능을 떨어뜨린다는 것.

v

루프를 지탱하는 컨텍스트 4전략

Offloading(파일시스템에 저장 후 조회) · Reduction(compaction·요약) · Retrieval(동적 주입) · Isolation(sub-agent 격리). Karpathy의 표현으로 "다음 스텝에 딱 맞는 정보로 컨텍스트 창을 채우는 기술".

vi

가장 단순한 루프 — Ralph, 그리고 Bitter Lesson

Geoffrey Huntley의 "Ralph is a Bash loop" — while true로 같은 프롬프트를 반복 투입한다. Martin의 경고: harness를 과설계하지 마라. 더 강한 모델로 바꿔도 성능이 안 오르면 harness가 병목이다.

02
Structure

그림으로 보는 구조

00 · 모델 관계Fable = Mythos

둘은 같은 가중치다. 모델 자체가 두 개인 게 아니라, 하나의 Mythos-class 코어 위에 두 가지 안전 정책 래퍼가 씌워진 것이다.

Fable 5는 분류기 + Opus 4.8 폴백이 붙은 일반 출시판, Mythos 5는 사이버 방어자·승인된 연구자에게만 일부 안전장치를 해제해 제공하는 제한판.

언제 구분하나

일반 개발·제품에는 Fable 5. 사이버보안 방어 연구나 생물의학 가속처럼 안전장치가 오히려 막는 영역에서, 승인을 받은 경우에만 Mythos 5(Glasswing).

01 · 안전분류기 → 폴백 라우팅

Fable 5의 안전장치는 응답을 거부하는 게 아니라, AI 분류기가 위험 요청으로 판정하면 더 보수적인 Claude Opus 4.8이 대신 답하게 라우팅하는 구조다.

세 도메인에서 발동한다 — 사이버보안 · 생물/화학 · distillation. 평균 5% 미만 세션에서만 트리거되고, 95% 이상은 Fable이 그대로 응답한다.

왜 폴백인가

완전 차단은 정상 사용자까지 막는다. 위험 구간만 약한 모델로 우회시키면 능력은 최대로 열어두되 오용 상한은 Opus 수준으로 묶을 수 있다.

02 · 에이전트도구를 호출하는 루프

Lance Martin이 인용하는 에이전트의 정의는 단순하다 — LLM이 스스로 판단하고, 도구를 호출하고, 결과를 관찰하고, 다시 판단하는 것을 종료 조건까지 반복한다.

Manus 기준 한 작업이 ~50 tool calls. 매 호출의 결과가 컨텍스트에 쌓이므로, 루프가 길어질수록 컨텍스트 창이 차서 성능이 떨어진다 — 이게 다음 절의 4전략이 필요한 이유다.

언제 쓰나

단계 수를 미리 예측할 수 없는 개방형 작업, 자동 검증(테스트·린트)이 가능한 작업. 도구는 20개 미만의 원자적(atomic) 함수로 유지.

03 · 단순 루프Ralph의 자기참조

Ralph Wiggum 기법(Geoffrey Huntley)의 "자기참조"는 출력을 다시 입력으로 먹이는 게 아니다. 프롬프트는 매 iteration 동일하고, 변하는 것은 파일과 git 히스토리에 남은 이전 작업이다.

Claude Code 구현(ralph-wiggum 플러그인)에서는 Stop hook이 세션 종료를 가로채 같은 프롬프트를 되먹인다. 외부 bash 루프 없이 세션 안에서 루프가 돈다.

언제 쓰나

완료 기준이 자동 검증되는 well-defined 작업(테스트 GREEN까지). 인간 판단·설계 결정·프로덕션 디버깅에는 부적합.

Ralph의 핵심 통찰은 "deterministically bad in an undeterministic world" — 실패가 예측 가능하면, 프롬프트 튜닝으로 체계적으로 개선할 수 있다. 모델이 아니라 오퍼레이터의 프롬프트 작성 실력이 성패를 가른다는 게 README의 명시적 주장이다.

Safety Architecture · 도입 전 평가

Fable · Mythos 안전 아키텍처

Mythos-class는 "능력을 최대로 열되 오용 상한은 묶는다"는 비대칭 설계다. 그래서 안전장치가 모델을 약하게 만드는 게 아니라, 위험 구간에서만 더 약한 모델로 우회시킨다. 아래는 공식 발표에서 확인된 토폴로지와 수치다.

사이버보안. Mythos-class는 "취약점 발견·익스플로잇에 탁월"하고 agentic hacking 능력이 강하다고 명시된다. Fable에서는 공격적 사이버 작업을 차단하고 Opus 4.8로 폴백. 외부 레드팀 테스트에서 30종 jailbreak에 걸친 사이버공격 단발성 유해 요청 0건 응답으로 보고됐다.

생물 / 화학. 이 영역의 폴백은 발표문이 "의도적으로 overly broad"하다고 인정한다 — 정상적인 생물학 질문까지 막히는 부작용을 감수하고 넓게 차단한다. (별도 승인 프로그램으로 생물의학 연구자에게는 안전장치를 해제해 제공.)

Distillation. 모델을 무단 복제(추출)하려는 시도를 탐지·차단한다. Mythos-class 트래픽은 30일 보존이 의무이며 안전 목적으로만 사용(모델 학습에는 미사용), 30일 후 삭제.

가정
"안전장치는 능력을 깎지 않는다"

가정. 폴백 설계의 전제는 "위험 구간은 좁고, 거기서만 Opus로 우회하면 일반 사용은 영향이 없다"이다. 발표 수치(95%+ 무폴백)는 이 전제를 뒷받침한다.

깨질 때. 당신의 워크로드가 생물·화학·보안 인접 영역에 몰려 있으면 이야기가 달라진다. 생물/화학 폴백은 "overly broad"라고 공식 인정됐으므로, 정상적인 도메인 작업이 조용히 Opus 4.8 응답으로 대체될 수 있다 — 품질·일관성이 흔들리는데 에러가 나지 않아 눈치채기 어렵다.

처방. 도입 전, 실제 트래픽 샘플로 폴백 발동률을 측정하라. 발동된 요청이 Opus 4.8 응답이라는 걸 식별할 수 있는 신호(응답 특성·메타데이터)를 로깅하고, 도메인 인접 워크로드라면 별도 승인 프로그램(생물의학·사이버 Trusted Access)을 검토한다.

04
Effective Agent Design · 도입 후 운영

Lance Martin의 설계 루프

강한 모델을 손에 쥐었다고 좋은 에이전트가 되는 게 아니다. Lance Martin(LangChain)이 정리한 핵심은 — 에이전트는 도구를 호출하는 루프이고, 그 루프가 길어지면 컨텍스트가 차서 무너진다. 그래서 진짜 설계는 컨텍스트를 어떻게 관리하느냐에 있다.

Core 컨텍스트 엔지니어링 4전략 Manus 사례 · ~50 tool calls/task

Offloading

밖으로 빼기

도구 결과를 컨텍스트에 쌓지 않고 파일시스템에 저장 → 필요할 때 glob/grep으로 조회. 샌드박스에서 Bash·파일 도구 몇 개로 수많은 유틸을 실행해 도구 정의 비대화도 방지.

  • raw 결과는 파일로, 컨텍스트엔 경로만
  • 도구 < 20개 원자적 함수로 유지

Reduction

줄이기

Compaction — 오래된 도구 결과는 "full(원문)"에서 "compact(파일 경로 참조)"로 치환하고 최신 결과만 full 유지. 한계에 도달하면 schema 기반 요약으로 전체 궤적을 압축.

  • 최신은 full → 즉각 판단 근거 유지
  • 요약은 일관된 schema 객체로

Retrieval

가져오기

필요한 시점에 정보를 동적으로 주입. Martin은 "agentic search(에이전트가 직접 탐색) vs 사전 retrieval"의 선택을 강조 — 무엇을 미리 넣고 무엇을 그때그때 찾게 할지의 경계 설계.

  • 전부 미리 넣지 않는다
  • 탐색을 에이전트에 위임할지 판단

Isolation

격리하기

planner가 sub-agent에 작업 위임 — 각자 격리된 컨텍스트 창. 단순 작업엔 지시만, 파일시스템 접근이 필요한 복잡 작업엔 full 컨텍스트 공유. 단, Cognition의 "don't build multi-agents" 경고도 함께 인용.

  • 병렬화 가능 작업이 명확한 후보
  • 남용 금지 — 단일 에이전트 우선
가정
루프가 암묵적으로 깔고 있는 전제
"이게 깨질 때 루프가 무너진다"

"컨텍스트는 충분하다". 에이전트 루프는 도구 결과가 컨텍스트에 쌓여도 괜찮다고 가정한다. 깨지는 지점 — Manus 기준 ~50 tool calls면 결과 누적으로 성능이 저하된다. 이게 4전략(특히 offloading·compaction)이 없으면 긴 작업이 그냥 안 되는 구조적 이유다.

"완료 기준이 검증 가능하다". Ralph 같은 루프는 "언제 끝났는지"를 모델이 정직하게 판단한다고 가정한다. 깨지는 지점 — 완료 기준이 자동 검증되지 않으면(테스트·린트 없으면) 에이전트가 거짓 완료를 선언하거나 무한 루프에 빠진다. 그래서 Claude Code의 Ralph 구현은 "거짓 promise 금지"를 강하게 주입하고 --max-iterations를 escape hatch로 강제한다.

"harness가 클수록 좋다". 정교한 오케스트레이션이 성능을 올린다는 가정. Martin의 Bitter Lesson 반박 — 더 강한 모델로 바꿔도 성능이 안 오르면, 당신의 harness가 모델 역량을 제한하고 있는 것이다. 모델이 좋아지면 무너질 추상화를 미리 쌓지 마라.

운영 처방 — 어떤 루프를 언제 쓰나

작업 성격에 따라 루프 형태와 컨텍스트 전략을 고른다. 임계점을 측정으로 잡는 게 핵심.

  1. 먼저 단일 에이전트 + offloading

    도구 결과를 파일로 빼고 경로만 컨텍스트에. tool call 수가 ~50을 넘기 시작하면 compaction(full→compact) 도입. multi-agent는 이걸로도 안 될 때만.

  2. 완료가 자동 검증되면 Ralph 루프

    테스트·린트로 GREEN 판정이 되는 작업만. --completion-promise는 검증 가능한 사실로 설정하고, --max-iterations를 반드시 함께 건다.

  3. 병렬 가능 작업만 Isolation

    독립적으로 쪼개지는 작업(예: 코드리뷰 차원별)에만 sub-agent. 공유 상태·순차 의존이 있으면 단일 에이전트가 낫다.

  4. harness를 모델로 검증

    더 강한 모델로 바꿔 성능이 오르는지 측정. 안 오르면 harness가 병목 — 추상화를 걷어내는 방향으로 리팩토링.

안티패턴 — 루프 설계에서 자빠지는 곳caution

  • escape hatch 없는 Ralph 배포 — --max-iterations 없이 돌리면 완료를 못 만나 무한 루프. 비용이 무한히 증가한다.
  • 검증 불가 작업에 자율 루프 — "디자인을 더 좋게"처럼 자동 판정 불가한 목표는 루프가 수렴하지 않는다. 인간 체크포인트로.
  • 컨텍스트 전략 없이 긴 작업 — offloading/compaction 없이 50+ tool calls를 돌리면 컨텍스트가 차서 후반부 판단이 망가진다.
  • 성급한 multi-agent — Cognition "don't build multi-agents". 단일 에이전트 + 컨텍스트 관리로 풀리는 걸 분산시키면 디버깅만 어려워진다.

A · Ralph Stop hook — 루프의 심장

bash · 발췌 해부 
# stop-hook.sh — Claude가 세션을 끝내려 할 때 호출되는 Stop hook
HOOK_INPUT=$(cat)                          # stdin으로 hook 페이로드 수신
RALPH_STATE_FILE=".claude/ralph-loop.local.md"

if [[ ! -f "$RALPH_STATE_FILE" ]]; then
  exit 0                              # 상태파일 없음 = 활성 루프 없음 → 정상 종료 허용
fi

# 1) frontmatter(YAML)에서 iteration · max · promise 파싱
ITERATION=$(echo "$FRONTMATTER" | grep '^iteration:' | sed 's/iteration: *//')

# 2) 종료 조건 ① — 최대 반복 도달
if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]; then
  echo "🛑 Max iterations reached."
  rm "$RALPH_STATE_FILE"; exit 0     # 상태파일 삭제 → 루프 종료
fi

# 3) transcript에서 마지막 assistant 메시지의 text만 추출
LAST_OUTPUT=$(echo "$LAST_LINE" | jq -r '.message.content
  | map(select(.type=="text")) | map(.text) | join("\n")')

# 4) 종료 조건 ② — <promise> 태그가 정확히 완료문구와 일치할 때만
PROMISE_TEXT=$(echo "$LAST_OUTPUT" | perl -0777 -pe \
  's/.*?<promise>(.*?)<\/promise>.*/$1/s; s/^\s+|\s+$//g')
if [[ "$PROMISE_TEXT" = "$COMPLETION_PROMISE" ]]; then   # = 는 리터럴 비교(glob 아님)
  rm "$RALPH_STATE_FILE"; exit 0
fi

# 5) 미완료 → iteration++ 하고 "같은 프롬프트"를 block 사유로 되먹임
NEXT_ITERATION=$((ITERATION + 1))
PROMPT_TEXT=$(awk '/^---$/{i++; next} i>=2' "$RALPH_STATE_FILE")  # 본문 추출
jq -n --arg prompt "$PROMPT_TEXT" --arg msg "$SYSTEM_MSG" '{
  "decision": "block",       # ← 종료를 막는다
  "reason": $prompt,         # ← 이 프롬프트가 Claude에게 다시 전달됨
  "systemMessage": $msg
}'
포인트. 루프의 정체는 {"decision":"block","reason":$prompt} 한 줄이다 — Stop을 막고 동일 프롬프트를 되먹인다. 출력을 입력으로 잇는 게 아니라, 변한 파일을 다시 보게 하는 self-reference. 종료는 오직 max-iterations 또는 정확히 일치하는 <promise> 두 가지뿐.

C · 에이전트 루프 + 컨텍스트 Offloading

python · autonomous 
from anthropic import Anthropic
import json, pathlib

client = Anthropic()
WORK = pathlib.Path(".agent_work"); WORK.mkdir(exist_ok=True)

def run_tool(name, args) -> str:
    result = _execute(name, args)            # 실제 도구 실행
    # ── Offloading: 큰 결과는 파일로 빼고, 컨텍스트엔 경로 + 요약만 ──
    if len(result) > 2000:
        path = WORK / f"{name}_{hash(args) & 0xffff}.txt"
        path.write_text(result)
        return f"[saved to {path}] head: {result[:200]} … (grep/read로 조회)"
    return result

def agent(goal: str, max_steps: int = 50):   # Manus 기준 ~50
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):
        resp = client.messages.create(
            model="claude-fable-5",           # Mythos-class
            max_tokens=2048, tools=TOOLS, messages=messages,
        )
        if resp.stop_reason == "end_turn":
            return resp.content[0].text     # 종료 조건: 모델이 완료 선언

        messages.append({"role": "assistant", "content": resp.content})
        results = []
        for b in resp.content:
            if b.type == "tool_use":
                results.append({
                    "type": "tool_result", "tool_use_id": b.id,
                    "content": run_tool(b.name, b.input),   # offloading 적용
                })
        messages.append({"role": "user", "content": results})

    raise RuntimeError("max_steps reached")   # escape hatch
포인트. 루프 자체는 building-effective-agents의 agent loop와 같다. 차이는 run_tool의 offloading — 2KB 넘는 결과를 파일로 빼고 경로+head만 컨텍스트에 남긴다. 이것만으로 50-step 루프에서 컨텍스트 누적이 극적으로 줄어든다.
