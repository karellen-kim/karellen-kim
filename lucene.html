01
TL;DR

한 줄로 이해하기

루신은 역인덱스(Inverted Index) 기반 전문 검색 라이브러리다. Elasticsearch와 Solr는 모두 Lucene 위에서 돌아간다. Lucene이 어떻게 동작하는지 이해해야 Elasticsearch 튜닝과 장애 대응이 가능하다.

01

역인덱스 구조

Term → (DocId, Position, Offset) 매핑. 검색 시 텍스트를 토크나이즈한 뒤 역인덱스를 조회해 DocId 집합을 얻고, AND 쿼리는 교집합, OR 쿼리는 합집합으로 계산한다. Posting List는 DocId를 delta 인코딩으로 압축해 저장한다.

02

세그먼트 아키텍처

Lucene 인덱스는 여러 세그먼트의 합집합이다. 세그먼트는 불변(immutable)이다. 쓰기는 새 세그먼트를 생성하고, 삭제는 삭제 마커만 기록한다. 세그먼트 병합(merge)으로 공간을 회수하고 검색 성능을 최적화한다.

03

BM25 스코어링

TF-IDF를 계승한 BM25. 기본값 k1=1.2, b=0.75. 문서 길이 정규화가 포함된다. IDF는 코퍼스 전체 문서 수와 해당 term이 등장하는 문서 수로 계산하므로, 샤드가 다르면 IDF 값이 달라진다.

04

근접 검색 — Position Index

역인덱스에 위치(Position) 정보를 함께 저장한다. PhraseQuery는 두 토큰의 position 차이가 1인지 확인한다. SpanQuery로 슬롭(slop)을 지정하면 최대 N 토큰 거리 이내의 근접 일치를 허용한다.

05

NRT — Near Real-Time 검색

IndexWriter가 문서를 추가하면 메모리 버퍼에 먼저 쌓인다. Flush 시 새 세그먼트가 생성되고, DirectoryReader.openIfChanged()가 이를 감지한다. 새 IndexSearcher로 교체하면 검색에 반영된다. 커밋(fsync) 없이도 검색 가능하다.

06

FST — Term Dictionary 압축

Term Dictionary를 Finite State Transducer(FST)로 압축한다. 1,000만 term을 수십 MB에 저장하고, O(term length) 시간에 조회한다. 공통 prefix를 공유하는 DAG(Directed Acyclic Graph) 구조다. Lucene의 높은 메모리 효율의 핵심이다.

02
Architecture

그림으로 보는 구조

01역인덱스 구조

문서 컬렉션을 토크나이즈해 Term → Posting List를 구성한다. 각 Posting에는 DocId, Term Frequency, Position이 포함된다. 쿼리 실행 시 관련 Term들의 Posting List를 가져와 교집합(AND) 또는 합집합(OR)을 계산한다.

Posting List는 DocId를 오름차순으로 정렬해 delta 인코딩으로 압축한다. 예: [1, 3, 7] → [1, 2, 4]. VInt로 인코딩하면 작은 숫자는 1바이트로 표현된다.

AND 쿼리 최적화

여러 term의 AND 조건은 Posting List가 가장 짧은 term부터 순회한다. 작은 집합을 기준으로 순차 탐색하면 불필요한 비교를 줄인다.

Term Dictionary → Posting List

doc3
pos:2,5
lucene
doc1
doc2
pos:1,3
search
doc2
doc3
pos:4,1
쿼리: "kafka AND lucene" → doc1 (교집합)

02세그먼트 아키텍처

IndexWriter는 문서를 메모리 버퍼에 쌓다가 임계값(기본 16MB) 또는 시간 주기로 Flush한다. Flush 시 새로운 불변 세그먼트가 생성된다. IndexReader는 모든 세그먼트를 합쳐 검색한다.

Merge Policy가 주기적으로 유사한 크기의 세그먼트를 합쳐 세그먼트 수를 줄인다. 병합 중에도 기존 세그먼트로 검색이 계속된다. 병합 완료 후 기존 세그먼트가 삭제된다.

세그먼트 수 vs 검색 성능

검색은 모든 세그먼트를 순회하므로 세그먼트가 많을수록 느려진다. Force Merge로 세그먼트 수를 1개로 줄이면 읽기 전용 인덱스에서 최적 성능을 낼 수 있다.

flush↓
Seg A2MB
Seg B1.8MB
Seg C120MB
TieredMergePolicy → Seg A+B 병합
Seg DA+B merged (3.8MB)
Seg C120MB
IndexReader: 모든 세그먼트 합집합 검색

03Lucene 파일 포맷

하나의 세그먼트는 역할별로 분리된 파일들로 구성된다. .tim/.tip은 Term Dictionary(FST), .doc는 Posting List(DocIDs), .pos는 Position Index다.

DocValues(.dvd/.dvm)는 집계·정렬에 특화된 열 지향(columnar) 저장소다. Stored Fields(.fdt/.fdx)는 검색 결과 반환용 원본 문서를 저장한다. 두 저장소는 목적이 완전히 다르다.

Norms — 필드 길이 정규화

.nvd/.nvm에 저장된 Norms는 BM25의 필드 길이 정규화에 사용된다. 집계 전용 필드(keyword, numeric)는 Norms를 비활성화(norms: false)하면 인덱스 크기를 줄일 수 있다.

04NRT — Near Real-Time 검색 흐름

IndexWriter.addDocument() 호출 후 즉시 검색되지 않는다. Flush가 발생해야 새 세그먼트가 생기고, DirectoryReader.openIfChanged()로 새 세그먼트를 감지해야 한다.

Elasticsearch의 refresh_interval=1s(기본값)는 이 Flush 주기다. 인덱싱 직후 검색 결과가 없는 현상은 refresh가 아직 일어나지 않은 것이다. _refresh API를 명시적으로 호출하면 즉시 반영된다.

Commit vs Refresh 차이

Refresh는 새 세그먼트를 검색에 노출(메모리). Commit은 세그먼트를 디스크에 fsync해 영속화. Elasticsearch는 기본 5분마다 Commit한다. Commit 없이도 검색은 된다.

Document → IndexWriter.addDocument()
↓ 메모리 버퍼 (즉시 검색 불가)
Flush (refresh_interval 또는 버퍼 임계값)
↓ 새 세그먼트 생성 (디스크)
DirectoryReader.openIfChanged()
↓ 새 IndexSearcher 생성
IndexSearcher.search() → 결과 반환
Commit(fsync)은 별도 — 검색과 무관
FST vs Trie 차이: 일반 Trie는 공통 prefix만 공유하지만 FST는 suffix도 공유한다. 예: "mop", "moth", "stop", "star" 4개 단어를 FST로 표현하면 shared suffix로 상태 수가 Trie의 절반 이하가 된다. Lucene이 수천만 term을 수십 MB에 적재할 수 있는 이유다.
03
Large Scale

대용량 처리

Wikipedia 전체 텍스트 인덱스는 약 21M 문서, 50GB Lucene 인덱스로 쿼리 p99 10ms 미만이다. Elasticsearch는 Lucene 위에서 수십 TB 인덱스를 운영한다. 이 수치의 배경에 있는 Merge 전략, DocValues 설계, 설정 파라미터를 살펴본다.

01 · Merge Policy
세그먼트 Merge 전략 — TieredMergePolicy vs LogByteSizeMergePolicy
기본값 Elasticsearch Lucene 9.x

TieredMergePolicy(기본): 세그먼트를 크기 계층으로 분류하고, 동일 계층 내 인접 크기끼리만 병합한다. Elasticsearch 기본값 maxMergeAtOnce=10, segmentsPerTier=10이다. 계층 수가 적을수록 세그먼트 수가 적어진다.

LogByteSizeMergePolicy: 세그먼트 크기를 로그 스케일로 보고 병합한다. 예측 가능한 동작이지만 TieredMergePolicy보다 세그먼트 수 조절 능력이 떨어진다.

샤드 크기 권장값: 10~50GB/shard. 너무 작으면 세그먼트 수 폭증, Merge 오버헤드 과다. 너무 크면 Merge 시간 증가, 복구 지연. Elasticsearch 권장 최대 샤드 크기는 50GB다.

Force Merge 전략

더 이상 쓰기가 없는 과거 시계열 인덱스는 _forcemerge?max_num_segments=1로 세그먼트를 1개로 병합한다. 검색 성능이 극적으로 향상된다. 단, Force Merge 중에는 쓰기 처리량이 감소한다.

02 · DocValues
DocValues와 집계 — 역인덱스와 열 지향 저장의 역할 분리
함정 Elasticsearch fielddata OOM

역인덱스는 검색용, DocValues는 집계·정렬용이다. 이 역할 분리를 이해하지 못하면 Elasticsearch에서 힙 OOM이 발생한다.

text 필드에서 집계를 시도하면 Elasticsearch는 역인덱스를 힙 메모리에 역변환(fielddata=true)해야 한다. 1,000만 문서 × 평균 10 토큰이면 힙 수 GB를 순식간에 소모한다. text 필드에는 집계하지 않는다는 원칙을 반드시 지켜야 한다.

DocValues는 keyword, numeric, date 필드에 기본 활성화된다. 열 지향 구조로 디스크에 저장하고 mmap으로 OS 페이지 캐시를 통해 접근한다. 집계 쿼리가 읽는 데이터가 페이지 캐시에 상주하면 I/O 없이 처리된다.

multi-field 패턴

text 필드에 fields: {keyword: {type: keyword}}로 sub-field를 추가한다. 전문 검색은 text 필드로, 집계·정렬은 keyword sub-field(DocValues)로 수행한다.

fielddata (비권장)
역인덱스 → 힙 역변환
메모리 상주 필수
OOM 위험
DocValues (권장)
열 지향 디스크 저장
mmap → OS 페이지 캐시
힙 사용 없음
text 필드 집계 → fielddata OOM
keyword 필드 집계 → DocValues 안전
03 · Configuration
핵심 설정 참조표 — Elasticsearch 기준
파라미터 권장값 설명
index.refresh_interval -1 (인덱싱 중) 기본 1s. 벌크 인덱싱 시 -1로 비활성화 → 완료 후 복구
index.number_of_replicas 0 (인덱싱 중) 초기 인덱싱 시 0으로 줄이고 완료 후 복구. 처리량 2배 향상

Lucene Codec: Lucene 9.x 기본 Codec은 Lucene90PostingsFormat이다. 압축 강도는 BEST_SPEED(기본)와 BEST_COMPRESSION(Deflate65) 중 선택한다. BEST_COMPRESSION은 인덱스 크기 20~40% 감소, 쓰기/읽기 CPU 15~25% 증가. 검색 빈도가 낮고 저장 비용이 중요한 냉장 데이터에 적합하다.
04
Gotchas

Gotchas

가정
세그먼트 폭증 — 왜 인덱싱 후 검색이 느려지는가
"refresh_interval=1s + 대량 인덱싱 = 재앙"

메커니즘. refresh_interval=1s(기본값)이면 초당 1개의 세그먼트가 생성된다. 1시간 대량 인덱싱을 하면 3,600개의 세그먼트가 생긴다. Elasticsearch 쿼리는 모든 세그먼트를 병렬로 순회한다. 세그먼트 수에 비례해 쿼리 지연이 증가한다. TieredMergePolicy가 백그라운드로 병합하지만, 인덱싱 속도를 따라잡지 못하면 세그먼트 수가 계속 증가한다.

refresh_interval=1s (기본)
... 수백~수천 개
쿼리 지연 수십~수백ms
refresh_interval=-1 + Force Merge
쿼리 지연 1~5ms

처방 — 3단계. (1) 벌크 인덱싱 전: PUT /인덱스/_settings로 refresh_interval: "-1", number_of_replicas: 0. (2) 인덱싱 완료 후: POST /인덱스/_forcemerge?max_num_segments=1. (3) 설정 복구: refresh_interval: "1s", number_of_replicas: 1. 이 순서를 지키면 인덱싱 처리량 2~5배, 검색 지연 10배 이상 개선된다.

가정
fielddata 힙 OOM — text 필드 집계 절대 금지
"text 필드에 aggregation = 힙 폭발"

무엇이 일어나는가. Elasticsearch에서 text 필드에 terms aggregation을 실행하면 기본적으로 오류가 난다 — fielddata=false가 기본이기 때문이다. fielddata: true로 활성화하면 역인덱스 전체를 힙 메모리에 역변환해서 올린다. 1,000만 문서, 평균 10 토큰이면 수 GB의 힙이 즉시 소모된다. 이것이 GC 압박 → 서비스 응답 지연 → OOM Killer로 이어진다.

가정이 깨지는 순간. text 필드에 집계가 필요하다는 요구사항이 생겼을 때 fielddata: true로 설정하면서 시작된다. "일단 되니까" 운영하다가 데이터가 늘면서 힙 사용량이 비선형으로 증가한다. JVM 힙의 40~60%를 fielddata가 점령한 상태에서 트래픽 피크가 오면 OOM이 발생한다.

처방. text 필드에 fields sub-field를 추가한다: {"type": "text", "fields": {"raw": {"type": "keyword"}}}. 전문 검색은 content 필드로, 집계·정렬은 content.raw keyword 필드로 수행한다. keyword 필드는 DocValues가 기본 활성화되므로 힙 없이 집계된다. 인덱스 매핑 설계 단계에서 이 원칙을 적용해야 한다 — 이미 생성된 인덱스의 매핑은 변경할 수 없다.

가정
BM25 스코어 비교 불가 — 크로스 샤드 스코어링 왜곡
"IDF는 샤드별 로컬 통계 — 전체가 아니다"

IDF가 왜 다른가. BM25의 IDF(Inverse Document Frequency)는 해당 샤드의 문서 수와 term 등장 문서 수로 계산한다. 샤드 A에 "machine learning"이 많고 샤드 B에 적다면, 샤드 B에서 "machine learning"의 IDF가 더 높게 계산된다. 결과적으로 동일한 문서라도 어느 샤드에 위치하느냐에 따라 스코어가 달라진다.

가정이 깨지는 구체적 시나리오. 5개 샤드로 구성된 인덱스에서 top-10 결과를 가져온다. 각 샤드는 로컬 IDF로 계산한 상위 결과를 coordinator에 보낸다. Coordinator는 이것을 병합해 최종 top-10을 만든다. 샤드별 데이터 분포가 불균일하면 전체 코퍼스 기준 top-10과 다른 결과가 나온다.

처방 2가지. (1) search_type=dfs_query_then_fetch: 1단계에서 모든 샤드의 term 통계를 수집해 전체 IDF를 계산한 뒤 2단계에서 검색한다. 네트워크 라운드트립 1회 추가, 정확도 향상. (2) 데이터 볼륨이 충분하면 샤드 1개로 운영한다 — IDF가 항상 전체 코퍼스 기준이 된다. 단, 단일 샤드는 수평 확장이 불가하다.

가정
Analyzer 불일치 — 인덱싱과 쿼리의 변환이 다르면 매칭 실패
"같은 단어인데 왜 안 찾히지?"

메커니즘. Lucene은 인덱싱 시와 쿼리 시 모두 Analyzer를 통해 텍스트를 변환한다. 인덱싱 시 standard analyzer는 "Running"을 "running"으로 소문자화해 저장한다. 쿼리 시 다른 analyzer(또는 분석 없음)를 사용하면 "Running" 그대로 역인덱스를 조회한다. "running"이 있어도 "Running"을 찾으면 매칭이 실패한다.

자주 발생하는 상황. (1) match 쿼리 대신 term 쿼리를 사용할 때: term은 분석 없이 그대로 조회한다. term: {content: "Running"}은 저장된 "running"과 매칭 안 된다. (2) keyword 필드에 match 쿼리: keyword 필드는 분석 없이 저장하므로 대소문자를 그대로 보존한다. (3) 인덱스 재생성 시 analyzer를 바꾸면 기존 문서와 새 문서의 토크나이제이션이 달라진다.

처방. GET /인덱스/_analyze API로 실제 토큰을 확인한다. 매핑에서 search_analyzer를 명시적으로 지정해 인덱싱 analyzer와 동일하게 맞춘다. term 쿼리는 keyword 필드에만, match 쿼리는 text 필드에만 사용한다는 원칙을 팀 전체가 공유한다.

Lucene Java — IndexWriter & TieredMergePolicy

lucene 9.x 
// Lucene 9.x 기준 — Maven: org.apache.lucene:lucene-core:9.x
import org.apache.lucene.analysis.standard.StandardAnalyzer;
import org.apache.lucene.document.*;
import org.apache.lucene.index.*;
import org.apache.lucene.store.MMapDirectory;

var analyzer = new StandardAnalyzer();
var config = new IndexWriterConfig(analyzer);
config.setOpenMode(IndexWriterConfig.OpenMode.CREATE_OR_APPEND);

// TieredMergePolicy 튜닝 — SSD 환경 기준
var mergePolicy = new TieredMergePolicy();
mergePolicy.setMaxMergeAtOnce(5);       // 기본 10 → 5로 낮춰 Merge I/O 분산
mergePolicy.setSegmentsPerTier(5.0);    // 기본 10 → 5로 낮춰 세그먼트 수 감소
config.setMergePolicy(mergePolicy);

// 인덱싱 중 Refresh 비활성화 → IndexWriter 레벨에서는 commitOnClose 제어
config.setCommitOnClose(true);

try (var directory = MMapDirectory.open(Path.of("/data/index"));
     var writer = new IndexWriter(directory, config)) {

    var doc = new Document();

    // 검색용 역인덱스 — position 포함
    doc.add(new TextField("title", "Apache Lucene Deep Dive", Field.Store.YES));

    // 집계·정렬용 DocValues (역인덱스 없음)
    doc.add(new SortedDocValuesField("category", new BytesRef("search")));

    // 숫자 범위 쿼리용 (BKD Tree로 저장됨)
    doc.add(new LongPoint("timestamp", System.currentTimeMillis()));

    writer.addDocument(doc);
    writer.commit();  // fsync — 생략하면 검색은 되지만 재시작 시 손실
}
TieredMergePolicy 튜닝 핵심. segmentsPerTier를 낮추면 세그먼트 수가 줄어 검색 속도가 향상되지만 Merge 빈도가 증가한다. SSD 환경에서는 max_thread_count를 CPU 코어수/2로 올려 Merge를 병렬화한다.

Elasticsearch Python — BM25 + kNN 하이브리드 RRF

elasticsearch 8.x 
from elasticsearch import Elasticsearch
import numpy as np

es = Elasticsearch("https://localhost:9200")

# 쿼리 임베딩 (실제로는 모델 추론)
query_vector = np.random.rand(768).tolist()

# 하이브리드 검색: BM25 + kNN RRF (Reciprocal Rank Fusion)
# Elasticsearch 8.9+에서 retriever API 사용
response = es.search(
    index="articles",
    body={
        "retriever": {
            "rrf": {
                "retrievers": [
                    {
                        "standard": {
                            "query": {
                                "match": {"content": "lucene inverted index"}
                            }
                        }
                    },
                    {
                        "knn": {
                            "field": "embedding",
                            "query_vector": query_vector,
                            "num_candidates": 100,  # HNSW ef_search
                        }
                    }
                ],
                "rank_window_size": 50,   # 각 retriever에서 가져올 후보 수
                "rank_constant": 60,      # RRF k 파라미터 (기본 60)
            }
        },
        "size": 10,
    }
)

for hit in response["hits"]["hits"]:
    print(f"score={hit['_score']:.4f} id={hit['_id']}")
RRF(Reciprocal Rank Fusion) 핵심. BM25 순위와 kNN 순위를 각각 1/(k+rank)로 변환해 합산한다. 두 스코어의 스케일이 달라도 순위 기반 합산이므로 정규화가 불필요하다. rank_constant=60은 순위 격차 완화 계수다.

세그먼트 진단 & 벌크 인덱싱 튜닝

ops 
import requests

ES = "http://localhost:9200"
INDEX = "articles"

# 1. 세그먼트 현황 확인 — 수가 많으면 검색이 느린 원인
r = requests.get(f"{ES}/_cat/segments/{INDEX}?v&h=segment,size,docs.count,docs.deleted")
print("=== 세그먼트 현황 ===")
print(r.text)

# 2. 벌크 인덱싱 최적화 설정 적용
requests.put(f"{ES}/{INDEX}/_settings", json={
    "index": {
        "refresh_interval": "-1",        # 자동 refresh 비활성화
        "number_of_replicas": "0"       # 복제 비활성화 → 인덱싱 처리량 2배
    }
})
print("[OK] 인덱싱 최적화 설정 적용")

# ... 벌크 인덱싱 수행 ...

# 3. Force Merge — 세그먼트 1개로 병합 (읽기 전용 인덱스 최적화)
#    주의: 대용량 인덱스는 수십 분 소요. 운영 중 실행 시 I/O 급증
r = requests.post(f"{ES}/{INDEX}/_forcemerge?max_num_segments=1")
print(f"[OK] Force Merge: {r.status_code}")

# 4. 설정 복구
requests.put(f"{ES}/{INDEX}/_settings", json={
    "index": {
        "refresh_interval": "1s",
        "number_of_replicas": "1"
    }
})
print("[OK] 설정 복구 완료")

# 5. Analyzer 검증 — 실제 토큰 확인
r = requests.post(f"{ES}/{INDEX}/_analyze", json={
    "analyzer": "standard",
    "text": "Running Lucene Indexer"
})
tokens = [t["token"] for t in r.json()["tokens"]]
print(f"토큰: {tokens}")  # ['running', 'lucene', 'indexer']
벌크 인덱싱 순서가 중요하다. refresh 비활성화 → 인덱싱 → force merge → 설정 복구 순서를 반드시 지킨다. Force Merge를 먼저 하면 이후 인덱싱이 다시 세그먼트를 쪼개고, refresh를 복구하기 전에 force merge하면 백그라운드 merge가 방해받는다.
