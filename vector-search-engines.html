01

한 줄로 이해하기

벡터 검색 엔진의 모든 결정은 Recall · Latency · Memory · Build cost 4축의 트레이드오프 위에서 좌표를 찍는 일이다. 알고리즘(HNSW · IVF · DiskANN · PQ)이 그 곡선의 어느 영역에 강한지를 먼저 알아야 하고, 엔진(Milvus · Vespa · Qdrant · pgvector …)은 그 알고리즘을 어떤 운영 모델로 감싸느냐의 차이다. billion-scale + hybrid + RAG + real-time을 동시에 요구하면 단일 엔진은 거의 답이 없다 — 티어 분리가 정답.

i

한 줄 정의 — O(N)과 O(log N) 사이

정확한 k-NN은 brute-force O(N). ANN은 그 정확도를 살짝 포기하고 O(log N)에 가까운 속도를 얻는다. "Recall을 얼마나 양보하느냐 ↔ Latency가 얼마나 줄어드느냐"가 모든 엔진의 본질적 결정.

ii

네 가지 근본 트레이드오프

Recall ↔ Latency (ANN 파라미터 ef_search·nprobe), Memory ↔ Recall (양자화 FP32→INT8→PQ→BQ), Build ↔ Query (ef_construction·M), Dynamic ↔ Static (real-time insert 지원 여부). 운영의 모든 고민은 이 네 축 중 하나에 매핑된다.

iii

알고리즘 — HNSW가 default, 한계 시 분기

일반 ANN: HNSW (recall 0.95+, latency 1~5ms, 메모리 1.5~3x). 메모리 압박: IVF-PQ (32x 압축). billion-scale: DiskANN (SSD 활용). 메모리 무제한 + 동적: IVF-Flat. RAM이 받쳐주면 거의 항상 HNSW가 답.

iv

엔진 — 알고리즘은 비슷, 운영 모델이 차이

대부분 HNSW 사용. 결정적 차이는 hybrid 표현력 · filter 통합 · 분산 · 운영 모델. Vespa/OpenSearch는 hybrid 강함, Qdrant는 filter 강함, Pinecone은 운영 0이지만 lock-in. pgvector는 Postgres에 흡수돼 트랜잭션 무료 — 작은 RAG에 황금.

v

4 워크로드 동시 충족은 거의 불가능

billion-scale + hybrid + RAG + real-time 네 가지를 한 엔진에 다 넣으려 하면 운영 복잡도가 폭주. 현실적 해법은 티어 분리: billion 검색 = Vespa/OpenSearch, RAG 캐시 = Qdrant, 트랜잭셔널 메타 = pgvector. 같은 SLA를 강제하지 마라.

vi

가장 흔한 함정 — selectivity 측정 누락

"pre-filter면 빠르다"는 일반화 → 거짓. filter selectivity 1%면 graph traversal 깨져 recall 폭락, 50%면 brute-force와 비슷. sweet spot은 5~20%. 측정 없이 결정하면 latency만 보고 잘못된 선택을 한다. Recall@k는 모든 결정의 출발점.

02 · 알고리즘주요 ANN 알고리즘 비교

각 알고리즘은 4축 곡선의 다른 좌표 — HNSW는 그래프 기반으로 latency·recall에 강하고 메모리 비쌈, IVF는 클러스터링으로 메모리·동적성에 유리, DiskANN은 SSD로 메모리 부담 해결.

06 · Pre-mortem6개월 뒤 트래픽 10x — 무엇이 먼저 깨지나

벡터 검색 시스템의 임계치 도달 순서. 메모리가 항상 가장 먼저. HNSW가 RAM을 못 들어가는 순간 latency가 100x 폭주.

예방의 핵심: 각 임계치의 trigger 지표를 미리 monitoring. memory headroom < 20%면 양자화·DiskANN 검토, network fan-in 시 tail latency가 dominate하면 sharding 전략 재검토.

가장 흔한 실수

"CPU가 먼저 깨질 것"이라 생각하는 것. 벡터 검색은 거의 항상 메모리 우선 → 네트워크 → CPU 순. CPU 모니터링만 보면 메모리 폭발 못 잡는다.

벡터 검색에서 가장 반직관적인 사실 — "알고리즘 자체보다 filter selectivity가 latency에 더 큰 영향을 준다". selectivity 1% 강한 필터에서 HNSW graph traversal이 깨져 recall이 폭락, 50% 약한 필터에서는 brute-force와 거의 같은 비용. "우리 워크로드의 filter selectivity 분포는 무엇인가"가 엔진 선택보다 먼저 묻혀야 할 질문.

참고
HNSW (Hierarchical Navigable Small World)
"에이치엔에스더블유"

아이디어. Skip list를 그래프 위로 확장. top layer는 sparse, 점차 dense해지는 multi-layer graph. 쿼리는 top에서 greedy descent로 거친 nearest 찾고, 아래 layer에서 점점 정밀하게. O(log N) 탐색.

핵심 파라미터. M(노드당 out-edge 수, 메모리 직접 비례), ef_construction(빌드 시 후보 큐 크기, recall ceiling을 결정), ef_search(런타임 후보 큐, 동적 조절 가능).

강점. 일반 ANN에서 가장 좋은 recall/latency 균형. ef_search로 런타임 recall/latency 곡선 그릴 수 있음.

약점. 메모리 1.5~3x raw. filter와 결합 시 graph traversal 깨짐 (selectivity 의존). 동적 삭제는 tombstone + 주기적 rebuild.

참고
Product Quantization (PQ)
"피큐"

아이디어. 768-dim 벡터를 m개의 sub-vector로 쪼개고 (예: m=96 → 각 8-dim), 각 sub-vector를 256개 centroid로 표현. 한 벡터당 m bytes로 압축 — 3072 byte → 96 byte = 32× 압축.

거리 계산. 쿼리 시 sub-vector × centroid의 distance lookup table을 미리 만들어 두고, 인덱스의 m개 byte를 indexing해서 합산. SIMD 친화적.

트레이드오프. m이 클수록 압축률 좋지만 sub-vector 표현력 부족 → recall 손상. sweet spot은 d/m = 4~8. d=768이면 m=96~192.

주의. PQ만으로는 recall 0.7~0.9 — 운영에선 first-stage PQ + second-stage exact re-rank가 정석. 그래서 IVF-PQ + re-rank 패턴이 흔하다.

참고
DiskANN (Vamana graph)
"디스크앤"

아이디어. Microsoft 2019 (Subramanya et al). HNSW와 유사한 Vamana 그래프(layer 없는 단일 그래프). 메모리에는 PQ-compressed sketch만, SSD에는 full-precision vector + neighbor list.

쿼리 흐름. ① greedy descent는 메모리 PQ로 빠르게, ② final re-ranking은 SSD에서 정확 거리 fetch. batch IO + async가 latency 핵심.

강점. billion-scale에서 HNSW 대비 메모리 1/10 수준. SSD IOPS만 받쳐주면 recall 거의 동등.

주의. NVMe 필수. 일반 SATA SSD에서는 latency 폭주. 빌드 시간이 HNSW보다 길다.

그래서 — 어떤 알고리즘부터?

HNSW로 시작 권장

  • RAM 충분 (벡터 수 × 차원 × 6 byte 미만)
  • recall > 0.95 필요
  • latency 5ms 이하 요구
  • insert/update 빈도 낮음 (시간 단위 reindex 허용)
  • filter selectivity가 5~20% 범위

HNSW 대신 다른 것 검토

  • RAM 한계 닥침 → DiskANN (NVMe 받쳐주면)
  • 극한 압축 필요 → IVF-PQ (recall 0.85 양보 가능 시)
  • real-time insert 많음 → IVF-Flat 또는 Qdrant HNSW 동적
  • filter selectivity 1% 미만 → partition별 인덱스 분리
  • recall 0.85로 충분 + 초저 latency → BQ + re-rank

GPU 최적화

GPU 최적화는 "더 빠른 하드웨어" 문제가 아니라 알고리즘 선택 자체를 바꾸는 일이다. CPU에서 좋은 HNSW가 GPU에서는 비효율, GPU-native CAGRA는 CPU에서 의미 없음. 어떤 작업에 GPU를 쓰느냐부터가 결정.

01 · 적합도GPU가 빠른 곳 vs 해로운 곳

벡터 검색의 모든 작업이 GPU에서 빠른 건 아니다. brute-force와 batched matrix 연산은 GPU의 동네, branchy graph traversal과 단일 쿼리는 CPU의 동네.

결정 규칙: 작업이 "많은 데이터에 동일한 연산을 동시 적용"으로 환원되면 GPU, "분기·포인터 추적이 많고 작은 작업 단위"면 CPU.

가장 큰 함정

PCIe transfer ~50μs + kernel launch ~10μs. 단일 쿼리에서는 이 오버헤드가 계산보다 크다 — GPU가 오히려 더 느림.

02 · 핵심 기술CAGRA · FAISS GPU · Tensor core

GPU 벡터 검색의 세 기둥. 알고리즘(CAGRA), 라이브러리(FAISS GPU), 하드웨어 가속(Tensor core + 양자화)의 조합.

도입 순서 권장: FAISS GPU로 기존 IVF-PQ를 GPU로 올려 검증 → CAGRA로 알고리즘 자체 교체 → Tensor core mixed precision으로 가속.

가장 큰 효과

CAGRA + INT8 양자화 + Tensor core 조합 시 single H100이 CPU 32 cores를 능가하는 경우가 흔하다. 운영 단순화도 같이 따라옴.

CAGRAcuVS · 2023~
GPU-native graph ANN. HNSW의 layer 구조 제거 + reverse-cuthill-mckee 정렬로 메모리 coalescing. Build 10×, query 10~100× 빠름 (vs CPU HNSW). Milvus 2.4+, Lucene 10+ 통합. 약점 — 단일 쿼리는 여전히 CPU HNSW가 더 낮은 latency.
FAISS GPU검증된 옵션
IndexFlatL2 → GpuIndexFlatL2, IndexIVFPQ → GpuIndexIVFPQ 단순 교체. Multi-GPU sharding (index_cpu_to_gpu_multiple) 지원. 학습은 5~20× 빠름. 마이그레이션 비용 낮음 — 가장 안전한 첫 도입.
Tensor core+ 양자화
H100/A100의 tensor core는 FP16/BF16/INT8 GEMM이 FP32보다 4~16× 빠름. Mixed precision (FP16 곱 + FP32 누적)으로 정확도 보존. INT8 PQ로 메모리 4× 절감. FAISS useFloat16=True, cuVS INT8 metric_type.

03 · 아키텍처Hot GPU + Cold CPU 계층

Billion-scale에 단일 GPU HBM은 부족 (H100 80GB / 141GB). Hot 코퍼스만 GPU에 두고, cold/long-tail은 CPU HNSW로 분리하는 게 비용 효율의 80%.

Hot tier — high-QPS endpoint + 큰 배치 쿼리 담당. Cold tier — catalog 전체 보유, low-QPS 또는 fallback 쿼리 담당. 둘 다 같은 SSD/object store에서 인덱스 매개체 공유.

비용 효과

전체를 GPU에 두면 H100 8개+. 핵심 20%만 GPU + 나머지 CPU면 H100 2개 + CPU node로 90% 성능. TCO 절감 폭이 큼.

그래서 — 언제 GPU를 도입할까?

도입 권장

  • QPS > 1000 + 큰 배치 (TCO 회수 가능)
  • 인덱스 빌드가 시간 단위로 길다
  • 코퍼스 100M~1B + 메모리 압박 (CAGRA · GPU IVF-PQ)
  • 관리형 GPU 옵션 가능 (Pinecone · Zilliz)
  • 임베딩 모델 자주 갱신 → 재빌드 GPU만 사용도 OK

도입 자제

  • 단일 쿼리 latency 결정적 — CPU HNSW가 더 빠를 수 있음
  • QPS < 100 또는 코퍼스 < 10M (TCO 안 나옴)
  • 운영 인력의 GPU/CUDA 경험 없음
  • real-time insert가 매우 빈번 (PCIe 이동 비용)
  • 예산 제약 (GPU 인스턴스 5~10× 비쌈)

02 · 인덱스 선택FAISS guideline by size

FAISS의 공식 가이드 — 데이터 사이즈별 권장 factory string. "무조건 HNSW"는 1M까지만 좋은 선택이다. 그 위로는 IVF가 들어가고, 100M+에서는 OPQ + IVF + PQ 조합이 표준.

Factory string은 FAISS의 강력한 DSL — 알고리즘 조합을 한 문자열로 표현. 예: OPQ32_128,IVF1048576_HNSW32,PQ32 = OPQ 차원축소 → 1M centroid IVF (HNSW로 빠른 centroid 탐색) → 32-byte PQ 압축.

03 · 적재 제어Backpressure & rate control

대용량 색인 작업은 "있는 만큼 빠르게"가 절대 금기. write throughput이 cluster capacity를 초과하면 segment merge 폭주 → query latency 폭주 → cascading failure.

5단계 control loop: rate limit → queue 모니터링 → memory ceiling → batch 튜닝 → circuit breaker. Pull-based 인제스천(Kafka)은 자연스럽게 backpressure가 큐에 남으니 가장 안전.

가장 흔한 실수

"한 번에 다 넣자"로 retry 폭주. 100M doc bulk 색인은 며칠에 걸쳐 점진 적재. rps 제한 + queue depth 알람 필수.

[1]
Token bucket rate limit writer당 RPS cap · burst 허용량 분리 · global / per-index 양쪽
[2]
Queue depth 모니터링 indexing queue length / pending segments 알람 · 임계치 시 producer 차단
[3]
Memory ceiling → throttle RSS / heap usage 80% 초과 시 자동 RPS 절반으로 · cgroup limit 활용
[4]

[5]
Circuit breaker HNSW build OOM 직전 차단 · search latency 임계치 초과 시 ingestion 일시 정지

04 · 배포 검증Blue-Green Shadow 트래픽

새 인덱스를 띄우자마자 production traffic을 받게 하지 마라. Shadow traffic: 실제 prod query를 새 인덱스에도 mirror해서 응답은 안 하고 결과만 비교.

측정 — recall@10 overlap · p99 latency diff · error rate. 임계치 통과 시에만 5% → 25% → 50% → 100% 점진 cutover. 위반 시 auto-rollback. 모델 변경 / 인덱스 schema 변경에 모두 필수.

shadow의 함정

green 인덱스에 read load만 들어가므로 cache 동작이 prod와 다를 수 있음. 진짜 cutover 후 latency가 더 나쁠 가능성 항상 염두.

배포 전 통과해야 할 4 게이트

통과 신호 (Go)

  • 인덱스 메모리 추정 × 1.5 ≤ 가용 RAM 70%
  • 데이터 사이즈에 맞는 FAISS factory string 선택
  • Backpressure 5단계 모두 구성 (rate / queue / memory / batch / breaker)
  • Shadow traffic recall@10 overlap > 0.95
  • Shadow p99 diff < 10%, error rate baseline 이하
  • Rollback 절차 문서화 + 자동 트리거 설정

차단 신호 (Stop)

  • 메모리 계산 안 함 / 추정만 함 — 측정 필수
  • "HNSW로 시작하고 나중에 본다" (1B 데이터에)
  • Bulk 색인 RPS 제한 없음 / 모니터링 없음
  • 새 인덱스를 prod traffic 바로 받게 함
  • recall regression 측정 없이 모델 변경
  • 장애 시 rollback에 수동 작업 필요

01 · Memory budget calculator

precheck 
def estimate_memory(n_vectors: int, dim: int, algo: str, **kwargs) -> int:
    """인덱스 빌드 전 메모리 사전 추정 (bytes).
    추정치 × 1.5는 실제 RAM 요구의 안전 marginal."""

    raw = n_vectors * dim * 4          # FP32 raw vectors

    if algo == "hnsw":
        M = kwargs.get("M", 16)
        graph = n_vectors * M * 8 * 1.5   # 포인터 + 1.5x overhead
        return raw + int(graph)

    elif algo == "ivf_flat":
        nlist = kwargs.get("nlist", int(n_vectors ** 0.5))
        centroids = nlist * dim * 4
        return raw + centroids

    elif algo == "ivf_pq":
        m = kwargs.get("m", 96)            # sub-vector 수
        nlist = kwargs.get("nlist", int(n_vectors ** 0.5))
        codes = n_vectors * m              # PQ 압축 코드 (1byte/sub-vec)
        centroids = nlist * dim * 4
        codebook = m * 256 * (dim // m) * 4
        return codes + centroids + codebook

    elif algo == "diskann":
        # PQ sketch만 메모리, full vector는 SSD
        m = kwargs.get("m", 96)
        return n_vectors * m + n_vectors * 8 * 32    # sketch + neighbor refs

    raise ValueError(f"unknown algo: {algo}")

# 사용 예 — 빌드 시작 전 assertion
def precheck(n: int, d: int, algo: str, available_ram_gb: int, **kw):
    est_bytes = estimate_memory(n, d, algo, **kw)
    est_gb = est_bytes / (1024**3)
    safe_gb = est_gb * 1.5                 # marginal

    if safe_gb > available_ram_gb * 0.7:
        raise MemoryError(
            f"{algo} for {n:,} × {d}d needs ~{safe_gb:.0f}GB "
            f"(70% of {available_ram_gb}GB = {available_ram_gb*0.7:.0f}GB)"
        )
    print(f"OK: {algo} est {est_gb:.1f}GB (safe {safe_gb:.0f}GB) ≤ {available_ram_gb*0.7:.0f}GB")

precheck(n=1_000_000_000, d=768, algo="ivf_pq", m=48, available_ram_gb=256)
# → OK: ivf_pq est 47.0GB (safe 71GB) ≤ 179GB

03 · Shadow traffic diff + auto rollback

deploy 
import asyncio
from dataclasses import dataclass, field

@dataclass
class ShadowMetrics:
    recall_overlap: list[float] = field(default_factory=list)
    p99_diff_ms:    list[float] = field(default_factory=list)
    error_count:    int = 0

    def healthy(self) -> bool:
        if len(self.recall_overlap) < 100: return True      # 표본 부족
        avg_recall = sum(self.recall_overlap) / len(self.recall_overlap)
        avg_p99    = sum(self.p99_diff_ms) / len(self.p99_diff_ms)
        error_rate = self.error_count / len(self.recall_overlap)
        return avg_recall > 0.95 and avg_p99 < 10 and error_rate < 0.001

class ShadowRouter:
    def __init__(self, blue, green):
        self.blue, self.green = blue, green
        self.metrics = ShadowMetrics()
        self.cutover_pct = 0.0                # 0 → 1로 점진

    async def search(self, query):
        # 1) blue (current)는 항상 실행 — 실제 응답
        blue_task = asyncio.create_task(self.blue.search(query))

        # 2) green (new)는 mirror — 결과 버리고 측정만
        green_task = asyncio.create_task(self.green.search(query))

        blue_result, green_result = await asyncio.gather(
            blue_task, green_task, return_exceptions=True
        )

        # 3) diff 측정 (응답에 영향 없음)
        if isinstance(green_result, Exception):
            self.metrics.error_count += 1
        else:
            overlap = len(set(blue_result.ids) & set(green_result.ids)) / len(blue_result.ids)
            latency_diff = green_result.latency_ms - blue_result.latency_ms
            self.metrics.recall_overlap.append(overlap)
            self.metrics.p99_diff_ms.append(latency_diff)

        # 4) 건강하지 않으면 자동 rollback
        if not self.metrics.healthy():
            await self.rollback()
            raise RuntimeError("green unhealthy — rolled back")

        return blue_result        # 응답은 항상 blue

    async def cutover(self, pct: float):
        assert self.metrics.healthy(), "can't cutover unhealthy green"
        self.cutover_pct = pct
        emit("cutover_pct", pct)         # 5 → 25 → 50 → 100

    async def rollback(self):
        self.cutover_pct = 0.0
        page_oncall("shadow validation failed")
포인트. Shadow는 application layer에서 구현 가능 — 인프라 변경 없이 시작할 수 있는 가장 안전한 검증. asyncio.gather(return_exceptions=True)로 green 장애가 blue에 영향 안 주게. recall overlap이 가장 중요 — latency만 보면 silent regression을 놓친다.

가정이 깨지는 순간. selectivity가 1%로 떨어지면 nprobe개 cell 내부에서 살아남는 벡터가 0~몇 개로 무너진다. 게다가 필터링이 특정 속성(tenant_id, category)에 의존하면 통과 데이터가 특정 cell에 편중되는 경향이 강하다. 그 cell이 nprobe에 안 잡히면 정답이 통째로 누락. 결과: recall이 0.95에서 0.4로 폭락. 후처리 필터(post-filter)는 더 나쁘다 — ANN이 작은 후보만 뱉은 뒤 필터로 또 깎이니 빈 결과가 된다.

HNSW가 더 견고한 이유. HNSW는 그래프 탐색이다. 필터 통과 노드를 따라 계속 hop이 가능하다 — 통과 못 하는 노드를 만나면 다른 엣지로 우회. IVF의 "cell 안에 후보가 없다"는 dead-end가 잘 발생하지 않는다. 단 HNSW도 selectivity 1% 미만으로 가면 그래프 연결성 자체가 끊겨 무너진다 — 차이는 임계점의 위치일 뿐.

회피 전략 — 세 갈래. ① nprobe를 nlist의 절반까지 확대: recall은 회복되지만 사실상 brute-force, 가속 효과 소멸. ② 필터 컬럼으로 파티션 자체 분리: tenant_id·category별로 별도 인덱스를 두면 IVF의 가정이 다시 성립. ③ HNSW로 전환: 메모리 여유가 있다면 가장 단순한 해결. IVF의 "빠르다"는 전제는 "필터가 약하다"이다.

주의 — 이건 Milvus 문제가 아니다. Faiss IndexIVF·pgvector IVFFlat·Elasticsearch IVF·OpenSearch IVF — IVF 구조를 채택한 모든 엔진이 동일하게 겪는 알고리즘 차원의 한계다. 엔진을 갈아도 해결되지 않는다. 인덱스 설계 자체를 바꿔야 한다.

pre-filter가 해결하는 것 — 빈 결과 문제만. 동작 원리: "스칼라 조건으로 비트맵을 미리 만들고, ANN 탐색 중 거리 계산할 때마다 비트맵 체크해서 통과한 것만 결과에 누적". post-filter처럼 "ANN이 뱉은 100개 후보를 필터로 깎아 5개만 남는" 빈 결과 사고는 막을 수 있다.

pre-filter가 해결하지 못하는 것 — IVF의 본질. 그러나 nprobe개 cell만 본다는 IVF의 골격은 그대로다. 16개 방 밖은 안 본다. 정답이 안 본 cell에 있으면 영원히 못 찾는다. pre-filter는 "본 후보를 효율적으로 거른다"는 거지 "안 본 cell을 더 본다"는 게 아니다. selectivity 매우 낮을 땐 pre-filter여도 recall이 떨어진다 — 빈 결과는 안 나오지만 정답률이 낮은 결과가 나온다.

Milvus의 실제 동작 — selectivity 매우 낮으면 IVF를 포기한다. Milvus 2.4+의 cost-based optimizer는 selectivity가 임계치 미만(대략 0.1~1%)일 때 IVF 인덱스를 무시하고 필터 통과한 ID 목록 위에서 brute-force 거리 계산으로 전환한다. 결국 "IVF가 통하는 구간에서만 IVF, 안 통하는 구간은 brute-force 폴백"하는 구조다.

IVF nlist × 39 법칙 — 학습 데이터 부족 시 centroid 붕괴
"39× rule"

IVF 학습의 숨은 전제. IVF는 k-means로 nlist개 클러스터를 만든다. k-means는 각 centroid가 최소 수십 개의 학습 벡터를 담당해야 수렴한다. FAISS 내부 가이드라인은 학습 벡터 ≥ 39 × nlist. nlist=4096이면 최소 160K 학습 벡터가 필요하다. 이 조건이 깨지면 여러 centroid가 같은 영역에 쏠리거나 0개 벡터를 가지는 빈 centroid가 생긴다.

10K 학습

증상. FAISS는 경고 없이 수렴 안 된 centroid로 인덱스를 완성한다. 이후 nprobe=16으로 가장 가까운 16개 cell을 보지만, 실제 정답 벡터들이 잘못 분할된 cell에 흩어져 있어 nprobe를 아무리 늘려도 recall이 올라가지 않는다. 진단 방법 — nprobe를 nlist/2까지 늘렸을 때 recall이 올라가면 centroid는 건강한 것. 올라가지 않으면 centroid 붕괴 의심.

04 · Hybrid scoring — Reciprocal Rank Fusion

hybrid scoring 
def rrf_fusion(rankings: list[list[str]], k: int = 60) -> list[tuple]:
    """Reciprocal Rank Fusion — 학습 데이터 없이도 robust한 hybrid.

    rankings: 각 retriever의 결과 ID 리스트 (rank 순서)
    k: 60이 일반적 (논문 default). 작을수록 top rank 가중치 ↑
    """
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

# 사용 예: BM25 + vector 두 retriever 결과 fusion
bm25_results   = bm25_index.search(query_text, k=100)      # IDs only
vector_results = qdrant.search(query_vec, limit=100)        # IDs only

fused = rrf_fusion([bm25_results, vector_results])
top_10 = [doc_id for doc_id, _ in fused[:10]]

# 비교: alpha-blending (점수 직접 합산 — scale 다른 점이 함정)
def alpha_blend(bm25: dict[str, float], vec: dict[str, float],
                alpha: float = 0.5):
    # min-max normalize 먼저
    bm25_n = {k: (v - min(bm25.values())) / (max(bm25.values()) - min(bm25.values()))
              for k, v in bm25.items()}
    vec_n = {k: v for k, v in vec.items()}      # cosine은 이미 0~1
    keys = set(bm25_n) | set(vec_n)
    return {k: alpha * bm25_n.get(k, 0) + (1-alpha) * vec_n.get(k, 0)
            for k in keys}
포인트. RRF는 학습 데이터 없이도 baseline보다 항상 우수한 거의 유일한 hybrid 방법. 절대 점수 무시하고 rank만 사용 — scale 다른 두 retriever를 자연스럽게 통합. k=60은 논문 default. alpha-blending은 normalization 잘못하면 더 나빠진다.

import numpy as np
from faiss import IndexFlatL2

def compute_ground_truth(corpus: np.ndarray, queries: np.ndarray, k: int):
    """brute-force k-NN — 작은 sample (예: 1만 query)로만 계산."""
    truth_index = IndexFlatL2(corpus.shape[1])
    truth_index.add(corpus)
    _, gt_ids = truth_index.search(queries, k)
    return gt_ids   # (n_queries, k)

def recall_at_k(ann_results: np.ndarray, ground_truth: np.ndarray, k: int):
    """ann_results, ground_truth: (n_queries, k) array of IDs"""
    recalls = []
    for ann_ids, gt_ids in zip(ann_results, ground_truth):
        overlap = len(set(ann_ids[:k]) & set(gt_ids[:k]))
        recalls.append(overlap / k)
    return np.mean(recalls)

# 핵심 측정 루프 — 파라미터 변경 시 항상 함께 측정
gt = compute_ground_truth(corpus, queries, k=10)

results = []
for ef in [32, 64, 128, 256, 512]:
    hnsw.set_ef(ef)
    start = time.time()
    ann_ids, _ = hnsw.knn_query(queries, k=10)
    latency_ms = (time.time() - start) / len(queries) * 1000
    recall = recall_at_k(ann_ids, gt, k=10)
    results.append((ef, recall, latency_ms))

# 출력: ef → recall → latency 곡선. 운영 SLA에 맞는 ef 선택의 근거.
for ef, r, l in results:
    print(f"ef={ef:4d}  recall@10={r:.3f}  latency={l:.2f}ms")
포인트. recall 측정 없는 latency 비교는 의미 없는 숫자. ground truth는 brute-force (Flat index)로 계산. 1만 query sample이면 충분. 파라미터를 바꿀 때마다 이 곡선을 다시 그려야 진짜 비교 가능. 이 한 가지 습관이 운영 결정의 90%를 옳게 만든다.

class DualIndexRouter:
    """새 임베딩 모델 출시 시 v1·v2 인덱스를 동시 운영, 점진 traffic shift.

    v1과 v2는 임베딩 공간이 완전히 다르므로 절대 섞으면 안 된다."""

    def __init__(self):
        self.v1_index, self.v1_encoder = load("v1")
        self.v2_index, self.v2_encoder = load("v2")
        self.v2_traffic_pct = 0.0     # 0 → 1로 점진 증가

    def search(self, query_text: str, k: int = 10):
        # A/B split — 사용자별 stable routing (해시 기반)
        use_v2 = hash(get_user_id()) % 100 < self.v2_traffic_pct * 100

        if use_v2:
            q_vec = self.v2_encoder.encode(query_text)
            return self.v2_index.search(q_vec, k=k)
        else:
            q_vec = self.v1_encoder.encode(query_text)
            return self.v1_index.search(q_vec, k=k)

    def shift_traffic(self, new_pct: float):
        """검증 게이트 통과 후 점진 shift: 5% → 25% → 50% → 100%"""
        assert self.v2_recall_check() > 0.95, "v2 recall regression"
        self.v2_traffic_pct = new_pct
        emit_metric("v2_traffic_pct", new_pct)

    def retire_v1(self):
        """v2 100% + 안정성 확인 후 v1 인덱스 삭제 (24h grace)"""
        assert self.v2_traffic_pct == 1.0
        schedule_delete(self.v1_index, after="24h")
포인트. 임베딩 모델 v1과 v2는 완전히 다른 좌표계 — v1 인덱스에 v2 query 벡터를 절대 섞으면 안 됨. dual index는 비용 일시 2배지만 안전 swap의 유일한 방법. 사용자별 stable routing이 중요 — 같은 사용자가 검색마다 다른 결과 받으면 UX 깨짐.

위 6개 코드는 독립적으로 도입 가능하다. 도입 순서 권장 — ① Recall 측정(05)부터, ② 그 다음 HNSW baseline(01), ③ 비용 압박이면 IVFPQ(02), ④ hybrid 필요하면 RRF(04), ⑤ 모델 교체 직전에 dual index(06). 측정 없는 최적화는 추측이다.
