01
TL;DR

한 줄로 이해하기

Airflow는 Python 코드로 DAG를 정의하는 배치 파이프라인 오케스트레이터다. 실행 엔진이 아니라 무엇을, 언제, 어떤 순서로 실행할지를 조율하는 조율자(Orchestrator)다. Scheduler가 DAG 파일을 주기적으로 파싱하고, 실행 가능한 Task를 Executor에게 위임한다.

01

DAG — Python 코드가 곧 파이프라인 정의

DAG(Directed Acyclic Graph)는 Task들의 의존성 그래프다. cron 표현식으로 스케줄링하고, start_date와 schedule_interval로 실행 주기를 정의한다. DAG 파일은 Python이므로 조건문·반복문·함수를 모두 사용할 수 있다. Airflow는 DAG를 구성 도구로만 사용하며 실제 데이터는 처리하지 않는다.

02

Operator — Task의 실행 단위

PythonOperator는 Python 함수를 실행. BashOperator는 쉘 명령. SparkSubmitOperator는 Spark 잡 제출. HttpSensor는 HTTP 엔드포인트 polling. Operator는 Task의 청사진이고, TaskInstance가 실제 실행 객체다. 같은 Operator를 여러 Task에서 재사용할 수 있다.

03

Scheduler — 단일 루프로 파싱·큐잉

Scheduler는 주기적으로 dags/ 폴더를 스캔해 DAG 파일을 파싱하고, 실행 가능 상태(upstream 완료, 스케줄 도달)의 Task를 Executor 큐에 넣는다. 단일 프로세스이므로 DAG 파일 수와 파싱 시간이 성능 병목이다. Airflow 2.0+에서는 DAG를 Metadata DB에 직렬화(serialization)해 Webserver가 DB에서 직접 읽도록 개선됐다.

04

Executor — Task를 실제 실행하는 방식

LocalExecutor: 단일 서버에서 subprocess로 실행. 소규모 적합. CeleryExecutor: Redis/RabbitMQ 큐를 통해 Worker 프로세스에 분산. 수십~수백 Worker 지원. KubernetesExecutor: Task마다 독립 Pod를 생성. 완전 격리와 자원 효율. 단, Pod 생성 오버헤드(~수십 초)가 있다.

05

XCom — Task 간 소량 데이터 교환

XCom(Cross-Communication)은 Task 간 소량의 데이터를 Metadata DB를 통해 공유한다. xcom_push로 저장하고 xcom_pull로 읽는다. 수 KB 이하의 메타데이터(파일 경로, 레코드 수, 상태 코드)에만 사용해야 한다. 대용량 데이터는 S3/GCS 경로를 XCom으로 전달하고 실제 데이터는 외부 저장소를 거친다.

06

TaskFlow API — @task 데코레이터

Airflow 2.0+의 현대적 API. @task 데코레이터가 붙은 Python 함수가 자동으로 Task가 된다. 함수 반환값이 자동으로 XCom으로 전달되어 의존성이 코드 흐름으로 표현된다. Dynamic Task Mapping(2.3+): .expand()로 런타임에 태스크 수를 결정한다. 입력 리스트 크기만큼 Task가 자동 생성된다.

02
Architecture

핵심 개념 도감

01DAG 구조

DAG는 Task들의 방향 비순환 그래프다. 화살표 방향이 의존성을 나타낸다. task_a >> task_b는 task_a가 완료된 후 task_b가 실행된다는 의미다. 다수의 upstream Task를 기다리거나, 다수의 downstream Task를 병렬로 실행하는 팬인/팬아웃 패턴이 가능하다.

execution_date: 논리적 실행 날짜. 매일 실행 DAG의 2026-05-29 실행은 2026-05-29 데이터를 처리한다는 의미다. Backfill 시 과거 execution_date로 재실행할 수 있다.

DAG 설계 원칙

한 DAG는 한 목적만 수행한다. 의존성이 없는 파이프라인을 억지로 같은 DAG에 넣지 않는다. Task는 멱등성(idempotent)을 가져야 한다 — 같은 execution_date로 재실행해도 동일한 결과를 내야 한다.

02컴포넌트 아키텍처

Scheduler: DAG 파일 파싱, 실행 가능 Task 감지, Executor 큐에 전달. Webserver: UI 제공, DAG/Task 상태 조회. Airflow 2.0+에서 직렬화된 DAG를 DB에서 직접 읽어 Scheduler 부하 감소. Metadata DB(PostgreSQL 권장): 모든 상태의 중심. DAG·Task·XCom·Variable·Connection 모두 여기에 저장된다.

Triggerer(2.2+): deferrable operator를 위한 별도 프로세스. asyncio 기반으로 대량의 Sensor를 효율적으로 처리한다. 기존 poke 모드 Sensor는 Worker 슬롯을 점유하지만, deferrable은 Triggerer가 비동기로 처리해 Worker를 해방한다.

프로덕션 배포

Scheduler와 Webserver를 별도 프로세스로 배포한다. Metadata DB는 별도 PostgreSQL 인스턴스를 사용한다(SQLite는 프로덕션 금지). CeleryExecutor 시 Redis/RabbitMQ가 추가된다. Helm chart(공식)로 Kubernetes 배포가 표준이다.

03Executor 비교

SequentialExecutor: Task를 순차 실행. SQLite와 함께 개발 환경에만 사용. LocalExecutor: 동일 프로세스 내에서 subprocess로 병렬 실행. 단일 서버에서 수십 Task/분 처리 가능. CeleryExecutor: Celery Worker가 Redis/RabbitMQ 큐에서 Task를 소비. 수십~수백 Worker로 수평 확장.

KubernetesExecutor: Task마다 K8s Pod를 생성하고 완료 후 삭제. 완전한 자원 격리, 태스크별 독립 환경(Docker 이미지). 단, Pod 생성 오버헤드(20~60초)가 있어 짧은 Task에는 비효율적이다. CeleryKubernetesExecutor: 두 방식을 혼합해 큐에 따라 Celery 또는 K8s로 라우팅한다.

선택 기준

단일 서버 운영이면 LocalExecutor, 분산 처리가 필요하고 Task가 짧으면 CeleryExecutor, Task가 크고 자원 격리가 중요하면 KubernetesExecutor. Airbnb·LinkedIn 규모에서는 KubernetesExecutor가 표준이다.

04Task 상태 머신

TaskInstance는 실행 중 여러 상태를 거친다. scheduled: Scheduler가 실행 가능으로 판단. queued: Executor 큐에 전달 완료. running: Worker에서 실행 중. success/failed: 실행 완료. up_for_retry: 재시도 대기(retry 설정 시).

Trigger Rule: downstream Task의 실행 조건을 결정한다. 기본 all_success: 모든 upstream 성공 시. one_failed: upstream 중 하나라도 실패 시 실행 — 알림 Task에 사용. none_failed: 실패가 없으면 실행(skipped 허용). all_done: 성공/실패 무관 모두 완료 시.

Task 재시도 설계

retries=3, retry_delay=timedelta(minutes=5)로 지수 백오프 없이 고정 지연 재시도. 외부 API 호출이나 네트워크 오류가 예상되는 Task에 설정한다. email_on_failure=True로 실패 시 알림을 받는다.

05XCom 데이터 흐름

XCom은 Metadata DB의 xcom 테이블을 통해 Task 간 데이터를 전달한다. TaskFlow API에서는 함수 반환값이 자동으로 XCom에 저장되고, 인자로 받는 함수가 자동으로 XCom에서 읽는다. 명시적인 push/pull 호출이 필요 없다.

XCom 값은 직렬화되어 DB에 저장되므로 크기 제한이 있다(PostgreSQL: 1GB BLOB, 실용 한계는 수십 KB). 사용 패턴: 파일 경로, row count, 처리 결과 코드, 다음 처리할 배치 ID 등 메타데이터. 대용량 DataFrame이나 배열을 XCom으로 전달하는 것은 안티패턴이다.

Custom XCom Backend

Airflow 2.x에서 XCom 백엔드를 S3/GCS로 대체할 수 있다. 큰 데이터를 반환하는 Task도 자동으로 S3에 저장하고 경로만 DB에 기록한다. AWS MWAA, Astronomer 등에서 기본 제공한다.

06Sensor — 외부 조건 대기

Sensor는 외부 조건이 충족될 때까지 대기하는 특수 Operator다. 파일 도착, API 응답, DB 레코드 존재 등을 polling한다. poke 모드(기본): Worker 슬롯을 점유하며 poke_interval마다 조건을 확인. 대기 시간이 길면 Worker 슬롯을 낭비한다.

reschedule 모드: polling 사이에 Task를 해제하고 Worker 슬롯을 반환한다. 다음 poke 시간이 되면 재스케줄된다. 장시간 대기하는 Sensor에 적합하다. deferrable Operator(2.2+): Triggerer 프로세스가 asyncio로 비동기 polling. Worker 슬롯을 전혀 소비하지 않는다. 수천 개의 동시 Sensor를 단일 Triggerer로 처리할 수 있다.

Sensor 선택 기준

대기 시간 <5분: poke 모드. 대기 시간 5분~수 시간: reschedule 모드. 수백~수천 동시 Sensor, 대기 시간 가변: deferrable(Triggerer). timeout과 soft_fail을 항상 설정해 무한 대기를 방지한다.

03
Large Scale

대용량 처리

Airflow 탄생지인 Airbnb는 3,000+개 DAG, 일 100만+ TaskInstance를 처리한다. LinkedIn은 수천 개의 데이터 파이프라인을, Lyft는 KubernetesExecutor로 완전 전환해 수십만 Task를 처리한다.

01 · Scheduler
Scheduler 성능 — 파싱 병목 해결
사례AirbnbLinkedIn

Scheduler는 dags/ 폴더를 dag_dir_list_interval(기본 300초)마다 스캔하고, 각 DAG 파일을 min_file_process_interval(기본 30초)마다 파싱한다. DAG 파일이 많을수록 파싱 루프가 느려지고 스케줄 지연이 발생한다.

DAG 파싱 최적화: (1) DAG 파일 최상단에 무거운 import를 줄인다 — DB 연결, 모델 로드는 Task 함수 내부에서. (2) .airflowignore로 불필요한 파일을 스캔 제외. (3) DAG 직렬화(2.0+): Metadata DB에 DAG 구조를 캐시해 Webserver가 파일 재파싱 없이 DB에서 읽는다. (4) Airbnb 기준 scheduler_heartbeat_sec=5, min_file_process_interval=30으로 튜닝.

DAG 파싱 시간 측정: airflow dags list의 응답 시간, Scheduler 로그의 DAG parsing time 지표로 확인한다. 개별 파일 파싱이 30초를 초과하면 해당 DAG를 분리해야 한다.

Scheduler HA (2.0+)

Airflow 2.0+에서 다중 Scheduler를 실행할 수 있다. Row-level lock으로 동일 Task의 중복 실행을 방지한다. Scheduler 하나가 죽어도 나머지가 이어받는다. 단, 모든 Scheduler가 동일한 dags/ 경로를 마운트해야 한다.

Scheduler 주요 루프
1. dags/ 스캔 (dag_dir_list_interval=300s)
↓
2. DAG 파일 파싱 (min_file_process_interval=30s)
↓
3. 실행 가능 TaskInstance 감지 → queued 상태로
↓
4. Executor 큐에 전달 → heartbeat(5s) 후 반복
병목: DAG 파일 수 × 파싱 시간 → parallelism 낮추거나 DAG 분리
02 · Executor Scaling
Executor 스케일링 — CeleryExecutor vs KubernetesExecutor
사례Lyft K8sSpotify Celery

CeleryExecutor 튜닝: worker_concurrency(기본 16)는 Worker당 동시 Task 수. CPU 바운드 Task는 CPU 코어 수와 동일하게, I/O 바운드 Task는 2~4배로 설정한다. parallelism(기본 32)는 전체 동시 실행 Task 수. Celery Flower UI로 Worker 상태를 모니터링한다.

KubernetesExecutor 튜닝: worker_pods_creation_batch_size(기본 1)를 높이면 Pod 일괄 생성으로 처리량 향상. delete_worker_pods=True(기본)로 완료된 Pod를 즉시 삭제해 리소스 회수. pod_template_file로 리소스 요청(CPU/메모리), tolerations, node affinity를 Task별로 다르게 설정할 수 있다.

Lyft 사례: 전체 파이프라인을 KubernetesExecutor로 전환해 환경 격리와 자원 효율을 동시에 달성했다. Task별로 다른 Docker 이미지를 사용해 의존성 충돌을 완전히 제거했다.

Task 큐 분리

CeleryExecutor에서 queue 파라미터로 Task를 특정 Worker 그룹에 배정한다. GPU Task는 queue="gpu" Worker로, 메모리 집약 Task는 high-memory Worker로 라우팅해 자원을 효율적으로 사용한다.

03 · Metadata DB
Metadata DB 관리 — 비대화 방지
중요도Critical

Metadata DB가 성능의 핵심이다. task_instance와 dag_run 테이블이 무제한으로 쌓이면 Scheduler의 쿼리가 느려지고 Webserver UI도 응답이 길어진다. 수백만 레코드가 쌓이면 인덱스 스캔도 초 단위 지연이 발생한다.

정기 정리: airflow db clean --clean-before-timestamp "2025-01-01" --tables task_instance,dag_run,xcom로 오래된 레코드를 삭제한다. 또는 max_dagruns_to_create_per_loop로 동시 실행 DAG Run 수를 제한한다. min_serialized_dag_update_interval(기본 30초)으로 직렬화 빈도를 조절한다.

XCom 테이블: 크기가 큰 XCom이 누적되면 테이블이 급격히 커진다. Custom XCom Backend(S3)를 사용하거나, DB 컬럼 타입을 확인해 BLOB 크기를 제한한다.

PostgreSQL 권장 설정

max_connections=200, Airflow 측 sql_alchemy_pool_size=5, sql_alchemy_max_overflow=10. Connection pool이 부족하면 Scheduler가 DB 연결 대기로 지연된다. PgBouncer로 연결 풀링을 추가하면 수백 Worker 환경에서도 안정적이다.

04 · Configuration

Airflow vs Prefect vs Dagster: Airflow는 배치 파이프라인 오케스트레이션의 업계 표준이지만 동적 파이프라인 표현이 복잡하다. Prefect는 Python 함수에 데코레이터를 붙이는 방식으로 더 유연하고 Cloud 네이티브지만 커뮤니티가 작다. Dagster는 데이터 자산(Asset) 중심의 설계로 데이터 품질과 타입 안전성에 강점이 있다. 이미 Airflow 생태계에 투자했다면 전환 비용이 크다.

01. TaskFlow API — 기본 ETL DAG

taskflow
from airflow.decorators import dag, task
from datetime import datetime, timedelta
import pandas as pd

@dag(
    schedule="0 2 * * *",          # 매일 02:00 UTC
    start_date=datetime(2026, 1, 1),
    catchup=False,                    # 과거 미실행 DAG Run 생성 안 함
    default_args={
        "retries": 2,
        "retry_delay": timedelta(minutes=5),
        "email_on_failure": True,
    },
    tags=["etl", "orders"],
)
def orders_etl():

    @task()
    def extract() -> dict:
        # 반환값이 자동으로 XCom에 저장됨
        row_count = _fetch_from_source("s3://raw/orders/*.parquet")
        return {"s3_path": "s3://staging/orders/", "rows": row_count}

    @task()
    def transform(extract_result: dict) -> dict:
        # XCom pull이 인자로 자동 전달됨
        path = extract_result["s3_path"]
        out = _run_transform(path)
        return {"output_path": out, "rows": extract_result["rows"]}

    @task()
    def load(transform_result: dict) -> None:
        _load_to_warehouse(transform_result["output_path"])

    # 의존성이 함수 호출 흐름으로 자동 설정됨
    extracted = extract()
    transformed = transform(extracted)
    load(transformed)

orders_etl()
포인트. @dag와 @task만으로 의존성과 XCom이 자동 처리된다. catchup=False는 DAG 활성화 시 과거 실행을 생성하지 않아 의도치 않은 대량 실행을 방지한다.

02. Dynamic Task Mapping — 파티션별 병렬 처리

dynamic
from airflow.decorators import dag, task

@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def partitioned_pipeline():

    @task()
    def get_partitions(**context) -> list[str]:
        # 런타임에 처리할 파티션 목록을 결정
        ds = context["ds"]  # execution date (YYYY-MM-DD)
        return [f"s3://data/{ds}/region={r}" for r in ["KR", "US", "JP", "EU"]]

    @task()
    def process_partition(partition_path: str) -> str:
        # 각 파티션이 독립 Task로 병렬 실행됨
        result = _process(partition_path)
        return result

    @task()
    def merge_results(results: list[str]) -> None:
        _merge(results)

    partitions = get_partitions()
    # .expand()으로 파티션 수만큼 Task 자동 생성
    processed = process_partition.expand(partition_path=partitions)
    merge_results(processed)

partitioned_pipeline()
포인트. .expand()는 Airflow 2.3+ 기능이다. 입력 리스트 크기만큼 Task가 동적으로 생성되어 병렬 실행된다. merge_results는 모든 process_partition 완료 후 자동으로 실행된다.

03. Sensor + Trigger Rule — 조건 대기 & 실패 알림

sensor
from airflow.decorators import dag, task
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor
from airflow.operators.python import PythonOperator
from airflow.utils.trigger_rule import TriggerRule

@dag(schedule="@hourly", start_date=datetime(2026, 1, 1), catchup=False)
def sensor_pipeline():

    # reschedule 모드: Worker 슬롯을 점유하지 않음
    wait_for_file = S3KeySensor(
        task_id="wait_for_file",
        bucket_name="my-data",
        bucket_key="uploads/{{ ds }}/data.parquet",
        mode="reschedule",
        poke_interval=60,       # 60초마다 확인
        timeout=60 * 60 * 6,   # 6시간 후 타임아웃
        soft_fail=True,         # 타임아웃 시 failed 대신 skipped
    )

    @task()
    def process_file():
        _process()

    # 성공/실패 무관 항상 실행되는 알림
    notify = PythonOperator(
        task_id="notify",
        python_callable=lambda: _send_slack(),
        trigger_rule=TriggerRule.ALL_DONE,  # 상위 Task 완료 시 무조건 실행
    )

    wait_for_file >> process_file() >> notify

sensor_pipeline()
포인트. mode="reschedule"로 Sensor가 Worker 슬롯을 반환하게 한다. soft_fail=True로 타임아웃 시 전체 DAG Run을 실패시키지 않고 해당 Task만 skipped로 처리한다. TriggerRule.ALL_DONE은 상위 Task의 성공/실패와 무관하게 실행된다.

04. DAG 파라미터화 — Variable & Params

config
from airflow.decorators import dag, task
from airflow.models import Variable
from airflow.operators.trigger_dagrun import TriggerDagRunOperator

@dag(
    schedule=None,  # 수동 트리거 전용
    start_date=datetime(2026, 1, 1),
    params={
        "target_date": "2026-05-01",   # UI에서 override 가능
        "max_rows": 1_000_000,
    },
)
def backfill_dag():

    @task()
    def run_backfill(**context) -> dict:
        params = context["params"]
        target = params["target_date"]
        max_rows = params["max_rows"]

        # Variable: Airflow UI에서 관리하는 환경변수
        db_conn = Variable.get("warehouse_conn_string")
        env = Variable.get("env", default_var="prod")

        result = _backfill(target, max_rows, db_conn)
        return {"processed_date": target, "rows": result}

    run_backfill()

backfill_dag()
포인트. Variable.get()은 호출 시 Metadata DB에서 읽는다. DAG 최상단(모듈 레벨)에서 호출하면 파싱마다 DB 쿼리가 발생해 Scheduler 부하가 증가한다. 반드시 Task 함수 내부에서만 호출한다.

05. KubernetesExecutor — Pod 리소스 설정

kubernetes
from airflow.decorators import dag, task
from airflow.providers.cncf.kubernetes.operators.pod import KubernetesPodOperator
from kubernetes.client import V1ResourceRequirements

@dag(schedule="@daily", start_date=datetime(2026, 1, 1), catchup=False)
def k8s_pipeline():

    # 독립 Docker 이미지로 실행되는 Task
    spark_job = KubernetesPodOperator(
        task_id="spark_transform",
        image="my-registry/spark-etl:v2.1.0",
        cmds=["spark-submit", "--master", "k8s://...", "etl.py"],
        container_resources=V1ResourceRequirements(
            requests={"cpu": "2", "memory": "8Gi"},
            limits={"cpu": "4", "memory": "16Gi"},
        ),
        namespace="airflow-workers",
        get_logs=True,
        is_delete_operator_pod=True,  # 완료 후 Pod 삭제
        env_vars={"DATE": "{{ ds }}"},
    )

    @task()
    def notify():
        _send_slack("spark_transform completed")

    spark_job >> notify()

k8s_pipeline()
포인트. KubernetesPodOperator는 Task마다 독립 Pod를 생성해 별도 Docker 이미지와 리소스를 사용할 수 있다. is_delete_operator_pod=True로 완료 Pod를 즉시 정리한다. Jinja 템플릿({{ ds }})은 환경변수에서도 사용 가능하다.
