01

Chapter 1. Four Key Metrics Unleashed

전달 성과의 네 지표와 개선의 출발점

이 장의 핵심

  • 전달 속도와 안정성을 함께 측정하면 변경이 어디서 막히고 실패하는지 팀이 설명할 수 있다.
  • 측정 경계와 계산을 공유해야 지표가 아키텍처 개선의 근거가 된다.

학습 목표

  • 변경·배포·장애 기록으로 네 지표를 계산하고, 수치가 가리키는 전달 흐름의 문제를 설명한다.

핵심 내용과 설명

01

전달 흐름과 네 지표

  • 측정 대상은 완료한 변경이 사용자에게 도달하는 과정이다. 개발자가 코드나 설정 변경을 완료해 커밋한 때부터 운영 서비스에 반영될 때까지를 본다. 아이디어를 정하고 코드를 작성하는 전체 제품 개발 기간과는 경계가 다르다. 빌드·검사·승인·배포 중 어디에서 기다렸는지 드러내는 것이 출발점이다.
관점 지표 필요한 기록과 계산 답하려는 질문
속도 배포 빈도 기간의 성공 운영 배포 수 ÷ 기간 변경을 얼마나 자주 전달하는가
속도 변경 리드 타임 변경별 운영 반영 시각 − 완료 커밋 시각 완료한 변경이 전달 중 얼마나 기다리는가
안정성 변경 실패율 같은 범위의 변경 유발 장애와 배포 기록 빠른 전달이 서비스 실패를 늘리는가
안정성 서비스 복구 시간 장애별 서비스 복구 시각 − 장애 인지·기록 시각 실패한 뒤 사용자가 얼마나 기다리는가
  • 네 값을 같은 범위에서 읽는다. 인프라 변경을 배포 수에 넣었다면 그 변경이 일으킨 장애도 안정성 측정에 넣어야 한다. 배포만 빨라지고 실패가 늘었다면 속도의 이득과 사용자 피해를 함께 살펴야 한다. 하나의 좋은 수치가 다른 문제를 가리지 않게 네 지표를 묶는다.
  • 처음부터 정밀한 자동화가 있어야 하는 것은 아니다. 성공 배포와 장애 기록을 수작업으로 모아 기준선을 만들 수도 있다. 팀이 무엇을 포함했고 어떻게 계산했는지 이해할 수 있어야 이후 수집 자동화도 같은 의미를 유지한다.
02

변경과 최종 배포의 연결

  • 배포 한 번에 여러 변경이 들어갈 수 있다. 저장소별 빌드가 공통 검증으로 모이면 최종 배포 완료 시각만으로는 개별 리드 타임을 알 수 없다. 최종 배포에 포함된 변경을 찾고 각 변경의 커밋 시각까지 거슬러 올라가야 한다. 배포 횟수는 한 번이어도 리드 타임 표본은 여러 개다.
  • 중간 실행의 종료를 전달 완료로 세지 않는다. 바이너리를 만들고 테스트 환경에 올린 뒤 승인을 기다리는 직렬 파이프라인이라면 그 대기도 포함한다. 컴파일에서 바로 실패한 실행을 성공 전달과 섞으면 짧은 실패 시간이 평균을 낮춘다. 변경 없는 정기 백업도 변경 전달의 표본이 아니다.
  • 시작점의 대용 여부를 명시한다. main 병합 시각부터 재면 병합 전 리뷰·브랜치 대기가 빠진다. 초기 도입에서 쓸 수 있는 대리값이지만 실제 전체 전달 시간이 짧아졌다는 뜻으로 읽으면 안 된다. 측정 목적에 맞춰 시작점과 최종 운영 확인 시점을 정한다.
03

기간 집계와 복구의 계산

  • 전체 표본으로 평균을 낸다. 배포 빈도는 배포가 없는 날도 0으로 포함한다. 리드 타임은 기간 안의 개별 변경을 모아 계산한다. 하루별 평균을 다시 단순 평균하면 변경 한 건인 날과 아홉 건인 날에 같은 무게가 붙는다.
보충 계산 예시 변경 수 변경별 시간 총 소요 시간
첫날 1 10시간 10시간
둘째 날 9 각각 1시간 9시간
전체 10 전체 평균 = (10+9)÷10 1.9시간

일평균 둘을 평균한 (10+1)÷2=5.5시간은 각 날짜에 같은 무게를 준 결과다. 알고 싶은 것이 변경 한 건의 평균 전달 시간이라면 1.9시간이 맞다. 이 숫자는 계산 원리를 설명하기 위한 보충 예시다.

  • 장애와 배포를 연결하기 어려운 경우에는 근사를 쓸 수 있다. 이 장의 사례는 복구된 장애 2건과 성공 배포 36건에서 2÷36≈5.56%를 계산한다. 장애 하나가 배포 하나에 대응한다고 단순화한 방식이다. 기간 보고도 장애 합계와 배포 합계를 나눠야 한다. 아직 복구되지 않은 장애는 이 계산 밖에 있으므로 열린 장애 수를 함께 표시한다.
  • 복구는 사용자 서비스가 돌아온 시점이다. 롤백으로 정상화했다면 원인 수정이 남아도 복구는 끝날 수 있다. 티켓을 늦게 열거나 원인 수정 때까지 닫지 않으면 실제 사용자 영향 시간과 달라진다. 평균 복구 시간은 긴 장애에 민감하고 중앙값은 덜 민감하므로 배우려는 문제에 맞춰 해석한다. 사례의 31일 전달 집계와 120일 복구 집계는 표본 수에 따른 선택이다.
04

수치에서 아키텍처 문제로의 연결

  • 숫자와 실제 전달 경로를 함께 살핀다. 리드 타임이 길면 변경이 머문 단계를 찾는다. 승인 대기가 원인인지, 다른 서비스와 묶어 배포해야 하는지, 테스트 환경을 준비하기 어려운지 조사한다. 지표가 원인을 자동으로 말해 주지는 않지만 조사할 공통 출발점을 만든다.
관찰한 상황 팀이 확인할 것 연결될 수 있는 개선
빌드는 빠르지만 운영 반영이 늦음 승인·환경 인계의 대기 전달 절차와 자동화
작은 수정도 공동 릴리스 필요 모듈·팀 간 변경 의존 책임 경계와 독립 배포
변경 뒤 실패가 반복됨 실패를 재현·관찰할 수 있는지 테스트 용이성·관찰 가능성
  • 팀이 데이터를 설명하도록 한다. 정의·기간·원시 기록에 접근할 수 있어야 “왜 값이 변했는가”를 논의할 수 있다. 처음에는 지표의 뜻과 누락을 이해하고, 그다음 개선 가설을 세운다. 아키텍트가 해법을 지시하는 데서 벗어나 팀이 구조 개선의 필요성을 발견하게 하는 것이 이 장의 목적이다.

한눈에 정리

  • 속도는 배포 빈도·변경 리드 타임, 안정성은 변경 실패율·복구 시간으로 함께 본다.
  • 같은 변경을 완료 커밋에서 최종 배포까지 연결하고, 기간 전체의 개별 표본으로 계산한다.
  • 수치 → 실제 병목 조사 → 테스트·배포·책임 경계 개선으로 이어져야 한다.

Quiz

01
첫날 한 변경이 10시간, 둘째 날 아홉 변경이 각각 1시간 걸렸다. 변경 한 건의 평균 리드 타임은 얼마이며 왜 일평균 둘을 평균하면 안 되는가?

총 19시간을 변경 10건으로 나눈 1.9시간이다. 일평균의 단순 평균은 변경 수가 다른 두 날짜에 같은 가중치를 주기 때문이다.

02
서로 다른 시각의 커밋 세 개를 한 번에 운영 배포했다. 배포 빈도와 리드 타임에는 각각 무엇을 기록해야 하는가?

배포는 한 번이다. 리드 타임은 각 커밋의 시작과 같은 최종 배포 시각을 연결한 세 표본이다.

03
공동 배포 때문에 리드 타임이 길다. 수치만 보고 빌드 서버를 늘리기 전에 무엇을 조사해야 하는가?

실제 대기 위치와 서비스·팀 간 변경 의존을 조사한다. 계산 속도보다 책임 경계와 공동 릴리스 조정이 병목일 수 있다.

02

Chapter 2. The Fitness Function Testing Pyramid: An Analogy for Architectural Tests and Metrics

품질 목표를 검사로 바꾸는 피트니스 함수

이 장의 핵심

  • 기능이 동작해도 지연·실패·변경 상황에서 필요한 품질을 지키는지는 따로 확인해야 한다.
  • 품질 목표와 평가 조건을 정한 뒤 검사 범위와 실행 방식을 선택한다.

학습 목표

  • 피트니스 함수의 목표·조건·측정값을 구별하고, 구체적인 검사를 설계해 분류한다.

핵심 내용과 설명

01

품질 목표와 검사 정의

  • “동작한다”와 “필요한 수준으로 동작한다”는 다른 질문이다. 객체 하나가 생성되는지 확인하는 검사는 기능을 본다. 여러 객체를 정한 시간 안에 생성하는지 보면 성능도 본다. 무엇을 얼마나 잘해야 하는지와 평가할 조건을 명시한 정의를 피트니스 함수라고 한다. 그 정의를 실행해 얻는 관측값이 지표다.
  • 목표값만으로는 검사를 만들 수 없다. 단위 테스트 커버리지 90% 초과를 CI 빌드마다 평가하는 경우와 통합 테스트 커버리지 50% 초과를 야간에 평가하는 경우는 조건이 다르다. 숫자·대상·실행 시점·환경·실패 조건을 함께 정해야 구현자가 같은 검사를 만든다. 이 숫자는 예시의 목표다.
  • 목표 정의를 검사 구현보다 먼저 한다. 먼저 유지보수성·신뢰성 등 필요한 품질을 이해관계자와 고른다. 그다음 목표를 평가할 방법을 찾는다. 쉽게 모을 수 있는 커버리지를 먼저 선택하면 중요한 품질을 관찰하지 못한 채 수치만 늘 수 있다.
02

외부 지연의 검사 사례

  • 정상 응답만 확인하면 느린 의존성을 만났을 때의 행동을 모른다. 사례에서는 외부 REST API에 10초 지연을 넣고 야간 통합 환경에서 실제 사용 경로를 실행한다. 오류율 목표는 0%다. 지연된 외부 호출을 시스템이 어떻게 처리하는지 관찰하려는 검사다.
설계 요소 사례의 정의 필요한 이유
입력 조건 외부 API 지연 10초 주입 평소에는 드러나지 않는 대기를 발생시킴
실행 야간 통합 환경의 사용 경로 해당 의존성을 실제로 거침
관측 오류율과 전체 검사 시간 실패뿐 아니라 끝나지 않는 대기도 확인
판단 오류율 0%, 전체 10분 이내 무한 대기를 성공으로 판정하지 않음
  • 지연 주입값과 완료 제한은 서로 다른 조건이다. 10초는 외부 응답에 더한 지연이다. 10분은 전체 검사의 수행 상한이다. 정상 지연에서 5분 미만인 검사에 이 제한을 둔다. 오류 없이 영원히 기다리는 구현도 오류율만 보면 통과할 수 있으므로 두 값을 함께 본다.
  • 검사 범위는 실제 사용 관계로 정한다. 해당 API가 제한된 기능 하나에만 영향을 주면 부분 검사에 가깝다. 주요 사용 흐름 대부분이 그 API에 의존하면 넓은 시스템 검사에 가깝다. 이름에 “통합”이 들어간다는 사실만으로 범위를 결정하지 않는다.
03

검사 분류와 피라미드

  • 범위와 실행 계기를 나눠 생각한다. 부분적 검사는 코드나 특성 일부를 본다. 전체적 검사는 여러 부분이 함께 만드는 넓은 결과를 본다. 이벤트 검사는 변경·예약 등에 반응해 실행하고, 지속 검사는 실행 상태를 계속 평가한다. 지속 실행도 좁은 특성 하나만 볼 수 있다.
분류 사례 범위와 계기 얻는 피드백
CI마다 커버리지 확인 부분적·이벤트 제한된 코드 특성의 빠른 변화
야간의 주요 흐름 지연 검사 넓은 범위·이벤트 구성요소가 함께 버티는지
운영에서 특정 요청 시간 감시 부분적·지속 특정 흐름의 성능 변화
운영 전체 흐름의 지속 평가 전체적·지속 사용자에 가까운 상태와 이상
  • 피라미드는 비용과 빈틈을 드러내는 도구다. 넓은 검사는 많은 구성요소를 준비해야 하고 실패 원인을 격리하기도 어렵다. 작은 검사는 다루기 쉽지만 전체 성공을 보장하지 않는다. 필요한 확신에 맞춰 조합한다. 피라미드의 층과 폭을 모든 시스템의 고정 할당량으로 쓰지 않는다.
  • 목표와 실행 환경도 명시한다. 같은 검사라도 CI가 시작하고 별도 테스트 환경에서 실행될 수 있다. 참·거짓이 필요한지 추세가 필요한지, 수동인지 자동인지, 일시적 검사인지 계속 유지할 검사인지도 정한다. 시간대별 정상 활동이 다른 시스템이라면 허용값도 조건에 따라 달라질 수 있다.
04

검사 목록의 선택과 유지

  • 목표별 후보를 만든 뒤 필요한 것부터 구현한다. 품질 목표 → 검사 후보 → 범위·조건·목표값 정의 → 구현 → 결과 공유로 이어진다. 처음부터 모든 검사를 구현하지 않아도 정의를 목록에 남기면 빠진 품질과 다음 우선순위를 볼 수 있다.
  • 실행 결과를 개선 판단에 사용한다. 실패가 실제 문제를 드러내는지, 불안정한 환경 때문에 흔들리는지 확인한다. 유지 부담이 큰데 결정을 바꾸지 못한다면 검사나 조건을 수정한다. 영구 검사도 효용을 잃으면 폐기할 수 있다.

한눈에 정리

  • 피트니스 함수는 품질의 기준과 조건, 검사 구현은 실행 방법, 지표는 얻은 값이다.
  • 범위와 실행 계기를 구별해 작은 검사와 넓은 검사를 조합한다.
  • 검사 수보다 필요한 품질을 실제로 관찰하고 개선할 수 있는지가 중요하다.

Chapter 3. Evolutionary Architecture: Guiding Architecture with Testability and Deployability

변경 능력을 지키는 테스트와 배포 경계

이 장의 핵심

  • 미래 요구를 모두 예측하기 어려우므로 학습한 뒤 안전하게 바꿀 수 있는 구조가 필요하다.
  • 테스트와 배포의 어려움은 변경을 가로막는 결합을 발견할 단서다.

학습 목표

  • 테스트 준비와 실제 출시 과정에서 결합을 찾고, 검증할 경계를 판단한다.

핵심 내용과 설명

01

미래의 선택지와 모듈 경계

  • 개발은 요구를 배워 가는 과정이다. 사용자가 늘 수도 있고 예상 수요가 오지 않을 수도 있다. 모든 미래에 대비한 구조는 현재 복잡성을 늘릴 수 있다. 처음부터 모든 답을 정하기보다 새 요구를 알았을 때 바꿀 능력을 지켜야 한다.
설계 성질 관계에서 확인할 것 변경에 주는 효과
모듈성 한 부분의 수정이 다른 부분 수정을 강제하는가 수정 범위 한정
응집도 함께 바뀌는 코드가 가까운가 한 변경이 흩어지는 부담 감소
관심사 분리 서로 다른 판단이 섞였는가 무관한 문제까지 다루는 일 감소
추상화·정보 은닉 내부 구현을 몰라도 행위를 이용하는가 구현 교체의 외부 전파 억제
결합 관리 별개 부분이 함께 바뀌어야 하는가 변경 연쇄·조정 부담 감소
  • 저장소 교체는 경계의 역할을 보여준다. 핵심 규칙이 특정 DB의 접근 방식에 얽혀 있으면 관계형 저장소를 그래프 저장소로 바꿀 때 여러 규칙도 수정해야 한다. 저장 행위의 경계 뒤에 구현을 두면 그 교체를 좁은 영역에서 다룰 수 있다. 경계가 변경의 전파를 제한하는 것이다.
  • 현재 구조를 영구히 고정하지 않는다. 경계가 있다고 모든 교체가 무료가 되는 것은 아니다. 새로운 요구가 생기면 실제 저장 방식이나 복구 전략을 바꿔야 할 수 있다. 그때 영향 범위를 이해하고 검증할 수 있도록 만드는 것이 목적이다.
02

테스트 과정과 설계 피드백

  • 테스트는 준비·실행·관찰·비교의 과정이다. 대상의 초기 상태를 만들고 관심 있는 행위를 실행한다. 응답을 수집해 기대와 비교한다. 이 중 어느 단계가 어려운지 보면 설계에서 무엇이 얽혔는지도 찾을 수 있다.
  • 작은 행위에 큰 환경이 필요하면 경계를 조사한다. 관련 변수만 통제할 수 없거나 많은 외부 상태를 맞춰야 한다면 결합이 클 수 있다. 여러 관심사가 섞여 있으면 무엇 때문에 결과가 바뀌었는지도 모호해진다. 테스트를 작성하는 과정이 모듈·응집도·관심사 분리에 피드백을 준다.
  • 공개한 행위를 검증하면 구현 변경의 자유가 남는다. 내부 필드와 호출 순서를 고정한 테스트는 리팩터링마다 함께 깨질 수 있다. 경계에서 보장하는 입력·출력을 확인하면 같은 행위를 유지하며 내부를 바꿀 수 있다. 자동화는 이 비교를 반복할 비용을 낮춰 학습한 구조 변경을 실행하기 쉽게 한다.
03

출시 가능성과 파이프라인의 범위

  • 파이프라인 통과는 출시 가능한 후보를 뜻해야 한다. 통과 뒤 다른 부분과 결합해 광범위한 재검사가 필요하다면 아직 일부만 검증한 것이다. 저장소나 팀의 편의가 아니라 실제 독립 배포 단위로 평가 범위를 정한다.
  • 운영에 갈 바로 그 산출물을 평가한다. 검사 뒤 새로 빌드하거나 다른 변경을 섞으면 앞서 통과한 대상과 운영 후보가 달라진다. 같은 버전·같은 조건의 반복 검사가 일관된 결과를 내야 후보 자체에 대한 판단도 신뢰할 수 있다.
  • 공동 배포의 필요성은 큰 구조의 결합을 보여준다. 작은 수정 하나에도 다른 팀의 일정과 통합 승인이 필요하다면 변경 자율성이 부족할 수 있다. 실제 결합 단위를 함께 검증할지, 경계를 바꿔 독립 배포할지 판단한다. 테스트 용이성과 배포 용이성은 작은 코드와 큰 시스템 양쪽에서 변경 능력을 지키는 기준이다.

한눈에 정리

  • 미래를 모두 예측하기보다 요구를 배운 뒤 바꿀 능력을 지킨다.
  • 테스트 준비·실행·관찰의 어려움에서 결합과 경계 문제를 찾는다.
  • 최종 출시 단위와 검사 대상을 맞춰야 통과 결과가 배포 판단에 쓰인다.

Chapter 4. Improve Your Architecture with the Modularity Maturity Index

MMI를 이용한 구조적 부채의 평가

이 장의 핵심

  • 구조적 부채는 코드량보다 책임과 의존 관계의 얽힘에서 드러난다.
  • 모듈화·위계·패턴 일관성을 평가하고 실제 구조와 목표를 비교해 개선 대상을 고른다.

학습 목표

  • MMI의 평가 관점과 가중 계산을 설명하고, 점수가 가리키는 구조적 문제를 조사한다.

핵심 내용과 설명

01

구조적 부채와 세 평가 관점

  • 기능을 추가하면서 구조를 정리하지 않으면 변경 비용이 쌓인다. 긴 메서드 같은 구현 문제는 코드 분석으로 찾기 쉽다. 여러 클래스·패키지의 책임과 의존이 어긋난 설계 문제는 팀의 의도까지 알아야 판단할 수 있다. 모듈화 성숙도 지수인 MMI는 이 구조적 부채를 평가한다.
평가 축 왜 이해 비용에 영향을 주는가 확인할 관계
모듈화 45% 의미 있는 단위로 세부를 묶어야 이해 범위가 줄어듦 책임·경계·인터페이스·크기 균형
위계 30% 계층의 방향이 안정돼야 추론할 순서가 생김 계층 위반·클래스와 패키지의 순환
패턴 일관성 25% 익힌 역할이 반복돼야 매번 새로 해석하지 않음 의도한 패턴과 실제 코드 역할의 대응
  • 모듈 개수는 모듈화의 증거가 아니다. 사례의 빌드 단위는 아홉 개지만 하나가 950,860 LOC이고 나머지 여덟 개의 합은 84,808 LOC다. LOC는 코드 줄 수다. 대부분의 코드가 한곳에 몰려 있으므로 개수보다 책임과 내부 구조를 조사해야 한다.
  • 포함 계층과 사용 방향은 다르다. 패키지가 폴더 안에 잘 정리돼도 아래쪽이 위쪽을 다시 참조하면 순환할 수 있다. 이름이 같은 패턴도 역할이 매번 다르면 오히려 잘못된 기대를 만든다. 도구로 관계를 추출하고 팀과 의미를 해석해야 한다.
02

관측값의 점수 변환과 가중 합산

  • 관측값을 먼저 평가하고 그다음 합산한다. 같은 하위 범주의 기준별 관측을 0~10점으로 바꾸고 평균을 낸다. 그 범주 평균에 가중치를 곱한다. 범주별 기여를 더하면 최종 MMI도 0~10점이다. 책임 명확성처럼 정성 판단이 필요한 항목도 포함한다.

  • 총점에서 문제 위치로 내려간다. 6.1이라는 숫자만 올리려 하지 말고 낮은 단위 크기와 패턴 일관성이 어떤 변경 비용을 만드는지 본다. 저자의 구간은 8~10이면 낮은 부채, 4~8이면 리팩터링 검토, 4 미만이면 리팩터링과 교체의 타당성 비교다. 자동 교체 명령으로 쓰는 구간은 아니다.
03

실제 구조와 목표 구조의 비교

  • 소스에서 실제 의존을 추출한 뒤 목표와 대응시킨다. 팀이 알고 있는 부채를 모으고, 분석 도구에서 클래스·패키지·모듈 관계를 얻는다. 팀이 의도한 계층과 패턴을 그 관계에 겹쳐 어떤 위반이 어디에 있는지 찾는다.
  • 불일치는 판단의 출발점이다. 계획이 여전히 적절하다면 코드를 리팩터링한다. 구현이 더 나은 해법이라면 목표 설계를 갱신한다. 둘 다 적절하지 않으면 새 목표를 만든다. 목표 문서가 있다는 이유로 실제 코드를 무조건 되돌리지 않는다.
  • 개선 목록과 후속 관찰까지 연결한다. 팀과 평가자가 문제 범위·비용·우선순위를 정해 일상 변경에 포함한다. 다시 관계와 점수를 살펴 부채가 줄었는지 본다. 코드량이 작거나 시스템이 새롭다는 이유만으로 구조가 건강하다고 가정하지 않는다.

한눈에 정리

  • MMI는 모듈화·위계·패턴 일관성으로 구조적 부채를 나눠 본다.
  • 관측 → 기준별 점수 → 범주 평균 → 가중 합산의 순서다.
  • 총점은 조사 방향을 정하고, 실제 구조와 목표의 비교가 개선 대상을 정한다.

Chapter 5. Private Builds and Metrics: Tools for Surviving DevOps Transitions

공유 전 검증과 숨은 개발 비용

이 장의 핵심

  • 자동화가 있어도 개발자가 진단·수정할 수 없으면 피드백이 막힌다.
  • 최신 공통 코드와 자기 변경을 공유 전에 검증하고, 뒤늦은 통합·복구 비용을 함께 관찰한다.

학습 목표

  • private build의 검증 위치를 설명하고, 세 지표의 조합으로 개발 흐름의 문제를 조사한다.

핵심 내용과 설명

01

자동화 책임과 개발자의 통제

  • 검사를 실행하는 도구와 실패를 해결할 능력은 다르다. 별도 자동화 팀만 환경과 스크립트를 수정할 수 있으면 개발자는 빌드가 깨져도 티켓 처리를 기다린다. QA도 다음 결과를 기다린다. 깨진 빌드를 즉시 복구하려면 진단 지식과 수정 권한이 함께 있어야 한다.
  • 발견이 늦어질수록 문제를 전달하는 일이 늘어난다. 자기 작업 중 오류를 찾으면 곧바로 재현·수정할 수 있다. QA나 운영에서 발견하면 접수·분류·담당자 확인·수정 결과 전달이 추가된다. 따라서 개발 흐름을 개선하려면 오류 수와 함께 발견 위치를 봐야 한다.
02

최신 변경과 private build

  • private build는 공유 전 통합 검증이다. 개발자가 통제하는 전용 환경에서 최신 공통 코드와 자기 변경을 함께 빌드하고 확인한다. 통과한 뒤 공통 코드라인에 넣는다. 개인 노트북만을 뜻하지 않으며 전용 클라우드 환경도 가능하다. 자기 단위 테스트만 돌리는 것보다 넓은 절차다.
  • 안정된 옛 환경은 새 호환 문제를 숨길 수 있다. 사례의 프런트엔드는 관리하기 쉬운 옛 API를 사용했다. 최신 백엔드가 보내는 미정의 값 때문에 QA에서 실패했다. 다른 직군도 최신 백엔드와 데이터를 실행·관리하게 교육해 공유 전에 같은 문제를 드러내도록 바꿨다.
사례의 실패 빠져 있던 검증 앞당긴 확인
최신 API의 값 때문에 화면 실패 최신 코드·데이터의 조합 프런트엔드도 최신 백엔드로 검사
API 타입이 계약과 불일치 소비자와의 계약 확인 백엔드도 프런트 환경의 사용 사례 확인
DB 변경이 코드와 충돌 변경 전후의 호환 관계 DBA·백엔드가 재현 검사와 수정을 함께 공유
  • 통제 가능한 작은 검사부터 시작한다. 자동화가 부족해도 핵심 API 계약과 사용 경로를 임시 수동 검사로 확인할 수 있다. 외부 환경이 불안정하면 가짜 구현으로 자기 검증을 계속한다. 반복되는 수동 작업은 자동화 대상으로 삼고, 가짜 구현 밖의 실제 통합도 후속 검사로 확인한다.
03

세 지표의 조합과 조사

지표 기록할 대상 답하는 질문
피드백까지의 시간·노력 구현 뒤 QA·소비자 등에서 유효한 반응을 얻는 지연 수정 결과를 알기까지 어디서 기다리는가
반복당 피할 수 있었던 통합 문제 공유 전 검사로 쉽게 잡을 수 있었던 후속 결함 검증이 뒤로 밀렸는가
반복당 trunk 복구 시간 공통 코드 파손을 디버깅·수정한 시간 안정성을 누군가의 복구 노동으로 유지하는가
  • QA의 적은 결함 뒤에 복구 노동이 숨을 수 있다. 누군가가 계속 공통 코드인 trunk를 고쳐 멀쩡한 결과만 QA에 넘기면 결함 수는 낮다. 하지만 기능 개발 시간은 복구에 쓰인다. trunk 복구 시간을 함께 봐야 이 비용이 드러난다.
관측 조합 먼저 조사할 가설
느린 피드백·많은 통합 결함·적은 복구 앞단 검사가 약해 QA에서 늦게 발견하는가
적은 통합 결함·많은 복구 시간 일부 사람이 파손을 계속 수리하는가
느린 피드백·두 결함 지표 모두 낮음 실제로 안정적인가, 오류 탐지도 늦는가, 승인만 막혔는가
  • 조합에서 실제 사건으로 내려간다. 같은 낮은 값도 안정성과 미탐지를 모두 뜻할 수 있다. 회고에서 결함이 언제 발견됐는지 분류하고, 환경 접근과 검사 실행을 확인한다. 세 수치는 자동 원인 판정식이 아니다.
04

사전 검사와 전체 비용의 비교

  • 검사 시간은 이후 비용과 비교한다. private build는 환경 준비와 실행 시간을 더한다. 그 대신 공유 후의 복구·QA 왕복·티켓 처리·대기를 줄일 수 있다. 검사하지 않는 시간을 0이라고 놓으면 뒤에서 발생하는 작업이 계산 밖으로 빠진다.
  • 안정된 공통 코드가 품질 측정의 기반이다. 계속 깨지는 환경에서는 성능 검사 실패가 구조 때문인지 환경 파손 때문인지 구별하기 어렵다. 공유 전 검증 → 안정된 trunk → 신뢰할 수 있는 아키텍처 검사로 이어져야 한다.

한눈에 정리

  • private build는 최신 공통 변경과 자기 작업의 통합을 공유 전에 검증한다.
  • 피드백 지연·피할 수 있는 통합 결함·복구 노동을 함께 봐야 숨은 비용이 드러난다.
  • 사전 검사의 부담을 후속 조정·복구를 포함한 전체 비용과 비교한다.

Chapter 6. Scaling an Organization: The Central Role of Software Architecture

조직 목표와 서비스 경계의 연결

이 장의 핵심

  • 서비스 수를 늘려도 업무와 팀의 책임이 얽혀 있으면 독립적인 전달은 어려워진다.
  • 조직 목표에서 업무 흐름·기술 지표로 내려가 경계를 바꾸고 효과를 관찰한다.

학습 목표

  • KPI 가치 트리를 설명하고, 업무·구현·팀 경계의 불일치를 개선 실험으로 연결한다.

핵심 내용과 설명

01

서비스 분할과 실제 변경 자율성

  • 가상 사례의 회사는 팀과 서비스를 늘렸지만 공동 배포가 남았다. 기능 하나를 내보내려면 여러 서비스와 팀을 함께 조정했다. 중복 기능 때문에 소유권도 모호했다. 모놀리스를 나눴다는 구조 변화가 독립 전달이라는 효과로 이어지지 않은 것이다. 이 이야기는 여러 경험을 합성한 사례다.
  • 배치 방식과 책임 구조를 따로 본다. 모놀리스도 모듈 경계가 건강할 수 있다. 마이크로서비스도 서로 얽혀 있으면 기존 조정 비용에 네트워크의 지연·실패가 더해진다. “서비스가 작은가”보다 “이 변경을 어느 팀이 얼마나 독립적으로 끝낼 수 있는가”를 묻는다.
  • 실제 소통과 업무를 함께 조사한다. 조직도만으로는 누가 누구의 지식을 기다리는지 알기 어렵다. 업무 전문가·제품·개발이 사건의 순서와 책임 영역을 함께 그리는 EventStorming 워크숍을 사용해 암묵적 경계를 드러낸다.
02

업무 흐름과 KPI 가치 트리

  • 업무 흐름 위에 서비스와 팀을 겹친다. 먼저 견적 요청·제안·계약 활성화 같은 사건과 규칙을 이해한다. 그다음 현재 서비스와 소유 팀을 대응시킨다. 한 팀이 서로 무관한 여러 영역을 맡거나 한 영역이 여러 팀으로 갈라져 있으면 지식·조정 부담이 커질 수 있다.
  • 상위 목표를 실제로 바꿀 수 있는 질문으로 좁힌다. 사례의 고객은 알맞은 보장과 가격을 찾으려 한다. 회사는 활성화된 계약을 늘리려 한다. 이 둘을 연결하면 활성화 비율과 요청부터 완료까지의 시간이 도메인 목표가 된다. 그 아래 적합한 제안을 찾는 시간·수동 정정 같은 업무 지표를 고른다.
  • 가치 트리는 개선의 연결 가설이다. 조직 KPI는 넓은 결과를 보고 도메인 KPI는 특정 업무를 본다. 기술 지표는 그 결과에 기여할 변화의 신호다. 배포가 빨라져도 고객의 완료율이 좋아지지 않을 수 있다. 따라서 아래 지표의 변화와 위 결과를 함께 관찰한다. 같은 KPI의 계산과 범위도 공동으로 맞춰야 전후 비교가 가능하다.
03

중앙 의존의 분리 실험

  • 중앙 정보 서비스에 여러 도메인이 모이면 릴리스도 얽힌다. 여행 보험 서비스가 자기 계약 정보를 바꿀 때마다 중앙 서비스 담당 팀과 일정을 맞춰야 했다. 새로운 경계가 해당 정보를 스스로 관리할 수 있는지, 의존과 기존 데이터를 옮기는 비용이 얼마인지 알아보려 한다.
  • 작은 확인 뒤 책임을 옮긴다. 먼저 새 요청을 중앙 서비스와 새 서비스 양쪽에 저장해 새 경계가 정보를 맡을 수 있는지 살핀다. 실험들이 성공하면 새 서비스를 해당 도메인의 기준 저장소로 삼는다. 이 장은 이중 저장의 충돌·트랜잭션 구현을 설명하지 않으므로 완성된 이전 절차로 사용하지 않는다.
  • 경계 변경의 기대 효과를 측정한다. 가설은 공동 릴리스 조정이 줄면 배포 빈도가 늘고 변경 실패율이 낮아진다는 것이다. 실험 중 기능 전달이 줄어드는 비용도 미리 설명한다. 사례는 성공을 서술하지만 전후 측정값을 제시하지 않는다. 정량 효과까지 확인된 실험으로 확대하지 않는다.
04

병목 변화와 지표의 갱신

  • 경계가 개선되면 다음 병목을 찾는다. 사례에서는 이후 수요 증가를 사람의 수작업 증가만으로 감당하기 어려워졌다. 제안을 찾는 시간보다 처음 제시한 선택을 수락하는 비율에 초점을 옮겼다. 상위 목표가 같아도 그 목표에 기여할 하위 지표는 바뀔 수 있다.
  • 배포 능력과 사용자 노출도 구별한다. 모바일 앱은 자주 배포할 능력이 있어도 사용자에게 업데이트를 매번 요구하는 것이 최선은 아닐 수 있다. 사례는 alpha·beta·production 채널을 나눠 모든 변경을 alpha에서 확인했다. 팀의 실제 흐름과 맥락을 이해해야 수치를 강제 목표나 순위로 오용하지 않는다.

한눈에 정리

  • 업무 사건 → 서비스 책임 → 팀 소유권을 겹쳐 실제 조정 부담을 찾는다.
  • 조직 KPI → 도메인 결과 → 업무·기술 관측으로 개선 가설을 연결한다.
  • 경계 변경을 작게 검증하고, 다음 병목에 맞춰 하위 지표를 갱신한다.

Quiz

01

업무 흐름과 규칙, 구현 서비스의 경계, 팀 소유권을 대응시킨다. 서비스 개수보다 변경이 경계를 얼마나 넘나드는지 확인한다.

02
배포 빈도가 늘었는데 계약 활성화율은 그대로다. 가치 트리를 어떻게 해석해야 하는가?

기술 지표는 상위 결과에 기여한다는 가설의 신호다. 실제 업무 병목과 결과를 다시 조사해 연결 가설을 보정해야 한다.

03
경계를 정리한 뒤 병목이 수동 제안 업무로 옮겼다. 기존 기술 지표만 계속 보면 무엇을 놓치는가?

상위 목표를 가로막는 새 업무 병목을 놓친다. 조직 목표는 유지하면서 제안 품질·처리 능력 등 필요한 하위 관측을 갱신해야 한다.

Chapter 7. The Role of Measurement in Software Architecture

품질 측정과 아키텍처 의사결정

이 장의 핵심

  • 측정은 지금 개선할 문제를 고르고 변경 효과를 확인하는 데 쓰인다.
  • 초기 추정에서 코드·실행·운영 관측으로 근거를 갱신한다.

학습 목표

  • 시스템 성숙도에 맞는 측정을 선택하고, 성능·확장성·복구 목표의 조건을 구별한다.

핵심 내용과 설명

01

측정과 개선의 순환

  • 아키텍처에는 언제나 더 할 일이 남는다. 현재 품질과 추세를 보면 지금 주의를 기울일 문제와 충분히 개선한 문제를 구별할 수 있다. 측정 → 우선순위 → 결정 → 변경 → 재측정으로 이어져야 값이 행동의 근거가 된다.
  • 시스템이 만들어지는 정도에 따라 근거도 달라진다. 초기에는 설계와 용량 모델을 분석한다. 코드가 생기면 복잡도·결합을 구한다. 실행 가능해지면 요청 시간과 복구를 검사한다. 운영에서는 실제 사용과 장애 기록으로 추정을 보정한다.
시점 얻을 수 있는 근거 예와 다음 사용
설계 구조 검토·추정 모델 예상 데이터량으로 용량 판단
구현 정적 코드 분석 복잡한 부분의 리팩터링 검토
실행 가능 부하·복구 실험 허용 응답과 복구 경로 확인
운영 실제 요청·성장·장애 초기 모델 보정·다음 개선 선정
  • 기록 방식도 질문에 맞춘다. 로그는 개별 사건, 트레이스는 한 요청에 속한 사건의 연결, 메트릭은 기간별 특성의 수치다. CPU처럼 쉽게 모으는 값에만 머물면 사용자가 겪는 긴 요청을 놓친다. 피트니스 함수는 얻은 값을 기준과 비교하게 하지만 실제 계측을 대신하지는 않는다.
02

성능과 확장성의 측정

  • 성능은 지정한 작업과 부하에서 본다. 한 요청이 끝나는 시간은 지연 시간, 일정 시간에 완료한 건수는 처리량이다. 요청 종류·데이터·자원·설정이 달라지면 결과도 달라진다. 한 번의 응답보다 분포를 보고 평균과 긴 요청을 함께 살핀다.
  • 확장성은 자원 변화와 처리 능력 변화의 관계다. 먼저 허용 응답 시간을 고정한다. 사례는 5초 동안의 처리 건수를 재면서 평균 0.5초, 요청 95%가 2초 미만이라는 조건을 둔다. 자원을 20%씩 늘린 뒤 그 조건을 지킨 처리량을 비교한다. 처리 건수만 늘고 응답이 무너지면 같은 품질의 확장이 아니다.
  • 비용과 사람의 작업도 확장 제약이다. CPU만 늘렸는지 메모리·I/O도 바꿨는지 기록한다. 기술 처리량이 늘어도 같은 비율로 수동 운영 인력이 필요하면 전체 확장은 제한된다. 병목을 찾으려면 자원 조합과 허용 성능을 함께 남겨야 한다.
03

가용성과 데이터 복구의 구별

  • 실패 빈도와 복구 능력은 별도다. 장애 사이 평균 시간 MTBF는 얼마나 자주 실패하는지 본다. 평균 복구 시간 MTTR은 실패 뒤 돌아오는 데 걸리는 시간을 본다. 운영 이력이 부족해 실패 빈도를 아직 몰라도 복구 경로는 미리 시험할 수 있다.
  • 데이터 손실과 복구 시간은 다른 목표다. RPO는 감수할 데이터 손실 범위다. 최근 10분의 갱신을 잃을 수 있는지처럼 정한다. RTO는 데이터를 다시 이용하기까지 허용할 시간이다. 일부 데이터로 서비스를 먼저 열 수 있다면 서비스 복구와 전체 데이터 복구의 시점은 다를 수 있다.
  • 사용자 기능과 실패 시나리오로 묶는다. DB·네트워크 등 각 구성요소는 다르게 실패한다. 하나의 구성요소 복구값이나 가용률 숫자만으로 전체 경험을 대표하기 어렵다. 중요한 기능이 언제 어떻게 영향을 받는지 정한 뒤 복구 방법과 데이터 요구를 함께 시험한다.
04

대리 지표와 측정의 수명

  • 보안 발견 건수는 검사에서 찾은 결과다. 같은 10건이라도 심각도와 오탐이 다르다. 발견이 0이어도 미탐지가 남을 수 있다. 일관된 검사·좋은 데이터·전문가 해석을 결합한다. 측정하기 쉬운 숫자를 품질 전체로 읽지 않는다.
  • 가상 사례 Civis는 관측을 점진적으로 넓힌다. 초기 저장량 모델을 보관하고, 코드 분석을 추가한 뒤, 주요 흐름의 응답·복구를 검사한다. 운영의 실제 데이터 증가와 장애 기록으로 모델을 수정한다. 초기 보안 분석은 불안정할 수 있어 측정부터 도입하고 즉시 빌드 차단을 강제하지 않았다.
  • 다음 선택을 바꿀 만큼 정밀하면 된다. 더 정확한 값이 우선순위나 결정을 바꾸지 못한다면 정밀화 비용을 다른 문제에 쓸 수 있다. 측정 뒤 개선할 시간을 확보하고, 더 이상 쓰이지 않는 관측은 정리한다.

한눈에 정리

  • 설계 추정 → 코드 분석 → 실행 검사 → 운영 관측으로 근거를 보정한다.
  • 확장성은 허용 성능을 지킨 처리량과 자원·비용의 변화로 본다.
  • 실패 빈도·서비스 복구·허용 데이터 손실·데이터 복구 목표를 구별한다.

Chapter 8. Progressing from Metrics to Engineering

측정값을 반복 가능한 검증으로 전환

이 장의 핵심

  • 관측값에 허용 기준과 반복 실행을 붙이면 구조 위반을 작은 변경에서 발견할 수 있다.
  • 교체 후보는 실제 입력에서 기존 구현과 비교하며 결과와 성능을 함께 확인한다.

학습 목표

  • 의존·호출 정책을 실행 가능한 검사로 연결하고, 기존 응답을 유지하는 교체 실험의 원리를 설명한다.

핵심 내용과 설명

01

순환 의존의 조기 발견

  • 수치가 있다는 것만으로 위반을 막지는 못한다. A가 B를, B가 C를, C가 A를 사용하면 A만 재사용하려 해도 나머지가 따라온다. 대시보드에서 나중에 순환을 발견하면 이미 더 많은 코드가 관계에 기대고 있을 수 있다. 변경 때마다 같은 규칙을 검사하면 고리가 작을 때 알 수 있다.
  • 객관적 기준과 실행을 연결한다. “패키지 사이에 순환이 없어야 한다”는 규칙을 코드 관계에 적용한다. 분석 → 위반 판정 → 실패 알림을 CI/CD의 반복 과정에 넣으면 모든 구현자가 같은 기준을 확인한다. ArchUnit 같은 도구는 이 관계를 검사하는 수단의 사례다.
  • 넓은 품질은 관찰 가능한 특성으로 나눈다. 신뢰성 전체를 단일 숫자로 만들기보다 가용성·무결성 등 확인할 대상을 구체화한다. 피트니스 함수는 코드 검사뿐 아니라 운영 감시·장애 실험도 포함하는 평가 방식이다.
02

설계 경계와 실제 호출의 검사

  • 계층의 역할을 패키지와 대응시킨다. Controller → Service → Persistence라는 설계라면 어떤 방향을 허용하고 어떤 우회·역참조를 금지할지 정한다. 그림에 계층을 쌓았다는 사실만으로 구현이 그 방향을 지키지는 않는다.
  • 실행 중 호출은 운영 관측에서 얻는다. 사례의 오케스트레이터는 세 도메인 서비스를 조정하지만 서비스끼리 직접 호출하지 않도록 한다. 호출 로그의 출발지·목적지를 허용 관계와 비교하면 이를 검사할 수 있다. 최근 24시간 로그를 주기적으로 분석하거나 호출 이벤트마다 판단하는 방법이 있다. 정적 패키지 검사와 다른 입력을 쓰는 것이다.
  • 검사 변경도 실행 계기가 된다. 애플리케이션 코드가 바뀌지 않는 오래된 프로젝트에도 새 보안 검사를 실행할 경로가 필요하다. 의존 라이브러리 검사나 피트니스 함수가 바뀌면 해당 빌드를 다시 실행해 발견과 알림으로 연결한다. 중요한 반복 규칙에 집중해 개발을 방해하는 규칙망을 피한다.
03

실제 요청에서의 교체 실험

  • 단위 테스트가 모르는 운영 조건을 비교한다. GitHub의 병합 구현 교체 사례에서는 기존 명령행 Git 경로와 새 메모리 기반 후보를 함께 넣었다. 기존 구현을 항상 실행하고 일부 실제 요청에서 후보도 실행했다. 사용자에게는 기존 결과를 주면서 후보의 차이를 배운다.
  • 같은 입력의 결과·예외·시간을 기록한다. 사례는 후보 실행 비율을 1%로 두고 실행 순서를 무작위화했다. 순서가 성능 비교를 편향시키지 않게 하려는 선택이다. 후보의 예외는 기록하되 사용자 응답에 전달하지 않는다. 발견한 불일치를 수정하고 다시 실험한다.
  • 응답 분리가 실행 위험까지 없애지는 않는다. 두 구현을 실행하는 비용은 남는다. 상태를 바꾸는 함수를 두 번 실행하면 부작용이 중복될 수 있다. 실제 입력을 후보에 적용해도 안전한지 검토해야 한다.
04

불일치와 성능의 해석

  • 작은 오류는 전체 실행량에 묻힐 수 있다. 같은 축에 수천 건의 실행과 1~수 건의 오류를 그리면 오류가 거의 보이지 않는다. 오류만 분리해 보면 반복되는 불일치가 드러난다. 시각화도 답하려는 질문별로 나눠야 한다.
사례의 실행 시간 요약 후보 기존

표는 노트에 기록된 그래프 범례의 값을 정리했다. 시간 단위는 명확하지 않아 밀리초로 단정하지 않는다. 후보가 두 구간 모두에서 더 짧다는 관계를 읽는다. 평균 응답만 좋아져도 긴 요청은 악화할 수 있으므로 높은 백분위도 함께 본다.

유지보수성 지표와 구조 개선의 판단

이 장의 핵심

  • 유지보수성은 의존 범위·순환의 집중·해체 부담·실제 변경 활동을 함께 봐야 이해할 수 있다.

학습 목표

  • 작은 의존 그래프에서 결합·순환 지표를 계산하고, 지표의 차이를 리팩터링 우선순위에 연결한다.

핵심 내용과 설명

01

의존 그래프와 CCD·ACD·PC

  • 작은 수정에 넓은 이해가 필요하면 의존 관계를 조사한다. 그래프의 노드는 파일 같은 분석 단위, A → B는 A가 B를 사용한다는 뜻이다. 직접 연결뿐 아니라 중간 요소를 거쳐 필요한 부분도 센다. 먼저 무엇을 노드로 보는지 정해야 시스템 간 비교가 가능하다.
노드 자기 자신을 포함해 필요한 노드 개수
A A·C·D·E·F 5
B B·C·D·E·F 5
C C·D·E·F 4
D D·F 2
E E 1
F F 1
  • 전체 의존 수에서 평균과 비율을 만든다. 누적 컴포넌트 의존 CCD는 5+5+4+2+1+1=18이다. 평균 컴포넌트 의존 ACD는 18÷6=3이다. 전파 비용 PC는 평균을 전체 노드 수로 나눈 3÷6=0.5, 즉 50%다. 평균적으로 전체 노드의 절반에 도달한다는 구조적 의미다. 실제 변경 때 절반을 반드시 수정한다는 예측은 아니다.
  • 같은 비율도 규모와 함께 읽는다. ACD가 100이면 전체 100개인 시스템에서는 전부, 전체 1,000개라면 일부에 해당한다. PC가 이 차이를 비율로 표현하지만 규모 효과를 모두 없애지는 않는다. 노드 수가 두 배로 늘 때 같은 PC를 유지하려면 CCD는 네 배가 돼야 한다. 코드가 늘면서 PC만 낮아졌다고 결합 개선으로 단정하지 않는다.
02

순환 그룹과 상대 순환도

  • 순환 그룹은 서로 직접·간접 도달할 수 있는 요소의 집합이다. A → B → C → A라면 하나만 이해하거나 재사용하려 해도 나머지가 따라온다. 의존 범위가 넓다는 사실에서 더 나아가 얼마나 큰 상호 의존 덩어리가 생겼는지 살핀다.
  • 참여 수가 같아도 집중도가 다르다. 100개가 하나의 그룹이면 큰 덩어리 전체를 함께 다뤄야 한다. 두 개짜리 그룹 50개라면 각각의 해체 범위는 작다. 상대 순환도는 그룹 크기를 제곱해 큰 그룹에 더 무게를 준다. 그룹 크기를 s, 전체 노드 수를 n으로 두면 다음과 같다.
상대 순환도 = 100 × √(그룹별 s²의 합) ÷ n
한 그룹 100개: 100 × √(100²) ÷ 100 = 100%
두 개씩 50그룹: 100 × √(50×2²) ÷ 100 ≈ 14.14%
  • 의존 방향을 바꾼 뒤 경로를 다시 확인한다. 인터페이스로 방향을 뒤집거나 상위 조정 객체로 상호작용을 옮기는 방법이 있다. 이름만 나누거나 인터페이스를 추가해도 실제 순환이 남을 수 있다. 파일 수준의 작은 순환과 패키지 경계를 넘는 큰 순환도 구별한다.
03

순환 해체 부담과 SDI

  • 그룹 크기만으로 끊을 작업량은 알 수 없다. 10개가 하나의 고리면 한 간선만 끊어도 순환이 풀린다. 모든 쌍이 서로 사용하는 10개라면 방향 간선이 90개이고 적어도 45개를 끊어야 한다. 상대 순환도는 같아도 해체 작업은 다르다.
  • 구조적 부채 지수 SDI는 끊을 관계와 사용 수를 함께 센다. 파일 A가 B의 메서드 세 개를 쓰면 파일 간 간선 하나 안에 세 사용 관계가 있다. SDI는 10×끊을 간선 수 + 그 간선의 사용 관계 가중치 합이다. 간선 1개·가중치 1을 끊으면 10×1+1=11이다. 상수 10은 의존 방향을 바꿀 기본 판단 부담을 반영한다.
  • 상대 순환도와 역할을 나눠 읽는다. 상대 순환도는 큰 순환의 집중을, SDI는 끊어야 할 관계의 부담을 근사한다. 실제 소요 인시를 그대로 예측하는 값은 아니다. 같은 점수라도 책임과 변경 이유를 보고 해체 방법을 고른다.
04

종합 지표 ML의 계산 의도와 한계

  • 유지보수성 수준 ML은 여러 관계를 모으려는 실험적 지표다. 먼저 순환 그룹을 한 논리 노드로 합쳐 순환 없는 층 구조를 만든다. 아래 요소가 위층의 얼마나 많은 요소에 영향을 주는지 계산한다. 위층에 미치는 영향이 작을수록 해당 요소의 기여가 커진다.
계산 단계 무엇을 하는가 왜 필요한가
순환 축약 서로 얽힌 그룹을 논리 노드 하나로 묶음 층과 영향 범위를 계산
기여 합산 실제 크기와 위층 영향 비율로 노드 기여 계산 넓은 변경 전파를 감점

  • 보정에는 평가자의 설계 판단이 들어간다. 노드 기여는 크기×(1−위층 영향 수÷위층 전체 수)÷전체 컴포넌트 수다. 예제의 A는 전체 12개 중 하나이고 위층 8개 중 3개에 영향을 줘 (1−3/8)÷12=5/96≈0.05208을 기여한다. 최상층은 위층이 없으므로 별도 처리한다. 보충 전개에서 기여 합은 53/96으로 첫 ML은 약 55.21%다.
  • 점수의 버전과 평가 수준을 확인한다. 작은 시스템 보정은 n<100일 때 (100−n)+(n/100)×ML₂다. n=12, ML₂=55라면 88+0.12×55=94.6%가 된다. 원래 구조가 갑자기 좋아진 것이 아니라 작은 규모에 대한 보정이다. 패키지 수준 대안값과 최종 결합 절차는 확보한 노트에서 완전히 재현할 만큼 명확하지 않다. 단일 ML만으로 전체 구조를 판정하지 않는다.
05

복잡도와 변경 활동의 결합

  • 복잡성과 크기를 나눠 본다. LOC는 코드량이다. 순환 복잡도는 조건·반복의 분기에서 독립 경로 구조를 근사한다. 중첩 깊이는 한 번에 따라가야 할 조건의 부담을 드러낸다. switch나 단락 평가를 세는 변형이 있으므로 도구 정의를 맞춘다. 단순 getter가 많아 복잡한 긴 메서드가 평균에 묻히지 않게 문장 수 가중도 고려한다.
  • 실제로 자주 바뀌는 복잡한 곳부터 조사한다. 최근 d일 변경 횟수, 추가·삭제 줄 수인 churn, 작성자 수를 함께 본다. 90일 churn rate가 2라면 추가·삭제의 합이 현재 파일 길이 두 배라는 뜻이다. 파일 전체를 정확히 두 번 교체했다는 뜻은 아니다. 작성자 수 역시 실제 지식의 직접 측정은 아니다.
  • 추가 지표는 다른 질문에 쓴다. Component Rank는 의존을 따라 자주 도달하는 공통 요소를 찾아 읽기 시작할 위치를 돕는다. LCOM4는 클래스 안의 메서드·필드 연결 묶음 수를 센다. 두 묶음이면 책임 분리 후보지만 상속 관계 등 맥락을 확인해야 한다. 높은 값 하나를 품질의 최종 점수로 취급하지 않는다.
06

한도와 추세를 이용한 지속 개선

  • 한도는 현재 위반, 추세는 악화 방향을 보여준다. 자동 빌드에서 같은 정의로 측정하고 값을 보관한다. 경고만 할 한도와 빌드를 중단할 한도를 구별한다. 아직 한도 안이어도 큰 순환이 계속 성장하면 일찍 조사할 수 있다.
  • 기존 시스템은 추가 침식을 막는 데서 시작한다. 처음부터 모든 위반을 없애려 하면 개발이 막힌다. 달성 가능한 기준을 두고 더 나빠지지 않게 한 뒤 월별·분기별로 줄인다. 측정값 → 실제 관계 조사 → 리팩터링 → 재측정으로 연결되는 소수 규칙을 유지한다.

한눈에 정리

  • CCD → ACD → PC는 전체 의존 합 → 노드당 평균 → 전체 대비 비율이다.
  • 상대 순환도는 집중, SDI는 해체 부담, ML은 여러 가정이 들어간 종합 신호다.
  • 복잡도와 실제 변경 활동을 겹쳐 개선 후보를 고르고 한도·추세로 지속 관찰한다.

Chapter 10. Measure the Unknown with the Goal-Question-Metric Approach

목표에서 필요한 관측을 찾는 GQM

이 장의 핵심

  • 목표를 판단할 질문을 먼저 만들고 그 질문에 답할 지표와 데이터를 고른다.
  • 측정을 설계하는 과정에서 빠진 관측과 모호한 구조적 책임도 드러난다.

학습 목표

  • 목표·질문·지표·데이터의 연결을 구성하고, 외부 의존 장애의 관측과 대응을 설계한다.

핵심 내용과 설명

01

목표와 질문에서 시작하는 측정

  • 모으기 쉬운 지표가 중요한 문제에 답한다는 보장은 없다. 기술 부채가 줄었는지처럼 모호한 문제는 먼저 어떤 관점에서 무엇을 개선할지 정한다. 그다음 진전을 판단할 질문을 만들고 필요한 값을 찾는다. 이 방법이 목표–질문–지표, GQM이다.
  • 데이터에서 목표까지 수집 이유를 설명할 수 있어야 한다. 장애 시작·복구 기록으로 장애 수와 복구 시간을 계산한다. 두 지표는 “얼마나 자주, 얼마나 오래 중단되는가”에 답한다. 그 질문들은 사용자 관점의 가용성 개선이라는 목표에 연결된다. 한 데이터가 여러 지표를 지원하고 한 질문에 여러 지표가 필요할 수 있다.
  • 목표를 구체화하며 질문도 다듬는다. 대상·목적·관심 문제·관점을 밝힌다. 사용자 가용성과 개발자 부채 감소는 같은 시스템에서도 다른 질문을 만든다. 당장 계산법을 모른다는 이유로 중요한 질문을 먼저 버리지 않는다.
02

공유 외부 서비스의 장애 사례

  • 외부 요청 예산을 여러 구성요소가 공유하고 있었다. 웹 요청은 내부 서비스와 큐를 거쳐 작업자로 전달된다. 작업자는 외부 Foo Service를 호출한다. 다른 팀도 같은 외부 서비스의 시간·일별 한도를 쓴다. 잠깐 외부 호출이 막혀도 큐가 버티면 사용자는 나중에 결과를 받을 수 있는 구조다.
  • 한 소비자의 재시도가 전체 한도를 소진했다. 주말 배치의 저장소 실패와 재시도 버그가 겹쳐 월요일 새벽 공유 API 한도가 소진됐다. 여러 구성요소의 호출이 거절되고 큐에 작업이 쌓였다. 몇 시간 뒤 작업 대기가 길어져 사용자에게 영향이 갔다. 한도 소진 시점과 사용자 피해 시점 사이에 대응할 여지가 있었다.
  • 버그 수정 뒤 목표를 다시 물었다. “사용자보다 먼저 외부 서비스 문제를 알고 완화할 수 있는가”를 목표로 삼았다. API 한도 여유, 외부 장애와 인증·연결 문제의 구별, 작업 실패, 적체 회복 능력이라는 질문을 만들었다. 그래야 단순 오류 건수보다 필요한 관측을 고를 수 있다.
03

04

빠진 관측과 재시도 책임의 개선

  • 호출이 없을 때는 실패 로그도 없었다. 사용자 요청에 따른 기록만으로는 무트래픽 중 외부 장애를 알 수 없다. 별도 heartbeat가 제공자의 사용량 조회 API를 주기적으로 호출해 도달성과 한도를 확인하도록 했다. 필요한 질문을 정하자 새 계측 구성요소가 필요하다는 사실이 드러난 것이다.
  • 재시도가 두 층에서 곱해지고 있었다. 한 작업이 5번 호출하고 큐가 그 작업을 10번 시도하면 5×10=50번의 실패 호출이 생길 수 있다. 공유 한도를 더 소모하므로 작업은 빨리 실패시키고 큐가 통제된 재시도를 맡도록 책임을 정했다. 예산과 외부 장애 상태를 고려할 위치를 한곳에 모은 것이다.
  • 관측을 대응 절차에 연결했다. 알림마다 원인 확인·오탐 제거·복구 방법을 정했다. 약 9개월 뒤 외부 서비스가 14시간 중단됐을 때는 10분 안에 알림을 받고 외부 문제를 확인했다. 큐는 정한 지수 백오프로 재시도했고 내부 사용자에게 먼저 알렸다. 외부 장애를 없앤 것이 아니라 탐지와 대응을 개선한 사례다.
05

공동 정의를 위한 워크숍

  • 결과물은 숫자 목록보다 연결된 합의다. 목표 초안을 준비하고 업무 전문가와 구조를 아는 개발자 등이 함께 질문을 모은다. 질문별 지표를 연결한 뒤 원래 목표를 평가하는지 다시 본다. 그다음 정의·데이터·우선순위·수집 작업을 정한다.
  • 모든 값을 당일 계산할 필요는 없다. 무엇을 왜 모으고 누가 어떤 작업을 할지 알아야 한다. 목표–질문–지표–데이터를 왕복하며 빠진 계측과 책임을 발견하는 것이 핵심이다. 대시보드 항목 추가에서 끝나지 않고 실제 구조와 행동으로 이어진다.

한눈에 정리

  • 목표 → 판단 질문 → 지표 → 원시 데이터로 수집 이유를 연결한다.
  • 외부 한도·상태·작업 결과·큐 회복 능력을 함께 봐야 사용자 영향 전에 대응할 수 있다.
  • GQM은 관측의 빈틈과 중복 책임을 드러내 구조·대응 개선으로 이어진다.
