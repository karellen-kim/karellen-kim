01
TL;DR

한 줄로 이해하기

분산 트랜잭션의 핵심 문제는 여러 독립 저장소에 걸친 변경을 원자적으로 완료하거나 되돌리는 것이다. 단일 DB라면 ACID가 해결하지만, 서비스가 분리되면 하나의 커밋을 공유할 수 없다. 각 기법은 일관성·가용성·복잡도 사이에서 서로 다른 점을 선택한다.

01

2PC — 강한 일관성, 블로킹 프로토콜

Coordinator가 참여자 전원에게 Prepare(준비 가능?), 전원 Yes면 Commit을 보낸다. 데이터베이스 수준의 XA 표준으로 구현된다. 문제: Coordinator 장애 시 참여자들이 무한 대기(blocking)에 빠진다. 락이 길게 유지되어 처리량이 낮다. 마이크로서비스 간에는 거의 사용하지 않는다.

02

Saga — 보상 트랜잭션으로 결과적 일관성

긴 트랜잭션을 로컬 트랜잭션 시퀀스로 분해한다. 중간에 실패하면 이미 완료된 단계를 되돌리는 보상 트랜잭션(Compensating Transaction)을 역순으로 실행한다. 락을 오래 잡지 않아 가용성이 높고 마이크로서비스 아키텍처에 자연스럽게 맞는다. 최종 일관성(Eventual Consistency)을 수용해야 한다.

03

TCC — 비즈니스 레벨 잠금으로 준실시간 확정

Try: 자원을 예약(잠금 없이 비즈니스 레벨로 보류). Confirm: 예약을 확정. Cancel: 예약을 해제. 2PC와 달리 DB 락이 아닌 애플리케이션 레벨 상태 관리로 원자성을 구현한다. 모든 참여 서비스에 Try/Confirm/Cancel API를 구현해야 하는 부담이 있다. Alibaba의 Seata 프레임워크가 대표적이다.

04

Outbox Pattern — 메시지 발행 보장

비즈니스 데이터와 이벤트를 같은 DB 트랜잭션으로 함께 기록한다(outbox 테이블). 별도 프로세스(CDC 또는 polling)가 outbox를 읽어 메시지 큐(Kafka 등)에 발행한다. 발행 실패 시 재시도하므로 at-least-once 발행이 보장된다. 분산 트랜잭션 없이 이벤트 발행 정합성을 달성하는 가장 실용적인 패턴이다.

05

Temporal / Conductor — Saga 오케스트레이션 엔진

Saga Orchestration을 직접 구현하면 상태 관리, 재시도, 타임아웃, 보상 로직이 복잡해진다. Temporal(Uber의 Cadence 후속)은 워크플로우를 코드로 정의하고 실행 히스토리를 내구성 있게 보관한다. Stripe, Netflix, Airbnb가 Temporal을 사용한다. Netflix의 Conductor는 JSON으로 워크플로우를 정의하는 대안이다.

06

CRDT — 충돌 없는 수학적 병합

CRDT(Conflict-free Replicated Data Type)는 동시 업데이트가 결정론적으로 병합되도록 수학적으로 설계된 데이터 구조다. 락이나 코디네이터 없이도 최종 일관성을 보장한다. G-Counter(단조 증가), PN-Counter(증감), LWW-Register(최신 타임스탬프 우선), OR-Set(추가·삭제 모두 가능한 집합). Riak, Cassandra 카운터, Redis RedisJSON이 활용한다.

기법 도감

012PC — Two-Phase Commit

Phase 1 (Prepare): Coordinator가 모든 참여자에게 Prepare 메시지를 보낸다. 각 참여자는 트랜잭션을 실행하고 커밋 가능 여부를 응답한다. 이 시점에서 DB 락이 걸린다.

Phase 2 (Commit/Abort): 전원 Yes면 Commit, 하나라도 No면 Abort를 보낸다. 블로킹 문제: Phase 2 전송 중 Coordinator가 장애나면 참여자는 락을 건 채로 응답을 기다린다. 3PC는 이 문제를 완화하지만 네트워크 파티션 시 여전히 불완전하다.

사용처

동일 DB 클러스터 내 샤드 간 트랜잭션(MySQL Cluster, PostgreSQL XA). 마이크로서비스 간에는 사용하지 않는다. 락 유지 시간이 길어 처리량이 낮고 Coordinator SPOF가 허용 불가하기 때문이다.

02Saga — Choreography (안무형)

중앙 조정자 없이 이벤트 기반으로 각 서비스가 이전 서비스의 이벤트를 구독하고 자신의 로컬 트랜잭션을 수행한 후 다음 이벤트를 발행한다. 결합도가 낮고 서비스가 독립적이다.

단점: 이벤트 흐름을 한눈에 파악하기 어렵다. 보상 트랜잭션 구현 시 순환 이벤트 발생 위험이 있다. 서비스가 4개를 초과하면 복잡도가 급격히 상승해 디버깅이 어렵다. 분산 추적(Jaeger, Zipkin)이 필수다.

적합한 경우

서비스 수가 3개 이하이고, 팀이 각 서비스를 독립적으로 배포해야 하며, 중앙 조정 서비스가 SPOF가 되는 것을 피하고 싶을 때. 흐름이 단순하고 선형일 때 유리하다.

↓ 구독
결제 서비스 → 결제 처리 → PaymentProcessed 이벤트
↓ 구독

보상: InventoryReleased → PaymentRefunded → OrderCancelled

03Saga — Orchestration (오케스트레이션형)

Saga Orchestrator가 각 단계를 직접 호출하고 결과를 수신한다. 전체 흐름이 Orchestrator 코드에 집중되어 있어 가시성이 높다. 실패 시 보상 트랜잭션 호출도 Orchestrator가 결정한다. Temporal, Netflix Conductor 같은 워크플로우 엔진이 Orchestrator 역할을 한다.

단점: Orchestrator 자체가 SPOF가 될 수 있다(워크플로우 엔진은 이를 DB 기반 상태 저장으로 해결). 각 서비스와 Orchestrator 간 통신 인터페이스를 유지해야 한다.

적합한 경우

복잡한 비즈니스 흐름(조건 분기, 병렬 단계, 재시도 정책이 다양할 때), 5개 이상의 서비스가 관여하는 경우, 중앙에서 모니터링과 운영이 필요한 경우. Uber의 결제·배달 흐름, Stripe의 결제 흐름이 이 방식을 사용한다.

04TCC — Try-Confirm-Cancel

Try: 자원을 비즈니스 레벨로 예약한다(실제 차감 없이 "보류" 상태로 표시). DB 락 없이 애플리케이션 상태 칼럼으로 관리한다. Confirm: 모든 Try가 성공하면 보류 → 확정으로 전환. Cancel: 하나라도 Try 실패 시 나머지 서비스의 Try를 취소(보류 해제).

2PC와의 차이: DB 수준 락 없이 애플리케이션 레벨 상태 전이로 구현하므로 처리량이 높다. 단, 모든 참여 서비스가 Try/Confirm/Cancel 3개 API를 구현해야 한다. 멱등성이 필수 — Confirm/Cancel이 중복 호출되어도 결과가 같아야 한다.

Alibaba Seata

Alibaba의 오픈소스 TCC 프레임워크. AT 모드(자동 보상), TCC 모드(수동 구현)를 지원한다. 중국 전자상거래의 대규모 결제 트랜잭션을 처리하는 데 사용된다.

05Outbox Pattern

비즈니스 데이터와 이벤트를 하나의 DB 트랜잭션으로 함께 기록한다. 주문 저장과 동시에 outbox 테이블에 이벤트를 삽입한다. 트랜잭션이 커밋되면 두 레코드가 원자적으로 존재한다.

CDC(Change Data Capture): Debezium 같은 CDC 도구가 DB의 WAL(Write-Ahead Log)을 읽어 outbox 테이블의 새 레코드를 감지하고 Kafka 같은 메시지 큐로 발행한다. Polling 방식: 별도 프로세스가 주기적으로 outbox 테이블을 SELECT해 미발행 이벤트를 가져온다. CDC보다 간단하지만 DB에 추가 부하가 생긴다. 발행 성공 후 published_at을 업데이트한다.

멱등 소비자

at-least-once 발행이므로 소비자(Kafka Consumer)는 중복 메시지를 처리할 수 있어야 한다. event_id를 기록해 중복을 감지하거나, 처리 자체가 멱등한 연산이어야 한다.

06기법 비교표

각 기법은 일관성 수준, 복잡도, 처리량, 사용 맥락이 다르다. 단일 기법만 사용하는 것보다 Saga + Outbox를 조합하는 것이 마이크로서비스의 실무 표준이다.

조합 패턴

Saga Orchestration(Temporal) + Outbox Pattern이 2024년 마이크로서비스 실무 표준에 가장 가깝다. Saga가 서비스 간 흐름을 조정하고, Outbox가 이벤트 발행 정합성을 보장한다.

03
Trade-offs

실무 트레이드오프

Uber는 Temporal(Cadence 후속)로 결제·배달 완료 Saga를, Stripe는 Temporal로 결제 흐름을 오케스트레이션한다. Airbnb는 Saga + Outbox 조합으로 숙소 예약·결제·포인트 지급을 원자적으로 처리한다.

01 · 2PC
2PC의 한계와 대안
문제BlockingSPOF

Coordinator 단일 장애점: Phase 2 전송 직전에 Coordinator가 죽으면 참여자들은 Commit/Abort 메시지를 받지 못한 채 락을 유지한다. 새 Coordinator가 복구되어도 어디까지 진행됐는지 알 수 없다. XA 프로토콜의 heuristic decision으로 강제 완료할 수 있지만 데이터 불일치 위험이 있다.

처리량 병목: Prepare 단계에서 모든 참여자가 락을 잡고 Coordinator의 Commit을 기다린다. 네트워크 레이턴시가 100ms라면 모든 레코드의 락이 최소 200ms 이상 유지된다. TPS가 높을수록 락 경합이 심해진다.

대안 선택: DB 샤드 간 트랜잭션이 필요하면 애플리케이션 레벨에서 "먼저 기록하고 나머지는 비동기 보정" 전략을 사용한다. 불가피하게 2PC가 필요하면 코디네이터 HA를 ZooKeeper/etcd로 구성한다.

Coordinator: Phase 1 완료, Commit 전송 중...
Coordinator 장애!
Participant A: Yes 응답 후 Commit 대기 중... (DB 락 유지)
Participant B: Yes 응답 후 Commit 대기 중... (DB 락 유지)
새 Coordinator 복구 → heuristic decision으로 강제 처리 → 불일치 위험
02 · Saga
Saga 설계 원칙 — 보상 트랜잭션
사례UberStripe

보상 트랜잭션 설계: 보상은 의미적 역전이지 물리적 롤백이 아니다. "결제 취소"는 "결제 거부"와 다르다 — 결제가 이미 성공한 사실을 기록하고 그 위에 환불 레코드를 추가한다. 이미 외부로 전송된 이메일, 쿠폰, 포인트는 취소할 수 없는 경우가 있다(재전송 방지 조치 필요).

격리성 이슈: Saga는 중간 상태가 외부에 노출된다. 결제는 완료됐지만 재고 차감이 실패한 상태에서 다른 요청이 결제 완료 상태를 읽을 수 있다(dirty read). Semantic Lock: 중간 단계에서 "processing" 상태를 명시해 다른 요청이 잘못 읽지 않도록 한다. Countermeasures: 재시도 가능 트랜잭션과 피벗 트랜잭션(되돌릴 수 없는 지점)을 구분해 설계한다.

멱등성: Orchestrator가 같은 단계를 중복 호출할 수 있다(재시도). 각 서비스의 API는 동일한 요청 ID로 여러 번 호출되어도 동일한 결과를 반환해야 한다. idempotency key를 DB에 저장하고 중복 요청을 검출한다.

03 · Outbox
Outbox + CDC — 실무 구현
도구DebeziumKafka

Debezium PostgreSQL Connector: PostgreSQL WAL(논리 복제 슬롯)을 읽어 outbox 테이블의 INSERT를 감지하고 Kafka 토픽에 발행한다. DB 변경 사항이 Kafka에 정확히 한 번(effectively) 반영된다. 장애 복구 후 WAL의 마지막 LSN부터 재개하므로 메시지 손실이 없다.

Outbox 테이블 설계: id(UUID PK), aggregate_type, aggregate_id, event_type, payload(JSONB), created_at, published_at(nullable). CDC 방식은 published_at이 필요 없고, Polling 방식은 필수다. 발행된 메시지는 주기적으로(7일 후) 삭제해 테이블 비대화를 막는다.

트랜잭션 로그 테일링 vs Polling: CDC는 WAL 슬롯 관리가 필요하고 DB에 복제 권한이 있어야 한다. Polling은 구현이 단순하지만 주기(1~5초) 동안 발행 지연이 발생한다. 처리량이 낮으면 Polling, 높으면 CDC를 사용한다.

04 · Decision
기법 선택 가이드

이벤트 발행 보장만 필요하면 Outbox Pattern으로 충분하다. 서비스 간 정합성이 아니라 "데이터 변경 시 메시지를 반드시 발행"하는 요건이면 Saga가 필요 없다.

3개 이하 서비스, 단순 흐름: Saga Choreography + Outbox. 4개 이상 서비스, 복잡한 분기·재시도: Saga Orchestration(Temporal) + Outbox. DB 수준 강한 일관성이 필수이고 수평 확장이 낮아도 됨: 2PC(동일 DB 클러스터 내). 비즈니스 레벨 잠금, 높은 처리량: TCC.

가장 흔한 실수: 분산 트랜잭션 없이 HTTP 호출로 여러 서비스를 순서대로 호출하는 것. 중간에 실패하면 일부만 완료된 상태가 되고 자동 복구 수단이 없다. 최소한 Outbox Pattern은 항상 적용한다.

Outbox Pattern

DB 수준 ACID → 2PC (동일 클러스터)
고처리량+비즈니스 예약 → TCC
분산 트랜잭션의 근본 한계: 네트워크는 신뢰할 수 없다. 어떤 기법도 네트워크 파티션 동안 강한 일관성과 가용성을 동시에 보장할 수 없다(CAP 정리). 실무에서는 "충분히 좋은 일관성"을 목표로 한다. Stripe는 "99.999% 일관성 + 수동 보정 프로세스"를 표준으로 가져가며, 완벽한 자동화보다 운영 가능한 시스템을 우선시한다.

Outbox Pattern — SQLAlchemy

outbox
from sqlalchemy import Column, String, DateTime, JSON, func
from sqlalchemy.dialects.postgresql import UUID
import uuid, datetime

# Outbox 테이블 모델
class OutboxEvent(Base):
    __tablename__ = "outbox"
    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    aggregate_type = Column(String(100), nullable=False)
    aggregate_id = Column(String(255), nullable=False)
    event_type = Column(String(100), nullable=False)
    payload = Column(JSON, nullable=False)
    created_at = Column(DateTime, server_default=func.now())

# 주문 생성과 이벤트를 하나의 트랜잭션으로
def create_order(session, user_id: str, items: list) -> Order:
    with session.begin():
        order = Order(user_id=user_id, items=items, status="pending")
        session.add(order)
        session.flush()  # order.id 생성

        # 동일 트랜잭션에 이벤트 삽입 — 원자적 보장
        event = OutboxEvent(
            aggregate_type="Order",
            aggregate_id=str(order.id),
            event_type="OrderCreated",
            payload={"user_id": user_id, "total": order.total},
        )
        session.add(event)
    return order  # 커밋 완료 — 두 레코드 모두 영구 저장

# Polling 발행자 (별도 프로세스)
def poll_and_publish(session, producer):
    while True:
        events = session.query(OutboxEvent).order_by(
            OutboxEvent.created_at
        ).limit(100).all()
        for event in events:
            producer.send(event.event_type, event.payload)
            session.delete(event)
        session.commit()
        time.sleep(1)
원자성 보장. OutboxEvent를 Order와 같은 트랜잭션에 삽입한다. 트랜잭션 실패 시 둘 다 롤백되므로 "주문은 됐지만 이벤트 없음" 상황이 발생하지 않는다.

Saga Orchestration — Temporal Python SDK

temporal
from temporalio import workflow, activity
from temporalio.client import Client
from dataclasses import dataclass

@dataclass
class OrderInput:
    order_id: str
    user_id: str
    amount: float

@activity.defn
async def process_payment(order_id: str, amount: float) -> bool:
    # 결제 서비스 호출 — 실패 시 Temporal이 재시도
    return await payment_client.charge(order_id, amount)

@activity.defn
async def reserve_inventory(order_id: str) -> bool:
    return await inventory_client.reserve(order_id)

@activity.defn
async def refund_payment(order_id: str):
    # 보상 트랜잭션 — 결제 환불
    await payment_client.refund(order_id)

@workflow.defn
class OrderSagaWorkflow:
    @workflow.run
    async def run(self, inp: OrderInput) -> str:
        payment_done = False
        try:
            # Step 1: 결제
            payment_done = await workflow.execute_activity(
                process_payment, inp.order_id, inp.amount,
                start_to_close_timeout=timedelta(seconds=10),
            )
            # Step 2: 재고 차감
            await workflow.execute_activity(
                reserve_inventory, inp.order_id,
                start_to_close_timeout=timedelta(seconds=10),
            )
            return "completed"
        except Exception:
            # 보상: 결제가 완료됐으면 환불
            if payment_done:
                await workflow.execute_activity(refund_payment, inp.order_id)
            raise
Temporal 내구성. 워크플로우 실행 히스토리가 DB에 저장되므로 Worker가 죽어도 재시작 후 정확히 중단 시점부터 재개된다. Activity는 자동 재시도된다.

TCC — Try/Confirm/Cancel API 패턴

tcc
from enum import Enum from fastapi import FastAPI, HTTPException class ReservationStatus(Enum): PENDING = "pending" CONFIRMED = "confirmed" CANCELLED = "cancelled" app = FastAPI() @app.post("/inventory/try") async def try_inventory(order_id: str, qty: int): # 재고를 실제 차감하지 않고 "예약" 상태로 표시 reservation = await db.create_reservation( order_id=order_id, qty=qty, status=ReservationStatus.PENDING ) # 실제 재고 available_qty는 변경하지 않음 if not reservation: raise HTTPException(409, "재고 부족") return {"reservation_id": reservation.id} @app.post("/inventory/confirm") async def confirm_inventory(reservation_id: str): # 멱등성: 이미 CONFIRMED면 그냥 성공 반환 reservation = await db.get_reservation(reservation_id) if reservation.status == ReservationStatus.CONFIRMED: return {"status": "already confirmed"} await db.confirm_reservation(reservation_id) # 실제 재고 차감 return {"status": "confirmed"} @app.post("/inventory/cancel") async def cancel_inventory(reservation_id: str): # 멱등성: 이미 CANCELLED면 성공 반환 reservation = await db.get_reservation(reservation_id) if reservation.status in ( ReservationStatus.CANCELLED, None ): return {"status": "ok"} await db.cancel_reservation(reservation_id) # 예약만 해제 return {"status": "cancelled"}
멱등성 필수. Confirm/Cancel은 여러 번 호출되어도 동일한 결과를 반환해야 한다. 상태 확인 후 이미 처리됐으면 성공으로 응답하는 패턴을 반드시 구현한다.
