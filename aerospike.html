01
TL;DR

한 줄로 이해하기

Aerospike는 인덱스를 항상 DRAM에, 실제 데이터를 SSD에 저장하는 하이브리드 메모리 아키텍처로 테라바이트 규모에서도 1ms 미만 P99 레이턴시를 달성한다. AdTech 실시간 입찰(RTB), 사기 탐지, 추천 시스템의 사용자 프로필 서빙처럼 초저지연이 필수인 영역에 특화된 데이터베이스다.

01

Hybrid Memory Architecture — 인덱스는 DRAM, 데이터는 SSD

Primary Index는 항상 DRAM에 상주한다. 레코드 1개당 64바이트의 고정 크기 인덱스 엔트리만 메모리에 보관하고, 실제 Bin 값은 SSD/NVMe에 저장한다. 읽기 경로: DRAM 인덱스에서 SSD 오프셋 조회 → SSD 단일 읽기로 완료. 파일시스템을 거치지 않고 raw block device에 직접 I/O해 OS 페이지 캐시 오버헤드를 제거한다.

02

Smart Client — 프록시 없는 직접 라우팅

Aerospike 클라이언트는 클러스터의 파티션 맵 전체를 로컬에 캐시한다. 키를 해시해 파티션 ID를 계산하고, 파티션 맵에서 담당 노드를 직접 조회한다. MongoDB의 mongos 라우터나 Redis Cluster의 MOVED 리다이렉션 없이 단일 네트워크 홉으로 요청이 처리된다. 노드 변경 시 클라이언트가 자동으로 파티션 맵을 갱신한다.

03

파티션 맵 — 4096 고정 파티션

전체 키 공간을 4096개 파티션으로 나눈다(Cassandra의 vnode 방식과 달리 노드당 파티션 수가 균등). RIPEMD-160 해시로 파티션 ID를 계산하고, 각 파티션의 master 노드와 replica 노드를 결정한다. Rack-Aware Replication: 복제본은 항상 다른 랙(rack)의 노드에 배치되어 랙 단위 장애를 허용한다.

04

Strong Consistency — 4.0+의 CP 모드

기본은 AP 모드(Eventually Consistent). 4.0+에서 Roster-based Strong Consistency를 지원한다. Roster에 등록된 노드의 과반이 응답해야 쓰기가 완료된다(Paxos 유사). strong-consistency true를 Namespace 단위로 설정하면 선형화 가능한(linearizable) 읽기·쓰기를 보장한다. 단, 가용성을 희생하므로 금융·결제 데이터에만 적용한다.

05

Cross-Datacenter Replication (XDR) — 비동기 멀티-DC

XDR은 로컬 클러스터에서 원격 클러스터로 쓰기를 비동기 복제한다. write digest log를 기록하고, XDR daemon이 이를 읽어 원격 DC로 전송한다. 충돌 해결: generation 번호가 높은 쪽이 우선(LWW 기반). Active-Active 멀티 DC 구성에서 양방향 XDR로 지역적 쓰기와 글로벌 동기화를 동시에 달성한다.

06

데이터 모델 — Namespace / Set / Record / Bin

Namespace: 최상위 컨테이너. 스토리지 엔진과 복제 인수를 Namespace 단위로 설정한다. Set: RDBMS의 테이블에 해당(선택적). Record: Primary Key로 식별되는 데이터 단위. Bin: Key-Value 쌍 컬럼(Integer, String, Blob, List, Map, GeoJSON 지원). 스키마가 없어 레코드마다 서로 다른 Bin을 가질 수 있다.

01하이브리드 메모리 아키텍처

읽기 경로는 두 단계다. ① DRAM Primary Index에서 키 조회 → 64바이트 인덱스 엔트리에 SSD 블록 오프셋이 담겨 있다. ② 해당 오프셋으로 SSD에서 레코드 읽기(raw I/O). 총 1번의 SSD 읽기로 완료된다. OS 페이지 캐시를 완전히 우회하므로 캐시 일관성 오버헤드가 없다.

쓰기 경로: 먼저 DRAM 쓰기 버퍼(write buffer)에 기록하고, 128KB 블록 단위로 묶어 SSD에 순차 기록한다. 순차 쓰기는 랜덤 쓰기보다 SSD 내구성(TBW)을 절약한다. 버퍼가 찰 때까지 DRAM에 남아 있으므로 직후 읽기도 DRAM에서 처리된다.

In-Memory 모드

Namespace를 storage-engine memory로 설정하면 인덱스와 데이터 모두 DRAM에 상주한다. 최고 속도지만 노드 재시작 시 데이터가 소실된다. 세션 캐시, 단기 카운터처럼 내구성이 불필요한 경우에만 사용한다.

02Smart Client 라우팅

Aerospike 클라이언트는 클러스터에 처음 연결할 때 전체 파티션 맵을 다운로드한다. 이후 클라이언트 프로세스 내에서 키 → 파티션 → 노드 계산을 완료하고 해당 노드에 직접 TCP 연결을 맺는다. MongoDB의 mongos나 Redis Cluster의 MOVED 리다이렉션이 필요 없다.

노드가 추가·제거되면 클라이언트가 파티션 맵을 자동 갱신한다. 마이그레이션 중에는 두 노드 모두에 시도해 데이터를 찾는다. 클라이언트 라이브러리가 connection pool을 노드별로 관리해 연결 재사용 효율을 높인다.

03데이터 모델

Namespace는 가장 큰 단위로 스토리지 엔진, 메모리 크기, TTL, 복제 인수를 결정한다. 하나의 클러스터에 여러 Namespace를 둘 수 있다(예: 핫 데이터용 DRAM Namespace + 웜 데이터용 SSD Namespace).

Record는 Primary Key(user_id, device_id 등)로 식별한다. Digest: Set + Key를 RIPEMD-160 해시한 20바이트 값으로 실제 파티션 계산에 사용한다. Bin은 동적 스키마를 지원해 레코드마다 다른 Bin을 가질 수 있으며, 지원 타입은 Integer, Double, String, Blob, Boolean, List, Map, HyperLogLog, GeoJSON이다.

TTL 설계

Namespace 단위로 default-ttl를 설정하고, 레코드 쓰기 시 개별 TTL을 오버라이드할 수 있다. TTL이 만료된 레코드는 Expiration Daemon이 배경에서 삭제한다. RTB 쿠키 데이터처럼 30일 TTL이 필요하면 max-ttl 2592000으로 설정한다.

04스토리지 엔진 비교

SSD (device) 모드가 프로덕션 표준이다. NVMe raw device를 직접 사용해 파일시스템 오버헤드 없이 예측 가능한 레이턴시를 제공한다. 인덱스는 DRAM, 데이터는 SSD에 위치한다.

In-Memory 모드: 인덱스·데이터 모두 DRAM. 재시작 시 소실되므로 내구성이 불필요한 캐시용. Persistent Memory(PMem): Intel Optane 등 바이트 주소 가능 NVDIMM 사용. SSD보다 ~10배 빠른 읽기 레이턴시(수십 μs). Shadow Device: PMem에 데이터 보관 + SSD에 내구성 복사본을 동시에 기록하는 혼합 모드.

SSD 선택 기준

Aerospike는 SSD 벤치마크 도구(ACT, Aerospike Certification Tool)로 SSD의 Aerospike 호환성을 검증한다. 소비자용 SSD는 쓰기 지연 스파이크가 커서 부적합하다. 엔터프라이즈 NVMe(Samsung PM9A3, Micron 9300 등)를 사용한다.

05Cross-Datacenter Replication (XDR)

XDR은 로컬 DC에서 원격 DC로 쓰기를 비동기로 전파한다. 각 노드가 자신이 master인 파티션의 쓰기를 digest log에 기록하고, XDR 데몬이 이를 읽어 원격 클러스터의 해당 파티션 master로 전송한다. 원격 클러스터에서 또 다시 로컬 복제가 이루어진다.

Active-Active 구성: 두 DC 모두에서 쓰기가 가능하고 XDR이 양방향으로 동기화한다. 충돌(같은 키를 양쪽에서 동시 수정) 시 generation 번호가 높은 쪽이 우긴다. 동일 generation이면 LUT(Last Update Time) 기준 LWW(Last Write Wins). 충돌 해결 커스터마이징은 Lua UDF로 구현 가능하다.

단방향 XDR (DR 구성)

Primary DC → DR DC로만 XDR을 흘리면 재해 복구 구성이 된다. 평시에는 DR DC에서 읽기만 허용(read-only). RPO는 XDR 지연(보통 수십 ms~수 초)에 의존한다.

06Consistency Mode — AP vs CP

AP 모드(기본): 파티션 split-brain 상황에서도 쓰기를 허용한다. 노드가 복구되면 master가 replica에 최신 버전을 push한다(replica resync). 네트워크 파티션 내에서 availability를 최우선으로 한다.

Strong Consistency(CP) 모드: Roster에 지정된 노드 과반이 살아있어야 쓰기가 성공한다. 선형화 가능성(linearizability)을 보장하므로 읽기 시 policy.readModeAP = ALL 또는 LinearizeRead를 사용한다. split-brain 발생 시 소수 파티션은 읽기·쓰기 모두 불가하다. 금융 거래처럼 데이터 정확성이 가용성보다 중요한 워크로드에 적합하다.

혼합 사용

Namespace 단위로 일관성 모드를 설정할 수 있다. 사용자 프로필(AP) + 잔액 데이터(CP)를 동일 클러스터에 둘 수 있다.

Large Scale

대용량 처리

AppNexus(Xandr)는 초당 100만+ 입찰 요청을 1ms 미만으로 처리하기 위해 Aerospike를 RTB 유저 데이터 저장소로 사용한다. Criteo는 수십억 쿠키 프로필을, PayPal은 세션·사기 탐지 데이터를 Aerospike에서 서빙한다.

01 · Storage
SSD 직접 접근 — 파일시스템 없이 예측 가능한 레이턴시
사례AppNexusNielsen

일반 데이터베이스는 OS 파일시스템(ext4, xfs)을 통해 SSD에 접근한다. OS 페이지 캐시가 읽기를 흡수하지만, 캐시 미스 시 레이턴시가 급등하고 캐시 플러시로 인한 예측 불가한 P99 스파이크가 발생한다. Aerospike는 파일시스템을 완전히 건너뛰고 raw block device에 직접 pread/pwrite를 호출해 일관된 P99를 달성한다.

Defragmentation: SSD에 128KB 블록으로 데이터를 기록하며, 레코드를 업데이트하면 새 블록에 기록하고 기존 블록을 마크한다. Defrag 데몬이 defrag-lwm-pct(기본 50%)보다 활성 데이터 비율이 낮은 블록을 압축해 공간을 회수한다. SSD의 쓰기 증폭(WAF)을 최소화한다.

쓰기 TBW 계획: NVMe SSD는 TBW(Total Bytes Written) 한계가 있다. Aerospike의 연속 쓰기 패턴(128KB 순차 블록)은 랜덤 쓰기보다 TBW 효율이 좋다. 서버 구매 시 예상 일일 쓰기 GB × 5년 × 365 < SSD TBW를 확인한다.

ACT 벤치마크

Aerospike Certification Tool(ACT)로 도입 전 SSD를 검증한다. 초당 2,000 TPS로 24시간 테스트해 P99.9 < 1ms를 통과해야 프로덕션에 사용 가능하다. 소비자용 SSD는 대부분 실패한다.

02 · Cluster
파티션 마이그레이션 & 리밸런싱
사례CriteoPayPal

노드가 추가·제거되면 파티션 마이그레이션이 시작된다. 새 파티션 맵이 계산되고, 데이터가 구 master에서 신 master로 이동한다. 마이그레이션 중 쿼리는 두 노드를 모두 시도해 응답을 반환하므로 무중단 리밸런싱이 가능하다.

마이그레이션 속도 제한: migrate-threads(기본 1)와 migrate-max-num-incoming(기본 4)로 마이그레이션이 일반 트래픽에 미치는 영향을 조절한다. 대규모 클러스터에서는 마이그레이션 완료까지 수 시간이 걸릴 수 있다.

Rack-Aware Replication: rack-id를 각 노드에 설정하면 replica가 다른 rack-id 노드에 배치된다. 랙 단위 전원 장애나 스위치 장애에서도 데이터를 보호한다. replication-factor=2이면 최소 2개 랙이 필요하다.

클러스터 확장 전략

노드를 한 번에 하나씩 추가하고 마이그레이션이 완료된 후 다음 노드를 추가한다. 동시에 여러 노드를 추가하면 마이그레이션 부하가 겹쳐 운영 트래픽에 영향을 준다.

03 · Throughput
핫키 & 처리량 튜닝
사례RTB AdTech

핫키 문제: 특정 레코드에 요청이 집중되면 해당 파티션의 master 노드가 병목이 된다. Aerospike는 read-replica 설정으로 replica에서도 읽기를 허용한다. Client-side에서 round-robin으로 master와 replica를 번갈아 읽으면 핫키 읽기 부하를 분산한다.

배치 요청: client.batchGet()으로 여러 키를 단일 요청으로 묶어 처리한다. 내부적으로 노드별로 요청을 그루핑해 노드당 1번의 RTT로 처리한다. 수천 키를 개별 요청으로 보내는 것보다 90% 이상 레이턴시가 줄어든다.

Pipeline(async): Aerospike 클라이언트의 async API로 inflight 요청을 다수 유지한다. 동기 API 대비 동일 CPU에서 처리량이 5~10배 향상된다. Node.js, Java, Go 클라이언트에서 기본 지원한다.

Secondary Index 주의

Secondary Index 조회는 전체 노드에 scatter-gather 방식으로 쿼리를 보내므로 레이턴시가 높다. 고빈도 쿼리에는 Secondary Index 대신 Primary Key 기반 접근 + 애플리케이션 레벨 인덱스를 사용한다.

Aerospike는 Redis와 비교될 때가 많지만 목적이 다르다. Redis는 캐시 레이어로 데이터 크기가 수 GB~수십 GB 수준이고, Aerospike는 수 TB의 데이터를 1ms 미만으로 서빙하는 기본 스토어로 사용된다. Aerospike Enterprise Edition은 ACID 트랜잭션(단일 레코드 수준)과 Strong Consistency를 제공한다. 멀티 레코드 ACID는 지원하지 않으므로 트랜잭션이 필요하면 애플리케이션 레벨에서 처리해야 한다.

Code

실전 코드

Python aerospike 클라이언트(aerospike-client-python)를 사용한 핵심 패턴. 클라이언트 연결, CRUD, Batch, 정책(Policy) 설정을 다룬다.

클라이언트 연결 & 기본 CRUD

client
import aerospike
from aerospike import exception as ex

# 클러스터 연결 — seed 노드 하나만 있으면 나머지 노드 자동 발견
config = {
    "hosts": [("as-node-1.internal", 3000)],
    "policies": {
        "timeout": 1000,          # ms
        "max_retries": 2,
        "connect_timeout": 3000,
    },
    "max_connections_per_node": 1000,
    "min_connections_per_node": 10,
}
client = aerospike.client(config).connect()

# (namespace, set, primary_key) 튜플이 key
key = ("user-profiles", "web", "user:123456")

# Write
bins = {"age": 34, "segments": ["sports", "tech"], "score": 0.87}
write_policy = {"ttl": 86400, "gen": aerospike.POLICY_GEN_IGNORE}
client.put(key, bins, meta={"ttl": 86400}, policy=write_policy)

# Read
try:
    key_out, meta, bins_out = client.get(key)
    print(bins_out["age"])
except ex.RecordNotFound:
    print("키 없음")

# Atomic increment (다른 클라이언트와 레이스 없이)
client.increment(key, "page_views", 1)

# Delete
client.remove(key)
연결 풀. AerospikeClient 인스턴스를 싱글톤으로 유지한다. 스레드/코루틴마다 생성하면 소켓 고갈이 발생한다.

Batch Get — 다중 키 단일 요청

batch
# 1000개 키를 노드별로 그루핑해 병렬 처리
user_ids = [f"user:{i}" for i in range(1000)]
keys = [("user-profiles", "web", uid) for uid in user_ids]

# batch_get은 (key, meta, bins) 리스트 반환. 없는 키는 None
results = client.get_many(keys)

profiles = {}
for key_out, meta, bins in results:
    if bins is not None:
        uid = key_out[2]   # (namespace, set, pk)
        profiles[uid] = bins

# Batch Write (aerospike-client-python 7.0+)
from aerospike_helpers.batch import records as br

batch_records = [
    br.Write(
        key=("user-profiles", "web", f"user:{i}"),
        ops=[aerospike.operations.write("score", i * 0.01)],
    )
    for i in range(100)
]
client.batch_write(batch_records)
배치 최적화. 1000개 개별 요청은 ~300ms, batch_get은 ~3ms. 클라이언트가 노드당 1번의 RTT로 요청을 병합한다.

Operate — 복합 원자 연산

operate
from aerospike_helpers import operations as ops from aerospike_helpers.operations import list_operations as lops key = ("user-profiles", "web", "user:999") # 여러 Bin에 대한 원자적 복합 연산 operations = [ ops.increment("page_views", 1), # 카운터 증가 lops.list_append("recent_pages", "/sports"), # List에 추가 lops.list_trim("recent_pages", -10, 10), # 최근 10개만 유지 ops.read("page_views"), # 업데이트 후 값 읽기 ] key_out, meta, result = client.operate(key, operations) print(result["page_views"]) # 증가 후 최신 값 # CAS (Check-and-Set) — generation 기반 낙관적 잠금 _, meta, _ = client.get(key) current_gen = meta["gen"] write_policy = { "gen": aerospike.POLICY_GEN_EQ, # generation이 일치할 때만 쓰기 } try: client.put(key, {"score": 0.99}, meta={"gen": current_gen}, policy=write_policy) except ex.RecordGenerationError: print("다른 프로세스가 먼저 수정함 — 재시도 필요")
원자 연산 활용. operate()로 읽기-수정-쓰기를 서버 사이드에서 원자적으로 처리한다. 클라이언트 레벨 RMW는 레이스 컨디션이 발생하므로 사용하지 않는다.

Async API — 고처리량 비동기 요청

async
import asyncio import aerospike_client_python as asc # async 지원 클라이언트 # aerospike-client-python의 async는 실험적; 실무에서는 Java/Go 클라이언트 권장 # 아래는 ThreadPoolExecutor로 동기 클라이언트를 async화하는 패턴 from concurrent.futures import ThreadPoolExecutor import asyncio executor = ThreadPoolExecutor(max_workers=50) async def async_get(client, key): loop = asyncio.get_event_loop() return await loop.run_in_executor( executor, client.get, key ) async def fetch_many_users(client, user_ids): keys = [("user-profiles", "web", uid) for uid in user_ids] tasks = [async_get(client, k) for k in keys] results = await asyncio.gather(*tasks, return_exceptions=True) return [r for r in results if not isinstance(r, Exception)]
비동기 처리량. Java 네이티브 async 클라이언트에서 단일 프로세스 1M RPS를 달성한다. Python은 GIL 때문에 ThreadPoolExecutor로 우회한다. 처리량이 중요한 파이프라인은 Java/Go 클라이언트를 사용한다.
